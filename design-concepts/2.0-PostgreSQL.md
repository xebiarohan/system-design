# 1. PostgreSQL Architecture

PostgreSQL uses a **client-server architecture**.

Your application doesn't directly manipulate database files.

Instead:

```text
Java Application
      │
      │ SQL
      ▼
PostgreSQL
      │
      ├── Parser
      ├── Planner
      ├── Executor
      ├── Transaction Manager
      ├── Buffer Manager
      ├── WAL
      └── Storage
```

For example:

```sql
SELECT name
FROM users
WHERE id = 100;
```

Your Java application sends this SQL to PostgreSQL.

PostgreSQL then:

```text
SQL
 ↓
Parse
 ↓
Analyze
 ↓
Plan
 ↓
Execute
 ↓
Read data
 ↓
Return rows
```

---

# 2. PostgreSQL Server Process Architecture

One interesting thing about PostgreSQL is that traditionally it uses a **process-per-connection architecture**.

Conceptually:

```text
             PostgreSQL Server
                    │
        ┌───────────┴───────────┐
        │                       │
   Backend Process          Backend Process
   Connection A              Connection B
        │                       │
        ▼                       ▼
      Client A                Client B
```

Suppose you have:

```text
Application
   │
   ├── Connection 1
   ├── Connection 2
   ├── Connection 3
   └── Connection 4
```

PostgreSQL generally has a backend process associated with each connection.

This is one reason **connection pooling** is important.

For example:

```text
1000 application requests
        │
        ▼
   Connection Pool
        │
        ├── 20 DB connections
        ├── 20 DB connections
        └── ...
        │
        ▼
    PostgreSQL
```

You don't want thousands of unnecessary database connections.

# 3. PostgreSQL Memory Architecture

PostgreSQL has two broad categories of memory:

```text
PostgreSQL Memory
│
├── Shared Memory
│
│   ├── shared_buffers
│   ├── WAL buffers
│   └── other shared structures
│
└── Per-process Memory
    │
    ├── work_mem
    ├── maintenance_work_mem
    └── temporary execution memory
```

The most important one is:

## `shared_buffers`

This is PostgreSQL's main shared buffer cache.

Suppose your table contains:

```text
users
 ├── page 1
 ├── page 2
 ├── page 3
 └── page 4
```

PostgreSQL doesn't necessarily read directly from disk every time.

Instead:

```text
Disk
 │
 │ read
 ▼
shared_buffers
 │
 ▼
Query Executor
```

If the required page is already in memory:

```text
Query
 ↓
shared_buffers
 ↓
Data
```

No disk read is necessary.

This is called a **buffer cache hit**.

# 5. Parser

First PostgreSQL parses your SQL.

Example:

```sql
SELECT name
FROM users
WHERE id = 100;
```

It checks syntax.

For example:

```sql
SELECT FROM users WHERE
```

is syntactically invalid.

The parser converts the SQL into an internal representation, essentially an **abstract syntax tree (AST)**.

Conceptually:

```text
SELECT
 │
 ├── column: name
 │
 ├── table: users
 │
 └── condition
       │
       └── id = 100
```

---

# 6. Query Analyzer

Next PostgreSQL determines whether the query actually makes sense against the database schema.

For example:

```sql
SELECT xyz
FROM users;
```

If `xyz` doesn't exist:

```text
ERROR: column "xyz" does not exist
```

The analyzer resolves:

```text
users
 ↓
actual table

id
 ↓
actual column

100
 ↓
integer constant
```

It also checks permissions, types, operators, functions, etc.

---

# 7. Query Planner / Optimizer

This is one of PostgreSQL's most important components.

PostgreSQL now asks:

> "What is the cheapest way to execute this query?"

Suppose:

```sql
SELECT *
FROM users
WHERE id = 100;
```

and you have:

```sql
CREATE INDEX idx_users_id ON users(id);
```

PostgreSQL could choose:

```text
Index Scan
```

instead of:

```text
Sequential Scan
```

The planner may consider multiple strategies.

For example:

```text
                 Query
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
      Seq Scan  Index Scan  Bitmap Scan
          │        │        │
          └────────┼────────┘
                   ▼
             Cost estimation
                   │
                   ▼
             Cheapest plan
```

---

# 8. Why Doesn't PostgreSQL Always Use an Index?

This is an important system-design question.

Suppose:

```text
users = 10 million rows
```

and:

```sql
WHERE id = 123
```

An index is probably useful.

But suppose:

```sql
WHERE country = 'India'
```

and:

```text
70% of rows are India
```

Using the index might be more expensive than simply scanning the table.

So PostgreSQL could choose:

```text
Sequential Scan
```

instead.

The planner uses **statistics** to estimate selectivity and costs.

You can inspect the chosen plan using:

```sql
EXPLAIN
SELECT *
FROM users
WHERE id = 100;
```

And actual execution with:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE id = 100;
```

# 10. How PostgreSQL Stores Data

Now let's go deeper.

PostgreSQL stores tables on disk as **pages**.

A page is normally:

```text
8 KB
```

Conceptually:

```text
users table
│
├── Page 0
├── Page 1
├── Page 2
├── Page 3
└── ...
```

Each page contains multiple tuples/rows.

For example:

```text
Page 1
┌──────────────────────────┐
│ Page Header              │
├──────────────────────────┤
│ Row 1                    │
├──────────────────────────┤
│ Row 2                    │
├──────────────────────────┤
│ Row 3                    │
├──────────────────────────┤
│ Row 4                    │
├──────────────────────────┤
│ Free Space               │
└──────────────────────────┘
```

This is an important mental model:

> PostgreSQL doesn't fundamentally think in terms of "rows"; its storage engine works heavily with **pages** and **tuples**.

---

# 11. Tuple

A PostgreSQL row is internally represented as a **tuple**.

For example:

```sql
users

id | name | age
---+------+----
1  | Bob  | 30
```

The tuple contains more than just:

```text
1
Bob
30
```

PostgreSQL also maintains tuple metadata important for MVCC.

Conceptually:

```text
Tuple
┌─────────────────────────┐
│ xmin                    │
│ xmax                    │
│ other tuple metadata    │
│                         │
│ id = 1                  │
│ name = Bob              │
│ age = 30                │
└─────────────────────────┘
```

This leads directly into **MVCC**, which you've been studying.

---

# 12. PostgreSQL MVCC

PostgreSQL uses **MVCC — Multi-Version Concurrency Control**.

The key idea:

> PostgreSQL doesn't simply overwrite the existing row when you update it.

Suppose:

```text
id = 1
name = Bob
```

Then:

```sql
UPDATE users
SET name = 'Robert'
WHERE id = 1;
```

Conceptually PostgreSQL creates a new row version.

```text
Old version
id = 1
name = Bob

        ↓ UPDATE

New version
id = 1
name = Robert
```

The old version isn't immediately physically removed.

This is extremely important.

---

# 13. Why MVCC?

Suppose:

```text
Transaction A
        │
        │ SELECT
        ▼
      Row X
```

At the same time:

```text
Transaction B
        │
        │ UPDATE
        ▼
      Row X
```

With MVCC, readers can often continue seeing the appropriate old version rather than being blocked by a writer.

Conceptually:

```text
                 Row versions

              ┌──────────────┐
              │ Version 1    │
              │ Bob          │
              └──────────────┘
                     │
                     ▼
              ┌──────────────┐
              │ Version 2    │
              │ Robert       │
              └──────────────┘
```

Which version a transaction sees depends on its **snapshot**.

---

# 14. xmin and xmax

This is a fascinating PostgreSQL detail.

Tuples have transaction-related metadata such as:

```text
xmin
xmax
```

Conceptually:

```text
xmin = transaction that created this tuple
xmax = transaction that deleted/replaced this tuple
```

For example:

```text
Tuple

name = Bob
xmin = 100
xmax = 150
```

could mean:

```text
Transaction 100 created it
Transaction 150 later invalidated it
```

PostgreSQL uses this information together with transaction snapshots to determine:

> "Is this tuple visible to my transaction?"

That's the heart of PostgreSQL MVCC.

---

# 15. UPDATE Is Not Really "Overwrite"

This is a crucial PostgreSQL concept.

When you do:

```sql
UPDATE users
SET name = 'Robert'
WHERE id = 1;
```

PostgreSQL generally creates a **new tuple version**.

Conceptually:

```text
Before

Page
┌──────────────┐
│ Bob          │
└──────────────┘


After UPDATE

Page
┌──────────────┐
│ Bob          │ ← old version
├──────────────┤
│ Robert       │ ← new version
└──────────────┘
```

The old version becomes dead once no transaction can see it anymore.

This is why PostgreSQL needs **VACUUM**.

---

# 16. VACUUM

Over time:

```text
INSERT
UPDATE
DELETE
UPDATE
UPDATE
DELETE
```

creates dead tuples.

For example:

```text
Page

Bob       ← dead
Robert    ← dead
Rob       ← dead
Robert    ← live
```

If PostgreSQL never cleaned them:

```text
table size ↑
disk usage ↑
scanning cost ↑
```

VACUUM helps reclaim space from dead tuples for reuse.

```text
Dead tuples
     │
     ▼
   VACUUM
     │
     ▼
Space becomes reusable
```

Important distinction:

> VACUUM is not simply "delete old rows from disk."

It primarily makes dead tuple space available for reuse and maintains visibility information; physical file shrinking is a different operation such as `VACUUM FULL`, which has much stronger locking/rewriting implications.

---

# 17. DELETE Internally

Consider:

```sql
DELETE FROM users
WHERE id = 1;
```

PostgreSQL doesn't necessarily immediately erase the tuple from the page.

Conceptually:

```text
Before

Tuple
Bob
xmin = 100
xmax = 0
```

After DELETE:

```text
Tuple
Bob
xmin = 100
xmax = 200
```

Transaction 200 marked it as deleted.

Later VACUUM can clean it up when appropriate.

# 18. INSERT Internally

For:

```sql
INSERT INTO users
VALUES (1, 'Bob', 30);
```

PostgreSQL roughly does:

```text
INSERT
  │
  ▼
Create tuple
  │
  ▼
Find page with free space
  │
  ▼
Put tuple into page
  │
  ▼
Update indexes
  │
  ▼
Write WAL
```

There is more nuance around WAL ordering, but this is the right conceptual model.

---

# 19. What Is WAL?

This is probably the second most important PostgreSQL internal concept after MVCC.

**WAL = Write-Ahead Logging.**

The fundamental rule is:

> PostgreSQL records the necessary change in the WAL before the corresponding modified data page is considered safely persisted.

Imagine:

```text
Database Page
      │
      │ modification
      ▼
   Memory
```

Instead of immediately forcing the entire modified page to disk, PostgreSQL writes a compact description of the change to the **WAL**.

Conceptually:

```text
Transaction
     │
     ├──────────────► WAL
     │                  │
     │                  ▼
     │              WAL on disk
     │
     ▼
Data page in memory
     │
     ▼
Data file later
```

---

# 20. Why WAL?

Imagine:

```text
UPDATE account
SET balance = 500
WHERE id = 1;
```

The database modifies a page in memory.

Then suddenly:

```text
💥 Server crashes
```

If the changed page wasn't written to the data file yet, how can PostgreSQL recover?

WAL.

Before the change is considered durable, PostgreSQL ensures the corresponding WAL information is durable.

After restart:

```text
Database starts
      │
      ▼
Read WAL
      │
      ▼
Replay required changes
      │
      ▼
Recover database
```

This is **crash recovery**.

---

# 21. WAL vs Data Files

Think of them as:

```text
WAL
│
└── "What changes happened?"

Data files
│
└── "What is the current stored state?"
```

WAL is sequentially written and used for:

* crash recovery
* replication
* point-in-time recovery

This is also why PostgreSQL can use WAL to support streaming replication.

---

# 22. Commit Internally

Suppose:

```sql
BEGIN;

UPDATE accounts
SET balance = 500
WHERE id = 1;

COMMIT;
```

Conceptually:

```text
BEGIN
 │
 ▼
Transaction ID / snapshot
 │
 ▼
UPDATE
 │
 ├── create new tuple version
 ├── modify indexes
 └── generate WAL
 │
 ▼
COMMIT
 │
 ▼
Commit record reaches durable WAL
 │
 ▼
Transaction is durable
```

The exact internals are more nuanced, but the critical idea is:

> **COMMIT durability is tied to WAL durability, not necessarily to every modified table page already being flushed to its final data file.**

---

# 23. Checkpoints

If PostgreSQL kept relying entirely on WAL forever, recovery could eventually become expensive.

So PostgreSQL periodically performs **checkpoints**.

Conceptually:

```text
WAL WAL WAL WAL WAL WAL
             │
             ▼
        CHECKPOINT
             │
             ▼
   Flush dirty data pages
```

A checkpoint establishes a known recovery point.

After a crash:

```text
Checkpoint
    │
    ▼
Replay WAL from appropriate point
    │
    ▼
Recover
```

# 24. Buffer Manager

Remember:

```text
Disk
 ↓
shared_buffers
 ↓
Executor
```

The **Buffer Manager** handles access to database pages in memory.

Suppose the executor needs:

```text
users page #500
```

It asks the buffer manager.

The buffer manager checks:

```text
Is page 500 already cached?
```

### Cache hit

```text
shared_buffers
     │
     ▼
page found
     │
     ▼
Executor
```

### Cache miss

```text
shared_buffers
     │
     X
     │
     ▼
Disk
     │
     ▼
Read page
     │
     ▼
shared_buffers
```

Disk I/O is expensive, so reducing unnecessary page reads is a huge part of database performance.

# 25. Index Internals

Let's connect this to the indexing topic you were studying.

Suppose:

```sql
CREATE INDEX idx_users_id
ON users(id);
```

PostgreSQL creates an index structure.

The default index type is generally **B-tree**.

Conceptually:

```text
             Root
              │
       ┌──────┴──────┐
       ▼             ▼
    Internal       Internal
       │             │
   ┌───┴───┐     ┌───┴───┐
   ▼       ▼     ▼       ▼
 Leaf    Leaf   Leaf     Leaf
```

The leaf entries contain key information plus a reference to the corresponding table tuple.

Conceptually:

```text
Index

id = 10 ─────► table tuple
id = 20 ─────► table tuple
id = 30 ─────► table tuple
```

So:

```sql
WHERE id = 30
```

can avoid scanning every table row.

---

# 26. Index Scan Internally

Suppose:

```sql
SELECT *
FROM users
WHERE id = 30;
```

With an index:

```text
Query
 │
 ▼
Index Scan
 │
 ▼
B-tree
 │
 ▼
Find key 30
 │
 ▼
Tuple location
 │
 ▼
Heap/Table page
 │
 ▼
Tuple visibility check
 │
 ▼
Return row
```

One important PostgreSQL term:

> The main table storage is often called the **heap**.

So you'll frequently see:

```text

  ↓

```

---

# 27. Why Indexes Aren't Free

An index improves reads but creates additional work for writes.

Suppose:

```sql
INSERT INTO users ...
```

PostgreSQL may need to update:

```text
Table
 +
Index 1
 +
Index 2
 +
Index 3
```

So:

```text
More indexes
     ↓
Better potential reads
     ↓
More write overhead
     ↓
More storage
     ↓
More maintenance
```

That's why system design shouldn't mean:

> "Put an index on everything."

# 28. PostgreSQL Concurrency

Now let's connect this with your recent **isolation levels + MVCC** study.

Suppose:

```text
Transaction A                  Transaction B

UPDATE account                 SELECT account
      │                              │
      ▼                              ▼
new tuple version              snapshot
      │                              │
      └──────── MVCC ────────────────┘
```

PostgreSQL uses multiple mechanisms together:

```text
MVCC
 +
Locks
 +
Transaction snapshots
 +
Isolation levels
```

MVCC primarily handles **visibility/concurrent versions**.

Locks are still required for operations that need explicit coordination.

---

# 29. MVCC ≠ No Locks

This distinction is very important.

MVCC doesn't mean:

```text
"No locks exist."
```

PostgreSQL still uses locks for things such as:

```text
Row-level locking
Table-level locking
Advisory locks
DDL coordination
```

For example:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

This explicitly asks PostgreSQL to lock the selected row for update.

Conceptually:

```text
Transaction A
      │
      ▼
FOR UPDATE
      │
      ▼
Row lock
      │
      ├────────► Transaction B waits
      │
      ▼
Update
```

---

# 30. Isolation Levels

PostgreSQL provides transaction isolation levels such as:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

The isolation level influences what a transaction is allowed to observe and how PostgreSQL handles concurrent activity.

The key internal mechanism is the **transaction snapshot**.

For example:

```text
Transaction A
    │
    ▼
Snapshot S1
    │
    ├── sees version 1
    └── doesn't see certain later versions
```

So when PostgreSQL examines a tuple:

```text
Is tuple visible to my snapshot?
```

It evaluates transaction visibility information.

# 33. PostgreSQL Storage Structure

At a high level, PostgreSQL organizes persistent data roughly like:

```text
Database Cluster
│
├── Database
│   │
│   ├── Tables
│   │   ├── Heap files
│   │   └── Index files
│   │
│   └── System catalogs
│
├── WAL
│
└── Configuration / metadata
```

Each table/index is represented internally by PostgreSQL relations and corresponding storage files.

You generally should **not manually manipulate these files**.

PostgreSQL's storage manager owns them.

---

# 34. System Catalogs

PostgreSQL itself stores metadata inside PostgreSQL tables.

For example:

```text
What tables exist?
What columns exist?
What indexes exist?
What data types exist?
Who owns this table?
What permissions exist?
```

PostgreSQL maintains this information in **system catalogs**.

For example:

```sql
pg_class
pg_attribute
pg_index
pg_namespace
pg_constraint
```

This is one of the cool things about PostgreSQL:

> PostgreSQL uses relational structures to store a lot of its own metadata.

---

# 35. Background Processes

PostgreSQL also has background processes that perform important maintenance work.

Conceptually:

```text
PostgreSQL
│
├── Backend processes
│
├── WAL writer
├── Checkpointer
├── Background writer
├── Autovacuum launcher
└── Autovacuum workers
```

Their responsibilities differ.

### WAL writer

Helps write WAL buffers to WAL files.

### Checkpointer

Performs checkpoint-related work and helps ensure dirty buffers are flushed appropriately.

### Background writer

Helps write dirty shared buffers in the background.

### Autovacuum

Automatically performs vacuum/analyze-related maintenance based on configured thresholds.

---

# 36. Autovacuum

This is particularly important for PostgreSQL production systems.

Imagine:

```text
10 million rows
```

and your application constantly does:

```text
UPDATE
UPDATE
DELETE
UPDATE
INSERT
```

Without maintenance:

```text
dead tuples ↑
table bloat ↑
index bloat ↑
performance ↓
```

Autovacuum automatically kicks in.

```text
              PostgreSQL
                   │
            Autovacuum
                   │
          ┌────────┴────────┐
          ▼                 ▼
       VACUUM             ANALYZE
          │                 │
          ▼                 ▼
  Clean dead tuples    Update statistics
```

`ANALYZE` is especially important for the planner because it updates statistics used for query planning.
