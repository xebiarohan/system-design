
# 1. SQL vs NoSQL — the big picture

At a high level:

|                | SQL                                                               | NoSQL                                          |
| -------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| Main idea      | Structured relational data                                        | Flexible/non-relational data                   |
| Schema         | Usually predefined                                                | Often flexible                                 |
| Data model     | Tables + rows + relationships                                     | Document, key-value, wide-column, graph        |
| Relationships  | Excellent                                                         | Depends on database                            |
| Joins          | Strong support                                                    | Usually avoided / limited                      |
| Transactions   | Strong ACID support                                               | Varies by database                             |
| Scaling        | Traditionally vertical, but modern SQL can scale horizontally too | Often designed with horizontal scaling in mind |
| Query language | SQL                                                               | Database-specific APIs/query languages         |
| Best for       | Transactional/relational data                                     | Large-scale, flexible, specialized workloads   |

The important thing:

> **NoSQL does NOT mean "better SQL" or "no SQL at all." It means "not primarily relational."**

---

# 2. SQL databases

SQL databases are also called **relational databases**.

Examples:

* PostgreSQL
* MySQL
* Oracle Database
* Microsoft SQL Server

Suppose we're designing an e-commerce system.

We might have:

```text
CUSTOMER
----------------
id
name
email

ORDER
----------------
id
customer_id
order_date
status

ORDER_ITEM
----------------
id
order_id
product_id
quantity

PRODUCT
----------------
id
name
price
```

There are explicit relationships:

```text
Customer
   |
   | 1:N
   ↓
 Order
   |
   | 1:N
   ↓
OrderItem
   |
   | N:1
   ↓
 Product
```

This is where relational databases shine.

---

# 3. Why relationships matter

Imagine:

```text
Customer 101
    |
    +---- Order 5001
    |       |
    |       +---- Product A
    |       +---- Product B
    |
    +---- Order 5002
            |
            +---- Product C
```

You may want to ask:

> "Give me all orders placed by customer 101, including product information."

SQL is very good at this:

```sql
SELECT
    o.id,
    p.name,
    oi.quantity
FROM orders o
JOIN order_items oi
    ON o.id = oi.order_id
JOIN products p
    ON oi.product_id = p.id
WHERE o.customer_id = 101;
```

The database is designed around these relationships.

---

# 4. Schema in SQL

Typically, you define the structure beforehand.

For example:

```sql
CREATE TABLE customer (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
);
```

The database knows:

```text
customer
 ├── id
 ├── name
 └── email
```

This gives you strong guarantees.

For example:

```text
id = BIGINT
email = VARCHAR
id = PRIMARY KEY
```

You can't casually insert completely different structures into the table.

---

# 5. ACID transactions

This is one of the biggest strengths of relational databases.

Suppose a customer transfers:

```text
$100 from Account A
       ↓
Account B
```

You need:

```text
A = A - 100
B = B + 100
```

You don't want this situation:

```text
A = A - 100
B = unchanged
```

because the system crashed between the two operations.

A transaction allows:

```text
BEGIN

A = A - 100
B = B + 100

COMMIT
```

or:

```text
ROLLBACK
```

The classic ACID properties are:

### Atomicity

All operations happen or none happen.

### Consistency

Database constraints remain valid.

### Isolation

Concurrent transactions don't incorrectly interfere with each other.

### Durability

Once committed, data survives failures.

# 6. What is NoSQL?

NoSQL databases use different data models depending on the problem.

There isn't actually one single "NoSQL database."

There are several major categories.

---

# 7. Type 1 — Document databases

Examples:

* MongoDB
* Couchbase

Data is stored as documents, commonly JSON-like structures.

For example:

```json
{
  "customerId": 101,
  "name": "Rohan",
  "email": "rohan@example.com",
  "orders": [
    {
      "orderId": 5001,
      "status": "SHIPPED",
      "items": [
        {
          "productId": 10,
          "quantity": 2
        }
      ]
    }
  ]
}
```

Instead of:

```text
Customer table
Order table
OrderItem table
Product table
```

you can model an aggregate as a document.

This is useful when your application usually accesses the **whole object together**.

---

# 8. Type 2 — Key-value databases

Examples:

* Redis
* Amazon DynamoDB can also be used as a key-value/document database.

Data looks conceptually like:

```text
KEY              VALUE
--------------------------------
user:101         {...}
session:abc123   {...}
cart:101         {...}
```

You primarily ask:

```text
Give me the value for key X
```

Example:

```text
GET session:abc123
```

This is extremely useful for:

* caching
* sessions
* shopping carts
* rate limiting
* temporary state
* fast lookups

---

# 9. Type 3 — Wide-column databases

Examples:

* Apache Cassandra
* ScyllaDB
* HBase

These are designed for very large-scale distributed workloads.

Conceptually:

```text
Partition Key
     ↓
Customer 101
     |
     +---- event1
     +---- event2
     +---- event3
     +---- event4
```

They're particularly useful when you have:

```text
huge amounts of data
        +
very high write/read throughput
        +
known access patterns
        +
distributed storage
```

For example:

```text
IoT telemetry
event tracking
time-series-like workloads
large-scale messaging data
```

---

# 10. Type 4 — Graph databases

Examples:

* Neo4j

These represent:

```text
Nodes + Relationships
```

For example:

```text
Alice
  |
  | FRIEND_OF
  ↓
Bob
  |
  | FRIEND_OF
  ↓
Charlie
```

Graph databases become useful when the **relationships themselves are central to the problem**.

Examples:

```text
social networks
recommendation systems
fraud detection
knowledge graphs
dependency graphs
```

---

# 11. So SQL vs NoSQL isn't really the right first question

This is probably the most important system-design lesson.

Don't ask:

> "Which database is better?"

Ask:

> **"What are the requirements of this component?"**

For example:

```text
Order Service
       ↓
Need strong transactions
       ↓
Relational DB is a strong candidate
```

But:

```text
Session Service
       ↓
Key → Value lookup
       ↓
Redis is a strong candidate
```

And:

```text
Social Graph Service
       ↓
Relationship-heavy queries
       ↓
Graph DB may be a strong candidate
```

---

# 12. The factors you should consider

When selecting a database for a component, I recommend going through these **8 questions**.

---

## Factor 1 — What kind of data do I have?

Ask:

> What does the data look like?

### Highly structured

```text
Customer
Order
Payment
Invoice
```

with relationships between them.

→ SQL is often a strong choice.

### Flexible / varying structure

For example:

```json
{
  "deviceId": "123",
  "temperature": 35
}
```

and another device sends:

```json
{
  "deviceId": "456",
  "temperature": 35,
  "humidity": 72,
  "battery": 88
}
```

→ Document-oriented NoSQL may be attractive.

---

# 13. Factor 2 — What are the access patterns?

This is **extremely important in system design**.

Suppose you have:

```text
100 million users
```

And your main query is:

```text
Get user by userId
```

You might choose:

```text
Key-value / document database
```

because the access pattern is simple:

```text
userId → user
```

But suppose your queries are:

```text
Find customers
    ↓
who bought product X
    ↓
in the last 6 months
    ↓
and spent > $1000
    ↓
and live in UAE
```

That's a much more relational/query-oriented workload.

SQL becomes very attractive.

---

# 14. Factor 3 — Do I need relationships and joins?

Ask:

> Are relationships between entities important?

For example:

```text
Customer
   ↓
Orders
   ↓
Products
   ↓
Payments
   ↓
Invoices
```

If you frequently need to traverse these relationships:

```sql
JOIN
JOIN
JOIN
```

then a relational database is usually a natural fit.

If your application instead retrieves:

```text
userId → complete user profile
```

then a document/key-value model may be simpler.

---

# 15. Factor 4 — How important are transactions?

This is a major decision point.

Imagine a payment system.

You might have:

```text
Payment
   ↓
Debit account
   ↓
Create transaction
   ↓
Update balance
   ↓
Record payment
```

You don't want half the operations committed.

Therefore:

```text
Strong transaction requirements
            ↓
       SQL becomes attractive
```

But don't oversimplify this into:

> NoSQL doesn't support transactions.

Some NoSQL databases **do support transactions**.

The correct statement is:

> **Transaction semantics, scope, consistency guarantees, and operational trade-offs vary by database.**

---

# 16. Factor 5 — Read vs write workload

Ask:

```text
How much do we read?
How much do we write?
```

For example:

### Read-heavy

```text
1000 reads/sec
10 writes/sec
```

You may consider:

```text
Read replicas
Caching
CDN
Redis
```

### Write-heavy

```text
100,000 writes/sec
```

You may need a database designed for high distributed write throughput.

This is where databases such as Cassandra/DynamoDB-style architectures can become attractive.

---

# 17. Factor 6 — Scale

Ask:

> How much data and traffic will this component eventually handle?

Imagine:

```text
10 GB
```

versus:

```text
100 TB
```

versus:

```text
10 PB
```

These are very different architectural problems.

Also consider:

```text
100 requests/sec
```

vs

```text
1 million requests/sec
```

And importantly:

### Vertical scaling

```text
Bigger machine
       ↓
More CPU/RAM/storage
```

### Horizontal scaling

```text
       DB
      / | \
     /  |  \
   DB  DB  DB
```

Different databases have different scaling characteristics and operational complexity.

---

# 18. Factor 7 — Consistency requirements

This is a **system-design interview favorite**.

Ask:

> Does the user need to immediately see the latest value?

Consider a banking balance.

```text
Account balance = $10,000
```

After withdrawing:

```text
$1,000
```

you generally want:

```text
$9,000
```

immediately and correctly reflected.

Strong consistency matters.

But consider:

```text
Instagram-like follower count
```

If it temporarily says:

```text
10,002
```

instead of:

```text
10,003
```

that's probably acceptable.

You might trade some consistency for:

```text
availability
scalability
latency
```

This leads into the CAP theorem, which you'll definitely want to learn as part of system design.

---

# 19. Factor 8 — Latency requirements

Ask:

> How quickly must this component respond?

For example:

```text
Rate limiter
     ↓
< 5 ms
```

You probably don't want every request going to a slow persistent database.

You might use:

```text
Redis
```

Similarly:

```text
Session lookup
```

might benefit from an in-memory/key-value store.

Whereas:

```text
Complex financial reporting
```

may accept much higher latency.

---

# 20. A practical decision framework

When designing a component, I would use this mental flow:

```text
                What kind of data?
                       |
          +------------+------------+
          |                         |
      Relational?               Non-relational?
          |                         |
          ↓                         ↓
        SQL                  What access pattern?
                                    |
                       +------------+-------------+
                       |            |             |
                   Key-value     Document       Graph
                       |            |             |
                     Redis       MongoDB         Neo4j
```

But then add the second layer:

```text
                Workload
                   |
       +-----------+-----------+
       |           |           |
     Reads       Writes     Mixed
       |           |           |
       +-----------+-----------+
                   |
             Scale required?
                   |
           +-------+-------+
           |               |
         Small           Massive
           |               |
        simpler       distributed DB
```

And finally:

```text
Consistency?
Transactions?
Latency?
Availability?
Operational complexity?
Cost?
```

# 21. Example — E-commerce system

Imagine you're designing:

```text
                    ┌──────────────┐
                    │   Frontend   │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
     User Service     Order Service    Product Service
          │                │                │
          ↓                ↓                ↓
       SQL DB           SQL DB          SQL/NoSQL
```

You don't necessarily use one database for everything.

### User Service

```text
Users
Profiles
Addresses
```

SQL is a good candidate.

---

### Order Service

```text
Order
OrderItem
Payment
Order status
```

Strong consistency and transactional behavior are important.

→ **SQL is a strong candidate.**

---

### Product catalog

Potentially:

```text
Product
   |
   +-- electronics attributes
   |
   +-- clothing attributes
   |
   +-- furniture attributes
```

Product attributes can vary substantially.

A document database can be attractive.

But SQL can also work perfectly well depending on requirements.

**There is no automatic rule that product catalog = MongoDB.**

---

### Shopping cart

```text
cart:user:123
      ↓
{
   product1: 2,
   product5: 1
}
```

Very fast lookup/update.

→ Redis or another key-value store could be appropriate.

---

### Recommendation system

```text
User A
  |
  +--- bought ---> Product X
  |
  +--- viewed ---> Product Y
  |
  +--- likes ----> Product Z
```

Depending on the design, you might use:

```text
Graph DB
```

or a specialized recommendation/analytics architecture.

---

# 22. One component can use multiple databases

This is another important system-design concept.

You don't necessarily have:

```text
Application
      ↓
One database
```

You might have:

```text
                 Order Service
                      |
             +--------+--------+
             |                 |
             ↓                 ↓
          PostgreSQL         Redis
             |                 |
        source of truth       cache
```

For example:

```text
PostgreSQL
    ↓
Authoritative order data

Redis
    ↓
Frequently accessed order/status data
```

This is called **polyglot persistence** when an architecture uses different database technologies for different needs.

---

# 23. Don't choose NoSQL just because "it's scalable"

This is a common beginner mistake.

Someone says:

> "We need millions of users, therefore MongoDB/Cassandra."

Not necessarily.

Modern SQL databases can handle **very large systems**.

The real question is:

```text
What is the workload?
What are the access patterns?
What consistency do we need?
What transactions do we need?
How much scale?
How much complexity can we operate?
```

Only then choose the technology.

---

# 24. Don't choose SQL just because "SQL is safer"

Another common mistake.

For example:

```text
Distributed event ingestion

500,000 events/sec
```

with access pattern:

```text
Get events by deviceId + time range
```

A distributed NoSQL/time-series-oriented design might be much more suitable than a traditional relational design.

---

# 25. A very useful interview framework

When an interviewer asks:

> **"Which database would you choose?"**

Don't immediately say:

> "PostgreSQL."

Instead say something like:

> "I'd first understand the data model, access patterns, consistency and transaction requirements, read/write ratio, expected scale, latency requirements, and availability requirements. Based on those, I'd select the database."

Then explain your choice.

For example:

> "For the Order Service, I'd start with PostgreSQL because orders have strong relationships between orders, items, customers and payments, and transactional consistency is important. If traffic grows, I can consider read replicas, partitioning, caching, and eventually other scaling strategies."

That's much stronger system-design reasoning.

# 26. My simple mental model

Keep this in your system-design notes:

```text
SQL
│
├── Structured data
├── Relationships
├── Joins
├── Complex queries
├── Strong transactional requirements
└── ACID

NoSQL
│
├── Flexible data models
├── Specialized access patterns
├── Massive distributed workloads
├── High throughput
├── Horizontal scaling
└── Different consistency/transaction models depending on DB
```

But the **real decision tree** is:

```text
                DATABASE SELECTION
                       │
                       ↓
                What is the data?
                       │
                       ↓
             What are the queries?
                       │
                       ↓
             What are the access patterns?
                       │
                       ↓
              Do we need transactions?
                       │
                       ↓
             What consistency is needed?
                       │
                       ↓
             Read/write characteristics?
                       │
                       ↓
                Expected scale?
                       │
                       ↓
                Latency requirements?
                       │
                       ↓
             Availability requirements?
                       │
                       ↓
             Operational complexity/cost?
                       │
                       ↓
                Choose database
```

### The key takeaway

**Database selection is a consequence of requirements, not a technology preference.**

For system design, I'd learn the database topics in roughly this order:

1. **SQL vs NoSQL**
2. **Database indexing**
3. **Transactions + ACID**
4. **Isolation levels**
5. **Replication**
6. **Sharding / partitioning**
7. **CAP theorem**
8. **Consistency models**
9. **Database scaling**
10. **Caching + Redis**
11. **Read/write patterns**
12. **Polyglot persistence**
13. Distributed tranaction : 2-phase commit and SAGA pattern

Once you understand those, you'll be able to look at a component and reason *why* PostgreSQL, Redis, MongoDB, Cassandra, etc. is appropriate rather than simply memorizing which database goes with which use case.
