
# Polyglot Persistence

### Simple definition

**Polyglot persistence means using different types of databases in the same application, choosing each database based on the problem it is best suited to solve.**

Instead of saying:

> "Our application uses PostgreSQL for everything."

you say:

> "We use PostgreSQL for transactional data, Redis for caching, Elasticsearch for search, and perhaps MongoDB for document-oriented data."

The key idea is:

```text
                    ┌─────────────────┐
                    │   Application   │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
         PostgreSQL       Redis       Elasticsearch
         transactions     cache          search
```

Each database has a **specific responsibility**.

---

# 1. Why do we need Polyglot Persistence?

Different databases are optimized for different access patterns.

For example, imagine you're building an e-commerce application.

You need to handle:

* orders
* payments
* users
* product catalog
* product search
* sessions
* recommendations
* analytics
* caching

Trying to force all of these into one database can create unnecessary problems.

### Example

PostgreSQL is excellent for:

```text
Order
Payment
Customer
Invoice
```

because you need:

* transactions
* relationships
* constraints
* consistency
* ACID guarantees

But imagine you're implementing:

```text
Search products by:
"red nike running shoes under $100"
```

A relational database can do this, but a search engine such as Elasticsearch/OpenSearch is designed specifically around this kind of workload.

Similarly:

```text
GET /products/123
```

might be served from Redis rather than hitting PostgreSQL every time.

So you might have:

```text
                 E-commerce application
                         │
          ┌──────────────┼───────────────┐
          │              │               │
          ▼              ▼               ▼
      PostgreSQL       Redis       Elasticsearch
       source of       cache          search
        truth
```

That's polyglot persistence.

---

# 2. Polyglot ≠ Multiple Databases of the Same Type

This distinction is important.

Suppose you have:

```text
PostgreSQL
PostgreSQL
PostgreSQL
```

because you've partitioned or replicated your database.

That's **not normally what we mean by polyglot persistence**.

You're still using one database technology.

Polyglot persistence usually means using **different persistence technologies**:

```text
PostgreSQL
Redis
MongoDB
Elasticsearch
Kafka
Cassandra
Neo4j
...
```

for different purposes.

---

# 3. A realistic example

Let's design a simple e-commerce system.

## Requirement 1 — Orders

We need:

```text
Order
OrderItem
Customer
Payment
```

Relationships matter.

We also need:

```text
BEGIN TRANSACTION

create order
create order items
reserve payment

COMMIT
```

A relational database is a natural fit.

```text
PostgreSQL
```

So:

```text
Orders ────────┐
               │
Customers ─────┼──> PostgreSQL
               │
Payments ──────┘
```

PostgreSQL becomes the **system of record** for these entities.

---

# 4. Requirement 2 — Caching

Suppose our product API receives:

```text
GET /products/123
```

10,000 times per minute.

We don't necessarily want:

```text
10,000 requests
       ↓
PostgreSQL
```

Instead:

```text
Request
   │
   ▼
 Redis
   │
   ├── HIT ──> return product
   │
   └── MISS
          │
          ▼
      PostgreSQL
          │
          ▼
        Redis
          │
          ▼
       Response
```

Redis is optimized for extremely fast key/value access.

So:

```text
PostgreSQL → durable source of truth
Redis      → temporary fast-access copy
```

---

# 5. Requirement 3 — Product Search

Now users want:

```text
"wireless headphones with noise cancellation"
```

and expect:

* full-text search
* relevance ranking
* typo tolerance
* filtering
* faceting
* autocomplete

That's a different problem.

We could use:

```text
Elasticsearch / OpenSearch
```

So:

```text
Product data
     │
     ├──────────────> PostgreSQL
     │                 source of truth
     │
     └──────────────> Elasticsearch
                       search index
```

Notice something important:

**Elasticsearch doesn't necessarily become the source of truth.**

PostgreSQL might still own the product.

Elasticsearch contains a representation optimized for searching.

---

# 6. Requirement 4 — Recommendations

Suppose we want:

> "Customers who bought X also bought Y."

This can involve relationships between entities such as:

```text
User → bought → Product
User → viewed → Product
Product → belongs to → Category
Product → similar to → Product
```

A graph database such as Neo4j could potentially be useful for certain recommendation/relationship-heavy workloads.

You could have:

```text
PostgreSQL
      │
      │ product/order data
      ▼
Graph database
      │
      ▼
recommendation relationships
```

Again, each database has a specific job.

# 7. So what does the architecture look like?

A simplified system might look like:

```text
                         ┌──────────────────┐
                         │   E-commerce API │
                         └────────┬─────────┘
                                  │
             ┌────────────────────┼────────────────────┐
             │                    │                    │
             ▼                    ▼                    ▼
        PostgreSQL             Redis            Elasticsearch
        transactions           cache                search
             │
             │
             ▼
        Source of Truth
```

Potentially:

```text
                         Application
                              │
          ┌───────────────────┼──────────────────┐
          │                   │                  │
          ▼                   ▼                  ▼
     PostgreSQL            Redis          Elasticsearch
     ------------          -----          -------------
     Orders                Cache          Product search
     Payments              Sessions       Full text
     Customers             Hot data       Filtering
          │
          │ events
          ▼
       Kafka
          │
          ├──────────────> Search indexing
          │
          └──────────────> Analytics
```

Now you're doing **polyglot persistence at system-design scale**.

# 8. The most important concept: Source of Truth

This is where people often get confused.

Suppose:

```text
Product 123
```

exists in:

```text
PostgreSQL
Redis
Elasticsearch
```

Which one is authoritative?

Usually:

```text
PostgreSQL
     ↓
Source of Truth
```

while:

```text
Redis
     ↓
Cache

Elasticsearch
     ↓
Search projection
```

So you might have:

```text
                Product
                   │
                   ▼
             PostgreSQL
             Source of Truth
                   │
             ┌─────┴─────┐
             │           │
             ▼           ▼
           Redis    Elasticsearch
           Cache       Search
```

If Redis disappears:

```text
No big deal.
```

You rebuild it from PostgreSQL.

If Elasticsearch loses its index:

```text
Reindex from PostgreSQL.
```

But if PostgreSQL loses the actual product/order data, that's a much bigger problem.

# 9. How do these databases stay synchronized?

This is one of the biggest challenges with polyglot persistence.

Imagine:

```text
User changes product price
```

You need:

```text
PostgreSQL
Redis
Elasticsearch
```

to eventually reflect the change.

You generally **don't want** to do:

```java
postgres.save(product);
redis.save(product);
elasticsearch.save(product);
```

inside one giant distributed transaction.

That creates a lot of complexity.

Instead, you can use an **event-driven approach**.

For example:

```text
                    Product Service
                          │
                          ▼
                    PostgreSQL
                          │
                     ProductUpdated
                          │
                          ▼
                        Kafka
                       /     \
                      /       \
                     ▼         ▼
                 Redis    Elasticsearch
```

Now consumers independently update their representations.

---

# 10. This introduces Eventual Consistency

Suppose:

```text
10:00:00
Product price = $100
```

User changes it to:

```text
$90
```

PostgreSQL updates immediately:

```text
PostgreSQL = $90
```

But Elasticsearch might receive the event a few milliseconds later:

```text
Elasticsearch = $100
```

for a short period.

Then:

```text
Event consumed
       ↓
Elasticsearch = $90
```

So you have:

```text
PostgreSQL → strongly consistent source
Redis      → eventually updated
Search     → eventually updated
```

This connects directly to the **Consistency Models** topic you studied earlier.

# 11. Polyglot persistence and microservices

Polyglot persistence becomes particularly interesting with microservices.

Imagine:

```text
                E-commerce
                    │
       ┌────────────┼────────────┐
       │            │            │
       ▼            ▼            ▼
  Order Service  User Service  Product Service
       │            │            │
       ▼            ▼            ▼
 PostgreSQL      PostgreSQL     MongoDB
```

Each service can potentially choose its own database.

This is sometimes called:

**Database-per-service**

For example:

```text
Order Service
    └── PostgreSQL

Product Service
    └── MongoDB

Search Service
    └── Elasticsearch

Notification Service
    └── Cassandra

Caching
    └── Redis
```

The advantage is that each service can optimize its persistence model independently.

---

# 12. But Polyglot Persistence has a price

This is **not**:

> "More databases = better architecture."

Quite the opposite.

Every additional database introduces operational and development complexity.

For example:

### One database

```text
Application
     │
     ▼
PostgreSQL
```

You need to understand:

```text
1 database
1 backup strategy
1 monitoring system
1 security model
1 deployment model
```

Now:

```text
Application
   │
   ├── PostgreSQL
   ├── Redis
   ├── Elasticsearch
   └── Kafka
```

You now have:

```text
multiple deployments
multiple backups
multiple monitoring systems
multiple failure modes
multiple security configurations
multiple client libraries
multiple operational skills
```

And you need to synchronize data.

---

# 13. Distributed failure becomes more complicated

Imagine:

```text
PostgreSQL ✅
Redis      ❌
Elasticsearch ❌
```

Your application needs to know:

> What happens now?

For example, if Redis is unavailable:

```text
Request
   ↓
Redis ❌
   ↓
PostgreSQL
   ↓
Response
```

That's manageable.

But if Elasticsearch is unavailable:

```text
Product search
      ↓
Elasticsearch ❌
```

you need a strategy.

Maybe:

```text
return error
```

or:

```text
use a degraded search
```

or:

```text
temporarily disable search
```

The architecture has to explicitly define these failure modes.

---

# 14. Polyglot persistence vs Polyglot programming

Don't confuse these.

### Polyglot programming

Using multiple programming languages:

```text
Java
Python
Go
JavaScript
```

### Polyglot persistence

Using multiple persistence technologies:

```text
PostgreSQL
Redis
MongoDB
Elasticsearch
```

You can have one without the other.

# 15. How do you decide which database to use?

This is the system-design question you should get comfortable answering.

Don't start with:

> "I want to use MongoDB."

Start with:

> **"What are my access patterns and consistency requirements?"**

Then choose the technology.

A simplified decision table:

| Requirement                              | Possible choice                |
| ---------------------------------------- | ------------------------------ |
| Relational data + transactions           | PostgreSQL / MySQL             |
| Key-value / extremely fast cache         | Redis                          |
| Full-text search                         | Elasticsearch / OpenSearch     |
| Document-oriented data                   | MongoDB                        |
| Huge write throughput / distributed data | Cassandra                      |
| Graph relationships                      | Neo4j                          |
| Time-series data                         | TimescaleDB / specialized TSDB |
| Analytics / large-scale OLAP             | Data warehouse / lakehouse     |

The word **possible** is important. These aren't hard rules.

# 17. One subtle but important point

**Polyglot persistence does not necessarily mean every service owns a different database.**

You can have:

```text
PostgreSQL
   +
Redis
   +
Elasticsearch
```

inside one application.

That's already polyglot persistence.

And you can also have:

```text
Service A → PostgreSQL
Service B → MongoDB
Service C → Cassandra
```

which is another form.

So the fundamental idea is:

> **Use different persistence technologies where their strengths match different data/access requirements.**

### The system-design mindset

The big takeaway I'd want you to remember is:

> **Don't choose a database because it's popular. Choose the persistence technology based on the data model, access pattern, consistency requirements, scalability requirements, and operational cost.**

And one more very practical rule:

> **Start with the simplest architecture that satisfies the requirements. Introduce another database only when you have a concrete reason for it.**

For an interview, if you say:

> "I'll use PostgreSQL, Redis, MongoDB, Elasticsearch, Cassandra and Neo4j."

the interviewer will probably ask:

**"Why do you need six databases?"** 😄

You should be able to justify **each one independently**.
