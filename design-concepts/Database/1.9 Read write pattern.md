
# Read/Write Patterns

The basic idea is:

> **How does your application read data and how does it write data to the database, especially when the system becomes large?**

At small scale, you might simply do:

```text
Application
    |
    v
Database
```

But at scale, you start making deliberate decisions about:

* Where reads should go
* Where writes should go
* How many reads vs writes you have
* Whether reads can tolerate stale data
* Whether writes need strong consistency
* Whether to use replicas
* When to use caching
* How to handle read-after-write consistency

---

# 1. First understand the Read/Write ratio

Not every application has the same workload.

For example:

### Social media

```text
1000 reads
   |
100 writes
```

Approximately:

```text
Read : Write = 10 : 1
```

A user may:

* Read posts
* Read comments
* View profiles
* View likes

while relatively fewer operations modify data.

This is a **read-heavy system**.

---

### Payment system

Imagine:

```text
100 reads
100 writes
```

or even a system where writes are very important.

This is closer to a **write-heavy / balanced system**, depending on the workload.

---

# 2. Read-heavy vs Write-heavy

This is the first thing you should identify during system design.

## Read-heavy

```text
Reads  >>> Writes
```

Example:

```text
Product catalog

10,000,000 reads
   |
100,000 writes
```

The database is mostly being asked:

> "Give me this data."

### Typical strategies

You can use:

```text
Application
    |
    +------> Cache
    |
    +------> Read Replicas
               |
               +--> DB
```

For example:

```text
                    +--> Redis
                    |
Application --------+
                    |
                    +--> Read Replica 1
                    |
                    +--> Read Replica 2
                    |
                    +--> Primary
```

Writes go to the primary.

Reads can be distributed.

---

# 3. Write-heavy systems

Now imagine:

```text
100 reads
10,000 writes
```

For example:

* telemetry ingestion
* logging
* event collection
* transaction processing
* IoT data ingestion

Here the problem isn't primarily:

> "How can I serve more reads?"

It's:

> "How can I handle a huge number of writes?"

You might use:

```text
Application
     |
     v
 Message Queue
     |
     v
Consumers
     |
     v
Database
```

For example:

```text
             +--> Consumer --> DB
             |
Producer ---> Kafka
             |
             +--> Consumer --> DB
```

The queue allows you to **buffer and distribute writes**.

This connects directly to another system-design concept you'll eventually encounter: **asynchronous processing**.

---

# 4. Read Replicas

This is one of the most important read/write patterns.

Suppose you have:

```text
             +--> Read Replica 1
             |
Application -+--> Read Replica 2
             |
             +--> Primary
```

The rule could be:

```text
WRITE ---> Primary

READ ----> Replica
```

For example:

```java
createUser()
    -> Primary

getUser()
    -> Replica
```

This allows you to scale reads horizontally.

Instead of:

```text
        100,000 reads
             |
             v
         Primary
```

you can have:

```text
                 +--> Replica 1
                 |
100,000 reads ---+--> Replica 2
                 |
                 +--> Replica 3
```

---

# 5. But there's a catch: replication lag

This is where read/write patterns become interesting.

Suppose:

```text
Primary
   |
   | replication
   v
Replica
```

You execute:

```sql
UPDATE users
SET name = 'Rohan'
WHERE id = 10;
```

on the primary.

Immediately afterward:

```sql
SELECT name
FROM users
WHERE id = 10;
```

goes to a replica.

The replica might still contain:

```text
Old value
```

because replication hasn't caught up yet.

So:

```text
WRITE
  |
  v
Primary
  |
  |  replication lag
  v
Replica

READ
  |
  v
Replica
```

You get:

```text
Old data
```

This is called **stale read**.

---

# 6. Read-after-write consistency

This is a very important pattern to remember.

Suppose a user changes their profile:

```text
POST /profile

name = "Rohan"
```

The application writes:

```text
Primary
    |
    | replication
    v
Replica
```

Then the UI immediately calls:

```text
GET /profile
```

If that request goes to a replica before replication completes:

```text
POST /profile
     |
     v
 Primary
     |
     | not replicated yet
     v
 Replica

GET /profile
     |
     v
 Replica
     |
     v
Old profile
```

That's a bad user experience.

The user thinks:

> "I just changed my name. Why is the old name showing?"

---

# 7. Solution: Read your own writes

One solution is:

```text
WRITE ---> Primary
            |
            v
For some time, READ ---> Primary
```

For example:

```text
POST /profile
      |
      v
   Primary
      |
      v
GET /profile
      |
      v
   Primary
```

After some point, reads can return to replicas.

This is often called **read-your-writes consistency**.

The important point:

> After a client writes data, subsequent reads from that client should see that write.

---

# 8. Another pattern: Sticky reads

You can also temporarily associate a user/session with a particular database node.

For example:

```text
User A
   |
   +----> Primary
   |
   +----> Primary
   |
   +----> Replica
```

versus:

```text
User B
   |
   +----> Replica 1
   |
   +----> Replica 1
   |
   +----> Replica 1
```

This is sometimes called **sticky routing**.

But it has trade-offs, especially around load balancing and failover.

---

# 9. CQRS

Now we reach a very important read/write pattern:

**CQRS — Command Query Responsibility Segregation**

The basic idea is:

> Separate the model used for writing from the model used for reading.

Instead of:

```text
Application
     |
     v
    DB
```

you can have:

```text
                +--> Write Model --> Write DB
                |
Application ----+
                |
                +--> Read Model ---> Read DB
```

For example, an e-commerce system.

### Write model

Optimized for:

```text
Create order
Update order
Cancel order
Update payment
```

### Read model

Optimized for:

```text
Show order history
Show dashboard
Show sales report
Show customer summary
```

The read model can be completely different from the write model.

---

# 10. CQRS example

Suppose your normalized database contains:

```text
customers
orders
order_items
products
payments
shipments
```

To display:

```text
Customer Order Dashboard
```

you might need a complicated query:

```sql
JOIN customers
JOIN orders
JOIN order_items
JOIN products
JOIN payments
JOIN shipments
```

That's potentially expensive.

With CQRS, you could maintain a read-optimized table:

```text
customer_order_summary

customer_id
order_id
customer_name
product_count
total_amount
payment_status
shipping_status
```

Now the UI can simply execute:

```sql
SELECT *
FROM customer_order_summary
WHERE customer_id = 100;
```

Much simpler.

---

# 11. How does the read model stay updated?

Usually through events.

```text
                Write DB
                   |
                   |
                OrderCreated
                   |
                   v
                Kafka
                   |
                   v
            Read Model Consumer
                   |
                   v
              Read Database
```

For example:

```text
User creates order
       |
       v
Write DB
       |
       v
OrderCreated event
       |
       v
Kafka
       |
       v
Read-model consumer
       |
       v
Read DB updated
```

Now we have an important consequence:

### The read database may be eventually consistent.

There may be a small delay:

```text
Write DB
   |
   | 100 ms
   v
Read DB
```

So CQRS is excellent for some high-scale systems, but it isn't something you automatically introduce into every application.

---

# 12. Cache-aside pattern

You already covered Redis, so this should look familiar.

A very common read pattern is:

```text
Application
     |
     v
   Redis
     |
     | cache miss
     v
 Database
```

Pseudo-code:

```java
User user = redis.get(userId);

if (user == null) {
    user = database.findUser(userId);
    redis.set(userId, user);
}

return user;
```

This is called **cache-aside**.

---

# 13. Write-through

Another pattern is:

```text
Application
     |
     v
   Cache
     |
     v
 Database
```

The application writes to the cache, and the cache updates the database.

Conceptually:

```text
WRITE
  |
  v
Cache
  |
  v
Database
```

This can keep cached data synchronized more systematically, but it adds complexity and depends on the caching technology.

---

# 14. Write-behind / write-back

Another approach:

```text
Application
     |
     v
   Cache
     |
     | asynchronous
     v
 Database
```

The application writes to the cache first.

The database update happens later.

This can provide very high write throughput, but now you have a bigger durability/consistency concern:

```text
Application
     |
     v
Cache
     X  <-- cache failure here?
     |
     v
Database
```

If the cache loses data before persistence, you can lose writes unless the system has appropriate durability mechanisms.

So this pattern should be used carefully.

---

# 15. Choosing the pattern

For system design, I'd think about it like this:

| Situation                         | Common approach                    |
| --------------------------------- | ---------------------------------- |
| Read-heavy                        | Read replicas + caching            |
| Write-heavy                       | Batching / queues / partitioning   |
| Reads can be stale                | Read replicas                      |
| Read-after-write required         | Route reads to primary temporarily |
| Complex read queries              | Read-optimized model               |
| Different read/write requirements | CQRS                               |
| Extremely frequent reads          | Cache                              |
| Asynchronous writes acceptable    | Queue/event-driven processing      |
| Strong consistency required       | Primary/leader reads               |
| Eventual consistency acceptable   | Replicas/read models               |

This is the mental model I want you to retain:

                    └───────┬───────┘

               ┌────────────┴────────────┐

             WRITE                     READ

          ┌─────────┐               ┌─────────┐
          │ Primary │               │  Cache  │

> **"You have 1 primary and 5 read replicas. A user updates their profile and immediately reads it, but sometimes sees the old value. Why, and how would you solve it?"**

The expected thought process is:

```text
Replication lag
      ↓
Replica hasn't caught up
      ↓
Stale read
      ↓
Read from primary after write
OR
session/user-aware routing
OR
track replication position / consistency mechanism
```
