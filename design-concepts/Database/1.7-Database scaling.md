# Database Scaling

## 1. What does database scaling mean?

Database scaling means:

> **Increasing the database's ability to handle more workload while maintaining acceptable performance, availability, and reliability.**

The workload can increase in several ways:

```text
Users ↑
Requests/sec ↑
Data size ↑
Concurrent connections ↑
Reads ↑
Writes ↑
```

For example:

```text
Today:
1,000 requests/sec

After growth:
10,000 requests/sec

Later:
100,000 requests/sec
```

At some point, your single database may become the bottleneck.

---

# 2. Start with a single database

A simple application might look like:

```text
                 Application
                      |
                      |
                 PostgreSQL
                      |
                 Disk / SSD
```

Initially, this can work extremely well.

You don't want to immediately introduce:

* sharding
* multiple replicas
* distributed databases
* caching
* complicated routing

because distributed systems introduce complexity.

A single database is often the simplest architecture.

But eventually you may hit limits.

---

# 3. What can become the bottleneck?

Suppose your database has:

```text
CPU       → 95%
Memory    → 90%
Disk I/O  → 95%
Connections → 1000
```

Or perhaps the database isn't CPU-bound at all.

Maybe you're getting:

```text
10,000 reads/sec
500 writes/sec
```

and the workload is mostly reads.

Or:

```text
500 reads/sec
10,000 writes/sec
```

The scaling strategy depends heavily on **what is actually limiting the system**.

That's an important system-design principle:

> **Don't scale the database blindly. Identify the bottleneck first.**

---

# 4. Two fundamental approaches

There are two major ways to scale a database:

```text
                 Database Scaling
                       |
              +--------+--------+
              |                 |
         Vertical            Horizontal
         Scaling              Scaling
              |                 |
          Bigger node       More nodes
```

Let's understand these properly.

---

# 5. Vertical Scaling — Scale Up

Vertical scaling means:

> **Make the database server more powerful.**

Suppose you have:

```text
Database Server

CPU:     4 cores
RAM:     16 GB
Storage: 500 GB
```

You upgrade it to:

```text
Database Server

CPU:     32 cores
RAM:     128 GB
Storage: 2 TB
```

Architecture remains:

```text
Application
     |
     v
   DB-1
```

You're simply making `DB-1` stronger.

---

# 6. Why vertical scaling works

Suppose your database is CPU-bound:

```text
CPU = 100%
```

Adding more CPU can allow more queries to execute concurrently.

If your workload is memory-heavy:

```text
RAM = 95%
```

Adding memory can allow:

* larger database cache
* more pages in memory
* fewer disk reads
* better query performance

If storage is the bottleneck:

```text
Disk I/O = 100%
```

faster SSD/NVMe storage can improve throughput.

---

# 7. Advantages of vertical scaling

### Simple

No application changes:

```text
Application
     |
     v
Database
```

### No distributed-data complexity

You don't have to deal with:

```text
Node A
Node B
Node C
```

and synchronization between them.

### Easier consistency

There's still one database authority.

---

# 8. Limitations of vertical scaling

Hardware has limits.

You can't infinitely scale:

```text
4 CPU
 ↓
16 CPU
 ↓
64 CPU
 ↓
256 CPU
 ↓
1024 CPU
```

Eventually:

```text
Hardware limit
      ↓
      X
```

And bigger machines can become expensive.

There's another important problem:

### Single point of failure

If you have:

```text
Application
     |
     v
   DB-1
```

and DB-1 dies:

```text
Application
     |
     X
   DB-1 💥
```

your database is unavailable.

So vertical scaling alone doesn't solve high availability.

---

# 9. Horizontal Scaling — Scale Out

Horizontal scaling means:

> **Add more database nodes.**

Instead of:

```text
             DB
```

you have:

```text
       +----- DB-1
       |
App ---+----- DB-2
       |
       +----- DB-3
```

Now multiple machines participate in handling the workload.

This is where your previous topics become important:

```text
Replication
     +
Sharding
     +
Partitioning
     ↓
Horizontal scaling
```

---

# 10. Horizontal scaling using Replication

Suppose your application has:

```text
10,000 reads/sec
1,000 writes/sec
```

Maybe your database can handle the writes but struggles with reads.

You can introduce read replicas:

```text
                  Application
                 /     |     \
                /      |      \
             Writes   Reads   Reads
                |       |       |
                ↓       ↓       ↓
             Primary   Replica Replica
```

For example:

```text
Primary
  |
  +----> Replica 1
  |
  +----> Replica 2
  |
  +----> Replica 3
```

Writes go to:

```text
Primary
```

Reads can be distributed:

```text
Replica 1
Replica 2
Replica 3
```

This is a very common scaling strategy.

---

# 11. Read scaling

Suppose:

```text
1000 writes/sec
9000 reads/sec
```

Replication can help significantly.

Without replicas:

```text
DB
 ↑
10,000 operations/sec
```

With replicas:

```text
                 +--> Replica 1 → reads
                 |
Application → Primary
                 |
                 +--> Replica 2 → reads
                 |
                 +--> Replica 3 → reads
```

Now read workload is distributed.

But remember your **consistency models** topic.

Replication can introduce:

```text
Primary:
value = 200

Replica:
value = 100
```

temporarily.

So if the application requires strong/read-after-write consistency, you need to design the read routing accordingly.

---

# 12. What about writes?

This is where things get harder.

Read replicas help with:

```text
READ scaling
```

But they don't automatically solve:

```text
WRITE scaling
```

If every write still goes to:

```text
Primary
```

then:

```text
                  Writes
                    |
                    ↓
                 Primary
                    ↑
              bottleneck
```

You can add 100 replicas, but writes still hit the same primary.

This is where **sharding** becomes important.

---

# 13. Horizontal scaling using Sharding

You already studied sharding, so let's connect it.

Suppose you have 100 million users.

Instead of:

```text
               DB
          100 million users
```

you can partition data across databases:

```text
                 Application
                /     |     \
               /      |      \
             DB-1    DB-2    DB-3
              |        |       |
          Users 1-33M  34-66M  67-100M
```

For example:

```text
Shard 1 → user_id 1 - 33,333,333
Shard 2 → user_id 33,333,334 - 66,666,666
Shard 3 → user_id 66,666,667 - 100,000,000
```

Now writes are distributed:

```text
User 10 → Shard 1
User 40M → Shard 2
User 90M → Shard 3
```

This provides **write scaling** as well as storage scaling.

---

# 14. Vertical vs Horizontal

This distinction is extremely important.

|                         | Vertical                    | Horizontal                  |
| ----------------------- | --------------------------- | --------------------------- |
| Also called             | Scale up                    | Scale out                   |
| Approach                | Bigger machine              | More machines               |
| Architecture complexity | Low                         | Higher                      |
| Application changes     | Usually minimal             | Often required              |
| Hardware limit          | Yes                         | Much higher                 |
| Distributed complexity  | Low                         | Higher                      |
| Read scaling            | Limited                     | Strong potential            |
| Write scaling           | Limited                     | Possible with sharding      |
| Availability            | Doesn't inherently solve it | Can improve with redundancy |

---

# 15. Database scaling isn't just adding machines

This is where system-design interviews get interesting.

Before scaling horizontally, you should optimize what you already have.

A typical progression is:

```text
1. Optimize queries
       ↓
2. Add proper indexes
       ↓
3. Increase resources
       ↓
4. Connection pooling
       ↓
5. Read replicas
       ↓
6. Caching
       ↓
7. Partitioning
       ↓
8. Sharding
```

You don't necessarily need every step, and the order depends on the bottleneck.

---

# 16. Query optimization

Suppose you're running:

```sql
SELECT *
FROM orders
WHERE user_id = 12345;
```

and `user_id` isn't indexed.

The database may scan a huge portion of the table.

Adding an appropriate index can change the situation dramatically:

```text
Without index:
10 million rows scanned

With index:
directly locate matching rows
```

So before throwing another database server at the problem:

> **Make sure the database isn't doing unnecessary work.**

This connects directly to your earlier **database indexing** topic.

---

# 17. Connection Pooling

This is a commonly overlooked scaling problem.

Suppose:

```text
100 application instances
```

and each creates:

```text
100 DB connections
```

You could end up with:

```text
100 × 100 = 10,000 DB connections
```

Your database might collapse under connection management even though query workload isn't huge.

Instead, use connection pooling:

```text
Application instances
       |
       ↓
Connection Pools
       |
       ↓
    Database
```

Examples in Java:

```text
HikariCP
```

Spring Boot commonly uses HikariCP by default.

The idea is:

```text
Don't create a new DB connection
for every request.

Reuse existing connections.
```

---

# 18. Database Partitioning

You already studied partitioning.

Partitioning means dividing data inside a database into manageable pieces.

For example:

```text
orders
   |
   +-- 2024
   +-- 2025
   +-- 2026
```

This can help with:

* query performance
* maintenance
* data lifecycle
* partition pruning
* large tables

But remember:

> **Partitioning doesn't necessarily mean multiple database servers.**

You can have:

```text
One DB server
   |
   +-- Partition A
   +-- Partition B
   +-- Partition C
```

Whereas sharding usually distributes data across separate nodes/databases:

```text
DB Server A → Shard A
DB Server B → Shard B
DB Server C → Shard C
```

---

# 19. Caching as database scaling

Caching is another major technique.

Suppose:

```text
100,000 requests/sec
```

but the same product information is requested repeatedly.

Instead of:

```text
100,000 requests
       ↓
   Database
```

use:

```text
             Application
                 |
             Cache/Redis
              /      \
           HIT        MISS
            |           |
            ↓           ↓
         Return       Database
```

If 90% of requests are cache hits:

```text
100,000 requests/sec

90,000 → Redis
10,000 → Database
```

That's a massive reduction in database load.

We'll cover this properly in your next topic:

**#10 Caching + Redis**

# 20. A practical scaling architecture

Let's put everything together.

Imagine an e-commerce system:

```text
                       Users
                         |
                    Load Balancer
                         |
              +----------+----------+
              |          |          |
             App       App        App
              |          |          |
              +----------+----------+
                         |
                    Redis Cache
                     /       \
                   HIT       MISS
                   |           |
                   |           ↓
                   |        DB Primary
                   |           |
                   |       Replication
                   |        /       \
                   |       ↓         ↓
                   |    Replica 1  Replica 2
                   |
                   +------ reads
```

If the system grows further:

```text
                  Application
                       |
                  Routing layer
                /       |       \
               ↓        ↓        ↓
            Shard 1   Shard 2   Shard 3
               |        |        |
            Replica   Replica   Replica
```

Now we're combining:

```text
Vertical scaling
       +
Connection pooling
       +
Caching
       +
Replication
       +
Sharding
```

# 21. How do you decide what scaling strategy to use?

This is the part I really want you to remember for system design.

Start with the workload.

### Case 1 — CPU is the bottleneck

```text
CPU → 100%
```

Consider:

```text
Vertical scaling
Query optimization
Better indexes
```

---

### Case 2 — Reads are the bottleneck

```text
Reads >> Writes
```

Consider:

```text
Read replicas
Caching
Indexes
```

---

### Case 3 — Writes are the bottleneck

```text
Writes >> Reads
```

Read replicas won't solve the fundamental problem.

Consider:

```text
Write optimization
Partitioning
Sharding
Distributed database
```

---

### Case 4 — Dataset doesn't fit comfortably on one machine

Consider:

```text
Partitioning
Sharding
Distributed storage
```

---

### Case 5 — Too many DB connections

Consider:

```text
Connection pooling
Connection limits
Application-side concurrency control
```

---

### Case 6 — Database is repeatedly serving the same data

Consider:

```text
Caching
Redis
Application-level caching
```

---

# 22. The scaling ladder

A useful mental model for interviews:

```text
                Database overloaded
                       |
                       ↓
               Identify bottleneck
                       |
          +------------+------------+
          |            |            |
         CPU          Reads        Writes
          |            |            |
          ↓            ↓            ↓
       Scale up     Replicas      Sharding
          |        + Caching    + Partitioning
          |
          ↓
      Still growing?
          |
          ↓
   Horizontal scaling
          |
          ↓
   Distributed database
```

But there's one important correction:

**Don't treat this as a rigid sequence.** For example, caching might be introduced before vertical scaling, and read replicas might be added before or after query optimization depending on the workload.

---

# 23. The most important distinction

For system design, remember:

```text
Vertical scaling
     ↓
Make ONE machine stronger

Horizontal scaling
     ↓
Use MORE machines
```

And then:

```text
Replication
     ↓
Copies of the same data
     ↓
Primarily useful for availability/read scaling

Sharding
     ↓
Different pieces of data on different nodes
     ↓
Useful for write/storage scaling
```

That relationship is extremely important:

```text
                Database Scaling
                      |
          +-----------+-----------+
          |                       |
       Scale Up                 Scale Out
          |                       |
    Bigger machine           More machines
                                  |
                       +----------+----------+
                       |                     |
                  Replication             Sharding
                       |                     |
                  Same data             Different data
```

## What I'd expect you to know for a system-design interview

After this topic, you should be able to answer:

> **"Our PostgreSQL database is becoming a bottleneck. How would you scale it?"**

A good answer shouldn't immediately be:

> "Let's shard it."

Instead:

```text
1. Identify the bottleneck
       ↓
2. Optimize queries/indexes
       ↓
3. Scale vertically if appropriate
       ↓
4. Add connection pooling
       ↓
5. If read-heavy → read replicas
       ↓
6. Add caching for frequently-read data
       ↓
7. If write/storage capacity becomes the limit
       → partition/shard
       ↓
8. Add monitoring and capacity planning
```
