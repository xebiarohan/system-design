
# Database Replication

## 1. What is replication?

**Replication means keeping copies of the same database data on multiple database servers.**

Instead of:

```text
Application
    |
    v
+-----------+
| DB Server |
+-----------+
```

we have:

```text
                 +-----------+
                 | DB Server |
                 |   Node 1  |
                 +-----------+
                      |
                 replicate
                      |
          +-----------+-----------+
          |                       |
          v                       v
   +-----------+           +-----------+
   | DB Node 2 |           | DB Node 3 |
   +-----------+           +-----------+
```

All nodes contain some version of the same data.

The primary reasons are:

* **High availability**
* **Fault tolerance**
* **Read scalability**
* **Disaster recovery**
* Sometimes **geographical distribution**

---

# 2. Why do we need replication?

Imagine an e-commerce application with one database:

```text
        10,000 requests/sec
               |
               v
        +-------------+
        |     DB      |
        +-------------+
```

There are two major problems.

### Problem 1 — Database failure

If the DB server crashes:

```text
Application
     |
     X
   DB DOWN
```

Your application may become unavailable.

### Problem 2 — Too many reads

Suppose you have:

```text
10,000 requests/sec

9,000 reads
1,000 writes
```

One database server has to handle everything.

Replication allows us to distribute the read workload.

```text
                    +-------------+
                    |   Primary   |
                    |   Database  |
                    +-------------+
                     /     |     \
                    /      |      \
                   v       v       v
              +-------+ +-------+ +-------+
              |Replica| |Replica| |Replica|
              |   1   | |   2   | |   3   |
              +-------+ +-------+ +-------+
```

Writes go to the primary.

Reads can potentially go to replicas.

---

# 3. Primary-Replica Architecture

The most common replication model you'll encounter in system design is:

**Primary → Replicas**

Sometimes you'll see the terms:

* Primary / Replica
* Leader / Follower
* Master / Slave — older terminology; generally avoided now

We'll use **Primary / Replica**.

Example:

```text
                   Application
                       |
              +--------+--------+
              |                 |
            Writes             Reads
              |                 |
              v                 v
        +-----------+      +-----------+
        |  Primary  | ---> |  Replica  |
        +-----------+      +-----------+
                              |
                              v
                         +-----------+
                         |  Replica  |
                         +-----------+
```

The primary is responsible for accepting writes.

The replicas receive changes from the primary.

---

# 4. How does replication actually happen?

This is the important part.

Suppose the database contains:

```text
Users

id | name
---+------
1  | Alice
2  | Bob
```

The application executes:

```sql
INSERT INTO users VALUES (3, 'Charlie');
```

The flow is approximately:

```text
Application
     |
     | INSERT
     v
+-----------+
|  Primary  |
+-----------+
     |
     | Replication
     v
+-----------+
|  Replica  |
+-----------+
```

The primary records the change and sends information about that change to replicas.

The exact implementation depends on the database.

For example, PostgreSQL uses **WAL (Write-Ahead Log)**.

Conceptually:

```text
Application
     |
     | INSERT
     v
 Primary DB
     |
     | write change to WAL
     v
    WAL
     |
     +---------> Replica 1
     |
     +---------> Replica 2
```

The replica replays those changes and updates its own local data.

---

# 5. Replication is usually log-based

This is a very important system-design concept.

Rather than sending the entire database every time something changes:

```text
"Here is the entire users table again"
```

the primary can send the **changes**.

For example:

```text
INSERT user 3
UPDATE user 1
DELETE user 2
```

Conceptually:

```text
Primary

Data:
Alice
Bob
Charlie

Replication Log:

1. INSERT Alice
2. INSERT Bob
3. INSERT Charlie
```

Replica reads the log and applies the operations.

Different databases implement this differently:

* PostgreSQL → WAL
* MySQL → binary log
* MongoDB → oplog

The underlying idea is similar:

> **Replicate the sequence of changes rather than repeatedly copying the whole database.**

---

# 6. Synchronous vs Asynchronous Replication

This is probably the **most important distinction** within replication.

There are two major approaches:

### Synchronous replication

The primary waits for replica acknowledgement.

### Asynchronous replication

The primary does **not** wait for replicas.

Let's see the difference.

---

# 7. Asynchronous Replication

Suppose:

```text
Application
     |
     | WRITE
     v
+-----------+
|  Primary  |
+-----------+
     |
     | replicate
     v
+-----------+
|  Replica  |
+-----------+
```

With asynchronous replication:

```text
Application
     |
     | WRITE
     v
 Primary
     |
     |---- send change ----> Replica
     |
     | immediately respond
     v
Application
```

The application doesn't wait for the replica.

So:

```text
Primary commits
       |
       v
Application gets response
       |
       |
       +---- later ----> Replica receives change
```

### Advantage

Very fast writes.

### Disadvantage

There can be **replication lag**.

For example:

```text
Primary:
User balance = $100

Replica:
User balance = $80
```

The replica hasn't received the latest update yet.

---

# 8. Replication Lag

Suppose the primary executes:

```sql
UPDATE account
SET balance = 100
WHERE id = 1;
```

The primary now has:

```text
Primary:
balance = 100
```

But the replica hasn't received the update yet:

```text
Replica:
balance = 80
```

For a short period:

```text
Primary != Replica
```

This is called **replication lag**.

Eventually:

```text
Primary:
balance = 100

Replica:
balance = 100
```

This is one reason why replicas may not always be appropriate for every read.

---

# 9. A real-world problem caused by replication lag

Imagine:

```text
POST /orders
```

creates an order.

The application writes to the primary:

```text
Primary:
Order #123 = CREATED
```

Then immediately the frontend calls:

```text
GET /orders/123
```

Suppose the read is routed to a replica.

Because of replication lag:

```text
Primary:
Order #123 exists

Replica:
Order #123 doesn't exist yet
```

The user could see:

```text
"Order not found"
```

even though the order was successfully created.

This is called a **read-after-write consistency problem**.

We'll come back to this when you study **consistency models**.

---

# 10. Synchronous Replication

Now consider synchronous replication.

```text
Application
     |
     | WRITE
     v
+-----------+
|  Primary  |
+-----------+
     |
     | replicate
     v
+-----------+
|  Replica  |
+-----------+
     |
     | ACK
     v
+-----------+
|  Primary  |
+-----------+
     |
     | response
     v
Application
```

The primary waits for the required replica acknowledgement before considering the operation complete.

Conceptually:

```text
Write
  |
  v
Primary
  |
  +------> Replica
  |           |
  |           +---- ACK
  |                 |
  +<----------------+
  |
  v
Respond to application
```

### Advantage

Stronger durability/consistency guarantees.

### Disadvantage

Higher latency.

And if the required replica is unavailable:

```text
Primary
   |
   X
Replica unavailable
```

the write may have to wait or fail, depending on the configuration.

---

# 11. Synchronous vs Asynchronous

|                                     | Synchronous             | Asynchronous                        |
| ----------------------------------- | ----------------------- | ----------------------------------- |
| Write latency                       | Higher                  | Lower                               |
| Replication lag                     | Very low/controlled     | Possible                            |
| Availability during replica failure | Can be reduced          | Usually higher                      |
| Consistency                         | Stronger                | Eventually consistent possibilities |
| Complexity                          | Higher                  | Lower                               |
| Performance                         | Lower write performance | Better write performance            |

Important:

**"Synchronous replication = perfectly consistent" is too simplistic.**

The actual guarantees depend on the database's replication configuration and transaction semantics.

---

# 12. Single-Leader Replication

The architecture we've discussed is called **single-primary / single-leader replication**.

```text
             Writes
               |
               v
         +-----------+
         |  Primary  |
         +-----------+
          /    |    \
         /     |     \
        v      v      v
    Replica Replica Replica
```

Usually:

```text
Writes ---> Primary
Reads ----> Replicas
```

This is extremely common.

---

# 13. What happens if the primary dies?

This is where replication becomes really useful.

Suppose:

```text
                 Primary
                   ❌
                  DOWN

                /       \
               v         v
          Replica 1   Replica 2
```

We need to promote one replica:

```text
                Replica 1
                   ↓
             becomes Primary
```

Now:

```text
              New Primary
                  |
          +-------+-------+
          |               |
          v               v
      Replica 2       Replica 3
```

This process is called:

# Failover

A system may use an automated mechanism to detect the primary failure and promote a replica.

---

# 14. Who decides which replica becomes primary?

Usually some combination of:

* Database cluster manager
* Consensus system
* Orchestration system
* Managed database service

The important system-design concept is:

> **Replication alone doesn't automatically solve failover.**

You need some mechanism to:

1. Detect primary failure
2. Select a replica
3. Promote it
4. Redirect application traffic
5. Reconfigure other replicas

For example:

```text
                 +----------------+
                 | Failure        |
                 | Detection      |
                 +-------+--------+
                         |
                         v
                 Primary is DOWN
                         |
                         v
                 Select Replica
                         |
                         v
                 Promote Replica
                         |
                         v
                 Redirect Writes
```

---

# 15. What happens to data during failover?

This is a very important trade-off.

Suppose:

```text
Primary:
Transaction A
Transaction B
Transaction C
```

Replica has only:

```text
Transaction A
Transaction B
```

because replication was asynchronous.

Then primary crashes.

If Replica becomes the new primary:

```text
New Primary:
A
B
```

Transaction C may be lost.

This is called **data loss due to replication lag**.

Therefore:

> Asynchronous replication improves performance/availability but can introduce a window where acknowledged data hasn't reached another node.

This is one of the fundamental trade-offs you'll encounter in distributed systems.

---

# 16. Replication and Read Scaling

Replication is also used to scale reads.

Suppose:

```text
100,000 requests/sec

90,000 READ
10,000 WRITE
```

Instead of:

```text
                DB
                 ↑
          100k requests
```

we can have:

```text
                  +-----------+
                  |  Primary  |
                  +-----------+
                       ↑
                    Writes
                       |
                       |
              +--------+--------+
              |        |        |
              v        v        v
          Replica   Replica   Replica
              ↑        ↑        ↑
             Reads    Reads    Reads
```

Now read traffic can be distributed.

This is often called:

**Read scaling through replicas.**

---

# 17. But replicas don't automatically solve everything

Suppose your workload is:

```text
90% reads
10% writes
```

Replication can help significantly.

But suppose:

```text
90% writes
10% reads
```

Adding read replicas won't solve your main bottleneck.

Because:

```text
                Primary
                  ↑
             ALL WRITES
                  ↑
       ---------------------
       |   |   |   |   |   |
      App App App App App App
```

The primary still handles the writes.

This is one reason **sharding** becomes important later.

---

# 18. Replication vs Backup

This distinction is extremely important.

People sometimes think:

> "If I have replicas, I don't need backups."

Not true.

Replication:

```text
Primary
   |
   +---- Replica
```

Backup:

```text
Database
    |
    +---- Backup copy
```

Suppose somebody accidentally executes:

```sql
DELETE FROM users;
```

Replication may faithfully replicate the deletion:

```text
Primary:
DELETE users

        |
        v

Replica:
DELETE users
```

Now all replicas have the same bad data.

A backup gives you a recovery point from before the mistake.

So:

> **Replication protects primarily against infrastructure/node failure. Backups protect against data loss, corruption, accidental deletion, and some disaster scenarios.**

You generally want **both**.

---

# 19. Multi-Region Replication

Replication can also be used across geographical regions.

For example:

```text
           Europe
        +-----------+
        | Primary   |
        +-----------+
             |
             | replication
             v
           USA
        +-----------+
        | Replica   |
        +-----------+
             |
             v
          Asia
        +-----------+
        | Replica   |
        +-----------+
```

Why?

### Disaster recovery

If an entire region becomes unavailable:

```text
Europe ❌
```

you may be able to fail over to:

```text
USA
```

### Lower read latency

Users in Asia could potentially read from a nearby replica.

But this introduces another issue:

```text
Europe
   |
   | network
   |
   +--------------------> Asia
```

Network latency makes synchronous cross-region replication expensive.

Therefore, cross-region replication is often asynchronous.

---

# 20. Replication Topologies

You don't always have only:

```text
Primary → Replica
```

You can have:

### Primary → multiple replicas

```text
             Primary
            /   |   \
           v    v    v
          R1   R2   R3
```

### Cascading replication

```text
Primary
   |
   v
  R1
 /  \
v    v
R2   R3
```

Here R1 can replicate changes to R2/R3.

This can reduce the replication workload on the primary.

---

# 21. Multi-Primary Replication

Another model is:

```text
       Primary A
          ↕
       Primary B
          ↕
       Primary C
```

Multiple nodes can accept writes.

This can be useful in some distributed systems, but it introduces a major problem:

# Write conflicts

Suppose:

```text
Primary A:
User balance = $100

Primary B:
User balance = $100
```

Two users update it simultaneously:

```text
A:
balance = 150

B:
balance = 120
```

Now:

```text
A → 150
B → 120
```

What should the final value be?

You need conflict-resolution rules.

That's why single-primary architectures are often simpler.

---

# 22. Replication and CAP

This topic will become much easier when you reach CAP, but there's a connection worth knowing now.

Distributed replicas communicate over a network:

```text
Node A
  |
  | Network
  |
Node B
```

Networks can fail.

```text
Node A     X     Node B
          network
          failure
```

Now the nodes may temporarily have different information.

Replication therefore forces you to think about:

* Consistency
* Availability
* Network partitions
* Failover
* Replication lag

These are exactly the problems you'll explore with **CAP theorem**.

# 23. A useful system-design example

Imagine you're designing Instagram-like application.

You have:

```text
Users
Posts
Comments
Likes
```

Suppose you have:

```text
1 Primary
3 Read Replicas
```

Architecture:

```text
                   Application
                  /           \
               Writes         Reads
                 |               |
                 v               v
             +-------+     +----------+
             |Primary| --> | Replica 1|
             +-------+     +----------+
                 |          | Replica 2|
                 |          +----------+
                 |          | Replica 3|
                 |          +----------+
                 |
                 +---- replication
```

### Creating a post

```text
POST /posts
     |
     v
Primary
     |
     v
Success
```

### Viewing posts

```text
GET /feed
    |
    v
Replica
```

This works well when slightly stale data is acceptable.

But for:

```text
POST /payment
```

you probably care much more about consistency and durability.

So the system might use a different strategy.

This is why **database architecture depends on the workload and consistency requirements**, not simply "replicas are always good."

---

# 24. Important concept: Read-after-write

This is worth remembering for interviews.

Suppose:

```text
User updates profile
       |
       v
Primary
       |
       v
Success
```

Immediately:

```text
GET profile
```

If the GET goes to a lagging replica:

```text
             Primary
             name=Rohan
                |
             replication
                |
                X  lag
                |
             Replica
             name=OldName
```

The user sees the old value.

Possible solutions include:

### Option 1 — Read from primary after a write

```text
Write → Primary
Read  → Primary
```

### Option 2 — Session stickiness

After writing to the primary, route that user's reads to the primary for some period.

### Option 3 — Track replication position

Only read from a replica after it has caught up sufficiently.

### Option 4 — Use stronger consistency guarantees

Depending on the database.

These approaches have different performance and complexity trade-offs.

---

# 25. Replication doesn't necessarily mean "one database"

This is another subtle point.

Replication is a **distributed system technique**.

For example:

```text
Database cluster

Node A → Node B → Node C
```

Each node has its own:

* CPU
* RAM
* Disk
* Database process

They communicate over the network.

So once you introduce replication, you're no longer dealing with a simple single-machine database problem.

You're dealing with:

> **Distributed state.**

And distributed state introduces failure scenarios.

---

# 26. Replication vs Sharding

You'll study sharding next.

The easiest way to distinguish them is:

### Replication

**Copy the same data.**

```text
Node A:
Users 1-1000

Node B:
Users 1-1000

Node C:
Users 1-1000
```

### Sharding

**Split the data.**

```text
Node A:
Users 1-1000

Node B:
Users 1001-2000

Node C:
Users 2001-3000
```

So:

```text
Replication
       ↓
More copies of data
       ↓
Availability + read scaling


Sharding
       ↓
Split data
       ↓
Write/storage scaling
```

And in real systems you often combine them:

```text
                 Database
                    |
          +---------+---------+
          |                   |
        Shard 1             Shard 2
          |                   |
      +---+---+             +---+---+
      |   |   |             |   |   |
     P   R1  R2             P   R1  R2
```

That's a very common large-scale architecture.

---

# 27. What you should remember for system design

If an interviewer asks:

> **"Why would you use database replication?"**

Think:

```text
Replication
    |
    +---- High availability
    |
    +---- Fault tolerance
    |
    +---- Read scalability
    |
    +---- Disaster recovery
    |
    +---- Geographic distribution
```

Then ask:

### 1. Is replication synchronous or asynchronous?

```text
Sync → stronger guarantees, higher latency
Async → lower latency, replication lag
```

### 2. What happens if primary fails?

```text
Failover → promote replica
```

### 3. Can replicas serve reads?

```text
Yes → read scaling
```

### 4. Can reads be stale?

```text
Yes, with asynchronous replication
```

### 5. Can acknowledged data be lost?

```text
Potentially, if primary fails before async replication catches up
```

### 6. Do replicas replace backups?

```text
No.
```

### 7. Does replication solve write scaling?

```text
Not by itself.
```

That's the key distinction between **replication and sharding**.

## Mental model

I'd keep this picture in your system-design notes:

```text
                    APPLICATION
                   /           \
                WRITE          READ
                  |              |
                  v              v
             +---------+    +---------+
             | PRIMARY |    | REPLICA |
             +---------+    +---------+
                  |
             replication
                  |
          +-------+-------+
          |               |
          v               v
     +---------+     +---------+
     | Replica |     | Replica |
     |    2    |     |    3    |
     +---------+     +---------+

Replication gives:
├── High availability
├── Fault tolerance
├── Read scaling
└── Disaster recovery

But introduces:
├── Replication lag
├── Failover complexity
├── Consistency questions
└── Potential data loss with async replication
```

### One-line interview definition

> **Database replication is the process of maintaining copies of database data across multiple nodes, primarily to improve availability, fault tolerance, read scalability, and sometimes geographic resilience.**

The natural next step after this is **Topic 6 — Sharding / Partitioning**, where you'll see why replication alone eventually stops being enough when **writes, storage, or dataset size** become the bottleneck.
