# 1. The problem: concurrent updates

Suppose we have:

```text
Product
-------------------------
id       = 101
name     = "Laptop"
stock    = 10
```

Two requests arrive at almost the same time:

```text
User A → buy 2 laptops
User B → buy 3 laptops
```

Both transactions read:

```text
stock = 10
```

Then:

```text
A calculates: 10 - 2 = 8
B calculates: 10 - 3 = 7
```

If both write their result:

```text
A → stock = 8
B → stock = 7
```

Final value:

```text
stock = 7
```

But it should have been:

```text
10 - 2 - 3 = 5
```

This is a **lost update** problem.

Concurrency control mechanisms prevent this.

There are two major approaches:

```text
                 Concurrency Control
                         │
              ┌──────────┴──────────┐
              │                     │
        Pessimistic             Optimistic
          Locking                 Locking
              │                     │
       "Lock first"          "Check before update"
```

---

# 2. Pessimistic concurrency

The pessimistic approach assumes:

> "Someone else may modify this data while I'm working with it."

So we **lock the database row**.

Conceptually:

```sql
SELECT *
FROM product
WHERE id = 101
FOR UPDATE;
```

The database locks that row.

Another transaction trying to acquire the same lock has to wait.

### Example

Transaction A:

```text
BEGIN

SELECT stock
FROM product
WHERE id = 101
FOR UPDATE;

stock = 10

UPDATE product
SET stock = 8
WHERE id = 101;

COMMIT
```

While A has the lock:

```text
Product 101
     ↓
   LOCKED
     ↓
Transaction B waits
```

After A commits:

```text
Transaction A
     ↓
COMMIT
     ↓
lock released
     ↓
Transaction B continues
```

B then sees the updated value:

```text
stock = 8
```

and can calculate:

```text
8 - 3 = 5
```

Final:

```text
stock = 5
```

# 3. Pessimistic locking in Spring Boot / JPA

Suppose we have:

```java
@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private Integer stock;

    // getters/setters
}
```

Repository:

```java
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Product findByIdForUpdate(@Param("id") Long id);
}
```

The important part is:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

This tells JPA:

> Acquire a database write lock when reading this entity.

Depending on the database, Hibernate will typically generate SQL similar to:

```sql
SELECT ...
FROM product
WHERE id = ?
FOR UPDATE
```

# 4. Service layer

The transaction is extremely important.

```java
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional
    public void purchase(Long productId, int quantity) {

        Product product =
                productRepository.findByIdForUpdate(productId);

        if (product.getStock() < quantity) {
            throw new RuntimeException("Not enough stock");
        }

        product.setStock(
            product.getStock() - quantity
        );
    }
}
```

Notice:

```java
@Transactional
```

Why?

Because the lock needs to remain held during the transaction.

The flow is:

```text
BEGIN TRANSACTION
       ↓
SELECT ... FOR UPDATE
       ↓
row locked
       ↓
check stock
       ↓
update stock
       ↓
COMMIT
       ↓
lock released
```

If you didn't have a transaction around the operation, the locking semantics wouldn't protect the whole read-modify-write sequence.

# 5. PESSIMISTIC_WRITE vs PESSIMISTIC_READ

JPA provides:

```java
PESSIMISTIC_READ
PESSIMISTIC_WRITE
```

### PESSIMISTIC_WRITE

Use when you intend to modify the row.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Conceptually:

```sql
SELECT ...
FROM product
WHERE id = ?
FOR UPDATE;
```

Other transactions attempting conflicting operations may have to wait.

### PESSIMISTIC_READ

Used when you want to prevent conflicting modifications while reading.

```java
@Lock(LockModeType.PESSIMISTIC_READ)
```

Exact behavior depends on the database and isolation/locking implementation.

For typical business operations where you're going to modify the entity, **`PESSIMISTIC_WRITE` is the important one to know**.

# 6. Optimistic concurrency

Now the opposite philosophy.

Optimistic concurrency says:

> "Most of the time, nobody will modify this row concurrently. Let's not lock it. We'll detect a conflict when updating."

This is extremely common in web applications.

The standard JPA mechanism is:

```java
@Version
```

---

# 7. `@Version`

Modify our entity:

```java
@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private Integer stock;

    @Version
    private Long version;

    // getters/setters
}
```

Database:

```text
product
--------------------------------
id | name   | stock | version
--------------------------------
101| Laptop | 10    | 5
```

The important column is:

```text
version = 5
```

---

# 8. How optimistic locking works

Transaction A reads:

```text
stock = 10
version = 5
```

Transaction B also reads:

```text
stock = 10
version = 5
```

A updates first.

Hibernate effectively performs something similar to:

```sql
UPDATE product
SET stock = 8,
    version = 6
WHERE id = 101
  AND version = 5;
```

One row is updated.

Now database:

```text
stock   = 8
version = 6
```

Then B tries:

```sql
UPDATE product
SET stock = 7,
    version = 6
WHERE id = 101
  AND version = 5;
```

But:

```text
database version = 6
```

while B expected:

```text
version = 5
```

Therefore:

```text
0 rows updated
```

Hibernate detects this and throws an optimistic locking exception, typically:

```text
OptimisticLockException
```

or a Hibernate/Spring-wrapped variant such as:

```text
ObjectOptimisticLockingFailureException
```

So instead of silently overwriting A's update, B gets a concurrency conflict.

# 9. Spring Boot implementation

Entity:

```java
@Entity
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    private Integer stock;

    @Version
    private Long version;

    // getters/setters
}
```

Repository can remain completely normal:

```java
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
```

Service:

```java
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional
    public void purchase(Long productId, int quantity) {

        Product product =
                productRepository.findById(productId)
                        .orElseThrow();

        if (product.getStock() < quantity) {
            throw new RuntimeException("Not enough stock");
        }

        product.setStock(
                product.getStock() - quantity
        );
    }
}
```

That's it.

The important thing is:

```java
@Version
private Long version;
```

JPA/Hibernate handles the version checking for you.

# 10. What actually happens in the database?

Suppose:

```text
id = 101
stock = 10
version = 5
```

Request A:

```text
read → stock 10, version 5
```

Request B:

```text
read → stock 10, version 5
```

A commits:

```sql
UPDATE product
SET stock = 8,
    version = 6
WHERE id = 101
AND version = 5;
```

Success.

B commits:

```sql
UPDATE product
SET stock = 7,
    version = 6
WHERE id = 101
AND version = 5;
```

Failure.

This is the key idea:

```text
Optimistic Locking
        │
        ↓
Read version
        │
        ↓
Do work
        │
        ↓
UPDATE ... WHERE version = oldVersion
        │
        ├── 1 row updated → SUCCESS
        │
        └── 0 rows updated → CONFLICT
```

# 11. Pessimistic vs Optimistic

Here's the important comparison:

|                    | Pessimistic                | Optimistic                       |
| ------------------ | -------------------------- | -------------------------------- |
| Philosophy         | Conflict is likely         | Conflict is unlikely             |
| Lock               | Yes                        | No database row lock during read |
| Mechanism          | DB lock                    | Version checking                 |
| JPA                | `@Lock(PESSIMISTIC_WRITE)` | `@Version`                       |
| Concurrent request | Usually waits              | Fails with conflict              |
| Performance        | Can reduce concurrency     | Usually better concurrency       |
| Deadlock risk      | Possible                   | Much lower                       |
| Good for           | High-contention data       | Normal web applications          |
| User experience    | Request may wait           | Request may need retry           |
| Complexity         | Lock management            | Conflict handling                |

# 12. A real-world example

Imagine an airline booking system.

Only **1 seat** remains:

```text
Flight
----------------
flight_id = 100
available = 1
```

Two users click:

```text
User A → Book seat
User B → Book seat
```

### Pessimistic

A gets the lock:

```text
A → SELECT ... FOR UPDATE
             ↓
          LOCK ROW
             ↓
        available = 1
             ↓
          update 0
             ↓
          COMMIT
```

B waits.

Then B gets the row:

```text
available = 0
```

and booking fails.

---

### Optimistic

Both initially read:

```text
available = 1
version = 10
```

A updates:

```text
available = 0
version = 11
```

B attempts:

```sql
UPDATE flight
SET available = 0,
    version = 11
WHERE flight_id = 100
AND version = 10;
```

No row matches.

Therefore:

```text
OptimisticLockException
```

Your application can tell B:

```text
"Sorry, this seat was just booked by another customer."
```

# 13. When should you use which?

A useful rule:

### Use optimistic locking when:

```text
Reads >>> Writes
```

and conflicts are relatively uncommon.

Examples:

```text
Product information
User profile
Blog post
CMS content
Order details
Configuration
Documents
```

For many normal Spring Boot CRUD applications, this is a good default.

---

### Use pessimistic locking when:

```text
Contention is high
AND
the operation must serialize access
```

Examples:

```text
Inventory
Bank account operations
Seat reservation
Limited resources
High-contention counters
```

But don't automatically choose pessimistic locking just because correctness matters. Optimistic locking can also provide correctness; the tradeoff is that conflicting transactions need to be rejected/retried rather than waiting on a lock.

---

# 14. One important distinction

Don't confuse **database transaction isolation** with **optimistic/pessimistic locking**.

They solve related but different problems.

You can have:

```text
Transaction Isolation
        +
Optimistic Locking
```

or:

```text
Transaction Isolation
        +
Pessimistic Locking
```

For example:

```java
@Transactional
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

uses a transaction plus an explicit pessimistic lock.

Whereas:

```java
@Version
```

adds optimistic conflict detection to your entity.

# 15. What I'd remember for interviews

If an interviewer asks:

> **"How does optimistic locking work in JPA?"**

A strong answer is:

> "JPA uses the `@Version` field for optimistic locking. When an entity is read, its version is captured. During update, Hibernate includes the expected version in the `WHERE` clause and increments the version. If another transaction has already updated the entity, the version no longer matches, the update affects zero rows, and Hibernate throws an optimistic locking exception."

For pessimistic:

> "Pessimistic locking acquires a database lock when the entity is read, typically using `SELECT ... FOR UPDATE`. Other transactions attempting conflicting access have to wait until the transaction holding the lock commits or rolls back. In JPA this can be requested using `@Lock(LockModeType.PESSIMISTIC_WRITE)`."

Those two explanations are worth knowing cold.
