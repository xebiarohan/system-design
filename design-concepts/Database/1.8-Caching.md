# Caching + Redis

## 1. What is caching?

Caching means:

> **Store frequently accessed data in a faster storage layer so that future requests don't need to go to the original data source.**

Without caching:

```text
User
 ↓
Application
 ↓
Database
 ↓
Return data
```

With caching:

```text
User
 ↓
Application
 ↓
Cache
 ├── HIT  → Return data
 └── MISS → Database
              ↓
           Store in cache
              ↓
           Return data
```

The key idea:

> **Cache = faster access + less database load.**

---

# 2. Why is a cache faster?

A database has to do quite a lot of work:

```text
Request
  ↓
Connection
  ↓
Query parsing
  ↓
Query planning
  ↓
Index lookup / table access
  ↓
Disk or memory
  ↓
Transaction/concurrency handling
  ↓
Response
```

A cache is generally much simpler:

```text
Request
  ↓
Lookup key
  ↓
Return value
```

And systems such as Redis keep data primarily in memory.

So you might have:

```text
Database → milliseconds
Redis    → sub-millisecond to a few milliseconds
```

Exact latency depends on network, deployment, payload size, workload, etc., but the basic principle is what matters.

---

# 3. Why do we need caching?

Imagine an e-commerce application.

You have:

```text
10,000 requests/sec
```

And a popular product is requested constantly:

```text
GET /products/123
```

Without caching:

```text
10,000 requests/sec
        ↓
   PostgreSQL
```

That's unnecessary if the product changes only occasionally.

With caching:

```text
                    +---- HIT → Return
                    |
Requests → Application → Redis
                    |
                    +---- MISS → PostgreSQL
                                  ↓
                                Redis
```

Suppose 95% of requests are cache hits:

```text
10,000 requests/sec

9,500 → Redis
  500 → PostgreSQL
```

You've dramatically reduced database traffic.

---

# 4. What is Redis?

Redis is an **in-memory data store** commonly used for:

* caching
* session storage
* distributed locks
* counters
* rate limiting
* queues/streams
* pub/sub
* temporary data

For your roadmap, initially think of Redis primarily as:

> **A very fast key-value store that can act as a cache in front of your database.**

Architecture:

```text
             Application
                 |
                 ↓
              Redis
             /     \
          HIT       MISS
          |           |
          ↓           ↓
       Return       Database
```

---

# 5. Redis vs Database

A common beginner misconception is:

> "If Redis is so fast, why don't we just use Redis instead of PostgreSQL?"

Because they're designed for different purposes.

### PostgreSQL

Excellent for:

* durable data
* relational data
* SQL
* joins
* transactions
* constraints
* complex queries
* ACID guarantees

### Redis

Excellent for:

* very fast key/value access
* temporary data
* caching
* counters
* session state
* simple data structures
* low-latency workloads

Think:

```text
PostgreSQL
    ↓
System of record

Redis
    ↓
Fast-access copy / temporary state
```

# 6. Cache-aside pattern

This is the **most important caching pattern** to learn first.

It's also called **lazy loading**.

Application controls the cache.

### Read flow

```text
Application
     |
     ↓
Check Redis
     |
   +---+---+
   |       |
 HIT     MISS
   |       |
   ↓       ↓
Return   Database
           |
           ↓
         Redis
           |
           ↓
        Return
```

Let's use a product.

---

## Step 1 — Check cache

Application asks:

```text
GET product:123
```

Redis:

```text
MISS
```

---

## Step 2 — Query database

Application executes:

```sql
SELECT *
FROM products
WHERE id = 123;
```

Database returns:

```json
{
  "id": 123,
  "name": "Laptop",
  "price": 1200
}
```

---

## Step 3 — Put it into Redis

Application stores:

```text
product:123 → {
    id: 123,
    name: "Laptop",
    price: 1200
}
```

---

## Step 4 — Return response

```text
Client ← Application ← Database
```

Next request:

```text
GET product:123
```

Redis:

```text
HIT
```

So:

```text
Client
  ↓
Application
  ↓
Redis
  ↓
Response
```

No database query.

---

# 7. Cache-aside pseudocode

In Java/Spring style, the logic is roughly:

```java
Product product = redis.get("product:" + id);

if (product == null) {
    product = database.findById(id);

    redis.set(
        "product:" + id,
        product,
        TTL
    );
}

return product;
```

This pattern is extremely common.

---

# 8. What happens when data changes?

This is where caching becomes interesting.

Suppose Redis contains:

```text
product:123
price = 100
```

Then the user updates the product:

```text
Database:
price = 120
```

But Redis still contains:

```text
Redis:
price = 100
```

Now:

```text
Client
  ↓
Redis
  ↓
price = 100 ❌
```

You've got **stale cache data**.

So caching introduces a fundamental problem:

> **Cache invalidation.**

And yes, this is the famous "one of the two hard things in computer science" territory. 😄

---

# 9. Cache invalidation

When database data changes:

```text
Database
   ↓
UPDATE
   ↓
Invalidate cache
```

For example:

```text
UPDATE products
SET price = 120
WHERE id = 123;
```

Then:

```text
DEL product:123
```

Next request:

```text
Redis → MISS
   ↓
Database → 120
   ↓
Redis → store 120
```

Now the cache becomes fresh again.

---

# 10. Cache-aside write pattern

A common approach:

```text
              UPDATE
                |
                ↓
           Database
                |
                ↓
        Delete cache key
                |
                ↓
             Redis
```

Example:

```java
database.update(product);

redis.delete("product:" + product.getId());
```

Then the next read repopulates the cache.

---

# 11. Why delete instead of update?

You could do:

```text
Database → update
Redis → update
```

But now you have two writes that need to stay consistent.

Suppose:

```text
Database update → SUCCESS
Redis update    → FAILURE
```

or:

```text
Redis update    → SUCCESS
Database update → FAILURE
```

Now you've got another consistency problem.

With cache-aside, a common strategy is:

```text
Update DB
   ↓
Delete cache
```

Then:

```text
Next read
   ↓
Cache MISS
   ↓
Read DB
   ↓
Populate cache
```

This is often simpler.

---

# 12. TTL — Time To Live

You generally don't want cached data to live forever.

Redis can assign a **TTL**.

For example:

```text
product:123
TTL = 5 minutes
```

After five minutes:

```text
product:123
      ↓
Expired
      ↓
Removed/treated as unavailable
```

Next request:

```text
MISS
 ↓
Database
 ↓
Redis
```

This protects you from stale data remaining indefinitely.

---

# 13. TTL example

Suppose:

```text
DB:
price = $100
```

Cache:

```text
product:123 → $100
TTL = 60 seconds
```

Database changes:

```text
price = $120
```

Cache may temporarily still contain:

```text
$100
```

But after 60 seconds:

```text
Cache expires
```

Next request retrieves:

```text
$120
```

So TTL provides a form of **eventual freshness**.

---

# 14. Cache invalidation + TTL

In real systems, you often combine both.

```text
Write:
    Update DB
       ↓
    Delete cache

Read:
    Check cache
       ↓
    MISS
       ↓
    Read DB
       ↓
    Put in cache with TTL
```

And TTL acts as a safety net.

```text
Cache invalidation
       +
TTL
       ↓
Reduced stale-data risk
```

---

# 15. Write-through cache

Another pattern is **write-through**.

Instead of the application explicitly doing:

```text
Application
   |
   +----> DB
   |
   +----> Cache
```

the cache layer handles the write-through behavior:

```text
Application
     |
     ↓
   Cache
     |
     ↓
 Database
```

When data is written:

```text
Application
    ↓
Cache
    ↓
Database
```

The cache is updated as part of the write operation.

### Advantage

Cache and DB can stay synchronized more automatically.

### Disadvantage

More complexity and potentially more write latency.

---

# 16. Read-through cache

With read-through:

```text
Application
     |
     ↓
   Cache
     |
   MISS
     ↓
  Database
```

The application doesn't directly know how to load missing data.

The cache layer handles it.

Conceptually:

```text
Application
     |
     ↓
   Cache
     |
     +---- HIT → return
     |
     +---- MISS → load DB → cache → return
```

Cache-aside is generally easier to understand and is extremely common.

---

# 17. Write-back / write-behind cache

This is more aggressive.

```text
Application
     |
     ↓
   Cache
     |
     ↓
   SUCCESS
     
     ...later...
     
     ↓
 Database
```

The cache acknowledges the write before the database is updated.

Example:

```text
Application
    ↓
Redis
    ↓
"success"
```

Then asynchronously:

```text
Redis
  ↓
Database
```

### Advantage

Very fast writes.

### Risk

If Redis fails before data reaches the database:

```text
Application
    ↓
Redis
    ↓
💥
```

you could lose data.

Therefore, write-back is much more appropriate for workloads where temporary durability is acceptable and the system is designed carefully around persistence/recovery.

---

# 18. The four patterns

Keep this table:

| Pattern           | Read                   | Write                             | Main idea                    |
| ----------------- | ---------------------- | --------------------------------- | ---------------------------- |
| **Cache-aside**   | App checks cache       | App writes DB + invalidates cache | Most common/general-purpose  |
| **Read-through**  | Cache loads DB on miss | Usually separate                  | Cache owns reads             |
| **Write-through** | Cache                  | Cache → DB                        | Cache owns write path        |
| **Write-back**    | Cache                  | Cache first, DB later             | Fast writes, durability risk |

For interviews, **cache-aside should be your first mental model**.

---

# 19. Cache stampede

Here's a nasty problem.

Suppose:

```text
product:123
TTL = 60 seconds
```

At exactly the same time, 10,000 requests arrive.

The cache expires:

```text
product:123 → EXPIRED
```

Now:

```text
10,000 requests
       ↓
Redis
       ↓
10,000 MISS
       ↓
10,000 DB queries 😱
```

Your cache was supposed to protect the database.

Instead, it just created a huge database spike.

This is called:

> **Cache stampede** / cache avalanche / thundering herd

depending on the exact failure pattern being discussed.

---

# 20. How do we prevent cache stampede?

Several techniques exist.

### Locking

Only one request loads the data:

```text
Request 1 → MISS → acquire lock → DB
Request 2 → MISS → wait
Request 3 → MISS → wait
Request 4 → MISS → wait
```

Then:

```text
DB
 ↓
Redis
 ↓
All requests receive cached value
```

### TTL jitter

Instead of every cache entry expiring at exactly:

```text
60 seconds
```

use slightly randomized TTLs:

```text
58 sec
63 sec
61 sec
67 sec
```

This spreads expirations over time.

---

# 21. Cache penetration

Another problem:

Suppose attackers or users repeatedly request:

```text
/product/999999999
```

and it doesn't exist.

Every request:

```text
Redis → MISS
    ↓
Database → "not found"
```

Then the next request does it again.

You can cache the negative result:

```text
product:999999999 → NOT_FOUND
TTL = 30 sec
```

Now:

```text
Request
  ↓
Redis
  ↓
NOT_FOUND
```

No database query.

This is called **negative caching**.

---

# 22. Cache eviction

Redis memory isn't infinite.

Suppose:

```text
Redis RAM = 16 GB
```

Eventually:

```text
Used = 16 GB
```

What happens when you insert more data?

Redis can use an **eviction policy**.

Common policies include:

```text
allkeys-lru
allkeys-lfu
volatile-lru
volatile-ttl
noeviction
```

You don't need to memorize all of them yet.

The important idea:

> When cache memory is full, Redis needs a strategy for deciding what data to remove—or whether to reject writes.

---

# 23. LRU

**LRU = Least Recently Used**

The idea:

> Remove data that hasn't been accessed recently.

Example:

```text
A → accessed recently
B → accessed recently
C → not accessed for a long time
D → accessed recently
```

Cache is full.

Remove:

```text
C
```

because it's least recently used.

This is intuitive for caching because frequently accessed data tends to remain useful.

---

# 24. LFU

**LFU = Least Frequently Used**

Instead of asking:

> "When was this accessed last?"

it asks:

> "How often has this been accessed?"

Example:

```text
Product A → 10,000 accesses
Product B → 5,000 accesses
Product C → 2 accesses
```

When memory is full, C is a candidate for eviction.

---

# 25. What should you cache?

Good candidates:

```text
Frequently read
+
Expensive to calculate/query
+
Changes relatively infrequently
```

Examples:

```text
Product catalog
User profile
Configuration
Reference data
Permissions
Popular content
Exchange rates
```

Poor candidates may include:

```text
Highly volatile data
Rarely accessed data
Huge objects
Data requiring strict real-time consistency
```

Although even these can sometimes be cached with the right design.

# 26. Redis data structures

Redis isn't limited to strings.

It provides several useful data structures.

### String

```text
SET user:123:name "Rohan"
GET user:123:name
```

### Hash

Useful for objects:

```text
HSET user:123 name "Rohan"
HSET user:123 age 30
```

Conceptually:

```text
user:123
 ├── name = Rohan
 └── age = 30
```

### List

Useful for ordered collections/queues:

```text
LPUSH queue item
RPOP queue
```

### Set

Unique values:

```text
SADD user:123:roles ADMIN
SADD user:123:roles USER
```

### Sorted Set

Values ordered by score:

```text
ZADD leaderboard 100 Alice
ZADD leaderboard 250 Bob
```

Great for:

```text
Leaderboards
Rankings
Scores
```

# 29. Cache consistency

This connects directly to the previous topic you studied.

Suppose:

```text
PostgreSQL:
price = 120

Redis:
price = 100
```

You now have:

```text
Strong consistency? ❌
Eventual consistency? Possibly
```

Caching introduces another copy of your data.

So your system effectively becomes:

```text
              +---- Redis
              |
Application --+
              |
              +---- Database
```

The application now needs to reason about **two versions of the data**.

That's why caching isn't "free performance."

It introduces:

* stale data
* invalidation complexity
* cache failures
* eviction
* stampedes
* synchronization issues

---

# 30. What happens if Redis goes down?

This is a crucial design question.

Suppose:

```text
Application
    |
    X
  Redis 💥
    |
    ↓
Database
```

For a cache, ideally:

> **Redis failure should degrade performance, not destroy the application.**

The application can fall back to:

```text
Redis unavailable
      ↓
Database
      ↓
Response
```

But now your database may suddenly receive all traffic:

```text
Before:

Redis → 95% requests
DB    → 5%

After Redis failure:

Redis → 0%
DB    → 100% 😱
```

This can cause a **cache failure cascading into database failure**.

So production systems need:

* Redis high availability
* sensible connection timeouts
* fallback behavior
* database protection
* rate limiting
* monitoring

# 31. Cache hierarchy

Large systems sometimes have multiple cache layers:

```text
Client
  ↓
CDN
  ↓
Application
  ↓
Local application cache
  ↓
Redis
  ↓
Database
```

For example:

```text
L1 → Local memory
L2 → Redis
L3 → Database
```

The closer the cache is to the application, generally the lower the network overhead—but local caches introduce their own invalidation challenges.

# 32. A realistic Spring Boot architecture

Since you're a Java/Spring developer, imagine:

```text
                   React
                     |
                     ↓
              Spring Boot API
                     |
              +------+------+
              |             |
              ↓             ↓
           Redis        PostgreSQL
           Cache        Database
```

Request:

```text
GET /products/123
```

Spring Boot:

```text
1. Check Redis
       ↓
2. HIT?
   yes → return

3. MISS?
   ↓
4. Query PostgreSQL
   ↓
5. Store result in Redis
   ↓
6. Return response
```

A common implementation can use Spring Data Redis, and Spring's caching abstraction can also provide annotations such as:

```java
@Cacheable("products")
public Product getProduct(Long id) {
    return productRepository.findById(id).orElseThrow();
}
```

Conceptually, Spring handles the cache lookup for you.

# 35. What you should know for system design

If an interviewer asks:

> **"Our database is overloaded because we're getting millions of read requests. What would you do?"**

A good thought process is:

```text
1. Identify whether workload is read-heavy
             ↓
2. Optimize queries/indexes
             ↓
3. Add read replicas if appropriate
             ↓
4. Identify frequently accessed data
             ↓
5. Add Redis/cache
             ↓
6. Choose cache strategy
             ↓
7. Define TTL
             ↓
8. Define invalidation strategy
             ↓
9. Handle cache stampede
             ↓
10. Design Redis failure behavior
```

Don't just say:

> "Use Redis."

The important part is explaining **what you cache, why, how long, how you invalidate it, and what happens when Redis fails.**
