# MySQL Internal Working

At a high level, think of MySQL like this:

```text
                    Java Application
                          │
                          │ SQL / TCP
                          ▼
              ┌──────────────────────────┐
              │       MySQL Server       │
              │                          │
              │  Connection Handling     │
              │          │               │
              │          ▼               │
              │      SQL Parser          │
              │          │               │
              │          ▼               │
              │   Query Optimizer        │
              │          │               │
              │          ▼               │
              │     Query Executor       │
              │          │               │
              │          ▼               │
              │       InnoDB             │
              │      Storage Engine      │
              │       │        │         │
              │       ▼        ▼         │
              │   Buffer Pool Redo Log   │
              │       │        │         │
              │       ▼        ▼         │
              │  Data Files   Log Files  │
              └──────────────────────────┘
```

Compare that with the PostgreSQL architecture from your notes, where the major components are Parser → Analyzer → Planner → Executor → Buffer/WAL/Storage. 

For MySQL, the **big conceptual difference** is that MySQL has a pluggable **storage-engine architecture**.

---

# 1. MySQL Architecture

A simplified architecture:

```text
Application
     │
     │ SQL
     ▼
┌──────────────────────────────┐
│        MySQL Server          │
│                              │
│  Connection Handler          │
│          │                   │
│          ▼                   │
│      SQL Parser              │
│          │                   │
│          ▼                   │
│      Optimizer               │
│          │                   │
│          ▼                   │
│      Executor                │
│          │                   │
│          ▼                   │
│    Storage Engine API        │
│          │                   │
└──────────┼───────────────────┘
           │
           ▼
        InnoDB
           │
     ┌─────┴─────┐
     ▼           ▼
 Buffer Pool   Redo Log
     │           │
     ▼           ▼
 Data Files   Log Files
```

This gives you an important separation:

### MySQL Server layer

Responsible for things like:

* accepting connections
* parsing SQL
* optimizing queries
* authentication
* privileges
* coordinating execution

### InnoDB layer

Responsible for things like:

* tables/indexes
* pages
* buffer pool
* transactions
* MVCC
* row locks
* redo log
* undo log
* crash recovery

That's the first major concept to remember.

---

# 2. Storage Engines

Historically, MySQL has supported multiple storage engines.

For example:

```text
MySQL
 │
 ├── InnoDB
 ├── MyISAM
 ├── MEMORY
 └── others
```

Today, **InnoDB is the important one for transactional applications**.

For example:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
) ENGINE=InnoDB;
```

The important architecture is therefore:

```text
                MySQL Server
                     │
          Storage Engine API
                     │
                  InnoDB
             ┌───────┼───────┐
             │       │       │
             ▼       ▼       ▼
         Storage    MVCC   Logging
```

This is different from PostgreSQL, where the PostgreSQL server itself owns the storage architecture.

```text
Spring Boot
     │
     │ JDBC
```

In production, you normally don't create a new database connection for every request.

```text

                │

```

So just like your PostgreSQL notes emphasize connection pooling, the same principle applies here.

# 4. MySQL Memory Architecture

For InnoDB, the most important memory structure is:

# Buffer Pool

Think:

```text
                    InnoDB
                       │
                       ▼
                 Buffer Pool
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Data Pages    Index Pages   Other pages
```

The buffer pool is basically InnoDB's main memory cache.

Suppose:

```text
users table

Page 1
Page 2
Page 3
Page 4
...
```

The query needs Page 3.

If Page 3 is already in the buffer pool:

```text
Query
  │
  ▼
Buffer Pool
  │
  ▼
Page 3
```

No disk read is required.

If it isn't:

```text
Query
  │
  ▼
Buffer Pool
  │
  │ MISS
  ▼
Disk
  │
  ▼
Page 3
  │
  ▼
Buffer Pool
```

So:

> **Buffer Pool is one of the most important performance components in InnoDB.**

# 6. SQL Parser

MySQL first parses the SQL.

```sql
SELECT name
FROM users
WHERE id = 100;
```

The parser checks the SQL structure.

For example:

```sql
SELECT FROM users WHERE
```

is invalid SQL.

Conceptually:

```text
SELECT
 │
 ├── column → name
 │
 ├── table  → users
 │
 └── WHERE
       │
       └── id = 100
```

The parser creates an internal representation of the SQL statement.

# 7. Query Optimizer

Next comes one of the most important components:

```text
Optimizer
```

The optimizer asks:

> "What is the cheapest way to execute this query?"

Suppose:

```sql
SELECT *
FROM users
WHERE id = 100;
```

and:

```sql
CREATE INDEX idx_users_id
ON users(id);
```

The optimizer can choose an index access path.

Conceptually:

```text
                 Query
                   │
           ┌───────┼────────┐
           ▼       ▼        ▼
       Table Scan  Index   Other
                   Scan    strategies
           │       │        │
           └───────┼────────┘
                   ▼
              Cost estimate
                   │
                   ▼
              Chosen plan
```

This is very similar to the PostgreSQL planner concept in your notes.

# 8. Why Doesn't MySQL Always Use an Index?

Same fundamental reason as PostgreSQL.

Suppose:

```text
users = 10 million rows
```

and:

```sql
WHERE id = 100
```

If `id` is highly selective:

```text
Index → find one row
```

is efficient.

But suppose:

```sql
WHERE country = 'India'
```

and:

```text
70% of rows = India
```

The optimizer might determine that scanning a large portion of the table is cheaper than jumping through the index.

So:

```text
Index exists
      ≠
Index will always be used
```

You can inspect the plan using:

```sql
EXPLAIN
SELECT *
FROM users
WHERE id = 100;
```

And MySQL also provides:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE id = 100;
```

for actual execution information.

# 9. InnoDB Storage

Now we reach the important part.

InnoDB stores table and index data in **pages**.

The standard InnoDB page size is commonly:

```text
16 KB
```

So conceptually:

```text
users
 │
 ├── Page
 ├── Page
 ├── Page
 ├── Page
 └── ...
```

Compare this with your PostgreSQL notes:

```text
PostgreSQL → normally 8 KB pages
InnoDB     → commonly 16 KB pages
```

That difference matters when you're thinking about I/O.

# 10. Clustered Index — Very Important MySQL Concept

This is one of the biggest differences you should understand when comparing MySQL/InnoDB with PostgreSQL.

In InnoDB:

> **The primary key index is a clustered index.**

Suppose:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    age INT
);
```

The primary key B-tree looks conceptually like:

```text
                Root
                 │
          ┌──────┴──────┐
          ▼             ▼
       Internal       Internal
          │             │
          ▼             ▼
        Leaf          Leaf
```

But the leaf pages contain the **actual row data**.

Conceptually:

```text
Primary Key B-tree

       100
        │
        ▼
┌──────────────────────┐
│ id=100               │
│ name=John            │
│ age=30               │
└──────────────────────┘
```

So:

```sql
SELECT *
FROM users
WHERE id = 100;
```

can traverse the primary-key B-tree and arrive directly at the row.

---

# 11. Secondary Indexes

Now suppose:

```sql
CREATE INDEX idx_users_name
ON users(name);
```

InnoDB creates another B-tree.

Conceptually:

```text
Secondary Index
      │
      ▼
 name = "Bob"
      │
      ▼
 Primary Key = 100
      │
      ▼
Clustered Index
      │
      ▼
Actual Row
```

So a secondary-index lookup can involve **two B-tree traversals**:

```text
Secondary Index
       │
       ▼
Find primary key
       │
       ▼
Primary Key Index
       │
       ▼
Actual row
```

This is a crucial MySQL/InnoDB interview concept.

# 14. InnoDB MVCC

Now we reach another major topic you've already studied.

InnoDB uses **MVCC**.

Suppose:

```text
id = 1
balance = 1000
```

Transaction A:

```sql
BEGIN;

UPDATE accounts
SET balance = 900
WHERE id = 1;
```

Conceptually, InnoDB doesn't simply say:

```text
1000 → 900
```

and forget the old state.

It maintains information that allows transactions to see the appropriate version of the row.

The important structures include:

```text
Current row
    │
    ▼
Undo information
    │
    ▼
Previous version(s)
```

This is somewhat different internally from PostgreSQL's `xmin/xmax` model.

---

# 15. Undo Log

This is one of the most important MySQL concepts.

InnoDB has an **undo log**.

Think:

```text
UPDATE
  │
  ├──────────────► Current row
  │
  └──────────────► Undo information
```

Suppose:

```text
Before:

balance = 1000
```

Transaction updates:

```text
balance = 900
```

The undo information allows InnoDB to reconstruct the older version when necessary.

Conceptually:

```text
Current data
balance = 900
     │
     │ undo
     ▼
Previous version
balance = 1000
```

This is used by:

* rollback
* MVCC
* consistent reads

---

# 16. MVCC + Undo Log

Suppose:

```text
Transaction A
    │
    │ SELECT
    ▼
balance = 1000
```

At the same time:

```text
Transaction B
    │
    │ UPDATE
    ▼
balance = 900
```

Transaction A may need to see the older version depending on its read view/isolation semantics.

Conceptually:

```text
                 Current row
                 balance=900
                      │
                      │ Undo
                      ▼
                 Old version
                 balance=1000
                      ▲
                      │
                Transaction A
```

So:

```text
InnoDB MVCC
      │
      ├── Current row
      │
      ├── Undo log
      │
      └── Read view
```

These work together to determine what a transaction sees.

---

# 17. Redo Log

Now we get to another critical concept:

> **Redo Log**

Think of redo as:

> "What changes need to be replayed to make the data pages reflect committed changes?"

Conceptually:

```text
Transaction
     │
     ├──────────────► Buffer Pool
     │                    │
     │                    ▼
     │                Dirty Page
     │
     └──────────────► Redo Log
                          │
                          ▼
                     Persistent Log
```

This is conceptually similar to PostgreSQL's WAL.

Your PostgreSQL notes describe WAL as recording the necessary change before the corresponding data page is safely persisted. 

For MySQL/InnoDB, the corresponding mechanism is the **redo log**.

---

# 18. Redo vs Undo

This distinction is extremely important.

### Redo

Think:

```text
"What should I REAPPLY?"
```

Used primarily for:

* durability
* crash recovery

### Undo

Think:

```text
"What should I UNDO / what older version can I reconstruct?"
```

Used for:

* rollback
* MVCC consistent reads

So memorize:

```text
             InnoDB
                │
       ┌────────┴────────┐
       ▼                 ▼
    REDO LOG          UNDO LOG
       │                 │
       ▼                 ▼
   Crash recovery    Rollback
                     MVCC
```

---

# 19. INSERT Internally

Suppose:

```sql
INSERT INTO users
VALUES (100, 'Bob');
```

Conceptually:

```text
INSERT
  │
  ▼
Optimizer / Executor
  │
  ▼
InnoDB
  │
  ▼
Create row
  │
  ▼
Find appropriate page
  │
  ▼
Modify buffer-pool page
  │
  ├──────────────► Update indexes
  │
  └──────────────► Generate redo information
```

The modified page is now a:

```text
Dirty Page
```

because memory differs from the durable data file.

---

# 20. UPDATE Internally

Suppose:

```sql
UPDATE users
SET name = 'Robert'
WHERE id = 100;
```

Conceptually:

```text
UPDATE
  │
  ▼
Optimizer
  │
  ▼
Executor
  │
  ▼
Find row
  │
  ▼
Acquire necessary locks
  │
  ▼
Modify row
  │
  ├─────────────► Undo information
  │
  ├─────────────► Redo information
  │
  └─────────────► Index changes if necessary
  │
  ▼
Dirty Buffer Pool Page
```

Then:

```text
COMMIT
   │
   ▼
Redo log made durable
```

The actual data page doesn't necessarily have to be flushed to its final data-file location at the exact instant of commit.

That's a very important database concept.

---

# 21. DELETE Internally

Suppose:

```sql
DELETE FROM users
WHERE id = 100;
```

Conceptually:

```text
DELETE
  │
  ▼
Find row
  │
  ▼
Lock / concurrency handling
  │
  ▼
Modify row state
  │
  ├──────────────► Undo
  │
  └──────────────► Redo
```

The storage engine then handles eventual cleanup of obsolete information.

This is conceptually related to PostgreSQL's dead tuples, but the actual internal mechanisms are different.

# 22. Transactions

Consider:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Conceptually:

```text
BEGIN
 │
 ▼
Transaction
 │
 ├── UPDATE account 1
 │      │
 │      ├── Undo
 │      └── Redo
 │
 ├── UPDATE account 2
 │      │
 │      ├── Undo
 │      └── Redo
 │
 ▼
COMMIT
 │
 ▼
Redo log durability
 │
 ▼
Transaction durable
```

If something goes wrong before commit:

```text
ROLLBACK
   │
   ▼
Undo information
   │
   ▼
Restore previous state
```

# 23. Crash Recovery

Now imagine:

```text
Transaction
     │
     ▼
Modify Buffer Pool
     │
     ▼
Generate Redo
     │
     ▼
COMMIT
     │
     ▼
💥 Server crashes
```

Some data pages may not yet have been written to their final data files.

After restart:

```text
MySQL starts
     │
     ▼
InnoDB recovery
     │
     ▼
Read redo log
     │
     ▼
Replay necessary changes
     │
     ▼
Database reaches consistent state
```

So:

```text
Redo Log
   ↓
Crash Recovery
```

This is roughly analogous to:

```text
PostgreSQL
WAL → Crash Recovery
```

---

# 24. Checkpointing

If InnoDB continuously accumulated redo information forever, recovery would become increasingly expensive.

So InnoDB uses checkpoints.

Conceptually:

```text
Redo
Redo
Redo
Redo
Redo
 │
 ▼
CHECKPOINT
 │
 ▼
Dirty pages flushed appropriately
```

After a crash:

```text
Checkpoint
     │
     ▼
Redo records after checkpoint
     │
     ▼
Recovery
```

So both PostgreSQL and InnoDB use the same broad strategy:

```text
Memory changes
     │
     ▼
Durable log
     │
     ▼
Data pages eventually persisted
```

But:

```text
PostgreSQL → WAL
InnoDB     → Redo Log
```

# 25. InnoDB Locks

Now let's connect this with the concurrency topic you've recently studied.

InnoDB supports row-level locking.

Suppose:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

Conceptually:

```text
Transaction A
      │
      ▼
Find row id=1
      │
      ▼
Acquire row lock
      │
      ▼
Update
```

Now Transaction B:

```sql
UPDATE accounts
SET balance = balance - 50
WHERE id = 1;
```

may have to wait:

```text
Transaction A
     │
     ▼
Row Lock
     │
     │
     ├─────────────┐
     │             │
     ▼             ▼
 Update          Transaction B
                       │
                       ▼
                     WAIT
```

So again:

> **MVCC does not mean "there are no locks."**

Your PostgreSQL notes make exactly the same distinction.

# 26. Isolation Levels

MySQL/InnoDB supports transaction isolation levels including:

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

The interesting point is that InnoDB's default isolation level is:

```text
REPEATABLE READ
```

This is an important interview fact.

The isolation level affects:

```text
What can my transaction see?
How are concurrent operations handled?
When do I need to wait?
What snapshot/read view do I use?
```

# 27. Consistent Read

Imagine:

```text
Transaction A
     │
     │ SELECT
     ▼
 balance = 1000
```

Transaction B:

```text
Transaction B
     │
     │ UPDATE
     ▼
 balance = 900
```

Depending on the isolation/read semantics, Transaction A can use a consistent historical version.

The simplified mental model:

```text
Current row
balance = 900
     │
     ▼
Undo information
     │
     ▼
Older version
balance = 1000
     │
     ▼
Read View
```

This is one of the key ways InnoDB implements MVCC.

# 28. MySQL vs PostgreSQL MVCC

This is worth memorizing.

| Concept               | PostgreSQL                         | MySQL/InnoDB                       |
| --------------------- | ---------------------------------- | ---------------------------------- |
| MVCC                  | Yes                                | Yes                                |
| Row versions          | Stored as tuple versions           | Current records + undo information |
| Transaction metadata  | `xmin`, `xmax`                     | Transaction IDs / undo/read views  |
| Main memory cache     | `shared_buffers`                   | Buffer Pool                        |
| Durable change log    | WAL                                | Redo Log                           |
| Rollback/MVCC history | Tuple versions remain until vacuum | Undo log                           |
| Cleanup               | VACUUM/autovacuum                  | Purge/background cleanup           |
| Primary key storage   | Heap + index                       | Clustered index                    |
| Default isolation     | READ COMMITTED                     | REPEATABLE READ                    |

The **clustered-index difference** is especially important.

# 29. MySQL Index Internals

Let's look at a B-tree.

Suppose:

```sql
CREATE INDEX idx_age
ON users(age);
```

Conceptually:

```text
             Root
               │
       ┌───────┴───────┐
       ▼               ▼
   Internal         Internal
       │               │
   ┌───┴───┐       ┌───┴───┐
   ▼       ▼       ▼       ▼
 Leaf    Leaf     Leaf    Leaf
```

The B-tree lets the database avoid scanning every row.

But InnoDB has an important distinction:

```text
PRIMARY KEY
    ↓
Clustered index
    ↓
Actual row data
```

versus:

```text
SECONDARY INDEX
    ↓
Index key + primary key
    ↓
Clustered index
    ↓
Actual row
```

---

# 30. Covering Index

This leads to a useful optimization.

Suppose:

```sql
CREATE INDEX idx_users_name_age
ON users(name, age);
```

Query:

```sql
SELECT age
FROM users
WHERE name = 'Bob';
```

The index itself contains everything needed:

```text
Index
 ├── name
 └── age
```

So MySQL may not need to access the clustered index to retrieve the row.

Conceptually:

```text
Query
 │
 ▼
Secondary Index
 │
 ▼
name = Bob
 │
 ▼
age
 │
 ▼
Result
```

This is called a **covering index**.

Very useful for performance tuning.

```text
                  Lock / MVCC
                       │
              ┌────────┴────────┐
              ▼                 ▼
         Undo information    Redo log
              │                 │
              ▼                 ▼
       Previous version     Recovery info
              │
              ▼
        Modify Buffer Pool
              │
              ▼
           Dirty Page
              │
              ▼
            COMMIT
              │
              ▼
        Redo becomes durable
              │

```

That's the core architecture-level picture.

# 33. Where Does the Data Actually Live?

At a high level:

```text
MySQL
 │
 └── InnoDB
      │
      ├── Table data
      ├── Primary indexes
      ├── Secondary indexes
      ├── Undo information
      └── Redo logs
```

Modern InnoDB commonly uses tablespaces and related files to organize persistent storage.

You generally shouldn't think of MySQL as:

```text
one table = one simple text file
```

Instead think:

```text
Logical table
     │
     ▼
InnoDB storage structures
     │
     ├── pages
     ├── clustered index
     ├── secondary indexes
     └── tablespaces
```

# 34. Background Processes / Threads

Another conceptual difference from PostgreSQL is useful here.

MySQL's architecture is heavily thread-oriented, while traditional PostgreSQL architecture is process-oriented.

Conceptually:

```text
MySQL Server
     │
     ├── Connection threads
     │
     ├── InnoDB background threads
     │
     ├── IO threads
     │
     ├── Buffer-pool related work
     │
     ├── Redo/log related work
     │
     └── Purge/cleanup work
```

Don't get too hung up on exact thread names at the system-design level.

The important idea is:

```text
MySQL
   ↓
Thread-oriented server
   ↓
InnoDB background work
```

versus the traditional PostgreSQL model:

```text
PostgreSQL
   ↓
Process-oriented architecture
```

# 35. Purge vs PostgreSQL VACUUM

This is another useful comparison.

PostgreSQL:

```text
UPDATE / DELETE
      │
      ▼
Dead tuples
      │
      ▼
VACUUM
```

InnoDB:

```text
UPDATE / DELETE
      │
      ▼
Old versions / undo information
      │
      ▼
Purge processing
      │
      ▼
Cleanup when no longer needed
```

So don't say:

> "MySQL has VACUUM."

That's not the right mental model.

Instead:

```text
PostgreSQL → VACUUM / Autovacuum
InnoDB     → Undo + Purge
```

# 39. PostgreSQL vs MySQL — The Architecture You Should Remember

This is probably the most useful part for your system-design preparation.

| Area                      | PostgreSQL                           | MySQL + InnoDB                    |
| ------------------------- | ------------------------------------ | --------------------------------- |
| Database                  | PostgreSQL                           | MySQL                             |
| Main storage engine       | PostgreSQL itself                    | InnoDB                            |
| Connection architecture   | Traditionally process-per-connection | Thread-oriented                   |
| Main cache                | `shared_buffers`                     | Buffer Pool                       |
| Page size                 | Usually 8 KB                         | Commonly 16 KB                    |
| Primary storage           | Heap                                 | Clustered primary-key index       |
| Primary key               | Separate index from heap             | Clustered index                   |
| Secondary index points to | Heap tuple                           | Primary key                       |
| MVCC                      | Tuple versions                       | Undo + read views                 |
| Transaction metadata      | `xmin/xmax`                          | InnoDB transaction/undo machinery |
| Durable log               | WAL                                  | Redo Log                          |
| Rollback/MVCC history     | Old tuples                           | Undo                              |
| Cleanup                   | VACUUM / Autovacuum                  | Purge                             |
| Default isolation         | READ COMMITTED                       | REPEATABLE READ                   |
| Query optimizer           | PostgreSQL planner                   | MySQL optimizer                   |
| `EXPLAIN`                 | Yes                                  | Yes                               |
| Crash recovery            | WAL replay                           | Redo recovery                     |

# 40. The 5 Things I Would Especially Remember

For **your System Design + Senior Java interview preparation**, don't try to memorize every internal class or file.

Understand these five deeply:

### 1. MySQL Server vs InnoDB

```text
MySQL Server
     │
     ▼
Storage Engine
     │
     ▼
InnoDB
```

---

### 2. Buffer Pool

```text
Disk
  │
  ▼
Buffer Pool
  │
  ▼
Query
```

This is the primary InnoDB memory cache.

---

### 3. Clustered Index

```text
Primary Key
     │
     ▼
Clustered B-tree
     │
     ▼
Actual row
```

This is probably the **single biggest MySQL concept** that differs from the PostgreSQL mental model you just studied.

---

### 4. MVCC + Undo

```text
Current row
     │
     ▼
Undo information
     │
     ▼
Previous version
```

Used for:

```text

+
Consistent reads
+
MVCC
```

---

### 5. Redo Log

```text
Transaction
     │
     ├── Buffer Pool
     │
     └── Redo Log
              │
              ▼
         Crash Recovery
```

And the beautiful comparison is:

```text
PostgreSQL                    MySQL/InnoDB

MVCC                          MVCC
 │                             │
 └─ Tuple versions             └─ Undo + Read Views

shared_buffers                 Buffer Pool

WAL                            Redo Log

VACUUM                         Purge

Heap + indexes                 Clustered index + secondary indexes
```

Your PostgreSQL notes' final mental model is essentially **SQL → Parser → Planner → Executor → Buffer → Storage → MVCC**, and MySQL follows the same broad query-processing pipeline, but the storage/concurrency machinery underneath is notably different. 

**The next MySQL topic I'd recommend is not another huge overview:** go deep into **InnoDB Storage Engine — Pages → Extents → Segments → Tablespaces → Clustered Index → Secondary Index**. Once that is clear, **Buffer Pool, B-tree indexes, MVCC, undo/redo logs, and performance tuning all connect together naturally.**
