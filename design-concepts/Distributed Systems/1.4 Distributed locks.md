## 1. What is a distributed lock?

A distributed lock is a mechanism that coordinates multiple application instances so that only one instance at a time can access a shared resource or execute a particular critical operation.

Let's understand why we need one.

Suppose you are building an e-commerce application using Spring Boot. A customer wants to buy the last available item in stock.

You have two application instances running behind a load balancer:

```
                 Load Balancer
                 /           \
                /             \
         Application A     Application B
                \             /
                 \           /
                  Shared Database
```

Two customers place orders simultaneously.

The execution might look like this:

```
Application A                  Application B
-------------                  -------------

Check stock: 1                 Check stock: 1
      |                              |
      v                              v
Reduce stock to 0              Reduce stock to 0
      |                              |
      v                              v
Order succeeds                 Order succeeds
```

Both applications read the same initial stock value before either update takes effect.

The result could be two successful orders for one available item.

This is called a race condition: the outcome depends on the timing and interleaving of concurrent operations.

### Why doesn't Java synchronized solve this?

You might try:

```
public synchronized void purchaseProduct(Long productId) {
    // Check stock and create order
}
```

This works only when the competing calls share the same Java monitor inside the same JVM.

With multiple application instances:

```
JVM 1                         JVM 2
-----                         -----
Application A                 Application B
Java Lock A                   Java Lock B
     |                             |
     v                             v
Independent lock              Independent lock
```

The two locks have no knowledge of each other. Both applications can enter their respective synchronized methods.

A distributed lock solves this by coordinating access through a shared system, such as Redis or a database.

Key takeaway: A Java lock coordinates threads within a JVM. A distributed lock coordinates processes across application instances.

## 2. How does a distributed lock work?

Imagine that three instances of your Spring Boot application need to process the same product.

They all use Redis as a shared lock manager.

```
     Application A
     Application B  ------> Redis
     Application C           |
                             |
                     lock:product:101
```

Suppose Application A acquires the lock first.

The sequence is:

1. Application A requests a lock for product 101.
2. Redis grants the lock to Application A.
3. Application B requests the same lock but cannot acquire it.
4. Application A performs the protected operation.
5. Application A releases the lock.
6. Application B can now acquire the lock.

This ensures that the applications coordinate their access to that resource, provided the locking mechanism's assumptions and failure guarantees hold.

Notice that the lock is resource-specific.

For example:

- `lock:product:101` protects product 101.
- `lock:product:102` protects product 102.

Operations on different products can run concurrently when they don't depend on one another.

### When are distributed locks useful?

Common examples include:

- Preventing multiple instances from executing the same scheduled job simultaneously.
- Coordinating updates to shared resources.
- Avoiding concurrent processing of a particular business entity.
- Preventing duplicate work when multiple consumers or application instances compete for a task.

However, a distributed lock is not always the best solution. Database constraints, atomic updates, and idempotency can sometimes solve the underlying problem more simply.

## 3. Redis-based distributed locks

Redis is commonly used for distributed locking because it supports fast, atomic operations on keys.

### 3.1 Basic lock acquisition

A naive implementation might store a key:

```
lock:product:101 = locked
```

But consider this command:

```
SET lock:product:101 locked
```

It is unsafe for lock acquisition because Redis can overwrite an existing key. Application B could overwrite Application A's value and incorrectly assume it owns the lock.

Instead, use:

```
SET lock:product:101 unique-token-123 NX PX 10000
```

Let's understand each component.

| Component          | Meaning                                                  |
| ------------------ | -------------------------------------------------------- |
| `lock:product:101` | Lock key for product 101                                 |
| `unique-token-123` | Unique token identifying the lock owner                  |
| `NX`               | Create the key only if it doesn't already exist          |
| `PX 10000`         | Set the expiration to 10,000 milliseconds, or 10 seconds |

Redis executes the conditional key creation atomically.

There are two possible outcomes:

Case 1: The lock does not exist

Redis creates the key and returns success. The application owns the lock.

Case 2: The lock already exists

Redis does not overwrite it. The application fails to acquire the lock and can wait, retry, or return an error.

### 3.2 Why do we need a unique owner token?

Suppose Application A acquires the lock:

```
Key:   lock:product:101
Value: token-A
```

Application B cannot acquire it while it exists.

The token is important when releasing the lock. Without it, an old owner could accidentally delete a lock that now belongs to another application.

We'll examine that failure shortly.

### 3.3 Java implementation using Redisson

In a Spring Boot application, you can use Redisson, a Java client that provides distributed locking APIs.

Example:

```
@Service
public class ProductService {

    private final RedissonClient redissonClient;

    public ProductService(RedissonClient redissonClient) {
        this.redissonClient = redissonClient;
    }

    public void updateProduct(Long productId)
            throws InterruptedException {

        RLock lock = redissonClient.getLock(
            "lock:product:" + productId
        );

        boolean acquired = lock.tryLock(
            2,  // Wait up to 2 seconds
            10, // Lease duration: 10 seconds
            TimeUnit.SECONDS
        );

        if (!acquired) {
            throw new IllegalStateException(
                "Product is currently being processed"
            );
        }

        try {
            // Critical section:
            // Perform the protected operation.
            // Revalidate relevant business conditions.
            // Update the product.
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

This example assumes Redisson has been added and configured in your Spring Boot application.

Important points:

- `getLock()` obtains a reference to the distributed lock identified by the key.
- `tryLock()` attempts to acquire the lock and limits the waiting time.
- The lease duration specifies how long the lock can remain valid without renewal.
- The `finally` block releases the lock on normal completion and when an exception occurs.
- `isHeldByCurrentThread()` checks that the current thread still owns the lock before unlocking it.

The lease must be chosen carefully. If the operation takes longer than the lease, the lock may expire while the original application is still working.

Redisson also provides a watchdog mechanism for supported lock-acquisition modes without an explicit lease. That can renew a lock while the owning client remains healthy, but it does not eliminate every failure scenario.

### 3.4 Safely releasing a Redis lock

Consider this sequence:

```
Time 0:
Application A acquires the lock.
Redis value = token-A

Time 10:
Application A's lock expires.

Time 11:
Application B acquires the lock.
Redis value = token-B

Time 12:
Application A resumes and executes DEL on the lock key.
```

If Application A blindly executes:

```
DEL lock:product:101
```

it deletes Application B's lock!

The solution is to check the token and delete the key only when the stored token matches the owner's token.

Redis supports doing both operations atomically using a Lua script:

```
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

Here:

- `KEYS[1]` is the lock key.
- `ARGV[1]` is the token belonging to the application attempting release.
- The lock is deleted only if the tokens match.

Important: Owner-token validation protects another application's lock from accidental deletion. It does not prevent an expired owner from continuing to modify the resource. We'll cover that issue in the expiration section.

## 4. Database locks

Redis is not the only way to coordinate access. If the resource is stored in a relational database, database locking is often the simpler choice.

There are two important approaches: pessimistic locking and optimistic locking.

### 4.1 Pessimistic locking

Pessimistic locking assumes that concurrent modifications are possible and locks the relevant database row to prevent conflicting operations.

Consider a PostgreSQL table:

```
CREATE TABLE seats (
    id VARCHAR(20) PRIMARY KEY,
    available BOOLEAN NOT NULL
);
```

A transaction can acquire a row lock with `SELECT ... FOR UPDATE`:

```
BEGIN;

SELECT id, available
FROM seats
WHERE id = 'A-101'
FOR UPDATE;

-- Check whether the seat is available.
-- If available, perform the update.

UPDATE seats
SET available = FALSE
WHERE id = 'A-101'
  AND available = TRUE;

COMMIT;
```

The row lock is held until the transaction commits or rolls back. A competing transaction trying to lock the same row normally has to wait.

In production, check the number of rows updated. If it is zero, the seat was not available for booking, or the requested row did not match.

In Spring Data JPA, you can express pessimistic locking like this:

```
public interface SeatRepository
        extends JpaRepository<Seat, String> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT s FROM Seat s WHERE s.id = :id")
    Optional<Seat> findByIdForUpdate(
        @Param("id") String id
    );
}
```

Call this method within an appropriate transaction, for example using `@Transactional` on the service method.

Advantages:

- Strong coordination for concurrent updates to the same row.
- The database manages the lock lifecycle.
- No separate Redis lock service is required.

Disadvantages:

- Transactions may block one another.
- Long-running transactions reduce throughput.
- Deadlocks can occur when transactions acquire multiple locks in conflicting orders.

A crucial point: a database row lock normally protects database operations within a transaction. It is not a mechanism for holding a database lock across arbitrary work performed by several microservices.

### 4.2 Optimistic locking

Optimistic locking takes a different approach. Instead of blocking concurrent operations at the start, it detects conflicting updates.

Suppose a product has this state:

| Product ID | Stock | Version |
| ---------- | ----- | ------- |
| 101        | 5     | 7       |

Application A and Application B both read stock 5 and version 7.

Application A updates the stock to 4 and advances the version to 8.

Application B then attempts to update using version 7. The database update fails because the version has changed.

In JPA, you can implement this with `@Version`:

```
@Entity
public class Product {

    @Id
    private Long id;

    private int stock;

    @Version
    private Long version;
}
```

The JPA provider uses the version to detect conflicting updates and typically throws an `OptimisticLockException` or a related Spring exception when a conflict is detected.

Your application must handle that failure, such as by returning a conflict response or retrying the operation when it is safe.

### Pessimistic vs optimistic locking

| Feature              | Pessimistic                   | Optimistic                                             |
| -------------------- | ----------------------------- | ------------------------------------------------------ |
| Approach             | Lock before modifying         | Detect conflicts during update                         |
| Blocking             | Possible                      | Usually avoids waiting for a lock during initial reads |
| Best suited for      | High contention               | Low/moderate contention                                |
| Conflict handling    | Waiting, timeout, or deadlock | Retry or report conflict                               |
| Database transaction | Yes                           | Yes, for version-checked writes                        |

Practical recommendation: If you need to protect a single database record, first consider an atomic SQL update, a unique constraint, or database locking. Introduce Redis locking when the coordination genuinely needs to happen across application instances or around work that isn't limited to a single database transaction.

## 5. Lock expiration

Lock expiration is one of the most important concepts in distributed locking.

Imagine Application A acquires a Redis lock and then crashes before releasing it.

Without an expiration, the key could remain in Redis indefinitely. Other applications would be unable to acquire the lock.

A time-to-live (TTL) allows the lock to expire automatically.

For example:

```
SET lock:report-generation token-A NX PX 30000
```

This creates a lock with a 30-second lease.

If the lock isn't released, it can expire after 30 seconds, allowing another application to attempt acquisition.

### 5.1 The danger of expiration

Suppose the protected operation takes 15 seconds, but the lease lasts only 10 seconds.

```
Time 0 seconds:
Application A acquires the lock.

Time 10 seconds:
The lock expires.

Time 11 seconds:
Application B acquires the lock.

Time 12 seconds:
Application A is still running.

Result:
Applications A and B may both modify the resource.
```

Why might Application A still be running?

- A long garbage-collection pause.
- A slow database or network operation.
- A thread being suspended by the operating system.
- An unexpected delay in processing.

Expiration releases the lock; it does not terminate the process that originally owned it.

### 5.2 How can we reduce the risk?

1. Choose a suitable lease duration.
2. Apply timeouts to downstream calls.
3. Renew the lease when appropriate.
4. Make operations idempotent where possible.
5. Use fencing tokens when stale owners must be prevented from writing.

### 5.3 What is a fencing token?

A fencing token is a monotonically increasing number assigned to each new lock owner.

For example:

| Application   | Fencing token |
| ------------- | ------------- |
| Application A | 41            |
| Application B | 42            |

Application A acquires the lock with token 41. Its lease expires, and Application B acquires the lock with token 42.

If Application A resumes later, it may still attempt a write using token 41.

The protected resource must reject this stale write because token 41 is older than token 42.

This requires the resource to validate and enforce fencing tokens. Merely generating tokens is not enough.

Fencing tokens are particularly useful when stale owners could overwrite data or perform operations that must be serialized.

## 6. Deadlocks

A deadlock occurs when two or more processes wait indefinitely for resources held by one another.

Consider two applications and two account locks:

```
Application A:
    Acquires lock: account-A
    Waits for lock: account-B

Application B:
    Acquires lock: account-B
    Waits for lock: account-A
```

Neither application can proceed because each holds the lock the other needs.

This can happen with Redis-based distributed locks or database locks.

### 6.1 How do we prevent deadlocks?

1\. Acquire locks in a consistent order.

If an operation needs both accounts A and B, always acquire A before B, regardless of which account the operation starts with.

2\. Use bounded waiting.

Don't wait forever to acquire a lock. Configure a timeout and handle failure.

3\. Keep critical sections short.

Avoid holding locks while making slow network calls or performing unrelated work.

4\. Release already-acquired locks when acquisition fails.

If an operation needs two locks but acquires only one, it should safely release the first before returning or retrying.

5\. Use expiration where appropriate.

Leases can help recover from abandoned locks, but they do not eliminate every deadlock or stale-owner problem.

### 6.2 Deadlock vs stuck lock

These terms describe different problems.

| Deadlock                                           | Stuck lock                                                                     |
| -------------------------------------------------- | ------------------------------------------------------------------------------ |
| Processes wait on one another in a cycle           | A lock remains held or appears held after its owner has failed or abandoned it |
| Often caused by inconsistent lock ordering         | Often caused by a crash or missing release                                     |
| Prevent with consistent ordering and bounded waits | Mitigate with leases, cleanup, and safe recovery                               |

A timeout can help a process escape waiting indefinitely, but the application must still handle the partially completed operation correctly.

## 7. Redis locks vs database locks

How do you choose between them in a real system design interview?

| Consideration  | Redis lock                                        | Database lock                                       |
| -------------- | ------------------------------------------------- | --------------------------------------------------- |
| Lock mechanism | Shared Redis key                                  | Database lock manager                               |
| Primary use    | Coordinate application instances                  | Protect database state                              |
| Expiration     | Usually configured through a lease or TTL         | Usually tied to transaction or connection lifecycle |
| Contention     | Wait, retry, or fail based on the client          | Wait, timeout, or deadlock handling                 |
| Main risks     | Lease expiration, stale owners, failover behavior | Long transactions, contention, deadlocks            |
| Good example   | Ensure only one instance runs a scheduled job     | Prevent concurrent booking of the same database row |

### Example 1: Distributed scheduled job

Suppose you deploy three Spring Boot instances:

```
@Scheduled(fixedRate = 60_000)
public void generateReport() {
    // Generate and publish the report.
}
```

Each instance may execute the scheduled method, potentially generating the same report three times.

A distributed lock can coordinate the instances so that only one runs the job at a time.

You could use Redis with Redisson or a library such as ShedLock, depending on your requirements.

However, the lock alone does not guarantee exactly-once execution. A process can fail after completing the report but before recording that completion. Use idempotency or durable job state if duplicate execution would cause a problem.

### Example 2: Preventing overselling

For a stock update, you might not need a Redis lock at all.

Consider this SQL statement:

```
UPDATE products
SET stock = stock - 1
WHERE id = 101
  AND stock > 0;
```

Check the affected-row count:

- One row updated: the stock decrement succeeded.
- Zero rows updated: the product does not exist or no stock was available.

Because the condition and update execute as a single database statement, competing requests cannot both decrement stock below zero through this operation.

This can be simpler than implementing a distributed lock.

System design rule: Choose the simplest mechanism that provides the required correctness guarantees. A distributed lock is not automatically the right answer for every concurrency problem.

## 8. Common distributed-lock interview questions

### Q1. Why doesn't `synchronized` work across multiple application instances?

Because Java monitors are local to a JVM. Different instances have independent memory and locks. They need a shared coordination mechanism.

### Q2. Why do we use `SET NX PX` in Redis?

- `NX` makes lock acquisition conditional on the key not already existing.
- `PX` sets a lease expiration.
- The combination allows atomic acquisition and helps recover from abandoned locks.

### Q3. Why is a unique owner token necessary?

It allows the application to verify ownership when releasing a lock. Otherwise, an old owner might delete a lock acquired by another application after its own lease expired.

### Q4. Does a Redis distributed lock guarantee that two applications can never modify a resource simultaneously?

Not under all failure conditions. A lease may expire while its original owner is still executing, or failover may affect the locking guarantees. For strict protection, consider fencing tokens enforced by the resource, database constraints, and other application-level safeguards.

### Q5. When should you use database locks instead of Redis?

When the protected resource is database state and the required operation can be handled safely within a database transaction, database locking or atomic SQL operations are often the simpler choice.

### Q6. What happens if an application crashes while holding a Redis lock?

If the lock has a TTL, it eventually expires. If there is no expiration, the lock may remain indefinitely. Expiration improves recovery but introduces the risk of stale owners continuing to execute.

### Q7. What is the difference between a distributed lock and a database transaction?

A transaction groups database operations and provides transaction guarantees such as atomicity. A distributed lock coordinates access among processes. A lock does not make several database transactions or microservice operations atomic.

### Q8. Can distributed locks guarantee exactly-once processing?

No. A lock alone cannot guarantee exactly-once execution across failures. Combine coordination with idempotency, durable state, and appropriate transaction or messaging guarantees.

## 9. Summary notes for your roadmap

Copy these points into your System Design notes.

Distributed Locks

- A distributed lock coordinates concurrent processes across multiple application instances.
- Java's `synchronized` and `ReentrantLock` operate within a JVM and are not shared across instances.
- Redis locks commonly use atomic `SET key token NX PX ttl` for acquisition.
- The unique owner token prevents an application from accidentally releasing another application's lock.
- Lock expiration helps recover from abandoned locks but doesn't stop the old owner from continuing to execute.
- Fencing tokens can protect resources against stale lock owners when the resource validates token ordering.
- Database pessimistic locking blocks conflicting operations; optimistic locking detects conflicting updates.
- Deadlocks occur when processes wait for resources held by one another.
- Consistent lock ordering, bounded waits, short critical sections, and safe cleanup help reduce deadlock risks.
- Always consider database constraints, atomic updates, and idempotency before introducing a distributed lock.
