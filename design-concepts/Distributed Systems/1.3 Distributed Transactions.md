# Topic 27 — Distributed Transactions

System Design Roadmap · Phase 4: Distributed Systems

This is an important topic for a Java/Spring Boot developer because it connects database transactions, microservices, Kafka, and real-world payment or order-processing systems.

According to your roadmap, we'll cover four core areas: Two-Phase Commit (2PC), the problems with 2PC, the Saga pattern, and compensating transactions.

The main question behind this topic is:

How do you keep business data consistent when one business operation involves multiple services, each with its own database?

## 1. What is a distributed transaction?

First, remember a normal database transaction.

Suppose your e-commerce application places an order and updates two tables in the same PostgreSQL database:

```
BEGIN TRANSACTION

1. Insert order
2. Reduce product inventory

COMMIT
```

If the inventory update fails, you can roll back the order insertion. Both changes can be committed or neither can be committed.

This is possible because both operations participate in the same database transaction.

Now imagine your application uses microservices.

Order Service

PostgreSQL — orders_db

Inventory Service

PostgreSQL — inventory_db

Payment Service

PostgreSQL — payments_db

Consider a customer ordering a laptop:

1. The Order Service creates an order.
2. The Inventory Service reserves one laptop.
3. The Payment Service charges the customer.

Each service owns its own database. A normal local database transaction cannot atomically commit changes across all three databases.

What if the order is created, the inventory is reserved, and the payment service fails?

You could end up with:

- An order marked as placed.
- A laptop reserved in inventory.
- No successful payment.

The system has reached an inconsistent business state.

A distributed transaction coordinates operations across multiple independent transactional resources to achieve a consistent outcome, despite failures.

There are two major approaches to understand:

- 2PC: Coordinate a global commit or rollback across participants.
- Saga: Let each service commit its own local transaction, and use additional business actions to recover if a later step fails.

These approaches solve related problems but provide different guarantees.

## 2. Why are distributed transactions difficult?

In a single database, the database engine controls the transaction. Across multiple services, failures can occur between any two steps.

Consider this sequence:

```
Order Service        Inventory Service        Payment Service
     |                       |                       |
     |---- Create order ---->|                       |
     |                       |                       |
     |<--- Reserved ---------|                       |
     |                                               |
     |---------------- Charge payment -------------->|
     |                                               |
     |                    Network timeout            |
     |<----------------------------------------------|
```

A timeout does not necessarily mean that the payment failed. The payment service might have successfully charged the customer, but its response could have been lost.

This creates several challenges:

| Challenge             | Example                                                  |
| --------------------- | -------------------------------------------------------- |
| Partial failure       | Order succeeds, payment fails                            |
| Network uncertainty   | Payment succeeds, but the response is lost               |
| Independent commits   | One database commits while another does not              |
| Concurrent operations | Two customers attempt to buy the last laptop             |
| Recovery              | A reserved laptop must be released after payment failure |

A good design must answer three questions:

1. How do we coordinate the different services?
2. What happens if a service or network connection fails?
3. How do we recover without creating duplicate payments, lost inventory, or incorrect orders?

Let's look at the two main patterns.

## 3. Two-Phase Commit (2PC)

Two-Phase Commit is a distributed transaction protocol that coordinates multiple participants so that they either all commit a transaction or all abort it.

It uses two roles:

- Coordinator: Manages the distributed transaction.
- Participants: The databases or transactional resources that must commit or abort.

For example, imagine an application that updates an order database and an inventory database. The coordinator makes sure both participants are ready before instructing them to commit.

### Phase 1: Prepare

The coordinator asks every participant:

> Can you commit your part of this transaction?

Each participant performs the necessary work and prepares to commit. It must be able to honor its decision if the coordinator later tells it to commit.

```
                 Coordinator
                 /         \
                /           \
       Order Database    Inventory Database
                \           /
                 \         /
              PREPARE REQUEST
```

Possible responses:

- `YES`: The participant has prepared successfully.
- `NO`: The participant cannot prepare the transaction.

A successful prepare is not the same as a commit. The changes are not yet globally committed, and the participant may need to retain locks or other resources while waiting.

### Phase 2: Commit or abort

The coordinator collects the responses.

Case A — All participants vote YES

```
Coordinator
    |
    |---- PREPARE ----> Order DB
    |<--- YES ---------|
    |
    |---- PREPARE ----> Inventory DB
    |<--- YES ---------|
    |
    |---- COMMIT -----> Order DB
    |---- COMMIT -----> Inventory DB
```

Both participants commit their prepared transactions.

Case B — At least one participant votes NO

```
Coordinator
    |
    |---- PREPARE ----> Order DB
    |<--- YES ---------|
    |
    |---- PREPARE ----> Inventory DB
    |<--- NO ----------|
    |
    |---- ABORT ------> Order DB
    |---- ABORT ------> Inventory DB
```

The coordinator instructs the participants to abort, including any participant that already prepared successfully.

The core rule is:

The coordinator must not commit if any participant votes NO.

### What if a participant fails?

Suppose both databases vote YES, but the coordinator crashes before sending the commit messages.

```
Order DB       Coordinator       Inventory DB
   |                |                  |
   |---- YES ------>|<------ YES ------|
   |                X                  |
   |           Coordinator            |
   |              crashes             |
   |                                   |
   |  Waiting for decision             |
   |  Waiting for decision             |
```

The participants might remain in a prepared state, holding locks and other resources until they can learn the transaction's outcome.

This is one of the biggest problems with 2PC.

### The important distinction: Atomicity versus availability

2PC aims to provide atomic commit across the participants, assuming the protocol and its recovery mechanisms are correctly implemented.

However, it can block when the coordinator fails at a critical point. Participants cannot always independently determine whether the transaction should commit or abort.

That trade-off becomes especially significant when participants are remote services communicating over an unreliable network.

## 4. Problems with 2PC

2PC is conceptually straightforward, but it introduces operational costs.

### Problem 1: Blocking

If a participant has prepared successfully and then loses contact with the coordinator, it may have to wait for recovery.

It cannot safely assume that the transaction should abort: the coordinator might already have decided to commit.

Impact: Database locks can remain held, connections and other resources can be tied up, and unrelated transactions may be delayed.

### Problem 2: Coordinator failure

The coordinator is responsible for collecting votes, recording the decision, and distributing it.

A production implementation needs durable transaction state and recovery logic. Participants may need to contact a recovered coordinator or use its durable decision records to resolve in-doubt transactions.

A coordinator crash is not necessarily fatal to the transaction forever, but recovery can be complicated and slow.

### Problem 3: Latency

The protocol needs at least two coordination phases, involving network round trips to the participants. Actual commit and acknowledgment traffic can add further latency.

If participants are spread across availability zones or regions, those network delays can become substantial.

### Problem 4: Resource retention

Prepared participants may hold locks while waiting for the global decision.

Long waits can reduce database throughput and increase contention.

### Problem 5: Operational complexity across microservices

A database transaction manager can coordinate compatible transactional resources. But coordinating independent services is more complicated because each service may own its database, deployment lifecycle, and internal business rules.

You also need to consider how the coordinator discovers participants, handles retries, persists transaction state, and recovers after crashes.

### Is 2PC ever useful?

Yes. It is useful when a strong atomic-commit guarantee is needed across compatible transactional resources and the infrastructure can support the protocol.

Examples include certain enterprise systems and distributed database or transaction-manager environments.

However, 2PC is often not the preferred approach for long-running business workflows across independently deployed microservices. Those workflows commonly use Saga instead.

## 5. Saga Pattern

A Saga breaks a distributed business transaction into a sequence of smaller local transactions.

Each service commits its own database transaction independently. If a later step fails, the system executes compensating business actions for the earlier successful steps.

Consider placing an order:

```
T1: Create order
       |
       v
T2: Reserve inventory
       |
       v
T3: Charge payment
       |
       v
T4: Arrange shipment
       |
       v
   Order completed
```

Each \\(T\\) represents a local transaction.

If payment fails after the order is created and inventory is reserved, the Saga can execute compensating actions:

```
Forward transaction:
Create Order
     |
     v
Reserve Inventory
     |
     v
Charge Payment ---- FAILURE
                         |
                         v
Compensation:
Release Inventory
     |
     v
Cancel Order
```

Notice the difference from 2PC.

In a Saga, the order and inventory transactions may already be committed. We do not magically roll back those committed database transactions. Instead, we perform new transactions that reverse their business effects.

For example:

- Create order → cancel order.
- Reserve inventory → release inventory.
- Charge payment → refund payment, if the charge succeeded and a refund is appropriate.

A Saga provides a way to recover business consistency without requiring one global database transaction.

### A concrete example

Imagine a customer orders a laptop for AED 4,000.

| Step | Service   | Operation        | Result       |
| ---- | --------- | ---------------- | ------------ |
| 1    | Order     | Create order     | Success      |
| 2    | Inventory | Reserve laptop   | Success      |
| 3    | Payment   | Charge AED 4,000 | Failure      |
| 4    | Inventory | Release laptop   | Compensation |
| 5    | Order     | Cancel order     | Compensation |

The resulting business state should be something like:

```
Order: CANCELLED
Inventory: AVAILABLE
Payment: NOT CHARGED
```

There was no single atomic commit spanning all three services. Instead, the application used local transactions and compensating actions to reach an acceptable final state.

One important detail: if the payment request timed out, you must first determine whether the payment actually succeeded. If it did, the recovery flow might need to refund the payment rather than simply assume no charge occurred.

### What does a Saga guarantee?

A Saga does not automatically guarantee that the system never exposes an intermediate state.

For example, an order might temporarily be `PENDING` while inventory is reserved and payment is processing.

The system aims to reach a valid final state through successful completion or compensation. If compensation itself fails, the Saga may require retries, reconciliation, or manual intervention.

This is why Saga implementations need careful failure handling.

## 6. Two ways to implement a Saga

There are two common approaches: choreography and orchestration.

### A. Choreography — services react to events

In choreography, there is no central component issuing every next step. Services publish events, and other services react to them.

Order Service

Creates order → publishes `OrderCreated`

Inventory Service

Reserves stock → publishes `InventoryReserved`

Payment Service

Processes payment → publishes `PaymentFailed` or `PaymentSucceeded`

Other services react to the resulting events to complete or compensate the workflow.

A typical successful flow:

1. Order Service creates a pending order and publishes `OrderCreated`.
2. Inventory Service receives the event, reserves stock, and publishes `InventoryReserved`.
3. Payment Service receives that event and processes the payment.
4. Payment Service publishes `PaymentSucceeded`.
5. Order Service marks the order as confirmed.

If payment fails, Payment Service publishes `PaymentFailed`. Inventory Service reacts by releasing the reservation, and Order Service cancels the order.

Advantages

- Services remain relatively independent.
- Event-driven communication can improve decoupling.
- There is no central workflow coordinator that must issue every command.

Disadvantages

- It can become difficult to understand the complete workflow.
- Event dependencies can become tangled as the number of services grows.
- Debugging and tracing the Saga requires good observability.
- Duplicate or out-of-order events must be handled correctly.

Choreography works well for relatively simple workflows. As workflows become more complex, orchestration may be easier to reason about.

### B. Orchestration — a central coordinator manages the workflow

In orchestration, a dedicated component, often called a Saga orchestrator, determines the next action based on the workflow's state.

Order Saga Orchestrator

Tracks state, decisions, retries, and compensations

Order

Inventory

Payment

The orchestrator sends commands and receives outcomes from each service.

A successful workflow might look like this:

1. Orchestrator sends `CreateOrder`.
2. Order Service returns success.
3. Orchestrator sends `ReserveInventory`.
4. Inventory Service returns success.
5. Orchestrator sends `ChargePayment`.
6. Payment Service returns success.
7. Orchestrator marks the Saga as completed.

If payment fails:

1. Orchestrator records the failure.
2. It sends `ReleaseInventory`.
3. After successful release, it sends `CancelOrder`.
4. It records the Saga as compensated or failed.

The orchestrator needs durable state. If it restarts, it must be able to resume the workflow rather than losing track of which steps completed.

Advantages

- The complete workflow is easier to visualize.
- Retry and compensation policies can be centralized.
- Complex business workflows are easier to manage explicitly.

Disadvantages

- The orchestrator adds another component to deploy and operate.
- Its state must be persisted and recovered.
- It can become overly coupled to the internal details of every service if designed poorly.

For a complex e-commerce checkout, an orchestration-based Saga is often a practical starting point.

## 7. Compensating transactions — the heart of Saga

A compensating transaction is a new business operation that counteracts the effect of a previously completed transaction.

This is one of the most important concepts in this topic.

Suppose you have these operations:

| Forward transaction | Compensating transaction           |
| ------------------- | ---------------------------------- |
| Create order        | Cancel order                       |
| Reserve inventory   | Release inventory                  |
| Charge payment      | Refund payment                     |
| Book hotel room     | Cancel booking                     |
| Allocate shipping   | Cancel shipment, if still possible |

Notice that compensation is not always an exact reversal.

For example, if you charge a customer and then refund them, the original charge still happened. The payment provider may charge fees, and the refund might take time to appear in the customer's account.

Similarly, you might not be able to cancel a shipment after it has been dispatched. You may need a different recovery process, such as a return.

### Compensation is not a database rollback

Consider the following sequence:

```
T1: Create order       → COMMITTED
T2: Reserve inventory  → COMMITTED
T3: Charge payment     → FAILED
```

A database rollback cannot undo `T1` and `T2`, because their local transactions have already committed.

Instead:

```
C2: Release inventory  → COMMITTED
C1: Cancel order       → COMMITTED
```

Here, `C1` and `C2` are new transactions.

The business state is eventually restored to an acceptable condition.

### Why compensation can fail

Suppose the payment fails, and the application tries to release inventory. But the Inventory Service is temporarily unavailable.

You now have two failures:

1. The forward workflow failed.
2. The compensation failed.

A production Saga must handle this situation.

Typical strategies include:

- Retry the compensation with exponential backoff and jitter.
- Persist the Saga state so recovery survives application restarts.
- Make compensation operations idempotent.
- Alert operators when compensation repeatedly fails.
- Reconcile incomplete workflows periodically.

A Saga should not be marked fully compensated until the required compensating actions have succeeded, or the workflow has explicitly entered a separate state requiring manual resolution.

## 8. Implementing a Saga with Java and Spring Boot

Let's turn the concept into a design you could implement in a Spring Boot microservices application.

We'll use orchestration and assume each service owns its own database.

### Step 1: Define the Saga states

The orchestrator could track the following states:

```
public enum SagaStatus {
    STARTED,
    ORDER_CREATED,
    INVENTORY_RESERVED,
    PAYMENT_PROCESSING,
    COMPLETED,
    COMPENSATING,
    COMPENSATED,
    COMPENSATION_FAILED
}
```

These are illustrative states; a real implementation might distinguish pending, retrying, and individual compensation steps more precisely.

A persisted Saga record could contain:

```
public record OrderSaga(
        String sagaId,
        String orderId,
        SagaStatus status,
        String failureReason
) {}
```

In production, you would generally persist the state in a database rather than keeping it only in application memory.

### Step 2: Implement forward transactions

Each service commits its own local transaction.

For example, the Inventory Service might have:

```
@Service
public class InventoryService {

    private final InventoryRepository repository;

    public InventoryService(InventoryRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void reserve(String orderId, String productId) {
        Inventory inventory = repository.findByProductId(productId)
                .orElseThrow();

        if (inventory.getAvailableQuantity() < 1) {
            throw new IllegalStateException("Out of stock");
        }

        inventory.reserve(1);
        repository.save(inventory);
    }
}
```

The database transaction ensures the local inventory update is atomic. However, this simplified example does not implement concurrency control, idempotency, or reservation expiry; those are essential considerations in a production implementation.

### Step 3: Implement compensation

The Inventory Service needs a separate operation to release the reservation.

```
@Transactional
public void release(String orderId, String productId) {
    // Find the reservation associated with this order.
    // If it has already been released, do nothing.
    // Otherwise, release it and persist the new state.
}
```

Why check whether it has already been released?

Because distributed messaging commonly provides at-least-once delivery. A command may be delivered more than once, and a retry must not increase inventory twice.

A robust implementation records reservation state and makes `release` idempotent.

### Step 4: Orchestrate the workflow

The high-level logic might be:

```
public void placeOrder(OrderRequest request) {
    String sagaId = sagaRepository.start(request);

    try {
        orderService.createPendingOrder(request);
        sagaRepository.updateStatus(
                sagaId, SagaStatus.ORDER_CREATED);

        inventoryService.reserve(
                request.orderId(), request.productId());
        sagaRepository.updateStatus(
                sagaId, SagaStatus.INVENTORY_RESERVED);

        paymentService.charge(
                request.orderId(), request.amount());
        sagaRepository.updateStatus(
                sagaId, SagaStatus.COMPLETED);

    } catch (Exception exception) {
        sagaRepository.markCompensating(
                sagaId, exception.getMessage());

        compensate(sagaId, request);
    }
}
```

This illustrates the workflow, not a production-ready implementation.

There are important limitations:

- If the orchestrator crashes, its in-memory execution is lost.
- A timeout may occur after a remote service has committed.
- A compensation failure needs independent retry and recovery.
- A synchronous chain of HTTP calls can make the workflow slow and fragile.

For production, a durable orchestration engine or a persisted state machine with asynchronous commands and events is usually more robust.

Also, do not blindly treat every timeout as a business failure. First reconcile ambiguous outcomes using the transaction or operation ID.

## 9. The Outbox Pattern and idempotency

Saga workflows frequently use Kafka or another message broker. This introduces another consistency problem.

Imagine the Order Service performs these operations:

```
1. Save order in PostgreSQL
2. Publish OrderCreated to Kafka
```

What if the database commit succeeds but Kafka publishing fails?

The order exists, but the next Saga step never receives the event.

This is the dual-write problem.

### Solution: Transactional Outbox

Within a single local database transaction, write both:

- The business change.
- An event record in an outbox table.

```
Order Service
     |
     v
PostgreSQL transaction
     |
     +---- Insert Order
     |
     +---- Insert Outbox Event
                    |
                    v
            Background Publisher
                    |
                    v
                  Kafka
                    |
                    v
            Inventory Service
```

A publisher or CDC-based mechanism subsequently delivers the outbox event to Kafka.

If publishing fails, the event remains available for retry.

The outbox pattern prevents the order and its event record from being committed independently. It does not, by itself, guarantee that the event will be delivered exactly once, so consumers still need to handle duplicates.

### Why idempotency matters

Suppose the Payment Service charges the customer, but the response is lost.

The orchestrator retries the charge request.

Without protection, the customer could be charged twice.

Use a stable payment operation ID or idempotency key:

```
POST /payments
Idempotency-Key: order-123-payment
Content-Type: application/json
```

The Payment Service should persist the key and the result of the operation. Repeated requests with the same key must return the existing result rather than creating another charge.

The same principle applies to inventory reservation, compensation, and event consumption.

Remember these three building blocks:

- Saga coordinates the business workflow.
- Outbox makes local database changes and event recording atomic.
- Idempotency makes retries safe.

They solve different problems and are often used together.

## 10. 2PC vs Saga — the interview comparison

| Dimension           | Two-Phase Commit                                                                              | Saga                                                             |
| ------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Approach            | Global atomic commit protocol                                                                 | Sequence of local transactions                                   |
| Coordination        | Coordinator plus participants                                                                 | Orchestrator or event choreography                               |
| Rollback            | Abort prepared transaction before global commit                                               | Execute compensating business operations                         |
| Intermediate states | Participants wait for a global decision; application visibility depends on the implementation | Intermediate business states are expected                        |
| Failure behavior    | Can block while resolving an in-doubt transaction                                             | Can retry, compensate, or require manual recovery                |
| Resource retention  | Prepared transactions may hold locks                                                          | Local transactions typically finish independently                |
| Consistency         | Atomic commit across participating resources                                                  | Business consistency through workflow completion or compensation |
| Best fit            | Compatible transactional resources requiring atomic commit                                    | Long-running business workflows across microservices             |

One subtle point: Saga is not simply a faster version of 2PC. They have different semantics. Compensation cannot always reverse the original effect, and intermediate results may be visible to other services.

### How do you choose?

Choose 2PC when you genuinely need atomic commit across compatible resources and can accept the protocol's coordination and blocking characteristics.

Choose Saga when you have independent services with separate databases, and your business process can tolerate intermediate states and define meaningful compensating actions.

For a typical order-processing system with separate Order, Inventory, and Payment services, Saga is often the more practical design.

## 12. A practical system design exercise

Imagine you're designing an e-commerce checkout service with three databases:

- `orders_db`
- `inventory_db`
- `payments_db`

The requirements are:

1. An order must not be confirmed if payment fails.
2. Inventory must be released if payment fails after a reservation.
3. Customers must not be charged twice if the payment response times out.
4. A service restart must not lose track of an incomplete checkout.
5. If compensation fails, the system must eventually recover or alert an operator.

A reasonable architecture would use an orchestrated Saga, persistent workflow state, idempotent service operations, and an outbox mechanism for reliable event publishing.

The state transitions might look like this:

```
PENDING
   |
   v
ORDER_CREATED
   |
   v
INVENTORY_RESERVED
   |
   v
PAYMENT_PROCESSING
   |
   +------ Payment succeeds ------> CONFIRMED
   |
   +------ Payment fails ---------> COMPENSATING
                                         |
                                         v
                                   INVENTORY_RELEASED
                                         |
                                         v
                                    ORDER_CANCELLED
```

You would also need to define what happens if payment times out, inventory release fails, or the orchestrator restarts between steps.

Those failure scenarios are what turn a basic diagram into a production-ready system design.

## 13. Final revision notes

Keep this mental model:

- Distributed transaction: One business operation spans multiple transactional resources.
- 2PC: Participants prepare first, then commit or abort according to a coordinator's decision.
- 2PC limitation: A prepared participant can block when the coordinator's decision is unavailable.
- Saga: A workflow composed of independently committed local transactions.
- Compensating transaction: A new business operation that counteracts an earlier transaction's effect.
- Choreography: Services coordinate through events.
- Orchestration: A coordinator tracks state and directs the workflow.
- Outbox: Business data and the event record are stored atomically in one local database transaction.
- Idempotency: Retries do not repeat the business effect.
- Recovery: Persist workflow state, retry safely, reconcile ambiguous outcomes, and handle failed compensations.

For interviews, the key is not merely knowing the definitions. You should be able to explain what happens when the network fails after a payment succeeds, how to prevent a duplicate charge, and how the system recovers after a service restart.

That is the real test of understanding distributed transactions.
