# Topic 26: Failure Detection

Phase 4 — Distributed Systems

Since you've already covered network failures, timeouts, and retries, this topic connects those concepts together.

The central question is:

How can one service determine whether another service is healthy, slow, or actually unavailable when they communicate over an unreliable network?

The surprising answer is that a service usually cannot know with absolute certainty that another service has failed just because it isn't responding.

Let's understand why, using Java and Spring Boot microservices.

## 1. What is failure detection?

Failure detection is the process of identifying when a service, server, process, or network component may have stopped working or become unresponsive.

Imagine your e-commerce system:

```
Order Service  ────────>  Payment Service
```

The Order Service sends a request to the Payment Service, but receives no response.

What happened?

- Payment Service crashed.
- Payment Service is overloaded.
- The network is temporarily unavailable.
- The request or response was lost.
- Payment Service is still processing the request, but very slowly.

From the Order Service's perspective, all these situations might look identical: no response arrived within the expected time.

That is the fundamental challenge of failure detection in distributed systems.

A timeout tells you that a response didn't arrive in time. It doesn't prove the remote service has crashed.

## 2. Failure detection vs health checking vs timeouts

These concepts are related, but they serve different purposes.

| Concept          | What it tells you                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| Timeout          | A particular operation took longer than the allowed duration.                                              |
| Health check     | Whether a service reports that it can perform some defined set of operations.                              |
| Failure detector | Uses observations, such as missed heartbeats or failed probes, to suspect that a component is unavailable. |

For example, a Payment Service might respond successfully to a health endpoint while its payment database is unavailable. Whether that service should report itself as ready depends on what the health check is designed to measure.

Similarly, one failed HTTP request doesn't necessarily mean the entire Payment Service is unhealthy.

System-design takeaway: Failure detection is about gathering enough evidence to make an operational decision, not obtaining perfect knowledge of another machine's state.

## 3. Heartbeats: the simplest failure detection mechanism

A heartbeat is a periodic signal that indicates a component is still alive or communicating.

Imagine the Payment Service sends a heartbeat every 2 seconds to a monitoring component.

### Normal operation

Payment Service

Sends heartbeat every 2 seconds

Heartbeat received ✓

Monitor

Records last successful heartbeat

The monitor might observe:

```
10:00:00  Heartbeat received
10:00:02  Heartbeat received
10:00:04  Heartbeat received
10:00:06  Heartbeat received
```

Everything appears normal.

Now suppose the Payment Service crashes.

### Missing heartbeats

Payment Service

Process has crashed

No heartbeat received

Monitor

Missed heartbeat threshold exceeded

Suspected failure

For example, if heartbeats arrive every 2 seconds and the monitor suspects failure after 3 consecutive missed heartbeats, it might declare a suspected failure after roughly 6 seconds.

This is an illustrative configuration, not a universal rule.

### The catch: missing heartbeat doesn't always mean a crash

What if the Payment Service is healthy but the network is temporarily unavailable?

The monitor will still miss heartbeats.

That leads to two important terms:

- False positive: The monitor suspects a failure, but the service is actually healthy.
- False negative: The monitor considers a service healthy even though it has failed.

A shorter timeout detects failures faster but may produce more false positives. A longer timeout reduces false alarms but delays detection.

This is a classic distributed-systems trade-off.

## 4. Health checks: liveness and readiness

Heartbeats are useful, but applications also expose health endpoints that infrastructure can periodically query.

For example, a Spring Boot application using Spring Boot Actuator can expose:

```
GET /actuator/health
```

A healthy application might return:

```
{
  "status": "UP"
}
```

Health checks are especially useful to load balancers, container orchestrators, and monitoring systems.

Two important checks are liveness and readiness.

Liveness — Is the process functioning?

If the application is stuck in a state from which it cannot recover, the infrastructure might restart it.

Typical question: Should this instance be restarted?

Readiness — Can this instance serve requests?

If an instance is starting up or temporarily unable to serve traffic, it should not receive new requests.

Typical question: Should this instance receive traffic?

For example, your Order Service may be running, but it has not finished initializing its dependencies.

- Liveness: `UP`
- Readiness: `OUT_OF_SERVICE`

The process doesn't necessarily need a restart. It simply shouldn't receive production traffic yet.

In Kubernetes, readiness probes control whether a pod is considered ready for service, while liveness probes can trigger a restart after repeated failures.

One important caution: don't make liveness depend indiscriminately on every remote dependency. If the database briefly becomes unavailable and every application instance fails its liveness check, you could trigger unnecessary restarts and make the incident worse.

## 5. Active vs passive failure detection

There are two broad approaches.

### A. Active detection

A monitor actively probes a component.

```
Monitor ── health request ──> Service
Monitor <── health response ── Service
```

Examples:

- HTTP health checks
- TCP connection probes
- Periodic heartbeat requests

Advantage: You can check a component even when it hasn't initiated communication.

Limitation: The probe itself consumes resources and can fail because of network problems.

### B. Passive detection

A component infers trouble from normal traffic.

Examples:

- Repeated request timeouts
- Connection resets
- Consecutive errors from a dependency
- Unexpectedly high failure rates

Advantage: Uses observations from real traffic.

Limitation: If there is no traffic, you may not discover the problem until a request arrives.

Real systems often combine both approaches. An orchestrator may run active health probes while an API client tracks failures from ordinary requests.

## 6. Failure detection in a distributed cluster

So far, we've looked at detecting whether a service is available. Now let's consider a more advanced case: a cluster of three nodes.

Imagine a distributed database:

```
       Node A
       /    \
      /      \
   Node B -- Node C
```

Each node communicates with the others. Suppose Node A stops receiving messages from Node B.

Can Node A safely conclude that Node B has crashed?

Not necessarily. Node B might be healthy but isolated by a network partition.

A distributed system may therefore use states such as:

- Healthy: Recent communication is working.
- Suspected: Expected communication hasn't arrived within the threshold.
- Confirmed unavailable: Additional evidence or a system-specific rule justifies treating the node as unavailable.

The exact states depend on the system. Some systems don't have a way to truly confirm a remote crash; they operate on suspicion and timeouts.

This distinction matters in leader election, distributed databases, and consensus algorithms. If Node A incorrectly assumes Node B is dead and takes over its responsibilities, both nodes might continue acting as leaders if coordination isn't designed correctly.

That's one reason failure detection and consensus are related but different topics.

## 7. How do real systems react to detected failures?

Detecting a failure is only the first step. The next step is deciding what to do.

| Detection signal                           | Possible response                                           |
| ------------------------------------------ | ----------------------------------------------------------- |
| Instance fails readiness check             | Stop routing new traffic to it                              |
| Instance fails liveness checks repeatedly  | Restart it, if appropriate                                  |
| Downstream requests repeatedly time out    | Open a circuit breaker                                      |
| One service instance becomes unavailable   | Route requests to healthy instances                         |
| A message repeatedly fails processing      | Retry according to policy or send it to a dead-letter queue |
| A distributed node is suspected of failing | Follow the cluster's membership and coordination protocol   |

Notice that failure detection is not the same as failure recovery.

For example, a load balancer might detect that one Order Service instance is unhealthy and stop routing traffic to it. That doesn't necessarily restart the instance or repair the underlying problem.

Likewise, a circuit breaker can stop sending requests to an unhealthy dependency, but it doesn't fix that dependency.

## 8. A practical Spring Boot example

Let's connect this to a system you could build.

Suppose your Order Service calls your Payment Service, and you want to avoid continuously sending requests to a failing instance.

A simplified design might look like this:

```
Order Service
     |
     v
Payment Service
     |
     +--> Request timeout
     |
     +--> Repeated failures
                |
                v
        Circuit breaker opens
                |
                v
        Stop normal calls temporarily
                |
                v
        Periodically allow a test call
                |
          +-----+-----+
          |           |
       Success      Failure
          |           |
       Recover      Stay open
```

The circuit breaker isn't itself a perfect failure detector. It uses observed failures to decide whether calls should be allowed.

In the Resilience4j library, you can configure a circuit breaker with a failure-rate threshold, a minimum number of calls, and an open-state wait duration. When it opens, calls are rejected locally instead of repeatedly waiting for the failing dependency.

This is an example of how failure observations drive protective behavior.

A complete implementation would also configure sensible timeouts and decide which exceptions count as failures. You shouldn't count every business error, such as an invalid payment request, as proof that the service is unhealthy.

## 9. Common interview questions

Q1. Can a service know with certainty that another service has crashed?

Generally, no—not from a missing response alone. Network failure, slow processing, and a crashed process can look identical to the caller.

Q2. What is the difference between a heartbeat and a health check?

A heartbeat is a periodic signal that indicates communication or liveness. A health check is a probe or status report that evaluates a defined aspect of service health. The exact distinction depends on the implementation.

Q3. Why not use a very short timeout to detect failures quickly?

It can generate false positives during temporary latency spikes, network congestion, or CPU pressure. Detection thresholds balance speed against false alarms.

Q4. If a service fails its readiness check, should it always restart?

No. Readiness means it should not receive traffic. Liveness is the check more commonly used to decide whether a restart may be necessary.

Q5. Is failure detection the same as a circuit breaker?

No. Failure detection identifies or suspects a problem. A circuit breaker uses observed failures to control whether further calls are allowed.

### What to remember

If you remember just four things from Topic 26, remember these:

1. Failure detection is inherently uncertain in distributed systems.
2. Heartbeats, health checks, and request failures provide evidence of trouble.
3. Detection thresholds trade off speed against false positives.
4. Detection must be connected to an appropriate response, such as removing an instance from traffic, restarting it, or opening a circuit breaker.
