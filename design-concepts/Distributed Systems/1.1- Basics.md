# Topic 22: What Is a Distributed System?

Phase 4 — Distributed Systems

Let's build this from the ground up, using examples from your Java and Spring Boot microservices experience.

The most important idea to understand is this:

A distributed system consists of multiple independent computers or processes that communicate over a network to accomplish a common goal.

The tricky part isn't simply having multiple services. It's making them work correctly when the network, individual services, or shared dependencies fail.

## 1. Start with a simple example

Imagine you're building an e-commerce application.

Initially, you have a single Spring Boot application running on one server.

### Architecture A — Single application

React Client

### Spring Boot Application

Users

Products

Orders

Database

One application contains several business modules.

This can be a perfectly valid architecture. A distributed system isn't automatically better than a monolith.

Now imagine the application grows. You want to scale the Order Service independently, deploy the Payment Service separately, and isolate failures between services.

You split the application into independent services running on different instances.

### Architecture B — Distributed application

React Client

API Gateway

User Service

Instance AUser DB

Product Service

Instance BProduct DB

Order Service

Instance COrder DB

Payment Service

Instance DPayment DB

Each service can run and fail independently and communicates with other services over a network.

Now the Order Service might call the Payment Service using HTTP, or publish an event to a message broker.

That introduces a fundamentally different set of engineering problems.

## 2. What makes a system distributed?

There are three essential characteristics.

### A. Multiple independent components

Each service runs in its own process and may run on a separate machine or container.

For example:

```
Order Service   → Container A
Payment Service → Container B
Product Service → Container C
```

They can be deployed, restarted, scaled, and updated independently.

### B. Communication over a network

One service usually cannot call another service's Java method directly across process boundaries.

Inside a single application, you might write:

```
paymentService.processPayment(order);
```

Across services, you might instead make an HTTP request:

```
PaymentResponse response =
    restClient.post()
        .uri("http://payment-service/payments")
        .body(request)
        .retrieve()
        .body(PaymentResponse.class);
```

The exact API depends on your Spring version and HTTP client configuration.

That network call can time out, fail to connect, or return an error even when the calling service is healthy.

### C. Independent failures

This is the defining challenge.

Your Order Service might be running normally while the Payment Service is unavailable. The Product Service could still be healthy while the database used by the User Service is down.

The whole system doesn't necessarily fail at once.

A distributed system can be partially available: some operations work while others fail.

That is a much bigger challenge than simply splitting a Java application into several services.

## 3. Why are distributed systems difficult?

Let's explore the problems one by one. These are the foundations for the next topics in your roadmap: network failures, timeouts, retries, failure detection, distributed transactions, and consensus.

### Problem 1: Network failures

Suppose the Order Service calls the Payment Service.

```
Order Service  ───── HTTP request ─────> Payment Service
               <──── HTTP response ─────
```

Several things can go wrong:

- Connection refused: the Payment Service isn't accepting connections.
- Timeout: the response doesn't arrive before the deadline.
- Network partition: the services cannot communicate across part of the network.
- DNS failure: the service hostname cannot be resolved.
- Connection reset: the connection breaks unexpectedly.

Here's the subtle part.

Suppose the Payment Service processes a payment, but the response gets lost.

```
Order Service             Payment Service
     |                           |
     |---- Process payment ----->|
     |                           | Payment succeeds
     |          X                |
     |   Response gets lost      |
     |                           |
     | Timeout!                  |
```

What should the Order Service do?

It doesn't know whether the payment failed or succeeded.

If it blindly retries, it might charge the customer twice.

This is why distributed systems need timeouts, carefully designed retries, idempotency, and sometimes reconciliation.

You already studied API idempotency in Topic 19. This is one of the reasons it matters so much.

### Problem 2: Partial failure

In a single application, a process crash may take down the entire application. In a distributed application, one component can fail while the others continue running.

Imagine an e-commerce homepage that depends on three services:

| Service                | Status  | Result                      |
| ---------------------- | ------- | --------------------------- |
| Product Service        | Healthy | Products load               |
| Recommendation Service | Down    | Recommendations unavailable |
| User Service           | Healthy | Profile loads               |

Should the entire homepage fail because recommendations are unavailable?

Usually not.

A better design degrades gracefully: show the products and profile, but omit recommendations.

Product Service

Products displayed normally

Healthy

Recommendation Service

Recommendation section hidden or replaced with a fallback

Unavailable

User Service

Profile loads normally

Healthy

The design goal is to prevent one failing dependency from unnecessarily bringing down unrelated functionality.

Later, we'll study circuit breakers, bulkheads, and graceful degradation to handle these situations.

### Problem 3: Latency and network overhead

A local Java method call may be extremely fast. A remote HTTP call requires network communication, request processing, serialization, and possibly TLS encryption.

Suppose a request follows this path:

```
Client
  |
  v
Order Service       20 ms
  |
  v
Inventory Service   30 ms
  |
  v
Payment Service     80 ms
  |
  v
Database            20 ms
```

If these operations happen sequentially, the total is approximately:

\\[ 20 + 30 + 80 + 20 = 150\text{ ms} \\]

This excludes any additional overhead not included in the individual measurements.

Now suppose Payment Service takes 2 seconds instead of 80 ms. The entire synchronous request can become slow, even if Order Service itself is fast.

This is called latency propagation: a slow dependency can make upstream requests slow.

We will address this with timeouts, concurrency, asynchronous communication, and careful service boundaries.

### Problem 4: Data consistency

In a monolithic application, several business operations might share one relational database and one transaction.

In a microservices architecture, the Order Service and Payment Service often own separate databases.

Consider placing an order:

1. Order Service creates an order.
2. Payment Service charges the customer.
3. Inventory Service reserves stock.

What happens if payment succeeds but inventory reservation fails?

There is no single ordinary database transaction that automatically rolls back all three independent services.

The system needs a business-level recovery strategy, such as a Saga with compensating actions.

This is why distributed transactions and eventual consistency are major topics in system design.

### Problem 5: No perfectly reliable way to know whether a remote service is dead

Suppose Order Service sends a request to Payment Service but receives no response.

Is Payment Service:

- Crashed?
- Running slowly?
- Overloaded?
- Healthy, but separated by a network problem?

From the caller's perspective, these situations can look identical.

A timeout tells you that a deadline was exceeded. It does not prove that the remote service crashed or that the operation failed.

This is one of the most important mental models in distributed systems.

## 4. Benefits of distributed systems

If distributed systems are harder, why use them?

Because they offer important advantages when the requirements justify the added complexity.

Independent scaling

Scale the Product Service to 10 instances during a sale without scaling every other service equally.

Fault isolation

A well-designed system can keep essential features working when a nonessential service fails.

Independent deployment

Teams can release a service without redeploying the entire application, provided interfaces remain compatible.

Organizational autonomy

Different teams can own services, technologies, and release schedules independently.

These benefits are not automatic. A distributed system with tightly coupled services, shared bottlenecks, and poor failure handling can be less reliable than a well-designed monolith.

## 5. Monolith vs distributed system: when should you choose each?

| Consideration    | Monolith                        | Distributed services                          |
| ---------------- | ------------------------------- | --------------------------------------------- |
| Deployment       | Usually one application unit    | Multiple independently deployed units         |
| Communication    | Often in-process method calls   | Network calls and/or messaging                |
| Transactions     | Easier within one database      | Cross-service coordination is harder          |
| Scaling          | Scale the application as a unit | Scale individual services                     |
| Operations       | Generally simpler               | More infrastructure and monitoring            |
| Failure handling | Process and dependency failures | Also partial failures and network uncertainty |

A useful rule of thumb:

- Start with a modular monolith when one deployable application meets your needs.
- Introduce distributed services when independent scaling, deployment, ownership, or isolation provides a concrete benefit.
- Don't split services just because microservices are fashionable.

## 6. Synchronous vs asynchronous communication in distributed systems

You already know the basics, but here is how they fit into the bigger picture.

### Synchronous communication

Order Service

HTTP request — waits for response

Payment Service

Useful when the caller needs the result immediately. The caller must handle timeouts and failures.

### Asynchronous communication

Order Service

Message Broker

Kafka / RabbitMQ

Payment Consumer

The producer and consumer can progress independently, but delivery, retries, duplicate messages, and eventual consistency still need to be handled.

Asynchronous communication can reduce direct runtime dependencies between services. However, it doesn't eliminate network failures or make a business workflow automatically reliable.

## 7. The mental model you should remember

Think of distributed systems as three challenges combined:

Communication

Services communicate over unreliable networks with variable latency.

Failure

Components fail independently, and the rest of the system must respond appropriately.

Coordination

Independent services must coordinate data, business operations, and decisions without assuming everything happens atomically.

## 8. Interview practice

Imagine you're interviewing for a Senior Java Developer or Principal Engineer position.

The interviewer asks:

"Your Order Service calls the Payment Service. The payment request times out. How do you handle it?"

A strong answer should cover these points:

1. A timeout doesn't necessarily mean payment failed. The payment might have succeeded and its response been lost.
2. Don't blindly retry a payment request. Use an idempotency key so the same logical payment isn't charged twice.
3. Apply appropriate connection and response timeouts.
4. If the result remains unknown, reconcile the payment status with the Payment Service instead of assuming failure.
5. For longer workflows, consider asynchronous processing and explicit order/payment states.

That's the kind of reasoning interviewers want: not just knowing what a distributed system is, but understanding its failure modes and designing around them.

Let's check your understanding with one question.

The Order Service sends a payment request. The request times out, but the Payment Service may already have charged the customer. What is the safest next step?

Immediately send a new payment request with a new ID.

Assume the payment failed and cancel the order.

Use the same idempotency key for a safe retry or check the existing payment status.

Increase the number of Order Service instances.

Once this concept is clear, Topic 23 — Network Failures — becomes much easier because we'll examine exactly what can happen between two services and how to handle each failure.
