# Rate Limiting

## 1. What is Rate Limiting?

Rate limiting means:

> **Controlling how many requests a client is allowed to make within a certain period of time.**

For example:

```text
100 requests / minute / user
```

Suppose a user calls:

```http
GET /api/products
```

and our rule is:

```text
100 requests per minute
```

Then:

```text
Request 1    → ✅
Request 2    → ✅
...
Request 100  → ✅
Request 101  → ❌
```

Typically the server responds:

```http
HTTP/1.1 429 Too Many Requests
```

---

# 2. Why do we need Rate Limiting?

There are several reasons.

### ① Protect the server

Imagine your API can safely process:

```text
10,000 requests/sec
```

but suddenly one client sends:

```text
100,000 requests/sec
```

Without rate limiting:

```text
Client
  |
  | 100k req/sec
  ↓
API
  |
  ↓
CPU 100%
  |
  ↓
Memory pressure
  |
  ↓
Database overloaded
  |
  ↓
💥 System failure
```

Rate limiting protects the system.

---

### ② Prevent abuse

For example:

```text
POST /login
```

An attacker could try:

```text
password1
password2
password3
password4
...
```

You could enforce:

```text
5 login attempts / minute / IP
```

Now the attacker gets blocked.

---

### ③ Fairness

Suppose you have:

```text
1000 users
```

One user shouldn't consume all your capacity.

Without rate limiting:

```text
User A → 9000 requests
User B → 10 requests
User C → 5 requests
```

With rate limiting:

```text
User A → max 100 req/sec
User B → max 100 req/sec
User C → max 100 req/sec
```

Resources are shared more fairly.

---

### ④ Protect downstream services

This is particularly important in microservices.

Imagine:

```text
Client
  ↓
Order Service
  ↓
Payment Service
  ↓
Bank
```

If 50,000 requests hit Order Service, you don't necessarily want all 50,000 requests reaching Payment Service.

Rate limiting can protect the downstream dependency.

---

# 3. Where should Rate Limiting happen?

There are several possibilities.

## Option 1 — Application

```text
Client
   ↓
Load Balancer
   ↓
Spring Boot
   ↓
Rate Limiter
   ↓
Business Logic
```

For example, Spring Boot could maintain request counts.

Problem:

If you have:

```text
App 1
App 2
App 3
```

and each instance maintains its own counter:

```text
User → App 1 → 100 requests
User → App 2 → 100 requests
User → App 3 → 100 requests
```

The user effectively gets:

```text
300 requests
```

instead of:

```text
100 requests
```

This is why distributed rate limiting becomes important.

---

# 4. API Gateway

A more common architecture is:

```text
                 ┌── App 1
                 │
Client
  ↓
API Gateway
  ↓
Rate Limiter
  ↓
                 ├── App 2
                 │
                 └── App 3
```

Now all requests pass through one logical rate-limiting layer.

Examples include:

* Nginx
* Envoy
* Spring Cloud Gateway
* cloud API gateways

This is also why your roadmap later lists **rate limiting as an API Gateway responsibility**.

# 5. What exactly are we limiting?

This is an important interview question.

You can rate-limit based on:

### IP

```text
100 requests/minute/IP
```

Useful for anonymous APIs.

But NAT can be a problem.

For example:

```text
100 users
    ↓
same corporate NAT
    ↓
1 public IP
```

All 100 users might share one limit.

---

### User

```text
1000 requests/minute/user
```

Usually better for authenticated APIs.

---

### API key

```text
API_KEY_123 → 10,000 requests/hour
API_KEY_456 → 100,000 requests/hour
```

Very common for public APIs.

---

### Endpoint

You might have:

```text
GET /products
→ 1000 req/sec

POST /payments
→ 10 req/sec
```

This is important because not all APIs cost the same.

---

### Combination

Real systems often use multiple dimensions:

```text
IP       → 100 req/min
User     → 1000 req/min
API key  → 10,000 req/hour
Endpoint → specific limit
```

The request must satisfy all relevant limits.

---

# 6. Fixed Window Algorithm

This is the simplest algorithm.

Suppose:

```text
Limit = 5 requests / minute
```

Divide time into fixed windows:

```text
10:00:00 ───────── 10:00:59
10:01:00 ───────── 10:01:59
10:02:00 ───────── 10:02:59
```

Maintain a counter:

```text
10:00 window → 0
```

Requests:

```text
Request 1 → counter = 1
Request 2 → counter = 2
Request 3 → counter = 3
Request 4 → counter = 4
Request 5 → counter = 5
Request 6 → ❌
```

At 10:01:

```text
counter = 0
```

and the process starts again.

### Simple implementation

Conceptually:

```java
if (counter < LIMIT) {
    counter++;
    allow();
} else {
    reject();
}
```

---

# 7. Problem with Fixed Window

There is a nasty boundary problem.

Suppose:

```text
Limit = 100 requests/minute
```

A client sends:

```text
10:00:59 → 100 requests
10:01:00 → 100 requests
```

That's:

```text
200 requests
```

in roughly:

```text
2 seconds
```

even though the configured limit was:

```text
100 requests/minute
```

Visualize it:

```text
          Window 1       Window 2

        100 requests    100 requests
             ↓               ↓
10:00:59 ───────────────── 10:01:00
```

This is called the **boundary burst problem**.

Fixed Window is:

**Simple + cheap**, but less accurate.

---

# 8. Sliding Window

Sliding Window tries to solve the boundary problem.

Instead of saying:

```text
10:00:00 → 10:00:59
```

we ask:

> How many requests did this client make during the previous 60 seconds?

Suppose current time is:

```text
10:01:30
```

We examine:

```text
10:00:30 → 10:01:30
```

If there were already 100 requests:

```text
Request → ❌
```

This provides a much smoother limit.

---

## Sliding Window example

Limit:

```text
5 requests / 60 seconds
```

Requests:

```text
10:00:10
10:00:20
10:00:30
10:00:40
10:00:50
```

At:

```text
10:00:55
```

another request arrives.

Previous 60 seconds contains:

```text
5 requests
```

Therefore:

```text
❌ Reject
```

At:

```text
10:01:11
```

the request at 10:00:10 has fallen outside the window.

Now:

```text
4 requests
```

remain.

So:

```text
✅ Allow
```

# 9. Token Bucket

This is probably the **most important algorithm to understand deeply** for interviews.

Imagine a bucket containing tokens.

```text
       Token Bucket

       ┌───────────┐
       │ ● ● ● ● ● │
       │ ● ● ●     │
       └───────────┘
```

Each request consumes one token.

Suppose:

```text
Bucket capacity = 10
Refill rate     = 2 tokens/sec
```

If a request arrives:

```text
token available?
       ↓
      YES
       ↓
remove token
       ↓
allow request
```

If there are no tokens:

```text
Bucket empty
     ↓
❌ Reject
```

---

# 10. Why Token Bucket is powerful

It allows **controlled bursts**.

Suppose:

```text
Capacity = 10
Refill = 2/sec
```

The bucket can accumulate:

```text
10 tokens
```

If the user suddenly sends 10 requests:

```text
Request 1 → token
Request 2 → token
...
Request 10 → token
```

All 10 can succeed.

But request 11:

```text
❌
```

Then tokens gradually return:

```text
2 tokens/sec
```

So after one second:

```text
2 tokens
```

are available.

---

# 11. Token Bucket mental model

Think:

```text
             tokens
               ↓
         ┌───────────┐
         │ ● ● ● ●   │
         │ ● ●       │
         └─────┬─────┘
               │
               ↓
            Request
               │
          consume 1
               │
               ↓
            Service
```

And simultaneously:

```text
time
 ↓
tokens refill
```

This gives us:

> **Average rate control + controlled bursts**

That's why Token Bucket is extremely common.

---

# 12. Leaky Bucket

Leaky Bucket is slightly different.

Imagine a bucket with a hole.

```text
       Requests
          ↓
     ┌───────────┐
     │ request   │
     │ request   │
     │ request   │
     │ request   │
     └─────┬─────┘
           │
           ↓
       fixed rate
           ↓
        Server
```

Requests enter the bucket.

The bucket processes them at a **fixed rate**.

For example:

```text
10 requests/sec
```

Even if 100 requests arrive instantly, the system processes them at the configured rate.

---

# 13. Token Bucket vs Leaky Bucket

This is a classic interview question.

|                 | Token Bucket              | Leaky Bucket               |
| --------------- | ------------------------- | -------------------------- |
| Main idea       | Tokens control requests   | Queue drains at fixed rate |
| Bursts          | Allows controlled bursts  | Smooths bursts             |
| Processing rate | Can burst                 | More constant              |
| Queue           | Usually no queue required | Often queue-based          |
| Good for        | API request limiting      | Traffic shaping            |

The simplest mental model:

```text
Token Bucket
→ "Can I spend a token?"

Leaky Bucket
→ "I'll process requests at this rate."
```

---

# 14. Fixed vs Sliding vs Token vs Leaky

You should be able to explain this from memory:

```text
Fixed Window
    ↓
Simple counter per time window

Sliding Window
    ↓
Count requests over a moving time period

Token Bucket
    ↓
Requests consume tokens
Tokens refill over time
Allows controlled bursts

Leaky Bucket
    ↓
Requests enter queue
Queue drains at fixed rate
Smooths traffic
```

# 15. Distributed Rate Limiting

This is where system design becomes interesting.

Suppose we have:

```text
              Load Balancer
             /      |      \
            ↓       ↓       ↓
         App 1    App 2    App 3
```

User limit:

```text
100 requests/minute
```

If each application maintains its own counter:

```text
App 1 → 100
App 2 → 100
App 3 → 100
```

we have a problem.

The global limit is no longer 100.

It's effectively:

```text
300
```

So we need shared state.

---

# 16. Redis to the rescue

A common architecture:

```text
                  ┌──────────┐
                  │  Redis   │
                  └────▲─────┘
                       │
                       │
              ┌────────┴────────┐
              │                 │
           App 1             App 2
              │                 │
              └──────┬──────────┘
                     │
                  App 3
```

All application instances consult the same Redis-based limiter.

For example:

```text
rate:user:123
```

could maintain the user's rate-limit state.

---

# 17. Redis example

Suppose:

```text
User = 123
Limit = 100 requests/minute
```

Redis could maintain something like:

```text
rate:user:123 → 73
```

Meaning:

```text
73 requests used
```

As requests arrive:

```text
73
 ↓
74
 ↓
75
 ↓
...
 ↓
100
 ↓
101 → ❌
```

And the key expires after the relevant window.

---

# 18. But there is an important distributed-systems problem

What if two servers simultaneously do:

```text
App 1:
read counter = 99

App 2:
read counter = 99
```

Both think:

```text
99 < 100
```

Both increment:

```text
100
```

Now we've potentially allowed two requests when only one should have been allowed.

This is a **race condition**.

So rate limiting needs an **atomic operation**.

Redis is useful because operations can be made atomic, commonly using:

```text
INCR
EXPIRE
Lua scripts
```

or other atomic server-side operations depending on the algorithm.

# 20. What happens when a request is rejected?

Usually:

```http
HTTP/1.1 429 Too Many Requests
```

You can also provide:

```http
Retry-After: 30
```

Meaning:

> Try again after 30 seconds.

Modern APIs may also expose rate-limit information through headers, for example:

```text
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

# 22. A very important distinction: Rate limiting vs throttling

People often use these terms interchangeably, but conceptually:

### Rate limiting

Controls **how many requests are allowed**.

```text
100 req/min
```

### Throttling

Controls **how quickly work is processed**.

For example:

```text
Incoming:
1000 requests/sec

Processing:
100 requests/sec
```

The excess may be queued, delayed, or rejected depending on the design.

A leaky bucket is closely related to traffic shaping/throttling.

# 23. What I want you to remember for interviews

Don't memorize every implementation detail.

Remember this decision tree:

```text
                 Need rate limiting?
                        │
                        ↓
               What granularity?
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
         IP            User         API key
          │             │             │
          └─────────────┼─────────────┘
                        ↓
                 Choose algorithm
                        │
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
 Fixed Window     Sliding Window    Token Bucket
       │                │                │
 Simple             More accurate     Controlled burst
       │                │                │
       └────────────────┼────────────────┘
                        ↓
                Multiple instances?
                        │
                       YES
                        ↓
                   Shared state
                        │
                      Redis
                        │
                        ↓
                  Atomic updates
```

### The four algorithms in one sentence each

**Fixed Window:**

> Count requests in fixed time intervals.

**Sliding Window:**

> Count requests over a continuously moving time interval.

**Token Bucket:**

> Requests consume replenishing tokens, allowing controlled bursts.

**Leaky Bucket:**

> Requests are processed/drained at a controlled rate, smoothing bursts.

## Your interview-level takeaway

If an interviewer asks **"How would you rate-limit a distributed API?"**, a strong answer would be:

> "I'd put rate limiting at the API Gateway so excessive requests are rejected before reaching the application tier. For a distributed deployment, I'd use a shared Redis-backed rate limiter so all application instances see the same limit. I'd likely use a Token Bucket when controlled bursts are acceptable. Redis operations need to be atomic to avoid race conditions. Requests exceeding the limit would receive HTTP 429, potentially with a Retry-After header."

That is already a **solid system-design answer**.

And importantly, this topic connects directly to the next one in your roadmap: **Topic 21 — API Gateway**, where rate limiting becomes one of the gateway's responsibilities.
