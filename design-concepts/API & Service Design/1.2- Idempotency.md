# API Idempotency

## 1. First: What does "idempotent" mean?

An operation is **idempotent** if performing it multiple times has the same final effect as performing it once.

Mathematically:

```text
f(f(x)) = f(x)
```

In API terms:

```text
Request
Request
Request
Request
```

should produce the same **final state** as:

```text
Request
```

---

# 2. Simple example

Suppose we have:

```http
PUT /users/123
```

with:

```json
{
  "name": "Rohan"
}
```

You send it once:

```text
User 123
name = Rohan
```

You send it again:

```text
User 123
name = Rohan
```

Again:

```text
User 123
name = Rohan
```

The final state is still:

```text
name = Rohan
```

So this operation is naturally idempotent.

---

# 3. Compare that with payment

Now imagine:

```http
POST /payments
```

```json
{
  "amount": 100,
  "currency": "USD",
  "account": "ABC"
}
```

First request:

```text
Client
   |
   | POST /payments
   ↓
Payment Service
   |
   ↓
Charge $100
   |
   ↓
Payment successful
```

But then something goes wrong.

The response doesn't reach the client:

```text
Client
   |
   | POST
   ↓
Payment Service
   |
   ↓
Charge $100
   |
   X
   |
Response lost
```

The client doesn't know whether the payment succeeded.

So what does a reasonable client do?

It retries.

```text
Client
   |
   | POST /payments
   ↓
Payment Service
   |
   ↓
Charge $100 AGAIN
```

Now:

```text
💰 First charge:  $100
💰 Second charge: $100

Total = $200
```

That's obviously bad.

And this is the exact failure scenario your roadmap highlights. 

---

# 4. Why did this happen?

The important thing is:

**The network doesn't guarantee that a client knows whether the server completed the operation.**

There are several possibilities:

```text
Client → Server
          ↓
       Operation
          ↓
       SUCCESS
          ↓
      Response
          X
       lost
```

From the client's perspective:

```text
"I don't know what happened."
```

It cannot distinguish:

```text
A. Server never received request
```

from:

```text
B. Server received request and succeeded
   but response was lost
```

So retrying is often necessary.

But retrying a non-idempotent operation can be dangerous.

---

# 5. Enter the Idempotency Key

The common solution for APIs such as payments is an:

```http
Idempotency-Key
```

For example:

```http
POST /payments
Idempotency-Key: 7f8e9c12-abc-456
Content-Type: application/json
```

Request:

```json
{
  "amount": 100,
  "currency": "USD",
  "account": "ABC"
}
```

The key is generated by the **client**.

---

# 6. First request

Client sends:

```http
POST /payments
Idempotency-Key: abc123
```

Payment service receives it.

It checks:

```text
Have I seen idempotency key = abc123?
```

Answer:

```text
NO
```

So it processes the payment:

```text
abc123
   ↓
Create payment
   ↓
Charge $100
   ↓
Save result
```

The server stores something conceptually like:

```text
Idempotency Key    Result
--------------------------------
abc123             Payment #789
                   SUCCESS
                   $100
```

---

# 7. Response gets lost

Unfortunately:

```text
Payment succeeds
       ↓
Response
       ↓
       X
     lost
```

The client doesn't know.

So it retries:

```http
POST /payments
Idempotency-Key: abc123
```

Notice:

**Same idempotency key.**

---

# 8. Server receives the retry

The server checks:

```text
abc123
```

and finds:

```text
Already processed!
```

Therefore:

```text
DO NOT charge again.
```

Instead, it returns the previously stored result:

```json
{
  "paymentId": "789",
  "status": "SUCCESS"
}
```

So:

```text
First request
     ↓
Payment created
     ↓
Response lost
     ↓
Retry
     ↓
Same idempotency key
     ↓
Existing result found
     ↓
Return existing result
```

Only **one payment** happened.

That's the core idea.

---

# 9. Think of the Idempotency Key as a request fingerprint

You can mentally model it as:

```text
Idempotency-Key
       ↓
"Have I already processed this logical operation?"
```

For example:

```text
abc123 → Payment #789
xyz456 → Payment #790
```

If:

```text
abc123
```

appears again:

```text
abc123 → already processed
```

Don't execute again.

---

# 10. Where do we store idempotency keys?

Usually somewhere durable.

For example:

### Database

```text
idempotency_key
payment_id
status
response
created_at
```

Example:

```text
abc123 | PAY-789 | SUCCESS | {...} | 10:30
```

This is often a good choice for financial operations because the payment and idempotency record can potentially be managed transactionally.

### Redis

You can also use Redis:

```text
SET idempotency:abc123 result EX 86400
```

This can be very fast, but you need to carefully think about:

* expiration
* durability
* failure scenarios
* consistency with the actual business operation

For critical financial operations, you generally don't want your correctness to depend solely on an ephemeral cache.

---

# 11. The really important part: Atomicity

Here's where the topic gets more interesting.

Suppose two requests arrive at almost exactly the same time:

```text
Request A
Key = abc123

Request B
Key = abc123
```

Both arrive concurrently.

If your code does:

```java
if (!exists(key)) {
    processPayment();
    save(key);
}
```

you have a race condition.

Both requests could execute:

```text
A: check → doesn't exist
B: check → doesn't exist

A: charge $100
B: charge $100
```

💥

You've charged twice.

---

# 12. You need atomic protection

You need something like:

```text
INSERT idempotency_key = abc123
```

with a **unique constraint**.

For example:

```sql
CREATE TABLE idempotency_keys (
    idempotency_key VARCHAR(100) PRIMARY KEY,
    status VARCHAR(20),
    response JSON,
    created_at TIMESTAMP
);
```

Now:

```text
Request A
   ↓
INSERT abc123
   ↓
SUCCESS
   ↓
process payment
```

While:

```text
Request B
   ↓
INSERT abc123
   ↓
PRIMARY KEY VIOLATION
   ↓
already being/was processed
```

This prevents both requests from independently creating the same idempotency record.

---

# 13. But there's another subtle problem

Imagine:

```text
INSERT idempotency key
       ↓
Process payment
       ↓
Database crashes
```

What happens?

You need to design the state machine carefully.

For example:

```text
PENDING
   ↓
PROCESSING
   ↓
SUCCESS
```

or:

```text
PENDING
   ↓
SUCCESS

PENDING
   ↓
FAILED
```

This becomes particularly important for distributed systems.

---

# 14. A better mental model

Think of the idempotency record as:

```text
┌─────────────────────────────┐
│ Idempotency Key             │
├─────────────────────────────┤
│ abc123                      │
│                             │
│ Status: SUCCESS             │
│                             │
│ Response: Payment #789      │
└─────────────────────────────┘
```

The key maps to the **result of the logical operation**.

So retries don't execute the operation again.

They retrieve the existing result.

---

# 15. Idempotency does NOT mean "same response every time" universally

There's an important distinction.

Idempotency is about the **effect on state**.

For example:

```http
PUT /users/123
```

Sending it twice results in:

```text
name = Rohan
```

But HTTP responses could technically differ:

```text
First:
200 OK

Second:
200 OK
```

or perhaps:

```text
First:
200 OK

Second:
204 No Content
```

The important concept is that the repeated operation doesn't create another state change.

For APIs using idempotency keys, however, it's common and useful to return the same stored business result for retries.

---

# 16. HTTP methods and idempotency

This is a classic interview question.

Generally:

| HTTP Method | Idempotent?   |
| ----------- | ------------- |
| GET         | ✅ Yes         |
| PUT         | ✅ Yes         |
| DELETE      | ✅ Yes         |
| POST        | ❌ Usually not |
| PATCH       | ⚠️ Depends    |

### GET

```http
GET /users/123
```

Calling it 100 times doesn't change the resource.

---

### PUT

```http
PUT /users/123
```

```json
{
  "name": "Rohan"
}
```

Repeated requests result in the same state.

---

### DELETE

```http
DELETE /users/123
```

First:

```text
User exists → deleted
```

Second:

```text
User doesn't exist → still doesn't exist
```

The final state is the same.

---

### POST

```http
POST /orders
```

Each request might create a new order:

```text
POST → Order #1
POST → Order #2
POST → Order #3
```

Therefore POST is **not inherently idempotent**.

But you can make a particular POST operation idempotent by using an idempotency key.

---

# 17. Important distinction: HTTP idempotency vs Idempotency-Key

Don't mix these up.

HTTP specification semantics say some methods are inherently idempotent.

For example:

```text
PUT
DELETE
GET
```

But:

```text
POST
```

is not inherently idempotent.

An application can make POST effectively idempotent using:

```http
Idempotency-Key: abc123
```

So:

```text
POST
  +
Idempotency-Key
  ↓
Effectively idempotent operation
```

# 18. Real-world payment flow

Let's design it properly.

```text
Client
  |
  | POST /payments
  | Idempotency-Key: abc123
  ↓
API Gateway
  |
  ↓
Payment Service
  |
  ├── Check idempotency record
  |
  ├── Not found
  |
  ├── Create idempotency record
  |
  ├── Process payment
  |
  ├── Save result
  |
  └── Return response
```

Retry:

```text
Client
  |
  | POST /payments
  | Idempotency-Key: abc123
  ↓
Payment Service
  |
  ├── Check idempotency record
  |
  ├── FOUND
  |
  └── Return previous result
```

No second payment.

---

# 19. What if the client changes the request?

This is another important detail.

Suppose:

### First request

```http
Idempotency-Key: abc123
```

```json
{
  "amount": 100
}
```

Then someone sends:

```http
Idempotency-Key: abc123
```

but:

```json
{
  "amount": 500
}
```

That's suspicious.

The server should not blindly say:

```text
abc123 exists → return old response
```

A robust implementation can store a **request fingerprint/hash**:

```text
Key: abc123

Request hash:
SHA256(amount=100,...)

Result:
Payment #789
```

Then the retry must match:

```text
abc123
+
same request parameters
```

Otherwise:

```http
409 Conflict
```

or another appropriate error.

Conceptually:

```text
Same key + same request
        ↓
      retry
        ↓
return previous result


Same key + different request
        ↓
    invalid reuse
```

---

# 20. How long should we keep idempotency keys?

You don't necessarily keep them forever.

For example:

```text
Idempotency key TTL = 24 hours
```

or:

```text
7 days
```

depends on the business operation.

Why?

Because storage grows:

```text
1 million requests/day
×
365 days
=
365 million records
```

You need a retention policy.

For financial systems, the retention period should be chosen based on business requirements, retry windows, audit requirements, and compliance—not just convenience.

---

# 21. Idempotency vs duplicate detection

They're related but slightly different.

### Duplicate detection

> "Have I seen this request before?"

### Idempotency

> "If I see this logical operation again, ensure it doesn't produce another effect."

Idempotency is the broader concept.

---

# 22. Idempotency doesn't solve every duplicate problem

Suppose:

```text
Payment Service
      ↓
Bank
```

You successfully charge the bank:

```text
Payment Service → Bank
                  ↓
               SUCCESS
```

But then Payment Service crashes **before saving its idempotency result**.

Now you have:

```text
Bank:
Payment happened ✅

Payment Service:
Doesn't know ❓
```

A retry could potentially charge again.

This is why real payment systems require deeper mechanisms involving:

* transaction boundaries
* durable payment states
* provider-side idempotency
* reconciliation
* unique business identifiers
* recovery workflows

So don't think:

> "I added Redis idempotency and payments are magically solved."

They aren't. 😄

---

# 23. Idempotency in distributed systems

This is where the topic connects directly to the later parts of your roadmap.

Imagine:

```text
Client
  ↓
Order Service
  ↓
Payment Service
  ↓
Bank
```

Network failures can happen anywhere:

```text
Client → Order Service
             ↓
       Payment Service
             ↓
           Bank
             X
         response lost
```

Retries are inevitable in distributed systems.

Therefore:

```text
Retries
   +
Non-idempotent operations
   =
Potential duplicate effects
```

That's why idempotency is such an important API-design pattern.

---

# 24. Idempotency + retries

This relationship is worth memorizing:

```text
Network failure
       ↓
Client doesn't know result
       ↓
Retry
       ↓
Could execute operation twice
       ↓
Idempotency protection
       ↓
Execute logical operation once
```

So whenever you design:

```text
POST /payments
POST /orders
POST /transfers
POST /subscriptions
```

ask yourself:

> **What happens if the client retries this request?**

That's a fantastic system-design habit.

# 25. Spring Boot example

Since you're working with Spring Boot, imagine:

```java
@PostMapping("/payments")
public PaymentResponse createPayment(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest request) {

    // 1. Check existing request

    // 2. If already processed,
    //    return previous response

    // 3. Otherwise process payment

    // 4. Save result against key

    // 5. Return response
}
```

The database could have:

```sql
CREATE TABLE idempotency_record (
    idempotency_key VARCHAR(100) PRIMARY KEY,
    request_hash VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL,
    response JSON,
    created_at TIMESTAMP NOT NULL
);
```

Then conceptually:

```java
String hash = hash(request);

Optional<IdempotencyRecord> existing =
        repository.findById(key);

if (existing.isPresent()) {

    validateSameRequest(existing.get(), hash);

    return existing.get().getResponse();
}

Payment payment = paymentService.process(request);

repository.save(
    new IdempotencyRecord(
        key,
        hash,
        "SUCCESS",
        payment
    )
);

return payment;
```

**But:** don't implement it exactly like this in production without addressing concurrent requests and atomicity. The `find → process → save` sequence itself can race.

---

# 26. The interview answer

If the interviewer asks:

> **"How would you make a payment API idempotent?"**

A strong answer would be:

> "I'd require the client to send a unique idempotency key for each logical payment attempt. The payment service would persist that key with a unique constraint, along with the request fingerprint, processing status, and result. If the same key is received again with the same request, I'd return the previously stored result instead of processing the payment again. Concurrent requests using the same key must be handled atomically to prevent both from executing. I'd also define an appropriate retention period for idempotency records."

That's a **solid system-design answer**.

# 27. The mental model

Remember this diagram:

```text
             Client
                |
                | POST /payments
                | Idempotency-Key: ABC
                ↓
        ┌───────────────────┐
        │ Payment Service   │
        └─────────┬─────────┘
                  │
          ┌───────▼────────┐
          │ Idempotency DB │
          └───────┬────────┘
                  │
             Key = ABC?
             /          \
           NO            YES
           |              |
           ↓              ↓
       Process         Return
       payment        saved result
           |
           ↓
       Save result
           |
           ↓
        Response
```

The one sentence I'd want you to remember is:

> **Idempotency makes retries safe by ensuring that repeated requests for the same logical operation don't produce duplicate side effects.**

And the most important practical example is:

```text
POST /payments
+
Idempotency-Key
+
durable storage
+
unique constraint
+
atomic/concurrent handling
=
safe retryable API
```

That last part—**"atomic/concurrent handling"**—is the bit many candidates forget, and it's where a basic answer becomes a strong system-design answer.
