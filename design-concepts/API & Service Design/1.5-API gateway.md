## 1. What is an API Gateway?

An API Gateway is a single entry point through which clients access backend services in a distributed system.

Imagine you're building an e-commerce application with these microservices:

- User Service — manages users and profiles.
- Product Service — manages products and inventory information.
- Order Service — creates and tracks orders.
- Payment Service — processes payments.

Without an API Gateway, the frontend may need to know the address of every service.

### Without an API Gateway

React Frontend

Calls multiple backend addresses directly

User Service

Port 8081

Product Service

Port 8082

Order Service

Port 8083

Payment Service

Port 8084

This can work, but the frontend must know where each service lives. Changing service addresses, enforcing common security rules, and handling cross-cutting concerns become more complicated.

Now introduce an API Gateway.

### With an API Gateway

React Frontend

Calls api.shop.com

## API Gateway

Routing · Security · Rate limiting · Logging

Routes each request to the appropriate service

User Service

Product Service

Order Service

Payment Service

The frontend only needs to know the gateway's address. The gateway handles how to reach the backend services.

Key interview definition: An API Gateway is an edge component that centralizes client access to backend APIs and can apply routing, security, traffic-management, and request-processing policies.

## 2. How does an API Gateway work?

Suppose the user clicks Place Order in your React application.

The frontend sends:

```
POST /api/orders
Host: api.shop.com
Authorization: Bearer <access-token>
Content-Type: application/json
```

The gateway processes the request in a sequence similar to this:

### 1

Receive request

Accept the request at the public API endpoint.

### 2

Authenticate

Validate the access token, or delegate validation to an identity component.

### 3

Apply policies

Check applicable authorization rules, rate limits, and request constraints.

### 4

Route request

Forward POST /api/orders to the Order Service.

### 5

Return response

Send the service response back to the client, subject to configured response handling.

The exact sequence depends on the gateway and its configuration. For example, authentication can be handled at the gateway, at the backend, or at both layers.

Notice that the React application doesn't need to know the Order Service's internal hostname or port.

## 3. The six responsibilities of an API Gateway

These are the responsibilities you should be able to explain in an interview.

### 1. Routing

Routing means deciding which backend service should receive a request.

For example:

| Incoming request       | Destination     |
| ---------------------- | --------------- |
| `GET /api/products/10` | Product Service |
| `POST /api/orders`     | Order Service   |
| `GET /api/users/5`     | User Service    |
| `POST /api/payments`   | Payment Service |

The gateway can route using paths, HTTP methods, hostnames, headers, or other configured rules.

An example configuration might look conceptually like this:

```
routes:
  - path: /api/products/**
    service: product-service

  - path: /api/orders/**
    service: order-service

  - path: /api/payments/**
    service: payment-service
```

This is illustrative pseudoconfiguration; the actual syntax varies by gateway.

Why is this useful? If the Product Service moves from one host to another, you can update the gateway's routing configuration without changing the frontend's API URL.

### 2. Authentication

Authentication answers: Who are you?

Suppose the client sends a JWT access token:

```
Authorization: Bearer eyJ...
```

The gateway can validate the token's signature, expiry, issuer, and other required claims before forwarding the request.

If the token is invalid, the gateway can return:

```
HTTP/1.1 401 Unauthorized
```

This connects directly to your OAuth2/OIDC learning.

For example, with Keycloak:

```
React SPA
    |
    | Access token
    v
API Gateway ---------> Keycloak (when needed)
    |
    | Validated request
    v
Order Service
```

The gateway doesn't necessarily contact Keycloak on every request. For JWTs, it can often validate tokens locally using trusted public keys cached from the identity provider.

### 3. Authorization

Authorization answers: What are you allowed to do?

Imagine a valid token contains:

```
{
  "sub": "user-123",
  "roles": ["CUSTOMER"]
}
```

The user is authenticated, but that doesn't mean they can access every operation.

For example:

- `GET /api/products` — allowed for customers.
- `POST /api/orders` — allowed for customers.
- `DELETE /api/products/10` — restricted to authorized administrators.

The gateway can enforce broad access rules based on roles or scopes.

However, the gateway should not be the only authorization layer. The Order Service may need to verify that an order belongs to the requesting user. The Product Service may need to enforce ownership or business-specific permissions.

This is particularly important for preventing broken object-level authorization.

### 4. Rate limiting

Rate limiting restricts how many requests a client can make within a defined period.

For example:

```
Client A → 100 requests/minute → Allowed
Client A → 101st request       → Rejected
```

The gateway can return:

```
HTTP/1.1 429 Too Many Requests
```

This protects backend services from excessive traffic and abuse.

Rate limits might be applied per:

- User or API key
- IP address
- Client application
- Endpoint
- Subscription or customer tier

In a distributed deployment with multiple gateway instances, a shared store such as Redis may be needed for consistent global limits.

Remember our previous rate-limiting topic? The gateway is one place where algorithms such as token bucket or sliding window can be enforced.

### 5. Request and response transformation

The gateway can modify requests or responses as they pass through.

Examples include:

- Rewriting `/api/v1/products` to an internal service path.
- Adding correlation IDs.
- Removing or adding selected headers.
- Converting between supported payload formats.
- Adapting a response to a client-specific contract.

For example:

```
External request:
GET /api/products/10

             ↓ API Gateway

Internal request:
GET http://product-service:8080/products/10
```

The gateway can hide internal service addresses from the client.

But don't turn it into a place for complicated business logic. Pricing calculations, inventory rules, and order validation should normally remain in their respective services.

### 6. Logging and observability

The gateway is an excellent place to collect metadata about incoming requests.

For example:

```
requestId: req-789
method: POST
path: /api/orders
status: 201
latencyMs: 84
```

This helps answer questions such as:

- Which endpoints receive the most traffic?
- How many requests fail?
- Which backend service is slow?
- Are particular clients generating excessive traffic?

The gateway should avoid logging access tokens, passwords, payment details, or other sensitive data.

Correlation IDs and distributed tracing can connect the gateway request to downstream calls, allowing you to follow one request across multiple services.

## 4. API Gateway vs Reverse Proxy vs Load Balancer

This is a classic system-design interview question.

These concepts overlap, so think in terms of their primary responsibilities, not rigid definitions.

| Component     | Primary responsibility                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| Reverse proxy | Receives requests on behalf of backend servers and forwards them                                                     |
| Load balancer | Distributes traffic across multiple server instances                                                                 |
| API Gateway   | Provides an API entry point with routing and API policies such as authentication, rate limiting, and transformations |

Consider this architecture:

Clients

### Load Balancer

Distributes traffic across gateway instances

Gateway 1

Gateway 2

Backend Services

Users

Orders

Products

Payments

A gateway can itself run behind a load balancer, and a gateway product can also perform load balancing and reverse-proxy functions. You don't necessarily need three separate products.

The key distinction is that an API Gateway adds API-aware policies to request forwarding.

## 5. Where does an API Gateway fit with Spring Boot?

For your Java/Spring Boot background, a common technology to explore is Spring Cloud Gateway.

It can provide routing, filters, security integration, and request processing.

A practical architecture could be:

```
React SPA
    |
    v
Spring Cloud Gateway
    |
    +----> User Service     (Spring Boot)
    |
    +----> Product Service  (Spring Boot)
    |
    +----> Order Service    (Spring Boot)
    |
    +----> Payment Service  (Spring Boot)
```

Example route configuration:

```
spring:
  cloud:
    gateway:
      routes:
        - id: product-service
          uri: http://localhost:8082
          predicates:
            - Path=/api/products/**
          filters:
            - StripPrefix=1

        - id: order-service
          uri: http://localhost:8083
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
```

With this illustrative configuration:

- `/api/products/10` is forwarded to `http://localhost:8082/products/10`.
- `/api/orders/20` is forwarded to `http://localhost:8083/orders/20`.

`StripPrefix=1` removes the first path segment, which is `api`.

This example demonstrates routing only; it does not configure authentication, authorization, or rate limiting.

## 6. What problems does an API Gateway introduce?

A good system designer doesn't just list benefits. They also understand trade-offs.

Single point of failure: If all client traffic depends on one gateway instance, its failure can make the whole API unavailable. Run multiple instances and design health checks and failover.

Extra latency: Every request passes through another component. Keep gateway processing efficient and avoid unnecessary network calls.

Bottleneck under high traffic: The gateway itself must scale to handle throughput, connections, and resource consumption.

Configuration complexity: Routing rules, security policies, and transformations can become difficult to manage as the number of services grows.

Too much business logic: Putting order processing or other domain logic in the gateway couples unrelated concerns and creates a difficult-to-maintain component.

Security assumptions: A request coming from the gateway is not automatically trustworthy. Backend services should protect their own sensitive operations and validate relevant identity and authorization information.

One more important point: an API Gateway does not automatically make a system highly available or secure. Those properties depend on its deployment, configuration, and the design of the entire system.

## 8. Your interview takeaway

If an interviewer asks, "Why do we need an API Gateway in a microservices architecture?", a strong answer is:

> An API Gateway provides a common entry point for clients and routes requests to the appropriate backend services. It centralizes cross-cutting API concerns such as authentication, authorization policies, rate limiting, request transformation, and logging. It hides internal service topology from clients and simplifies client integration. However, it introduces an additional network hop and must itself be designed for scalability, security, and high availability.
