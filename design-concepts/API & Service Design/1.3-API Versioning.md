
# Why do we need API versioning?

Imagine you have:

```http
GET /api/users/123
```

Today it returns:

```json
{
  "id": 123,
  "name": "Rohan",
  "email": "rohan@example.com"
}
```

You have 100 clients using this API.

Now you want to change the response to:

```json
{
  "userId": 123,
  "fullName": "Rohan",
  "emailAddress": "rohan@example.com"
}
```

Your frontend/mobile/partner applications may still expect:

```javascript
response.name
```

Suddenly:

```javascript
response.name // undefined
```

💥 Existing clients break.

That's where **API versioning** comes in.

---

# 2. What exactly is a version?

Instead of changing the existing contract:

```http
GET /api/users/123
```

you introduce a new contract:

```http
GET /api/v2/users/123
```

Now you can have:

```text
/api/v1/users/123
        ↓
Old response contract

/api/v2/users/123
        ↓
New response contract
```

Both can coexist.

```text
                    ┌──> V1 clients
                    │
Client ──> API ─────┤
                    │
                    └──> V2 clients
```

This gives existing clients time to migrate.

---

# 3. What changes require versioning?

This is an important interview question.

### Usually breaking changes require a new version.

For example:

### Removing a field

V1:

```json
{
  "id": 1,
  "name": "Rohan",
  "email": "..."
}
```

V2:

```json
{
  "id": 1,
  "name": "Rohan"
}
```

A client depending on `email` can break.

---

### Renaming a field

```text
name → fullName
```

Breaking.

---

### Changing the type

V1:

```json
{
  "age": 30
}
```

V2:

```json
{
  "age": "30"
}
```

Potentially breaking.

---

### Changing the meaning of a field

Suppose:

```json
{
  "status": "ACTIVE"
}
```

Originally means:

> Account is currently active.

Then you change it to mean:

> Account is active and has completed verification.

That's potentially a breaking semantic change even though the JSON structure hasn't changed.

---

# 4. What does NOT necessarily require a new version?

Adding an optional field is usually backward compatible.

V1:

```json
{
  "id": 123,
  "name": "Rohan"
}
```

Later:

```json
{
  "id": 123,
  "name": "Rohan",
  "phone": "123456"
}
```

Old clients generally continue working because they can ignore unknown fields.

So:

```text
Adding optional field      → usually non-breaking
Removing field             → breaking
Renaming field             → breaking
Changing field type        → breaking
Changing semantics         → potentially breaking
```

This distinction is **very important in API design**.

---

# 5. Where should we put the version?

There are several common strategies.

## Strategy 1 — URI/path versioning

Probably the easiest to understand:

```http
GET /api/v1/users/123
GET /api/v2/users/123
```

Example:

```text
/api/v1/orders
/api/v2/orders
```

### Advantages

Very obvious.

You can immediately see which API contract you're using.

```text
Client A → /v1/orders
Client B → /v2/orders
```

It's also easy to implement with Spring Boot routing.

### Disadvantage

Your URL contains version information.

---

# 6. Spring Boot example

You can literally have:

```java
@RestController
@RequestMapping("/api/v1/users")
class UserControllerV1 {

    @GetMapping("/{id}")
    public UserResponseV1 getUser(@PathVariable Long id) {
        ...
    }
}
```

And:

```java
@RestController
@RequestMapping("/api/v2/users")
class UserControllerV2 {

    @GetMapping("/{id}")
    public UserResponseV2 getUser(@PathVariable Long id) {
        ...
    }
}
```

So:

```http
GET /api/v1/users/123
```

hits:

```text
UserControllerV1
```

while:

```http
GET /api/v2/users/123
```

hits:

```text
UserControllerV2
```

---

# 7. Strategy 2 — Query parameter

Another approach:

```http
GET /api/users/123?version=1
```

or:

```http
GET /api/users/123?version=2
```

### Pros

The URL path stays the same.

### Cons

It's generally less clean and less explicit.

For example:

```http
/api/users/123
```

doesn't tell you which contract you're getting unless you inspect the query parameter.

I would generally prefer URI versioning for a straightforward public API unless there's a specific reason to use another strategy.

---

# 8. Strategy 3 — Header versioning

You can put the version in a header.

For example:

```http
GET /api/users/123
Accept: application/vnd.mycompany.user.v2+json
```

Now the URL doesn't change.

The client tells the server:

> "Give me version 2 of this representation."

This is sometimes called **media type/header versioning**.

---

# 9. Strategy 4 — Custom header

Another possibility:

```http
GET /api/users/123
API-Version: 2
```

The server uses that header to determine which contract to return.

Again, the URL stays:

```text
/api/users/123
```

---

# 10. Which one should you choose?

For interviews, I'd know these four:

| Strategy    | Example                               | Main idea                 |
| ----------- | ------------------------------------- | ------------------------- |
| URI         | `/api/v1/users`                       | Version in URL            |
| Query param | `/api/users?version=1`                | Version in query          |
| Header      | `API-Version: 1`                      | Version in header         |
| Media type  | `Accept: application/vnd.api.v1+json` | Version in representation |

For most practical REST APIs, **URI versioning is simple and explicit**:

```http
/api/v1/users
/api/v2/users
```

But there's no universal "correct" choice. The important system-design consideration is **consistent API evolution and backwards compatibility**.

---

# 11. Very important: Don't version everything unnecessarily

Suppose you have:

```http
GET /api/v1/users
```

You add:

```json
{
    "phoneNumber": "..."
}
```

You don't necessarily need:

```http
GET /api/v2/users
```

just because the response changed.

If the change is backward compatible, keep V1.

Think:

```text
Is this change breaking?

       |
   ┌───┴────┐
   |        |
  No       Yes
   |        |
Same      New API
version   version
```

This prevents your system from becoming:

```text
v1
v2
v3
v4
v5
...
```

with dozens of nearly identical APIs. 😄

---

# 12. What happens to V1?

This is where API versioning becomes a **real system-design problem**.

Suppose:

```text
2026
  ↓
V1 released

2027
  ↓
V2 released
```

Do you immediately delete V1?

Usually **no**.

You need a migration/deprecation strategy.

For example:

```text
V1
 │
 │  supported
 │
 ▼
V2 released
 │
 │
 │  V1 deprecated
 │
 ▼
Migration period
 │
 │
 ▼
V1 sunset
```

Clients get time to migrate.

---

# 13. Deprecation vs removal

These are different.

### Deprecation

Means:

> "This API is old. Don't use it for new development. Migrate to V2."

But:

```http
/api/v1/users
```

still works.

### Removal / sunset

Means:

> "V1 is no longer available."

Now:

```http
GET /api/v1/users
```

might return:

```http
410 Gone
```

or another documented error.

---

# 14. Don't expose database versions as API versions

This is a subtle but important architecture point.

Suppose your database changes:

```text
users table
    ↓
add phone_number column
```

That **doesn't automatically mean**:

```text
API V1 → API V2
```

Your API contract and database schema are separate concerns.

You might have:

```text
                ┌── API V1
Clients ────────┤
                └── API V2
                      |
                      ↓
                 Service layer
                      |
                      ↓
                  DB schema
```

Both V1 and V2 can potentially use the same underlying service/database.

---

# 15. A better architecture

Avoid duplicating your entire business logic:

```text
V1 Controller
     ↓
V1 Service
     ↓
V1 Repository
```

and:

```text
V2 Controller
     ↓
V2 Service
     ↓
V2 Repository
```

You often want:

```text
                 ┌── V1 Controller
                 │
Client ──────────┤
                 │
                 └── V2 Controller
                        |
                        ↓
                  Common Service
                        |
                        ↓
                    Repository
                        |
                        ↓
                       DB
```

The controllers/adapters can translate between API contracts and your internal domain model.

For example:

```text
V1 Response
{
    "name": "Rohan"
}

        ↓ mapping

Internal User
{
    id: 123,
    firstName: "Rohan",
    ...
}

        ↓ mapping

V2 Response
{
    "fullName": "Rohan"
}
```

This keeps version-specific concerns near the API boundary.

---

# 16. API versioning vs application versioning

Don't confuse:

```text
API version
```

with:

```text
Application version
```

Your application might be:

```text
payment-service 5.7.2
```

while its API exposes:

```text
/v1/payments
/v2/payments
```

The application version is about the deployed software.

The API version is about the **client-facing contract**.

---

# 17. API Gateway and versioning

This becomes particularly interesting in your next topic: **API Gateway**.

You could have:

```text
                    ┌── Payment Service V1
Client ──> Gateway ┤
                    └── Payment Service V2
```

The gateway can route:

```http
/api/v1/payments
        ↓
Payment Service V1
```

and:

```http
/api/v2/payments
        ↓
Payment Service V2
```

This is one reason API versioning is an important system-design topic rather than just a controller annotation.

---

# 18. Interview scenario

Imagine an interviewer asks:

> "You have 50 million mobile users. You need to introduce a breaking change to the `/users` API. How would you do it?"

A strong answer would be:

> "I would introduce a new API version rather than modifying the existing contract in place. For example, `/api/v2/users`. V1 would continue serving existing clients while new clients migrate to V2. I'd keep the version-specific representation logic at the API boundary and reuse the underlying business/domain logic where possible. I'd establish a deprecation period, communicate a sunset date, monitor V1 usage, and remove V1 only after the migration window."

That's a **very good system-design answer**.

---

# 19. The mental model

Remember API versioning as:

```text
           API CONTRACT
                |
        ┌───────┴───────┐
        |               |
       V1              V2
        |               |
 Old clients        New clients
        |               |
        └───────┬───────┘
                |
          Common domain
                |
             Database
```

The **version belongs to the contract**, not necessarily to your business logic or database.

## 🔥 What I'd remember for interviews

There are **5 things** I'd keep in your notes:

1. **Version when you introduce breaking API contract changes.**
2. Common strategies: **URI, query parameter, header, media type**.
3. **Don't create a new version for every backward-compatible change.**
4. Keep old versions during a **deprecation/migration period**.
5. Keep version-specific mapping at the **API boundary** and reuse common business logic where possible.

And the one-liner:

> **API versioning allows an API to evolve while preserving compatibility with existing clients.**
