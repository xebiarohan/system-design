
# API Pagination

Imagine you have:

```text
GET /api/users
```

and your database contains **10 million users**.

You obviously don't want the API to return all 10 million:

```json
{
  "users": [
    "... 10 million users ..."
  ]
}
```

Instead, the client asks for a **small portion** of the data.

That's pagination.

```text
10,000,000 users

┌────────────────┐
│ Users 1 - 20   │ → Page 1
├────────────────┤
│ Users 21 - 40  │ → Page 2
├────────────────┤
│ Users 41 - 60  │ → Page 3
├────────────────┤
│      ...       │
└────────────────┘
```

The interesting part is **how the server determines which 20 records to return**.

That's where the three approaches differ.

---

# 1. Why do we need pagination?

There are several reasons.

### 1. Response size

Returning thousands/millions of records creates huge HTTP responses.

### 2. Database load

A query returning millions of rows consumes:

* CPU
* memory
* I/O
* network bandwidth

### 3. API latency

Larger responses take longer to:

* query
* serialize
* transfer
* deserialize

### 4. Client performance

Imagine a React application receiving 100,000 products.

Rendering that list is going to be... unpleasant. 😄

### 5. Scalability

Pagination allows the API to provide predictable amounts of data per request.

---

# 2. Offset Pagination

This is the simplest and probably the first pagination style you've seen.

Suppose:

```text
Page size = 20
```

The client sends:

```http
GET /api/users?page=0&size=20
```

The server executes something conceptually like:

```sql
SELECT *
FROM users
ORDER BY id
LIMIT 20
OFFSET 0;
```

For page 2:

```http
GET /api/users?page=1&size=20
```

```sql
SELECT *
FROM users
ORDER BY id
LIMIT 20
OFFSET 20;
```

Page 3:

```http
GET /api/users?page=2&size=20
```

```sql
SELECT *
FROM users
ORDER BY id
LIMIT 20
OFFSET 40;
```

So:

```text
page = 0 → OFFSET 0
page = 1 → OFFSET 20
page = 2 → OFFSET 40
page = 3 → OFFSET 60
```

---

# 3. Typical REST API

A Spring Boot API might look like:

```http
GET /api/users?page=0&size=20
```

Response:

```json
{
  "content": [
    {
      "id": 1,
      "name": "Alice"
    },
    {
      "id": 2,
      "name": "Bob"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1000,
  "totalPages": 50
}
```

Spring Data makes this particularly convenient:

```java
@GetMapping("/users")
public Page<User> getUsers(
        @RequestParam int page,
        @RequestParam int size) {

    Pageable pageable =
        PageRequest.of(page, size);

    return userRepository.findAll(pageable);
}
```

This is one reason offset pagination is extremely common in CRUD applications.

---

# 4. The big problem with Offset Pagination

Offset pagination looks great initially.

But it has a major problem at **large offsets**.

Suppose we want:

```sql
LIMIT 20 OFFSET 9,000,000
```

The database may need to scan/skip a huge number of records before finding the 20 records you actually want.

Conceptually:

```text
1
2
3
4
5
...
8,999,999   ← skip
9,000,000   ← finally start returning
9,000,001
...
```

That's inefficient for very large datasets.

So:

> **Offset pagination is simple, but performance can degrade as the offset becomes large.**

---

# 5. Another problem — changing data

This is actually an even more important system-design issue.

Imagine:

```text
Page size = 3

Page 1:

1 Alice
2 Bob
3 Charlie
```

You request page 2:

```text
4 David
5 Emma
6 Frank
```

But before you request page 2, a new user is inserted at the beginning:

```text
0 John
1 Alice
2 Bob
3 Charlie
4 David
5 Emma
6 Frank
```

Now your second request:

```sql
OFFSET 3 LIMIT 3
```

returns:

```text
3 Charlie
4 David
5 Emma
```

You see **Charlie twice**.

That's called a pagination consistency problem.

Similarly, records can be skipped if records are deleted between requests.

---

# 6. Cursor Pagination

Cursor pagination solves many of these problems.

Instead of saying:

> "Give me records starting from position 1,000."

we say:

> "Give me records after this particular record."

For example:

```http
GET /api/users?limit=20
```

Response:

```json
{
  "data": [
    {
      "id": 101,
      "name": "Alice"
    },
    {
      "id": 102,
      "name": "Bob"
    }
  ],
  "nextCursor": "eyJpZCI6MTAyfQ"
}
```

The client then sends:

```http
GET /api/users?limit=20&cursor=eyJpZCI6MTAyfQ
```

The server uses the cursor to determine where to continue.

Conceptually:

```text
First request

        ↓
     records
        ↓
   nextCursor
        ↓
     client
        ↓
 second request
        ↓
cursor = X
        ↓
records after X
```

---

# 7. What is inside a cursor?

The cursor is usually an encoded representation of the position.

For example, internally it could represent:

```json
{
  "id": 102
}
```

But instead of exposing:

```text
?cursor=102
```

we commonly encode it:

```text
?cursor=eyJpZCI6MTAyfQ
```

The cursor can contain more than just an ID.

For example:

```json
{
  "createdAt": "2026-10-05T10:30:00Z",
  "id": 102
}
```

This becomes particularly useful when sorting by multiple fields.

---

# 8. Cursor Pagination Query

Suppose users are ordered by:

```sql
ORDER BY id ASC
```

and the cursor represents:

```text
id = 102
```

The next query can conceptually be:

```sql
SELECT *
FROM users
WHERE id > 102
ORDER BY id ASC
LIMIT 20;
```

Notice something important.

We are **not asking the database to skip 100,000 records**.

We're saying:

```text
Give me records after ID 102.
```

With an appropriate index:

```text
INDEX(id)
```

the database can efficiently locate the next records.

---

# 9. Cursor vs Offset

This is the key comparison.

### Offset

```text
GET /users?page=5000&size=20
```

Database conceptually:

```sql
OFFSET 100000
LIMIT 20
```

### Cursor

```text
GET /users?cursor=ABC&limit=20
```

Database conceptually:

```sql
WHERE id > 100000
LIMIT 20
```

The second approach scales much better for very large datasets.

---

# 10. Keyset Pagination

Now we arrive at the third term in your roadmap:

> **Keyset pagination**

Keyset pagination is closely related to cursor pagination.

The key idea is:

> Use an indexed column (or columns) as the position for the next page.

Suppose:

```text
id
---
101
102
103
104
105
```

Query:

```sql
SELECT *
FROM users
WHERE id > 105
ORDER BY id
LIMIT 20;
```

That's keyset pagination.

The "key" is:

```text
id = 105
```

---

# 11. Why Keyset is powerful

Suppose you have:

```text
100 million records
```

Offset:

```sql
OFFSET 50,000,000
```

can become expensive.

Keyset:

```sql
WHERE id > 50,000,000
LIMIT 20
```

can use an index efficiently.

Think of it like a bookmark.

### Offset

> "Go to page 2,500,000."

### Keyset

> "Continue after this record."

The second is generally much more scalable.

---

# 12. But what if we sort by createdAt?

This is where things become more interesting.

Suppose:

```sql
ORDER BY created_at DESC
```

You might try:

```sql
WHERE created_at < '2026-10-05T10:30:00'
```

But what if two records have the exact same timestamp?

Example:

```text
id    created_at
101   10:30:00
102   10:30:00
103   10:29:59
```

If you only use:

```text
created_at
```

you can potentially get duplicates or miss records.

So we introduce a **tie-breaker**.

---

# 13. Composite Keyset Pagination

Use:

```text
created_at + id
```

Ordering:

```sql
ORDER BY created_at DESC, id DESC
```

Then the next page condition becomes something like:

```sql
WHERE
    created_at < :lastCreatedAt
    OR (
        created_at = :lastCreatedAt
        AND id < :lastId
    )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

And ideally the database has a matching composite index:

```sql
CREATE INDEX idx_users_created_id
ON users(created_at DESC, id DESC);
```

This is a **very important system-design concept**.

---

# 14. Cursor vs Keyset — are they the same?

You'll see people use these terms somewhat interchangeably, but conceptually it's useful to distinguish them.

### Keyset pagination

Describes the **database/query technique**:

```sql
WHERE id > :lastId
ORDER BY id
LIMIT 20
```

### Cursor pagination

Describes the **API mechanism**:

```http
GET /users?cursor=abc123
```

The cursor might internally contain:

```json
{
  "lastId": 105
}
```

So you can think:

```text
Cursor pagination
       ↓
API-level concept
       ↓
cursor token
       ↓
Keyset query
       ↓
database
```

A cursor API can use keyset pagination underneath.

---

# 15. Important: Cursor doesn't necessarily mean keyset

A cursor could technically represent other state or a database position.

But for typical REST APIs backed by relational databases, a very common design is:

```text
Cursor API
     ↓
decode cursor
     ↓
extract last sort key
     ↓
keyset query
     ↓
database
```

That's the pattern I'd recommend you remember for interviews.

---

# 16. Pagination with Sorting

Pagination and sorting are tightly connected.

Suppose:

```http
GET /users?sort=name&limit=20
```

If you want cursor/keyset pagination, you need a deterministic ordering.

For example:

```sql
ORDER BY name ASC, id ASC
```

Why include `id`?

Because `name` isn't necessarily unique.

You might have:

```text
Alice → id 10
Alice → id 27
Alice → id 51
Bob   → id 72
```

So:

```text
name
```

alone isn't enough to uniquely identify the position.

Use:

```text
name + id
```

as the ordering key.

---

# 17. API Response Design

For cursor pagination, a common response is:

```json
{
  "data": [
    {
      "id": 101,
      "name": "Alice"
    },
    {
      "id": 102,
      "name": "Bob"
    }
  ],
  "pagination": {
    "nextCursor": "eyJpZCI6MTAyfQ",
    "hasNext": true
  }
}
```

The client doesn't need to know what the cursor contains.

It simply does:

```text
response.nextCursor
        ↓
next API request
```

This is nice because the server controls the pagination implementation.

---

# 18. Should the API return `totalPages`?

With offset pagination, it's common:

```json
{
  "page": 2,
  "size": 20,
  "totalElements": 1000,
  "totalPages": 50
}
```

But cursor pagination often doesn't return:

```text
totalElements
totalPages
```

because calculating the total can itself be expensive for huge datasets.

Instead:

```json
{
  "data": [...],
  "nextCursor": "abc",
  "hasNext": true
}
```

is enough.

---

# 19. When should you use each?

This is probably the most important interview question.

| Pagination | Best suited for                                             |
| ---------- | ----------------------------------------------------------- |
| **Offset** | Small/medium datasets, admin UIs, simple CRUD               |
| **Cursor** | Large datasets, APIs consumed by clients, feeds             |
| **Keyset** | Large relational datasets where you control the query/order |

### Offset

Example:

```text
Admin users page
```

User wants:

```text
Page 1
Page 2
Page 3
...
Page 50
```

Offset is convenient.

### Cursor

Example:

```text
Twitter/X-like feed
Instagram feed
Facebook feed
```

You typically want:

```text
Give me the next 20 posts
```

rather than:

```text
Give me page 8472
```

### Keyset

Example:

```text
100 million orders
```

sorted by:

```text
created_at DESC
```

You want efficient traversal through the dataset.

# 20. A real example

Imagine an e-commerce API:

```http
GET /api/products?limit=20
```

First query:

```sql
SELECT *
FROM products
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Suppose the last record is:

```text
created_at = 2026-09-30 10:00:00
id = 500
```

Server creates a cursor representing:

```json
{
  "createdAt": "2026-09-30T10:00:00",
  "id": 500
}
```

Client asks:

```http
GET /api/products?limit=20&cursor=ABC123
```

Server decodes it and executes:

```sql
SELECT *
FROM products
WHERE
    created_at < '2026-09-30 10:00:00'
    OR (
        created_at = '2026-09-30 10:00:00'
        AND id < 500
    )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

And the process continues.

```text
Page 1
   ↓
cursor A
   ↓
Page 2
   ↓
cursor B
   ↓
Page 3
   ↓
cursor C
   ↓
...
```

# 21. One subtle problem: Cursor security

Don't blindly expose internal database information.

Bad:

```http
?cursor=500
```

Better:

```http
?cursor=eyJpZCI6NTAwfQ
```

And for sensitive/high-value APIs, the cursor can be:

* encoded
* signed
* opaque
* potentially encrypted

For example:

```text
cursor = Base64(
    JSON(lastCreatedAt, lastId)
)
```

You may additionally sign it so the client can't modify:

```text
cursor
   ↓
HMAC signature
   ↓
server validates
```

This prevents clients from tampering with pagination state.

---

# 22. What about `pageSize`?

Never blindly trust:

```http
GET /users?size=10000000
```

Otherwise someone can request a massive amount of data.

Instead impose a maximum:

```text
default = 20
maximum = 100
```

For example:

```http
GET /users?limit=50
```

is allowed.

But:

```http
GET /users?limit=1000000
```

becomes:

```text
400 Bad Request
```

or the server caps it:

```text
limit = min(requestedLimit, 100)
```

---

# 23. Pagination + Filtering + Sorting

Real APIs usually combine all three.

For example:

```http
GET /api/orders
    ?status=COMPLETED
    &sort=createdAt
    &limit=20
    &cursor=ABC123
```

Conceptually:

```text
                  API Request
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
    Filter          Sort         Pagination
       │              │              │
       └──────────────┼──────────────┘
                      ↓
                   Database
```

And your database indexes should support these access patterns.

---

# 24. System Design Interview Perspective

If an interviewer asks:

> "Design an API that returns millions of orders."

Don't immediately say:

> "I'll use `page` and `size`."

Instead think:

```text
How large is the dataset?
        ↓
How frequently does data change?
        ↓
Does the client need random page access?
        ↓
What is the sorting requirement?
        ↓
Can I use an indexed sort key?
```

Then choose.

For example:

> "For a relatively small administrative dataset, I'd use offset pagination because it's simple and supports jumping directly to a page. For a large, continuously changing dataset such as an order feed, I'd prefer cursor/keyset pagination because it avoids large offsets and provides more stable traversal."

That's a **much stronger system-design answer**.

---

# 25. The mental model I want you to remember

Think of pagination as three levels:

```text
                    PAGINATION
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       OFFSET          CURSOR         KEYSET
          │              │              │
     position/page    opaque token    sort key
          │              │              │
       OFFSET n       cursor →        WHERE >
          │              │              │
          ↓              ↓              ↓
      Simple         API-friendly    DB-efficient
      but can        and scalable    for large data
      degrade
```

And the most important distinction:

```text
OFFSET

"Skip N records."

vs

KEYSET

"Continue after this record."
```

## Interview cheat sheet

If you remember only this, you're in good shape:

**Offset**

```sql
LIMIT 20 OFFSET 10000
```

* Simple
* Easy page navigation
* Good for small/medium datasets
* Large offsets can become expensive
* Can suffer from duplicates/skips when data changes

**Cursor**

```http
GET /users?cursor=abc&limit=20
```

* API exposes a cursor
* Good for feeds and large datasets
* Avoids page-number semantics
* Usually opaque to the client

**Keyset**

```sql
WHERE id > :lastId
ORDER BY id
LIMIT 20
```

* Uses indexed sort keys
* Excellent for large datasets
* Very efficient
* Requires deterministic ordering
* Often used underneath cursor pagination

### One-liner for interviews

> **Offset pagination is position-based, while cursor/keyset pagination is continuation-based. Offset is simpler, but cursor/keyset generally scales better for large, frequently changing datasets.**

And that distinction will become especially useful when you reach **Topic 19 — Idempotency**, because that's where API design starts interacting heavily with real distributed-system failure scenarios.
