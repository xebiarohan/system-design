
# Consistency Models

## 1. What is a consistency model?

Imagine you have replicated data:

```text
                Application
                 /       \
                ↓         ↓
            DB Node A   DB Node B
                |           |
             value=100    value=100
```

Now the application updates the value:

```text
WRITE value = 200
```

The write reaches Node A first:

```text
Node A → 200
Node B → 100
```

There is now a question:

> If another client reads from Node B immediately, should it see `200` or can it see `100`?

A **consistency model** defines the rules for what values clients are allowed to observe.

---

# 2. Why do we need different consistency models?

Because stronger consistency usually comes with costs.

For example:

```text
             Strong consistency
                    ↑
                    |
              More coordination
                    |
                    |
                    |
              More latency
                    |
                    ↓
             Eventual consistency
```

If every read must always see the newest value across all replicas, replicas need coordination.

That can mean:

* more network communication
* higher latency
* reduced availability during failures
* more coordination between nodes

For some applications, that's worth it.

For others, it isn't.

---

# 3. The most important models

For system design, I'd learn these in roughly this order:

```text
1. Strong consistency
2. Eventual consistency
3. Read-after-write consistency
4. Monotonic reads
5. Monotonic writes
6. Causal consistency
7. Session consistency
```

Let's go through them.

---

# 4. Strong Consistency

The simplest mental model:

> **After a successful write, every subsequent read sees that write.**

Suppose:

```text
Initial:
balance = $100
```

Client A:

```text
WRITE balance = $50
```

After the write succeeds:

```text
Client B → READ
           ↓
          $50
```

It should not see:

```text
$100 ❌
```

even if the request goes to another replica.

### Example

```text
             DB
          /       \
       Node A    Node B
          |         |
         $50       $50
```

Everything is synchronized from the client's perspective.

### Good for

* Banking
* Inventory
* Financial transactions
* Account balances
* Critical configuration
* Systems where stale data can cause serious problems

### Cost

Strong consistency may require:

```text
Client
  ↓
Node A
  ↓
Coordinate with replicas
  ↓
Confirm
  ↓
Response
```

That coordination can increase latency.

---

# 5. Eventual Consistency

Now let's relax the requirement.

> **If no new writes occur, all replicas will eventually converge to the same value.**

Suppose:

```text
Node A = 100
Node B = 100
```

Client writes:

```text
WRITE = 200
```

Node A receives it:

```text
Node A = 200
Node B = 100
```

For a short period, different clients may see different values:

```text
Client 1 → Node A → 200
Client 2 → Node B → 100
```

Later replication catches up:

```text
Node A = 200
Node B = 200
```

That's **eventual consistency**.

---

# 6. Why would anyone want eventual consistency?

Because you can reduce coordination.

Instead of:

```text
WRITE
  ↓
Update every replica
  ↓
Wait
  ↓
Success
```

you can do something closer to:

```text
WRITE
  ↓
Update local/available node
  ↓
Success
  ↓
Replicate asynchronously
```

This can provide:

* lower latency
* better availability
* easier geographic distribution
* better tolerance of network failures

The price is that clients may temporarily see stale data.

---

# 7. Strong vs Eventual

This is probably the most important comparison to remember.

|                                   | Strong                                           | Eventual                                     |
| --------------------------------- | ------------------------------------------------ | -------------------------------------------- |
| Latest value immediately visible? | Yes                                              | Not necessarily                              |
| Replicas can temporarily differ?  | Generally no from client's consistency guarantee | Yes                                          |
| Coordination                      | More                                             | Less                                         |
| Latency                           | Potentially higher                               | Potentially lower                            |
| Availability during partitions    | Can be reduced                                   | Can be higher                                |
| Stale reads                       | Not allowed by the model                         | Possible                                     |
| Typical use                       | Financial/critical state                         | Feeds, counters, caches, distributed systems |

---

# 8. Read-after-write Consistency

This is weaker than strong consistency.

The guarantee is:

> **After I write something, I will be able to read my own write.**

Consider:

```text
Client A
   |
   | WRITE name = "Rohan"
   ↓
Node A
   |
   | asynchronous replication
   ↓
Node B
```

Immediately afterward:

```text
Client A → Node B → READ
```

If Node B still has:

```text
name = "OldName"
```

that's annoying.

With **read-after-write consistency**, Client A must see:

```text
"Rohan"
```

even if another replica hasn't caught up yet.

---

# 9. Why is this useful?

Think about a social application.

You update your profile:

```text
Name:
"Rahul"
   ↓
"Rohan"
```

You refresh the page.

You'd expect:

```text
Rohan
```

not:

```text
Rahul
```

for several seconds.

But you may be okay with **other users** temporarily seeing the old value.

So:

```text
You → must see your update
Others → may temporarily see old value
```

That's weaker than global strong consistency.

---

# 10. Monotonic Reads

This one sounds complicated but is actually simple.

> **Once you've seen a value, you should never subsequently see an older value.**

Suppose you're reading from replicas.

First request:

```text
Request 1 → Node A → version 10
```

Then:

```text
Request 2 → Node B → version 8
```

That's bad.

You observed:

```text
10 → 8
```

The system went **backward** from your perspective.

With monotonic reads:

```text
10 → 10
10 → 11
10 → 12
```

are okay.

But:

```text
10 → 8
```

isn't.

---

# 11. Real-world example of monotonic reads

Imagine you're reading comments:

```text
Request 1:
Comments:
A
B
C
```

Then you refresh:

```text
Request 2:
Comments:
A
B
```

And refresh again:

```text
Request 3:
Comments:
A
B
C
D
```

Seeing data disappear and then reappear can happen if you're reading different replicas with different states.

Monotonic reads prevent that kind of backward movement for a given client/session.

---

# 12. Monotonic Writes

This applies to **writes**.

> **Writes from the same client must be observed in the order they were issued.**

Suppose a client performs:

```text
WRITE 1:
name = "Rohan"

WRITE 2:
name = "Rohan Aggarwal"
```

The system shouldn't apply:

```text
WRITE 2
   ↓
WRITE 1
```

because then the final state could incorrectly become:

```text
"Rohan"
```

instead of:

```text
"Rohan Aggarwal"
```

So:

```text
Write 1 → Write 2
```

must maintain ordering.

---

# 13. Causal Consistency

Now we're getting into a very useful distributed-systems concept.

Causal consistency says:

> **If one operation causally depends on another operation, everyone should see them in that order.**

Example:

```text
User creates post
      ↓
User comments on post
```

The comment logically depends on the post existing.

Therefore clients shouldn't see:

```text
Comment: "Nice!"
       ↓
Post: "My vacation..."
```

They should observe:

```text
Post
 ↓
Comment
```

because:

```text
Post creation
     ↓
Comment creation
```

has a causal relationship.

---

# 14. Another causal example

Suppose Alice sends Bob a message:

```text
Alice → "Hello Bob"
```

Bob responds:

```text
Bob → "Hi Alice"
```

There's a causal relationship:

```text
Alice's message
       ↓
Bob's response
```

A client shouldn't observe:

```text
"Hi Alice"
       ↓
"Hello Bob"
```

because Bob's response couldn't logically have happened before Alice's message.

Causal consistency preserves that ordering.

---

# 15. Session Consistency

Session consistency is often discussed as a collection of guarantees for one user's session.

For example:

```text
User Session
     |
     +--- Read-your-writes
     |
     +--- Monotonic reads
     |
     +--- Monotonic writes
```

The idea is:

> A particular user should have a predictable view of the data during their session, even if the overall system isn't strongly consistent.

This is very useful for web applications.

---

# 16. A useful hierarchy

You can visualize these models roughly like this:

```text
          Strong consistency
                 ↑
                 |
        Causal consistency
                 |
        Session consistency
                 |
       Read-after-write
                 |
          Monotonic reads
                 |
       Eventual consistency
                 ↓
        Weaker guarantees
```

Don't treat this as a strict mathematical ranking of every consistency model. Some models provide **different dimensions of guarantees**, rather than simply being "stronger/weaker" in every respect.

But as a learning mental model, it's useful.

---

# 17. CAP vs Consistency Models

This is where the two topics connect.

### CAP asks:

> What happens when there is a network partition?

```text
Node A  ←──X──→  Node B
```

Do we prioritize:

```text
Consistency
      OR
Availability
```

### Consistency models ask:

> What values are clients allowed to observe?

For example:

```text
Strong
Eventual
Read-after-write
Monotonic reads
Causal
```

So:

```text
CAP
 ↓
Distributed system encounters partition
 ↓
Trade-off between consistency and availability
 ↓
Consistency model
 ↓
Defines the actual consistency guarantees
```

# 18. Replication example tying everything together

Suppose:

```text
                 Application
                /     |     \
               ↓      ↓      ↓
             DB-A   DB-B   DB-C
```

Initial:

```text
A = 100
B = 100
C = 100
```

Client writes:

```text
WRITE 200
```

Node A receives it:

```text
A = 200
B = 100
C = 100
```

### Strong consistency

System ensures reads don't expose stale state:

```text
READ B
 ↓
200
```

Potentially by waiting for/using appropriate replication coordination.

### Eventual consistency

```text
READ B
 ↓
100
```

may be allowed temporarily.

Later:

```text
A = 200
B = 200
C = 200
```

### Read-after-write

The client that performed:

```text
WRITE 200
```

must subsequently see:

```text
READ → 200
```

even if another client might temporarily see `100`.

### Monotonic reads

If a client has already seen:

```text
200
```

it shouldn't later see:

```text
100
```

### Causal consistency

If:

```text
Write A
   ↓
Write B
```

because B depends on A, other clients should observe:

```text
A → B
```

and not:

```text
B → A
```

---

# 19. What you should remember for system design

When designing a distributed database, don't simply say:

> "We'll use eventual consistency."

Ask **what guarantees the application actually needs**.

For example:

### Bank balance

```text
Need:
- strong/read-your-writes
- correct ordering
- no dangerous stale state
```

### Social media feed

```text
Could tolerate:
- eventual consistency
- stale reads
- asynchronous replication
```

### Product inventory

Interesting middle ground:

```text
Product catalog:
    eventual consistency may be okay

Available stock:
    stronger guarantees may be needed
```

That's an important system-design insight:

> **Different data in the same application can require different consistency guarantees.**
