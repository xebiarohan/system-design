This is a very important system-design topic because it answers:

> **What happens when multiple transactions execute at the same time and access the same data?**

---

# 1. Why do we need isolation?

Imagine two users trying to buy the **last item** in stock.

Database:

```text
product_id = 101
stock = 1
```

Two requests arrive almost simultaneously:

```text
User A                         User B
   |                              |
   ↓                              ↓
Transaction A                 Transaction B
   |                              |
   +------ read stock = 1 -------+
```

Both transactions might see:

```text
stock = 1
```

Then both try:

```text
stock = stock - 1
```

You could accidentally sell **two items when only one existed**.

So databases need rules governing:

> **How much can one transaction see of another transaction's work while they execute concurrently?**

That's what **isolation levels** control.

---

# 2. Isolation is one of ACID

ACID:

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

You already know the other three.

The **I** means:

> Concurrent transactions should behave as though they are appropriately isolated from each other, according to the selected isolation level.

But here's the important part:

**Isolation isn't simply ON or OFF.**

There are different levels of isolation.

```text
Less isolation
      ↓
More concurrency
      ↓
Potentially more anomalies

More isolation
      ↓
Stronger consistency guarantees
      ↓
Potentially less concurrency / more overhead
```

---

# 3. The four standard isolation levels

The SQL standard defines four commonly discussed levels:

```text
1. READ UNCOMMITTED
2. READ COMMITTED
3. REPEATABLE READ
4. SERIALIZABLE
```

Think of them as a ladder:

```text
                 Stronger isolation
                        ↑
                        |
                SERIALIZABLE
                        |
                REPEATABLE READ
                        |
                READ COMMITTED
                        |
                READ UNCOMMITTED
                        |
                        ↓
                 Weaker isolation
```

The stronger you go, the more concurrent anomalies the database prevents.

---

# 4. First understand the anomalies

Before learning the levels, you need to understand **what can go wrong**.

There are three classic anomalies:

```text
1. Dirty Read
2. Non-repeatable Read
3. Phantom Read
```

There's also a broader concept called **lost update**, which is extremely important in practical system design.

Let's understand each.

---

# 5. Dirty Read

Suppose the database has:

```text
Account A
balance = $1000
```

Transaction A starts:

```text
T1:
UPDATE account
SET balance = 500
WHERE id = 1;
```

But T1 hasn't committed yet.

Now T2 executes:

```text
SELECT balance
FROM account
WHERE id = 1;
```

If T2 sees:

```text
$500
```

even though T1 hasn't committed, that's a:

> **Dirty read**

Because T2 has read **uncommitted data**.

---

# 6. What if T1 rolls back?

This is where the problem becomes obvious.

Timeline:

```text
T1                              T2
│                               │
│ UPDATE balance = 500          │
│                               │
│          NOT COMMITTED        │
│                               │
│                         READ balance
│                               │
│                         sees $500
│                               │
│ ROLLBACK                       │
│                               │
│ balance = $1000               │
```

T2 used information that **never actually became committed database state**.

That's the dirty read.

---

# 7. READ UNCOMMITTED

At the weakest standard isolation level:

```text
READ UNCOMMITTED
```

a transaction may be allowed to see uncommitted changes from other transactions.

Therefore:

```text
Dirty Read → possible
```

This level gives you high concurrency but weak guarantees.

It's relatively uncommon for important transactional applications.

---

# 8. Non-repeatable read

Now suppose T1 reads:

```text
balance = $1000
```

Then T2 changes the balance:

```text
UPDATE account
SET balance = 500;
COMMIT;
```

T1 reads again:

```text
balance = $500
```

Same transaction.

Same query.

Different result.

Timeline:

```text
T1                              T2
│                               │
│ SELECT balance               │
│ → $1000                       │
│                               │
│                               │ UPDATE balance = $500
│                               │ COMMIT
│                               │
│ SELECT balance               │
│ → $500                        │
```

That's:

> **Non-repeatable read**

The first read cannot be reproduced because another transaction committed an update between the reads.

---

# 9. READ COMMITTED

With:

```text
READ COMMITTED
```

a transaction only sees **committed data**.

Therefore:

```text
Dirty read ❌
```

But:

```text
Non-repeatable read ✅ possible
```

Why?

Because another transaction can commit a change between your two reads.

Example:

```text
T1:
SELECT balance → $1000

T2:
UPDATE balance → $500
COMMIT

T1:
SELECT balance → $500
```

Both values were committed, so there is no dirty read.

But the same query produced different results inside T1.

---

# 10. Phantom read

This one is slightly different.

Suppose T1 executes:

```sql id="tq3k2s"
SELECT *
FROM orders
WHERE status = 'PENDING';
```

It gets:

```text
Order 101
Order 102
```

Then T2 inserts:

```text
Order 103
status = 'PENDING'
```

and commits.

T1 executes the same query again:

```sql id="4c1xwq"
SELECT *
FROM orders
WHERE status = 'PENDING';
```

Now it gets:

```text
Order 101
Order 102
Order 103
```

A new row has **appeared**.

That's a:

> **Phantom read**

---

# 11. Why is it called a phantom?

Because from T1's perspective:

```text
First query:
101
102

Second query:
101
102
103
```

The new row appeared like a phantom.

It's not necessarily that an existing row changed.

Instead:

> **The set of rows matching the query changed.**

That's the key distinction.

---

# 12. Non-repeatable vs phantom read

This is worth memorizing.

### Non-repeatable read

An **existing row's value changes**.

```text
First:
Account 1 → $1000

Second:
Account 1 → $500
```

### Phantom read

The **set of matching rows changes**.

```text
First:
101
102

Second:
101
102
103
```

So:

```text
Non-repeatable
→ existing row changed

Phantom
→ matching row set changed
```

---

# 13. Now the isolation levels make sense

Here's the classic matrix:

| Isolation Level  | Dirty Read | Non-repeatable Read |                   Phantom Read |
| ---------------- | ---------: | ------------------: | -----------------------------: |
| READ UNCOMMITTED |          ✅ |                   ✅ |                              ✅ |
| READ COMMITTED   |          ❌ |                   ✅ |                              ✅ |
| REPEATABLE READ  |          ❌ |                   ❌ | depends on DB / implementation |
| SERIALIZABLE     |          ❌ |                   ❌ |                              ❌ |

**Important:** real databases don't all implement these levels identically. In particular, PostgreSQL's `REPEATABLE READ` is stronger than the minimum SQL-standard definition and prevents phantom reads under its MVCC implementation.

So don't blindly memorize the table as if every database behaves identically.

---

# 14. REPEATABLE READ

The goal is:

> If I read a row during my transaction, another committed transaction shouldn't make that row appear differently to me during that transaction.

Example:

```text
T1:
SELECT balance
→ $1000
```

T2:

```text
UPDATE balance = $500
COMMIT
```

T1:

```text
SELECT balance
→ $1000
```

T1 continues seeing its transactionally consistent view.

Therefore:

```text
Dirty read              ❌
Non-repeatable read     ❌
```

Phantom behavior depends on the database's implementation.

---

# 15. SERIALIZABLE

This is the strongest standard isolation level.

The goal is essentially:

> **Concurrent transactions should produce a result equivalent to some serial execution order.**

Imagine:

```text
T1
T2
```

executing concurrently.

Serializable isolation tries to make the result equivalent to:

```text
T1 → T2
```

or:

```text
T2 → T1
```

even though they physically overlapped.

---

# 16. Example of SERIALIZABLE

Suppose:

```text
stock = 1
```

Two transactions:

```text
T1                         T2
│                          │
│ read stock = 1           │
│                          │ read stock = 1
│                          │
│ update stock             │
│                          │
│ commit                   │
│                          │
│                          │ update stock
│                          │
│                          │ conflict!
```

The database may:

```text
T1 → COMMIT
T2 → FAIL / SERIALIZATION ERROR
```

The application can then retry T2.

The exact behavior depends on the database's concurrency-control mechanism.

---

# 17. The trade-off

This is the core system-design concept:

```text
             Isolation
                ↑
                |
       SERIALIZABLE
                |
      REPEATABLE READ
                |
       READ COMMITTED
                |
      READ UNCOMMITTED
                |
                ↓
        Concurrency
```

It's not literally a perfect linear trade-off in every database, but as a mental model:

```text
Stronger isolation
       ↓
Fewer anomalies
       ↓
More concurrency-control work
       ↓
Potentially more blocking/conflicts/retries
```

---

# 18. How databases actually implement isolation

This is where things get interesting.

There are two major concepts you should know:

### Pessimistic concurrency control

```text
Locks
```

### Optimistic/MVCC-style concurrency control

```text
Multiple versions of data
```

Many modern databases use **MVCC — Multi-Version Concurrency Control**, sometimes combined with locks.

---

# 19. Pessimistic locking

The idea:

> Assume conflicts are likely, so lock the data.

Suppose:

```sql id="s5j22q"
SELECT *
FROM account
WHERE id = 1
FOR UPDATE;
```

Conceptually:

```text
T1
 ↓
Lock account 1
 ↓
Update account
 ↓
Commit
 ↓
Release lock
```

Meanwhile:

```text
T2
 ↓
tries to access locked row
 ↓
waits
```

This is pessimistic concurrency control.

---

# 20. Optimistic concurrency

The idea is:

> Assume conflicts are relatively rare; let transactions proceed and detect conflicts when necessary.

For example, you might use a version column:

```text
id    balance    version
------------------------
1     1000       5
```

T1 reads:

```text
version = 5
```

T2 also reads:

```text
version = 5
```

T1 updates:

```sql id="pprc7d"
UPDATE account
SET balance = 900,
    version = 6
WHERE id = 1
  AND version = 5;
```

Success.

Now T2 tries:

```sql id="gwd8la"
UPDATE account
SET balance = 800,
    version = 6
WHERE id = 1
  AND version = 5;
```

No row is updated because:

```text
version is now 6
```

So T2 knows:

> Someone changed this record while I was working.

It can retry or return a conflict.

---

# 21. MVCC

MVCC stands for:

> **Multi-Version Concurrency Control**

Instead of having only:

```text
balance = 1000
```

the database may internally maintain versions conceptually like:

```text
Version 1 → balance = 1000
Version 2 → balance = 900
Version 3 → balance = 800
```

Different transactions can see the version appropriate to their transaction snapshot.

This allows:

```text
Reader
   ↓
read consistent version

Writer
   ↓
create/update another version
```

without necessarily blocking the reader in the same way traditional locking would.

The exact internals differ significantly between databases.

---

# 22. Why MVCC is important

Imagine a busy application:

```text
1000 readers
+
100 writers
```

If every reader had to wait for writers:

```text
Writer
 ↓
LOCK
 ↓
1000 readers WAIT
```

performance could suffer.

MVCC can allow many reads and writes to proceed concurrently while maintaining transactional visibility rules.

That's one reason MVCC is so common in modern relational databases.

---

# 23. Isolation and locks are NOT the same thing

Important distinction:

```text
Isolation level
      ↓
Defines visibility/concurrency guarantees
```

while:

```text
Locking
      ↓
One mechanism databases can use to enforce those guarantees
```

And:

```text
MVCC
      ↓
Another major mechanism
```

A database can combine them.

---

# 24. READ COMMITTED — practical example

Suppose you're building an e-commerce application.

```text
Product:
stock = 10
```

Transaction A:

```text
BEGIN

SELECT stock
FROM product
WHERE id = 1;

→ 10
```

Transaction B changes it:

```text
UPDATE product
SET stock = 9
WHERE id = 1;

COMMIT;
```

Transaction A reads again:

```text
SELECT stock
FROM product
WHERE id = 1;

→ 9
```

At `READ COMMITTED`, this can happen.

Each statement sees data committed before that statement's snapshot/visibility point.

---

# 25. REPEATABLE READ

Now:

```text
T1:
BEGIN

SELECT stock
→ 10
```

T2:

```text
UPDATE stock = 9
COMMIT
```

T1:

```text
SELECT stock
→ 10
```

T1 maintains a stable transactional view under databases such as PostgreSQL.

Again, exact behavior depends on the database.

---

# 26. SERIALIZABLE

Now suppose T1 and T2 have a conflict.

The database can effectively say:

```text
These two transactions cannot both successfully
commit as if nothing conflicted.
```

One may:

```text
WAIT
```

or:

```text
FAIL
```

or:

```text
SERIALIZATION ERROR
```

depending on the database and implementation.

The application may need to retry.

---

# 27. Important: Serializable can cause retries

This is a system-design point people often miss.

If you use:

```text
SERIALIZABLE
```

your application should be prepared for transaction failures caused by concurrency conflicts.

Conceptually:

```text
Request
   ↓
Transaction
   ↓
Conflict
   ↓
Serialization failure
   ↓
Retry
```

Therefore, if you choose strong isolation, your application design may need:

```text
Retry logic
+
Idempotency
+
Backoff
```

especially under high contention.

---

# 28. Lost update

Now let's look at a practical concurrency bug.

Initial:

```text
balance = 1000
```

Two transactions read:

```text
T1 → 1000
T2 → 1000
```

T1 calculates:

```text
1000 - 100 = 900
```

T2 calculates:

```text
1000 - 200 = 800
```

Then:

```text
T1 writes 900
T2 writes 800
```

Final:

```text
800
```

But logically:

```text
1000 - 100 - 200 = 700
```

T1's update has effectively been lost.

This is a:

> **Lost update**

Whether and how a particular isolation level prevents this depends on the database, statement pattern, and concurrency mechanism. Don't assume the four-level table alone tells the whole story.

---

# 29. How to prevent lost updates

Several approaches exist.

### Atomic SQL operation

Instead of:

```text
read balance
calculate
write balance
```

do:

```sql id="y09u9r"
UPDATE account
SET balance = balance - 100
WHERE id = 1;
```

The database performs the modification atomically.

This is often much better.

---

### Pessimistic locking

```sql id="q3f8dw"
SELECT *
FROM account
WHERE id = 1
FOR UPDATE;
```

Then update.

---

### Optimistic locking

Use:

```text
version
```

and update only if the version hasn't changed.

---

# 30. Isolation level selection in system design

This is where you need to move beyond memorization.

Suppose you're designing:

## Banking/payment service

You probably care strongly about:

```text
Correctness
+
Consistency
+
Transactions
+
Concurrency control
```

You might choose:

```text
READ COMMITTED
```

with appropriate locking/atomic operations, or stronger isolation for particular workflows where necessary.

You don't automatically choose SERIALIZABLE for everything.

---

# 31. Why not use SERIALIZABLE everywhere?

Because it can reduce concurrency or increase conflict/retry overhead.

Imagine:

```text
10,000 concurrent transactions
```

all touching the same small set of records.

At very strong isolation:

```text
many conflicts
     ↓
waiting/retries
     ↓
lower throughput
```

You may be better off with:

```text
READ COMMITTED
+
precise locking
+
atomic updates
+
optimistic concurrency
```

depending on the use case.

---

# 32. Read-heavy systems

Suppose you're building:

```text
Product Catalog
```

Millions of reads:

```text
GET product
GET product
GET product
...
```

You might not need extremely strong isolation for every read.

You could use:

```text
READ COMMITTED
+
caching
+
read replicas
```

depending on consistency requirements.

---

# 33. Reporting / analytics

Suppose you're generating:

```text
Monthly sales report
```

You care about:

```text
consistent snapshot
```

but perhaps not:

```text
blocking every concurrent write
```

MVCC/snapshot-based approaches can be very useful here.

Again, the appropriate isolation depends on the database and reporting semantics.

---

# 34. Isolation level ≠ consistency of the entire system

This distinction is very important for distributed systems.

Suppose:

```text
Order Service
      ↓
PostgreSQL
```

uses:

```text
SERIALIZABLE
```

That only gives you transactional guarantees **within the scope supported by that database transaction**.

It doesn't automatically make this distributed workflow atomic:

```text
Order Service
     ↓
Database

Payment Service
     ↓
Different Database

Inventory Service
     ↓
Different Database
```

You can't simply say:

> "All databases are SERIALIZABLE, therefore the whole system is transactional."

That's false.

For distributed transactions, you need other patterns/mechanisms such as:

```text
Saga
Outbox pattern
Distributed transactions / 2PC
```

depending on the architecture.

This will become very important when you reach distributed systems.

---

# 35. A practical decision table

Here's the mental model I'd use:

| Requirement                            | Possible approach                                             |
| -------------------------------------- | ------------------------------------------------------------- |
| Basic web CRUD                         | READ COMMITTED often sufficient                               |
| Need stable reads within transaction   | REPEATABLE READ / snapshot semantics                          |
| Very strong serial execution semantics | SERIALIZABLE                                                  |
| Prevent specific row conflicts         | `SELECT ... FOR UPDATE` / atomic updates                      |
| Rare concurrent update conflicts       | Optimistic locking                                            |
| High contention                        | Carefully designed atomic operations / locking / partitioning |
| Distributed workflow                   | Saga/outbox/etc., not merely isolation level                  |

The exact choice depends heavily on the database.

---

# 36. One example tying everything together

Imagine:

```text
E-commerce inventory

stock = 1
```

Two customers click:

```text
BUY
```

at the same time.

You could design:

```text
Request A
   ↓
BEGIN
   ↓
UPDATE product
SET stock = stock - 1
WHERE id = 101
AND stock > 0
   ↓
Check affected rows
   ↓
1 → success
0 → sold out
   ↓
COMMIT
```

Request B executes concurrently.

The database's concurrency control ensures the updates don't simply overwrite each other incorrectly.

This is often better than:

```text
SELECT stock
→ 1

application:
stock - 1

UPDATE stock = 0
```

because the latter creates more opportunity for a race condition.

---

# 37. The most important distinction to remember

Don't think:

```text
Isolation = locking
```

Think:

```text
Isolation
    ↓
What can concurrent transactions observe?
    ↓
What anomalies are allowed?
    ↓
Database uses mechanisms such as
    ├── locks
    ├── MVCC
    └── conflict detection
```

# 38. Your system-design notes

I'd summarize the topic like this:

```text
# Database Isolation Levels

Isolation controls how concurrent transactions interact
and what data one transaction can see from other transactions.

Four standard levels:

1. READ UNCOMMITTED
   - Weakest
   - Dirty reads possible

2. READ COMMITTED
   - Only committed data visible
   - Dirty reads prevented
   - Non-repeatable reads possible

3. REPEATABLE READ
   - Stable reads within a transaction
   - Dirty reads prevented
   - Non-repeatable reads prevented
   - Phantom behavior depends on DB implementation

4. SERIALIZABLE
   - Strongest standard level
   - Result equivalent to serial transaction execution
   - May cause blocking/conflicts/retries

Common anomalies:

Dirty Read
→ Read uncommitted data

Non-repeatable Read
→ Same row gives different values
   within one transaction

Phantom Read
→ Same query returns a different set of rows

Lost Update
→ Concurrent updates overwrite each other

Concurrency mechanisms:

Pessimistic locking
→ Assume conflicts will happen
→ Lock data

Optimistic locking
→ Assume conflicts are rare
→ Detect conflict using version/check

MVCC
→ Maintain multiple versions of data
→ Allows concurrent readers/writers
   according to transaction visibility rules
```

### The key system-design takeaway

When choosing an isolation level, don't say:

> **"SERIALIZABLE is safest, so I'll always use SERIALIZABLE."**

Instead ask:

```text
What anomalies can my component tolerate?
              ↓
How much concurrency do I need?
              ↓
How much contention exists?
              ↓
What consistency does the business require?
              ↓
What does my specific database actually guarantee?
              ↓
Choose isolation + locking/concurrency strategy
```

That is the level of reasoning you want in a system-design interview.
