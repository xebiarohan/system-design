
# DNS — Domain Name System

Let's start with the simplest question:

You type:

```text
https://www.google.com
```

Your computer cannot directly send an IP packet to:

```text
www.google.com
```

The network needs an IP address, such as:

```text
142.250.x.x
```

So DNS performs the translation:

```text
www.google.com
       ↓
      DNS
       ↓
142.250.x.x
```

Think of DNS as the **phone book of the Internet**.

---

# 1. Why do we need DNS?

Imagine there were no DNS.

You would have to remember:

```text
142.250.190.4
```

instead of:

```text
google.com
```

And if Google's server IP changed?

You would need to learn the new IP.

DNS separates:

```text
Human-friendly name
        ↓
     DNS
        ↓
Network address
```

This gives us an important property:

> **The domain name can remain stable even when the underlying infrastructure changes.**

That's extremely useful in system design.

---

# 2. DNS is not just "domain → IP"

This is where DNS becomes interesting.

DNS can answer many types of questions.

For example:

```text
What is the IP address for example.com?

Where should email for example.com go?

What is the canonical name for this domain?

Which name servers are authoritative?
```

That's why DNS has different **record types**.

---

# 3. Important DNS Records

You don't need to memorize every DNS record.

For system design, know these well:

```text
A
AAAA
CNAME
MX
NS
TXT
```

Let's go through them.

---

# 4. A Record

An **A record** maps a domain name to an IPv4 address.

```text
example.com
     ↓
   A record
     ↓
192.0.2.10
```

Example:

```text
example.com → 192.0.2.10
```

So:

```text
A = IPv4 address
```

---

# 5. AAAA Record

AAAA does the same thing but for **IPv6**.

```text
example.com
     ↓
 AAAA record
     ↓
2001:db8::10
```

So:

```text
A     → IPv4
AAAA  → IPv6
```

Easy one to remember.

---

# 6. CNAME

CNAME means:

**Canonical Name**

It creates an alias from one domain name to another domain name.

For example:

```text
www.example.com
       ↓
    CNAME
       ↓
example.com
```

Conceptually:

```text
www.example.com → example.com
```

Then DNS resolves `example.com` to its actual address.

A useful distinction:

```text
A record
→ name → IP

CNAME
→ name → another name
```

---

# 7. MX Record

MX means:

**Mail Exchange**

It tells the Internet which mail servers handle email for a domain.

For example:

```text
example.com
      ↓
     MX
      ↓
mail.example.com
```

When someone sends:

```text
user@example.com
```

the sending mail server uses the domain's MX records to determine where to deliver the email.

---

# 8. NS Record

NS means:

**Name Server**

It tells us which DNS servers are authoritative for a domain.

Conceptually:

```text
example.com
     ↓
NS
     ↓
ns1.example-dns.com
ns2.example-dns.com
```

We'll come back to **authoritative DNS servers**, because they're an important part of how DNS actually works.

---

# 9. TXT Record

TXT records store text associated with a domain.

They're commonly used for things like:

```text
Domain verification
SPF
DKIM-related configuration
DMARC-related information
```

You don't need to go deep into email security for this topic.

Just remember:

```text
TXT → arbitrary text/configuration information
```

---

# 10. The DNS Resolution Process

Now let's understand the important part.

Suppose you enter:

```text
https://api.example.com/users
```

What actually happens?

A simplified flow is:

```text
Browser
   ↓
OS / DNS cache
   ↓
Recursive DNS resolver
   ↓
Root DNS server
   ↓
.com DNS server
   ↓
Authoritative DNS server
   ↓
IP address
```

Then:

```text
IP address
   ↓
TCP/UDP connection
   ↓
HTTPS
   ↓
Server
```

This connects directly with the previous topic.

---

# 11. Step-by-step DNS Resolution

Suppose we need:

```text
api.example.com
```

The client asks its DNS resolver:

```text
"What is the IP address of api.example.com?"
```

Let's assume the answer isn't cached.

The resolver starts looking.

---

## Step 1 — Root DNS

The resolver asks a **root DNS server**:

```text
Where can I find information about .com?
```

The root doesn't necessarily know:

```text
api.example.com → 192.0.2.10
```

Instead, it points the resolver toward the `.com` name servers.

Conceptually:

```text
Resolver
   ↓
Root
   ↓
.com name servers
```

---

# 12. Step 2 — TLD DNS

Now the resolver asks the `.com` DNS infrastructure:

```text
Who is authoritative for example.com?
```

The `.com` servers respond with the relevant authoritative name servers.

For example:

```text
example.com
     ↓
ns1.example-dns.com
ns2.example-dns.com
```

So:

```text
.com
 ↓
example.com authoritative DNS
```

---

# 13. Step 3 — Authoritative DNS

Now the resolver asks the authoritative server:

```text
What is the IP address of api.example.com?
```

The authoritative server might respond:

```text
api.example.com
       ↓
192.0.2.10
```

Now the resolver knows the answer.

---

# 14. Step 4 — Return to the Client

The resolver returns:

```text
api.example.com
       ↓
192.0.2.10
```

to the client.

Then the client can communicate with:

```text
192.0.2.10
```

For HTTPS:

```text
DNS
 ↓
IP address
 ↓
TCP connection
 ↓
TLS handshake
 ↓
HTTP request
```

That's a very useful mental model.

---

# 15. But does this happen every time?

**No.**

And this is where DNS caching becomes extremely important.

Imagine every browser request had to do:

```text
Root
 ↓
TLD
 ↓
Authoritative server
```

That would be terribly inefficient.

Instead, DNS responses are cached.

---

# 16. DNS Caching

There are several places where DNS information can be cached.

For example:

```text
Browser
   ↓
Operating System
   ↓
Local network / router
   ↓
Recursive DNS resolver
```

If someone recently looked up:

```text
api.example.com
```

the resolver may already know:

```text
api.example.com → 192.0.2.10
```

So it doesn't need to ask the authoritative server again.

---

# 17. TTL — Time To Live

This brings us to one of the most important DNS concepts:

**TTL**

TTL tells caches approximately how long they can reuse a DNS answer before they should obtain a fresh answer.

For example:

```text
api.example.com
A
192.0.2.10
TTL = 300 seconds
```

Means the cached answer can generally be reused for:

```text
5 minutes
```

After that, the resolver needs to refresh it.

---

# 18. Why does TTL matter in system design?

Imagine you have:

```text
api.example.com
        ↓
192.0.2.10
```

Then you migrate your application:

```text
192.0.2.10
      ↓
192.0.2.20
```

You change DNS:

```text
api.example.com → 192.0.2.20
```

But some DNS resolvers may still have:

```text
api.example.com → 192.0.2.10
```

cached.

Why?

Because their cached value hasn't expired.

So:

```text
DNS change
   ≠
Immediate global change
```

That's a very important system-design concept.

---

# 19. TTL trade-off

You can think of TTL like this:

### High TTL

```text
TTL = 1 hour
```

Advantages:

```text
Less DNS traffic
More caching
Lower DNS lookup overhead
```

Disadvantage:

```text
Changes take longer to propagate through caches
```

### Low TTL

```text
TTL = 30 seconds
```

Advantages:

```text
Changes can be reflected sooner
```

Disadvantages:

```text
More DNS queries
More load on DNS infrastructure
```

So:

```text
High TTL
→ better caching
→ slower change propagation

Low TTL
→ faster changes
→ more DNS queries
```

---

# 20. DNS Load Balancing

Now we're getting into the **system design** part.

Suppose your application has three servers:

```text
Server A → 10.0.0.1
Server B → 10.0.0.2
Server C → 10.0.0.3
```

DNS can return multiple IP addresses:

```text
api.example.com

→ 10.0.0.1
→ 10.0.0.2
→ 10.0.0.3
```

A client/resolver may receive these addresses and attempt to connect using one of them.

This can distribute traffic across multiple servers.

Conceptually:

```text
                 DNS
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      App 1     App 2     App 3
```

This is one form of **DNS-based load distribution**.

---

# 21. But DNS isn't a replacement for a Load Balancer

This is important.

Suppose you have:

```text
             DNS
              ↓
       ┌──────┼──────┐
       ↓      ↓      ↓
      App1   App2   App3
```

What happens if App2 dies?

DNS doesn't inherently know that your application has a broken process unless the DNS infrastructure has some health-check/failover capability configured.

Compare that with:

```text
              Load Balancer
             /      |      \
          App1     App2     App3
```

The load balancer can actively perform health checks and stop sending traffic to unhealthy instances.

So DNS-based distribution and load balancing are related but **not the same thing**.

---

# 22. DNS Failover

DNS can also participate in failover.

Imagine:

```text
Primary Region
10.0.0.10

Secondary Region
20.0.0.10
```

Normal state:

```text
api.example.com
       ↓
10.0.0.10
```

If the primary region becomes unavailable, a DNS system with health checking/failover policies can direct new DNS answers toward:

```text
20.0.0.10
```

Conceptually:

```text
                  DNS
                   │
             ┌─────┴─────┐
             ↓           ↓
         Region A     Region B
          Primary      Backup
```

But remember the TTL issue.

Existing cached DNS answers may continue pointing toward the old destination until their TTL expires.

So DNS failover is **not instantaneous**.

# 23. DNS and your System Design Architecture

This is where I want you to connect today's topic with your overall roadmap.

Suppose we're designing an e-commerce system:

```text
                    User
                      │
                      ↓
                     DNS
                      │
                      ↓
                Load Balancer
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       App Server  App Server  App Server
          │           │           │
          └───────────┼───────────┘
                      ↓
                    Cache
                      ↓
                   Database
```

DNS doesn't replace the other components.

Its job is primarily to answer:

> **"Where should this domain name resolve?"**

Then the resulting network address takes the request into the rest of the architecture.

---

# 24. DNS hierarchy

One more concept worth understanding.

DNS is hierarchical.

Think:

```text
                         Root
                          .
                          │
              ┌───────────┼───────────┐
             .com        .org        .net
               │
            example
               │
        ┌──────┴──────┐
       www           api
```

For:

```text
api.example.com
```

the hierarchy is:

```text
.                ← root
└── com           ← TLD
    └── example   ← domain
        └── api   ← subdomain/host
```

This hierarchical design allows DNS to scale globally.

---

# 25. Recursive vs Authoritative DNS

This distinction is very important.

### Recursive Resolver

The recursive resolver does the work of finding the answer on behalf of the client.

For example:

```text
Your computer
      ↓
Recursive Resolver
      ↓
Root
      ↓
TLD
      ↓
Authoritative DNS
```

It asks other DNS servers as necessary and returns the final answer.

### Authoritative DNS Server

The authoritative server is the source that holds the actual DNS records for a domain.

For example:

```text
example.com

A:
192.0.2.10
```

So:

```text
Recursive resolver
→ finds the answer

Authoritative server
→ owns/provides the authoritative DNS data
```

```text

```

```text

       ↓

```

### Step 2

```text

 ↓

```

```text

  ↓

```

```text

  ↓

  ↓

```

```http
GET /users
```

### Step 6

Application processes it:

```text
Spring Boot
    ↓

    ↓
Database
```

So the overall picture becomes:

```text
             DNS
              ↓

              ↓
             TCP
              ↓
             TLS
              ↓
            HTTP
              ↓
        Load Balancer
              ↓

              ↓

              ↓

```

This is exactly how your **Networking → API → Distributed Systems → Scalability** topics start connecting together.

If I were reducing DNS to the essential system-design knowledge, I'd remember these **7 things**:

### 1. DNS maps names to network addresses

```text

```

### 2. DNS is hierarchical

```text

```

### 3. DNS responses are cached

```text
Browser
OS
Resolver
```

### 4. TTL controls cache lifetime

```text
Higher TTL → better caching, slower changes
Lower TTL → faster changes, more DNS traffic
```

### 5. Know the important records

```text
A      → IPv4
AAAA   → IPv6
CNAME  → another domain name
MX     → mail server
NS     → authoritative name server
TXT    → text/configuration
```

### 6. DNS can distribute traffic

```text
domain
  ↓
multiple IPs
```

### 7. DNS can participate in failover

```text
Primary
  ↓
failure
  ↓
DNS directs new resolutions toward backup
```

But **caching/TTL means DNS failover isn't necessarily immediate**.
