# CDN

## 1. What is a CDN?

**CDN = Content Delivery Network.**

The basic problem is **distance**.

Imagine your application is hosted in a data center in Europe:

```text
                  Your Application
                  🇫🇷 Europe
                       │
                       │
                       │
                  ┌────┴────┐
                  │ Database │
                  └─────────┘
```

Now a user in India requests:

```text
User 🇮🇳
   │
   │ 8,000+ km
   ↓
Server 🇫🇷
```

The request and response have to travel a long distance.

A CDN puts servers called **edge locations** geographically closer to users:

```text
                         Origin
                       🇫🇷 Europe
                           │
              ┌────────────┼────────────┐
              │            │            │
              ↓            ↓            ↓
          Edge 🇮🇳     Edge 🇦🇪      Edge 🇺🇸
              │            │            │
              ↓            ↓            ↓
           Users        Users        Users
```

So instead of every user traveling all the way to the origin, cached content can be served from a nearby edge.

---

# 2. What exactly does a CDN store?

This is important.

A CDN is primarily useful for **content that can be cached and reused**.

For example:

```text
Static files
────────────
JavaScript
CSS
Images
Videos
Fonts
Downloads
```

Suppose your React application contains:

```text
index.html
main.js
styles.css
logo.png
```

Instead of every user downloading these from your application server:

```text
                 App Server
                /    |    \
               ↓     ↓     ↓
             User  User  User
```

the CDN can cache them:

```text
                     Origin
                       │
                       ↓
                  CDN Edge
                 /    |    \
                ↓     ↓     ↓
              User  User  User
```

---

# 3. Origin Server

The **origin** is the original server where the content comes from.

For example:

```text
                    Origin Server
                   🇫🇷 Europe
                       │
                       ↓
                  CDN Network
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          Edge A    Edge B    Edge C
```

Suppose `logo.png` doesn't exist in Edge A's cache.

The CDN asks the origin:

```text
User
 ↓
Edge A
 ↓
"Do you have logo.png?"
 ↓
Origin
```

Origin returns it:

```text
Origin
 ↓
logo.png
 ↓
Edge A
 ↓
User
```

The edge can then cache it.

---

# 4. Cache Hit

This is one of the most important CDN concepts.

Suppose a user requests:

```text
GET /images/logo.png
```

The nearby CDN edge already has it:

```text
User
 ↓
CDN Edge
 ↓
logo.png exists in cache
 ↓
Return immediately
```

This is a:

> **Cache Hit**

```text
User
   ↓
CDN Edge
   ↓
✅ Cache HIT
   ↓
Response
```

The request doesn't need to reach your origin server.

---

# 5. Cache Miss

Now suppose the CDN edge doesn't have the file.

```text
User
   ↓
CDN Edge
   ↓
❌ Cache MISS
   ↓
Origin Server
```

The origin returns the content:

```text
Origin
  ↓
logo.png
  ↓
CDN Edge
  ↓
User
```

The CDN can then store the object:

```text
CDN Edge Cache
└── logo.png
```

Next user:

```text
User 2
   ↓
CDN Edge
   ↓
✅ HIT
   ↓
logo.png
```

So the origin doesn't need to serve it again.

---

# 6. Why is this useful?

Imagine:

```text
1 million users
```

all requesting:

```text
GET /images/banner.jpg
```

Without CDN:

```text
             1,000,000 requests
                    ↓
              Origin Server
```

Your origin has to deal with all of them.

With CDN:

```text
                       Origin
                          ↑
                    Cache Misses
                          ↑
              ┌───────────┼───────────┐
              ↓           ↓           ↓
           Edge A       Edge B       Edge C
              ↑           ↑           ↑
           300K users  400K users  300K users
```

Most requests can be served from the edge.

This reduces:

* Origin traffic
* Latency
* Bandwidth usage
* Load on application servers

---

# 7. Edge Locations

An **edge location** is a CDN location geographically closer to users.

For example:

```text
                    Origin
                    Europe
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       London       Dubai       Mumbai
        Edge         Edge         Edge
          ↓           ↓           ↓
       UK users    UAE users   India users
```

The goal is to serve cached content from a location closer to the user.

This is why CDNs are particularly useful for globally distributed applications.

---

# 8. CDN doesn't mean "everything is cached"

This is a very important distinction.

Consider an e-commerce application.

### Static content

```text
GET /images/product123.jpg
GET /css/app.css
GET /js/app.js
```

Excellent CDN candidates.

### Dynamic API

```text
GET /api/account/balance
```

You generally **cannot blindly cache this** because the response is user-specific and potentially changes frequently.

So:

```text
Static content
     ↓
   CDN
     ↓
Origin

Dynamic API
     ↓
Origin / API infrastructure
```

---

# 9. Static vs Dynamic Content

Your roadmap specifically calls this out. 

### Static

Same content for many users:

```text
logo.png
app.js
styles.css
product-image.jpg
```

Great for CDN caching.

### Dynamic

Generated based on the request/user/current state:

```text
GET /api/user/profile
GET /api/cart
GET /api/account/balance
```

Usually needs to reach your application.

But there's an important nuance:

**Dynamic content can sometimes be cached too**, if the caching rules are safe.

For example:

```text
GET /products
```

might return the same catalog data for thousands of users.

You could potentially cache that response for a short period.

---

# 10. TTL — Time To Live

Now we have a problem.

Suppose CDN caches:

```text
product.jpg
```

How long should it keep it?

That's what **TTL** helps control.

For example:

```text
TTL = 1 hour
```

Meaning approximately:

```text
Cache object
     ↓
Valid for 1 hour
     ↓
TTL expires
     ↓
CDN needs to revalidate/refetch according to its caching rules
```

You can have different TTLs for different content.

For example:

```text
app.js          → 1 day
product image   → 1 hour
API response    → 30 seconds
```

The exact values depend on how frequently the content changes and how much staleness is acceptable.

---

# 11. Cache Invalidation

This is where CDN design gets interesting.

Suppose:

```text
product.jpg
```

is cached at 100 edge locations.

You replace the image at your origin:

```text
Origin
product.jpg → NEW VERSION
```

But CDN edges may still have:

```text
product.jpg → OLD VERSION
```

So how do we make the CDN stop serving the old version?

That's **cache invalidation**.

Conceptually:

```text
Origin
  ↓
"Invalidate /images/product.jpg"
  ↓
CDN
  ↓
Remove cached copy
```

The next request:

```text
User
 ↓
CDN
 ↓
Cache miss
 ↓
Origin
 ↓
New image
 ↓
CDN caches new image
```

---

# 12. Cache Busting

A very common technique for static assets is to change the URL when the content changes.

Instead of:

```text
app.js
```

use:

```text
app.a82f91.js
```

When you deploy a new version:

```text
app.b72c11.js
```

Now the CDN sees this as a completely different resource.

```text
Old:
app.a82f91.js

New:
app.b72c11.js
```

This is extremely common in frontend build systems.

For your React applications, you'll see this idea frequently because build tools generate hashed filenames.

# 13. CDN + Load Balancer

Now connect today's topic with the previous one.

Without CDN:

```text
User
 ↓
Load Balancer
 ↓
App Servers
```

With CDN:

```text
User
 ↓
CDN
 ↓
Load Balancer
 ↓
App Servers
```

But there's a catch.

If the CDN has the requested content:

```text
User
 ↓
CDN
 ↓
✅ HIT
 ↓
User
```

The request doesn't need to reach the load balancer.

For a cache miss:

```text
User
 ↓
CDN
 ↓
❌ MISS
 ↓
Load Balancer
 ↓
App Server
```

That's a major benefit.

# 14. CDN + Object Storage

For large static files, you often don't want your application servers serving them.

For example:

```text
                     CDN
                      │
                      ↓
                 Object Storage
```

Your application might upload:

```text
video.mp4
image.jpg
document.pdf
```

to object storage.

Then the CDN serves those files to users.

A larger architecture might look like:

```text
                         Users
                           │
                           ↓
                          CDN
                       ↙       ↘
                 Static        Dynamic
                   │              │
                   ↓              ↓
             Object Storage    Load Balancer
                                  │
                                  ↓
                              App Servers
                                  │
                                  ↓
                              Database
```

This separates static content delivery from application processing.

---

# 15. Does CDN replace a Load Balancer?

**No.**

They solve different problems.

### CDN

Primarily:

> "Can I serve this content from a nearby cache?"

### Load Balancer

Primarily:

> "Which backend server should handle this request?"

So:

```text
CDN
 ↓
Reduce distance + origin traffic
```

while:

```text
Load Balancer
 ↓
Distribute requests across backend instances
```

They work together.

---

# 16. A very important system-design distinction

Suppose 1 million users request the same image.

### Without CDN

```text
1,000,000 requests
        ↓
       LB
        ↓
   App Servers
        ↓
   Object Storage
```

That's wasteful.

### With CDN

```text
1,000,000 users
       ↓
      CDN
       ↓
  Cache HITs
       ↓
    Users
```

Maybe only a small number of requests need to reach the origin.

That's the real power of a CDN.

---

# 17. CDN and Latency

Suppose your origin is:

```text
🇫🇷 France
```

and your user is:

```text
🇦🇺 Australia
```

Without CDN:

```text
Australia
    ↓
 long network distance
    ↓
France
    ↓
response
    ↓
Australia
```

With CDN:

```text
Australia
    ↓
Australian CDN Edge
    ↓
response
```

The network distance can be dramatically reduced.

So CDN primarily helps with **latency for cacheable content**.

---

# 18. One subtle point: CDN doesn't make your database faster

This is a common misconception.

Suppose:

```text
GET /api/orders/123
```

requires:

```text
Application
 ↓
Database
```

Putting a CDN in front doesn't magically make the database query faster.

Instead, if that response is safely cacheable, the CDN may prevent some requests from reaching the application/database at all.

So the distinction is:

```text
CDN doesn't make:
Database → faster

CDN can make:
Database → receive fewer requests
```

That's a very useful system-design insight.
