# Reverse Proxy

## 1. First: What is a proxy?

A **proxy** is an intermediary between two parties.

For example:

```text
Client → Proxy → Server
```

Instead of the client communicating directly with the server, it communicates with the proxy.

There are two directions:

### Forward proxy

```text
Client → Forward Proxy → Internet/Server
```

The proxy represents the **client**.

Example:

```text
Your Laptop
     ↓
Corporate Proxy
     ↓
Google
```

The Google server sees the proxy rather than directly seeing your laptop's network connection.

---

### Reverse proxy

```text
Client → Reverse Proxy → Application Server
```

Here the proxy represents the **server**.

The client thinks it is communicating with the application:

```text
Client → api.example.com
```

But actually:

```text
Client
   ↓
Reverse Proxy
   ↓
Application Server
```

The client doesn't necessarily know which internal application server ultimately handles the request.

That's the important idea.

---

# 2. Why do we need a Reverse Proxy?

Suppose you have a Spring Boot application:

```text
Internet
   ↓
Spring Boot
   ↓
Port 8080
```

You could expose:

```text
https://example.com:8080
```

But in production, you often don't want your application server directly exposed to the internet.

Instead:

```text
                    Internet
                       ↓
                 Reverse Proxy
                  Nginx/Envoy
                       ↓
                Spring Boot
                  :8080
```

Now the reverse proxy becomes the **public-facing entry point**.

For example:

```text
https://example.com
       ↓
      Nginx
       ↓
localhost:8080
```

---

# 3. What does the Reverse Proxy actually do?

A reverse proxy can perform several responsibilities.

The most important ones are:

```text
                    Reverse Proxy
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
     Routing           TLS               Security
        ↓                 ↓                 ↓
   Load balancing    HTTPS termination    Filtering
        ↓
   Request handling
```

Let's go through them.

---

# 4. TLS termination

This is particularly relevant to you because you've already studied TLS/mTLS.

Suppose:

```text
Client
   │
   │ HTTPS
   ↓
Nginx
   │
   │ HTTP
   ↓
Spring Boot
```

Nginx handles:

```text
HTTPS
TLS handshake
Certificate
Encryption/decryption
```

The Spring Boot application can then receive ordinary HTTP traffic internally.

For example:

```text
Client
   │
   │ HTTPS :443
   ↓
┌──────────────┐
│    Nginx     │
│              │
│ TLS handling │
└──────┬───────┘
       │
       │ HTTP :8080
       ↓
┌──────────────┐
│ Spring Boot  │
└──────────────┘
```

This is called **TLS termination**.

### Why do this?

Instead of configuring certificates and TLS handling on every application instance:

```text
              ┌─ Spring Boot + TLS
              │
Nginx ────────┼─ Spring Boot + TLS
              │
              └─ Spring Boot + TLS
```

you can terminate TLS at the reverse proxy:

```text
                 ┌─ Spring Boot
                 │
Nginx ───────────┼─ Spring Boot
                 │
                 └─ Spring Boot
```

This can simplify certificate management.

**Important:** TLS termination does **not** automatically mean the internal connection is insecure. You can still use HTTPS/mTLS between Nginx and your applications when required.

---

# 5. Routing

A reverse proxy can route requests based on the URL.

Imagine you have:

```text
api.example.com
```

with multiple applications:

```text
                  Nginx
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   User Service  Order Service  Payment
```

Nginx could route:

```text
/api/users/*
       ↓
User Service

/api/orders/*
       ↓
Order Service

/api/payments/*
       ↓
Payment Service
```

So:

```text
GET /api/users/123
```

could become:

```text
Nginx
  ↓
http://user-service:8080/users/123
```

while:

```text
GET /api/orders/456
```

could become:

```text
Nginx
  ↓
http://order-service:8080/orders/456
```

The client doesn't need to know the internal service addresses.

# 6. Load balancing

This is where reverse proxy starts connecting to your **next topic: Load Balancers**.

Suppose you have three Spring Boot instances:

```text
                    Nginx
                      │
             ┌────────┼────────┐
             ↓        ↓        ↓
           App 1    App 2    App 3
```

Nginx can distribute requests:

```text
Request 1 → App 1
Request 2 → App 2
Request 3 → App 3
Request 4 → App 1
```

For example, using round robin:

```text
App1 → App2 → App3 → App1 → App2 → App3
```

So a reverse proxy **can also act as a load balancer**.

But don't mentally equate the two.

A **reverse proxy** describes its position/role:

```text
Client → intermediary → backend
```

A **load balancer** describes an important function:

```text
Distribute traffic across multiple backend instances
```

A product such as Nginx or Envoy can perform both roles.

Your next roadmap topic, **Load Balancers**, will go deeper into L4/L7 balancing, algorithms, health checks, sticky sessions, etc. 

---

# 7. Hiding internal infrastructure

This is another major reason for a reverse proxy.

Without one:

```text
Client
  ↓
10.20.1.15:8080
```

The client may directly interact with your application server.

With a reverse proxy:

```text
Client
   ↓
api.example.com
   ↓
Nginx
   ↓
10.20.1.15:8080
```

The internal topology can remain private.

For example, your infrastructure might actually be:

```text
                     Internet
                         ↓
                    Nginx
                      :443
                         ↓
             ┌───────────┼───────────┐
             ↓           ↓           ↓
         App Server   App Server   App Server
         10.0.1.10    10.0.1.11    10.0.1.12
```

Users only interact with:

```text
api.example.com
```

They don't need to know:

```text
10.0.1.10
10.0.1.11
10.0.1.12
```

---

# 8. Security filtering

A reverse proxy can also reject unwanted traffic before it reaches your application.

For example:

```text
Internet
   ↓
Reverse Proxy
   │
   ├── ❌ Block malicious IP
   ├── ❌ Reject oversized request
   ├── ❌ Reject invalid method
   ├── ❌ Rate limit
   │
   ↓
Spring Boot
```

This means your application doesn't have to process every incoming request.

This becomes particularly useful when combined with:

* rate limiting
* authentication
* request filtering
* WAF
* IP allow/deny rules

Though once you add lots of API-management responsibilities, you're getting into **API Gateway** territory, which appears later in your roadmap. 

---

# 9. Request/response modification

A reverse proxy can modify requests before forwarding them.

For example:

```text
Client

GET /users/123

       ↓

Nginx

       ↓

GET /api/v1/users/123
```

It can also add headers:

```http
X-Forwarded-For
X-Forwarded-Proto
X-Request-ID
```

This is important because your Spring Boot application may need to know information about the **original client request**.

For example:

```text
Client
  ↓ HTTPS
Nginx
  ↓ HTTP
Spring Boot
```

Spring Boot sees:

```text
HTTP
```

but the original client used:

```text
HTTPS
```

A proxy can communicate that using headers such as:

```http
X-Forwarded-Proto: https
```

---

# 10. Static content

A reverse proxy can serve static files directly.

For example:

```text
Client
   ↓
Nginx
   ├── /images/logo.png → serve directly
   │
   └── /api/users → Spring Boot
```

So:

```text
GET /images/logo.png
```

doesn't need to wake up your Java application.

But:

```text
GET /api/users/123
```

gets forwarded to Spring Boot.

This can reduce application-server work.

# 11. Reverse Proxy vs Load Balancer

This distinction is **very important for interviews**.

Think of them like this:

### Reverse Proxy

```text
Client
   ↓
Reverse Proxy
   ↓
Server
```

Main idea:

> "I am an intermediary representing the backend."

It can provide:

* TLS termination
* routing
* request modification
* security filtering
* caching
* compression
* load balancing

### Load Balancer

```text
Client
   ↓
Load Balancer
   ↓
┌───────┬───────┬───────┐
App 1   App 2   App 3
```

Main idea:

> "I distribute traffic across multiple backend instances."

Therefore:

**A reverse proxy can be a load balancer, but a reverse proxy isn't defined solely by load balancing.**

# 12. Reverse Proxy vs API Gateway

This distinction will matter later when you study Topic 21.

### Reverse Proxy

Usually focused on infrastructure-level concerns:

```text
TLS
Routing
Proxying
Load balancing
Caching
Headers
```

### API Gateway

Usually focused on API-level concerns:

```text
Authentication
Authorization
Rate limiting
API routing
Request transformation
API policies
Logging
```

Your roadmap explicitly lists those API Gateway responsibilities later. 

There is overlap, though. In real systems, one technology can perform both roles.

# 13. Where does Nginx fit?

A common architecture for your Java/Spring world might look like:

```text
                    Internet
                       │
                       │ HTTPS
                       ↓
                  ┌─────────┐
                  │  Nginx  │
                  └────┬────┘
                       │
              ┌────────┼────────┐
              ↓        ↓        ↓
           App 1     App 2     App 3
          Spring     Spring    Spring
           Boot       Boot      Boot
```

Nginx could:

1. terminate TLS
2. route requests
3. load balance
4. add forwarding headers
5. serve static content
6. reject certain requests

# 14. Where does Envoy fit?

Envoy is another popular proxy, especially in distributed/microservice architectures.

For example:

```text
                Client
                  ↓
               Envoy
                  ↓
            Spring Boot
```

Or in a service-mesh architecture:

```text
Service A
    ↓
Envoy Sidecar
    ↓
Envoy Sidecar
    ↓
Service B
```

That's why Envoy becomes particularly interesting later when your roadmap reaches **Service Mesh**.

Your roadmap specifically calls out service mesh concepts including sidecars, mTLS, traffic management, and observability.

# 15. The complete mental model

I would remember reverse proxy using this picture:

```text
                         INTERNET
                            │
                            │ HTTPS
                            ↓
                   ┌─────────────────┐
                   │  REVERSE PROXY  │
                   │                 │
                   │ • TLS           │
                   │ • Routing       │
                   │ • Filtering     │
                   │ • Caching       │
                   │ • Load Balance  │
                   └────────┬────────┘
                            │
                  ┌─────────┼─────────┐
                  ↓         ↓         ↓
               App 1      App 2      App 3
             Spring      Spring      Spring
              Boot        Boot        Boot
```

The key principle is:

> **The client talks to the reverse proxy, and the reverse proxy talks to the backend on the client's behalf.**

## 16. One interview-style example

Suppose you're asked:

> "You have a Spring Boot application receiving 50,000 requests/sec. How would you expose it to the internet?"

You might start with:

```text
                    Clients
                       │
                       ↓
                     DNS
                       │
                       ↓
                Reverse Proxy
                 /    |    \
                /     |     \
             App1    App2    App3
               \      |      /
                \     |     /
                  Database
```

Then explain:

* **DNS** resolves the public domain.
* **Reverse proxy** provides the public entry point.
* TLS can terminate at the proxy.
* Requests can be routed to application instances.
* Multiple application instances allow horizontal scaling.
* The proxy can perform health checks/load balancing.
* Application servers don't need to be directly exposed.

That connects **DNS → TLS → Reverse Proxy → Load Balancer → Horizontal Scaling**, which is exactly the mental chain you're building in this phase.

### The one sentence to remember

**Reverse proxy = a server-side intermediary that receives client requests and forwards them to backend services, often adding TLS termination, routing, security, caching, and/or load balancing along the way.**
