## Load Balancer

Your roadmap defines Topic 14 around five concepts: **L4 vs L7, load-balancing algorithms, health checks, and sticky sessions**. 

Let's build the mental model first.

### 1. Why do we need a Load Balancer?

Suppose you have only one application server:

```text
                    ┌──────────────┐
User ──────────────→│ App Server   │
                    └──────────────┘
```

This creates several problems:

* That server can become overloaded.
* If it crashes, the application is unavailable.
* You can't easily scale horizontally.

So we add multiple application instances:

```text
                    ┌──────────────┐
                ┌──→│ App Server 1 │
                │   └──────────────┘
User ──→  Load ─┤
        Balancer │   ┌──────────────┐
                ├──→│ App Server 2 │
                │   └──────────────┘
                │
                │   ┌──────────────┐
                └──→│ App Server 3 │
                    └──────────────┘
```

The **Load Balancer** receives incoming requests and decides **which backend server should handle each request**.

This gives us:

* **Horizontal scaling**
* **High availability**
* **Failure detection**
* **Traffic distribution**

---

# 2. What exactly does the Load Balancer do?

Imagine 10,000 users hitting your application.

Without a load balancer:

```text
10,000 requests
       ↓
   App Server
```

With one:

```text
                  ┌→ App 1 → DB
                  │
10,000 requests → LB ├→ App 2 → DB
                  │
                  └→ App 3 → DB
```

The LB distributes those requests.

For example:

```text
Request 1 → App 1
Request 2 → App 2
Request 3 → App 3
Request 4 → App 1
Request 5 → App 2
...
```

But **how does it decide?**

That's where load-balancing algorithms come in.

---

# 3. L4 vs L7 Load Balancer

This is one of the most important interview concepts.

## L4 — Transport Layer

L4 operates at the **TCP/UDP level**.

It primarily looks at things such as:

```text
Source IP
Destination IP
Source Port
Destination Port
TCP/UDP
```

Example:

```text
Client
  │
  │ TCP connection
  ↓
L4 Load Balancer
  │
  ├──→ Server 1
  ├──→ Server 2
  └──→ Server 3
```

It doesn't need to understand your HTTP request.

For example, it doesn't care whether you're calling:

```http
GET /users
```

or

```http
POST /payments
```

It operates below HTTP.

### Advantages

L4 can be very fast because it doesn't need to deeply inspect HTTP requests.

It can also handle protocols other than HTTP, such as TCP-based protocols.

---

# 4. L7 Load Balancer

L7 operates at the **application layer**, typically HTTP/HTTPS.

It can understand:

```http
GET /users
Host: example.com
Authorization: Bearer ...
```

So it can make routing decisions based on HTTP information.

For example:

```text
                    ┌→ User Service
                    │
Client → L7 LB ─────┼→ Order Service
                    │
                    └→ Payment Service
```

It could route:

```text
/users/*      → User servers

/orders/*     → Order servers

/payments/*   → Payment servers
```

It can also route based on:

* URL path
* HTTP method
* Hostname
* Headers
* Cookies

### Example

```text
api.example.com/users
        ↓
     L7 LB
        ↓
   User Service
```

while:

```text
api.example.com/orders
        ↓
     L7 LB
        ↓
   Order Service
```

This is something an L4 LB cannot do based on HTTP URL semantics.

---

# 5. L4 vs L7

Think about it like this:

|                                     | L4      | L7         |
| ----------------------------------- | ------- | ---------- |
| Layer                               | TCP/UDP | HTTP/HTTPS |
| Understands HTTP                    | ❌       | ✅          |
| URL-based routing                   | ❌       | ✅          |
| Header-based routing                | ❌       | ✅          |
| Cookie-based routing                | ❌       | ✅          |
| Generally lower processing overhead | ✅       | ❌          |
| Can handle non-HTTP TCP traffic     | ✅       | Usually ❌  |

A useful interview mental model:

```text
L4
 ↓
"I need to get this connection to a server."

L7
 ↓
"I understand this HTTP request and can decide
where it should go."
```

# 6. Round Robin

The simplest load-balancing algorithm.

Suppose:

```text
App 1
App 2
App 3
```

Requests are distributed sequentially:

```text
Request 1 → App 1
Request 2 → App 2
Request 3 → App 3
Request 4 → App 1
Request 5 → App 2
Request 6 → App 3
```

Like dealing cards around a table.

### Advantage

Very simple.

### Problem

It assumes servers can handle approximately the same amount of traffic.

Imagine:

```text
App 1 → powerful server
App 2 → powerful server
App 3 → weak server
```

Round robin still gives App 3 roughly the same number of requests.

So it isn't always ideal.

---

# 7. Weighted Round Robin

We can assign weights.

For example:

```text
App 1 → weight 5
App 2 → weight 3
App 3 → weight 1
```

Then App 1 receives more traffic.

Useful when servers have different capacities.

---

# 8. Least Connections

Instead of asking:

> "Whose turn is it?"

the LB asks:

> "Which server currently has the fewest active connections?"

Example:

```text
App 1 → 100 connections
App 2 →  20 connections
App 3 →  50 connections
```

New request:

```text
             ↓
        Load Balancer
             ↓
           App 2
```

because App 2 has the fewest active connections.

This can be better than round robin when requests have **very different processing times**.

---

# 9. IP Hashing

The LB calculates a hash based on the client's IP.

Conceptually:

```text
hash(clientIP) % numberOfServers
```

For example:

```text
User A → hash → App 1
User B → hash → App 3
User C → hash → App 2
```

The same client IP tends to go to the same server.

This is useful when you want some degree of **session affinity** without explicitly using cookies.

But there is an important problem.

If the number of servers changes:

```text
3 servers
   ↓
4 servers
```

the hashing distribution can change significantly, causing many clients to move to different servers.

More sophisticated systems use **consistent hashing** to reduce this problem.

---

# 10. Health Checks

This is extremely important.

Suppose:

```text
              Load Balancer
              /     |     \
             ↓      ↓      ↓
           App 1  App 2  App 3
                    ❌
```

App 2 has crashed.

The LB shouldn't continue sending requests to it.

So the load balancer periodically performs health checks.

For example:

```http
GET /health
```

And the application responds:

```http
200 OK
```

The LB considers it healthy.

If it repeatedly gets:

```text
timeout
500
connection refused
```

it can mark the server unhealthy:

```text
              Load Balancer
              /           \
             ↓             ↓
           App 1          App 3

                         App 2 ❌
```

New requests aren't sent to App 2.

---

# 11. Health check vs Readiness

This becomes particularly important in modern applications.

Imagine a Spring Boot application has started:

```text
Application process
       ↓
    Running
```

But the database connection isn't ready yet.

A simple "process is alive" check might say:

```text
I'm alive! ✅
```

But the application isn't actually ready to receive production traffic.

That's why systems commonly distinguish:

### Liveness

> "Is this application process alive?"

### Readiness

> "Can this application currently handle requests?"

For load balancing, **readiness is often particularly important**.

For example:

```text
App starts
   ↓
Application initialized
   ↓
DB connection ready
   ↓
Readiness = OK
   ↓
Load Balancer sends traffic
```

# 12. Sticky Sessions

Now an interesting problem.

Suppose you have:

```text
             Load Balancer
              /    |    \
             ↓     ↓     ↓
           App 1 App 2 App 3
```

User logs in.

Request:

```text
Login → App 1
```

Suppose App 1 stores the user's session in its own memory:

```text
App 1
 └── Session: user123
```

Next request:

```text
User → Load Balancer → App 2
```

App 2 doesn't know about that session.

```text
App 2
 └── "Who is user123?" 🤷
```

Sticky sessions solve this by trying to send that user back to the same server:

```text
User 123
   ↓
LB
   ↓
App 1
```

and subsequent requests:

```text
User 123
   ↓
LB
   ↓
App 1
```

The LB can use a cookie or another affinity mechanism to maintain this association.

---

# 13. Why Sticky Sessions are not ideal for stateless architecture

This connects directly to your earlier **Stateless vs Stateful** topic.

With sticky sessions:

```text
User
 ↓
LB
 ↓
App 1
```

You become somewhat dependent on App 1.

If App 1 dies:

```text
App 1 ❌
```

the session may be lost unless the session is stored elsewhere.

A more scalable architecture is:

```text
                Load Balancer
                /     |     \
               ↓      ↓      ↓
             App 1  App 2  App 3
               \      |      /
                \     |     /
                  Redis
```

Session data lives in a shared store:

```text
Redis
 └── user123 → session data
```

Now any application instance can process the request.

This gives us:

```text
User
 ↓
Load Balancer
 ↓
Any App Server
 ↓
Redis
```

That's one reason **stateless services are easier to horizontally scale**.

# 14. Load Balancer as a Single Point of Failure?

This connects nicely to the question you asked about reverse proxies.

You might initially think:

```text
              Load Balancer
                   ❌
                    |
                    X
              Entire system down
```

Yes — **if you deploy only one LB**, it can become a single point of failure.

So production systems generally use redundancy:

```text
                    DNS
                     |
              ┌──────┴──────┐
              ↓             ↓
             LB1           LB2
              |             |
        ┌─────┼─────┐ ┌─────┼─────┐
        ↓     ↓     ↓ ↓     ↓     ↓
       App   App   App App   App   App
```

There are various ways to implement this depending on infrastructure/cloud provider.

The important system-design principle is:

> **A component intended to provide high availability should itself not become a single point of failure.**

---

# 15. Load Balancer vs Reverse Proxy

These two concepts overlap, which is why they can be confusing.

A **reverse proxy** is a broader concept:

```text
Client
  ↓
Reverse Proxy
  ↓
Backend
```

It can provide:

* TLS termination
* routing
* request filtering
* compression
* caching
* load balancing

A **load balancer** specifically focuses on distributing traffic across backend instances.

So:

```text
                    Reverse Proxy
                         │
              ┌──────────┴──────────┐
              │                     │
        Load Balancing         Other functions
```

And many modern products can perform **both roles**.

For example, an L7 reverse proxy can also act as the load balancer.

# 16. Where does the Load Balancer fit in our architecture?

Your roadmap's overall architecture eventually becomes:

```text
                         Users
                           │
                           ↓
                          DNS
                           │
                           ↓
                         CDN
                           │
                           ↓
                    Load Balancer
                           │
                           ↓
                     API Gateway
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
          User Service Order Service Payment Service
              │            │            │
              └────────────┼────────────┘
                           ↓
                         Cache
                           │
                           ↓
                       Database
```

And the load balancer's job is primarily:

```text
                    Load Balancer
                   /      |       \
                  ↓       ↓        ↓
                App1    App2     App3
```

while deciding **which healthy instance receives each request**.

## The mental model I want you to remember

For interviews, think about Load Balancers through these **5 questions**:

```text
1. WHAT traffic?
   └── L4 or L7?

2. WHICH server?
   └── Round Robin
   └── Least Connections
   └── IP Hash
   └── Weighted variants

3. IS the server healthy?
   └── Health Checks

4. SHOULD the same user return to the same server?
   └── Sticky Sessions

5. WHAT if the Load Balancer itself fails?
   └── Redundant / highly available LB
```

And the big picture:

```text
                     ┌───────────┐
                     │   Users   │
                     └─────┬─────┘
                           │
                           ↓
                  ┌─────────────────┐
                  │  Load Balancer  │
                  │                 │
                  │ L4 / L7         │
                  │ Algorithm       │
                  │ Health Checks    │
                  │ Session Affinity│
                  └───────┬─────────┘
                     ┌────┼────┐
                     ↓    ↓    ↓
                   App1  App2  App3
```

**The key idea:** a load balancer isn't just "something that distributes requests." In system design, it's the component that lets us put **multiple service instances behind one stable entry point while detecting unhealthy instances and controlling how traffic is distributed**.
