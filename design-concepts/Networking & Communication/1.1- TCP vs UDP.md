#  TCP vs UDP

At a high level:

```text
TCP
──────────────────────────────
Connection-oriented
Reliable
Ordered
Retransmits lost data
Flow control
Congestion control


UDP
──────────────────────────────
Connectionless
Best-effort
No ordering guarantee
No retransmission
No built-in flow control
No built-in congestion control
```

Think of them as two different philosophies for transporting data across a network.

---

# 1. Where do TCP and UDP fit?

Let's first place them in the networking stack.

```text
Application
────────────────────
HTTP
HTTPS
DNS
WebSocket
gRPC
...

Transport
────────────────────
TCP
UDP

Internet
────────────────────
IP

Network
────────────────────
Ethernet / Wi-Fi
```

For example, when your Spring Boot application receives:

```http
GET /users/123
```

the HTTP request eventually gets transported using **TCP**.

Conceptually:

```text
HTTP
  ↓
TCP
  ↓
IP
  ↓
Ethernet / Wi-Fi
```

UDP works similarly:

```text
Application
  ↓
UDP
  ↓
IP
  ↓
Ethernet / Wi-Fi
```

---

# 2. TCP — Transmission Control Protocol

TCP is designed to provide a **reliable byte stream** between two endpoints.

Imagine:

```text
Client                         Server

   TCP connection
─────────────────────────────────────>

       "Hello World"
```

TCP tries to make the network look reliable to the application even though the underlying IP network can lose, duplicate, reorder, or delay packets.

That's a huge part of TCP's value.

---

# 3. TCP Connection Establishment

Before sending application data, TCP establishes a connection.

This is called the **TCP three-way handshake**.

```text
Client                                  Server

   SYN ────────────────────────────────>

       <──────────────────────── SYN + ACK

   ACK ────────────────────────────────>

           Connection established
```

### Step 1 — SYN

Client says:

> "I want to establish a TCP connection."

```text
Client → Server : SYN
```

### Step 2 — SYN + ACK

Server responds:

> "Okay, I received your request, and I'm also ready."

```text
Server → Client : SYN + ACK
```

### Step 3 — ACK

Client confirms:

> "I received your response."

```text
Client → Server : ACK
```

Now:

```text
TCP connection established
```

Only after this does normal application data flow.

---

# 4. Why does TCP need this connection?

Because TCP maintains **state** about the communication.

For example:

```text
Sequence numbers
Acknowledgements
Window size
Connection state
Retransmission timers
Congestion state
```

This allows TCP to provide reliability and ordering.

UDP doesn't establish this kind of connection.

---

# 5. TCP Reliability

This is probably the most important TCP concept.

Suppose the application sends:

```text
Packet 1
Packet 2
Packet 3
Packet 4
Packet 5
```

But packet 3 gets lost.

```text
Sender                         Receiver

Packet 1 ────────────────────>
Packet 2 ────────────────────>
Packet 3 ─────── X

Packet 4 ────────────────────>
Packet 5 ────────────────────>
```

TCP detects that something is missing and can retransmit it.

# 6. TCP Acknowledgements

TCP uses acknowledgements to know what data the receiver has received.

Simplified example:

```text
Sender                         Receiver

Packet 1 ────────────────────>
                 <──────────── ACK

Packet 2 ────────────────────>
                 <──────────── ACK

Packet 3 ────────────────────>
                 <──────────── ACK
```

If the sender doesn't receive the expected acknowledgement, TCP can eventually retransmit.

So:

```text
TCP
 ↓
Send data
 ↓
Receiver confirms
 ↓
If necessary → retransmit
```

This gives TCP its reliability.

---

# 7. TCP Ordering

TCP also guarantees that the application receives the byte stream **in order**.

Imagine:

```text
Sender

1
2
3
4
5
```

The network could deliver them like:

```text
2
1
4
3
5
```

TCP handles the sequencing internally.

The application sees:

```text
1
2
3
4
5
```

This is important.

Your Java application doesn't normally need to implement packet ordering itself.

---

# 8. TCP Retransmission

Packet loss is normal on networks.

TCP detects missing data and retransmits it.

For example:

```text
1 → received
2 → received
3 → LOST
4 → received
5 → received
```

TCP eventually determines:

```text
Packet 3 is missing
```

and retransmits it.

So:

```text
TCP = reliability + ordering + retransmission
```

---

# 9. TCP Flow Control

Now we get into an important distinction.

**Flow control protects the receiver.**

Imagine:

```text
Very fast sender
       ↓
       ↓↓↓↓↓↓↓↓↓
Slow receiver
```

The sender could overwhelm the receiver.

TCP solves this using a **receive window**.

Conceptually:

```text
Receiver says:

"I can currently accept 64 KB."
```

The sender should not blindly send more data than the receiver can handle.

So:

```text
Flow Control
     ↓
Protect the receiver
```

This is different from congestion control.

---

# 10. TCP Congestion Control

Congestion control protects the **network**.

Imagine millions of clients sending traffic:

```text
Client A ──┐
Client B ──┤
Client C ──┼──> Network ──> Server
Client D ──┤
Client E ──┘
```

The network can become congested.

TCP dynamically adjusts how aggressively it sends data.

Simplified:

```text
Network healthy
      ↓
Increase sending rate

Network congestion detected
      ↓
Reduce sending rate
```

So remember:

| Mechanism              | Protects |
| ---------------------- | -------- |
| **Flow control**       | Receiver |
| **Congestion control** | Network  |

That's a very common interview question.

---

# 11. UDP — User Datagram Protocol

UDP takes a very different approach.

There is no TCP-style connection establishment.

You can think of it as:

```text
Sender                         Receiver

Packet 1 ────────────────────>
Packet 2 ────────────────────>
Packet 3 ────────────────────>
Packet 4 ────────────────────>
```

UDP essentially says:

> "Here's a datagram. Good luck."

😄

It does **not** provide TCP's built-in guarantees.

---

# 12. UDP doesn't guarantee delivery

Suppose:

```text
Packet 1 → received
Packet 2 → received
Packet 3 → LOST
Packet 4 → received
Packet 5 → received
```

UDP does not automatically say:

> "Oh, packet 3 is missing. Let me retransmit it."

Instead, the application receives whatever arrives.

```text
1
2
4
5
```

If the application needs reliability, **the application itself has to implement the necessary mechanisms**.

---

# 13. UDP doesn't guarantee ordering

Suppose the sender sends:

```text
1
2
3
4
5
```

The receiver might receive:

```text
1
3
2
5
4
```

UDP doesn't automatically reorder those datagrams.

Again:

```text
TCP → ordered byte stream
UDP → independent datagrams
```

---

# 14. TCP vs UDP — the important comparison

Here's the table I'd memorize for interviews:

| Feature            | TCP                         | UDP                               |
| ------------------ | --------------------------- | --------------------------------- |
| Connection         | Connection-oriented         | Connectionless                    |
| Handshake          | Yes                         | No                                |
| Reliable delivery  | Yes                         | No                                |
| Ordering           | Yes                         | No guarantee                      |
| Retransmission     | Yes                         | No                                |
| Acknowledgements   | Yes                         | No                                |
| Flow control       | Yes                         | No                                |
| Congestion control | Yes                         | No                                |
| Data model         | Byte stream                 | Datagram                          |
| Overhead           | Higher                      | Lower                             |
| Typical use        | HTTP, HTTPS, DB connections | DNS, streaming, real-time traffic |

The important point is that **UDP isn't simply "TCP but faster."**

It provides fewer guarantees.

---

# 15. Why can UDP be useful?

Consider a real-time game.

Imagine you're playing:

```text
Player position:

10:00:01 → x=100
10:00:02 → x=105
10:00:03 → x=110
10:00:04 → x=115
```

Suppose the packet containing:

```text
x=110
```

gets lost.

By the time you retransmit it, the game might already have:

```text
x=115
```

The old information isn't very useful anymore.

You might prefer:

```text
New data > old missing data
```

This is where UDP can make sense.

---

# 16. Real-time communication

Think about:

```text
Voice call
Video call
Online gaming
Live streaming
```

A delayed packet can sometimes be worse than a lost packet.

For example:

```text
Voice:

"Hello"
```

If one packet containing part of the audio is lost:

```text
Hel_o
```

the application may tolerate a tiny audio glitch.

But waiting several hundred milliseconds for retransmission could make the conversation feel terrible.

So sometimes:

```text
Low latency
    >
Perfect reliability
```

That's an application-level trade-off.

---

# 17. Where TCP makes sense

TCP is appropriate when losing or reordering data is unacceptable.

Examples:

### HTTP/HTTPS

```text
Browser
   ↓
TCP
   ↓
Web Server
```

You don't want:

```text
GET /users

becoming

GET /ers
```

😄

### Database connections

For example:

```text
Java application
      ↓
     TCP
      ↓
PostgreSQL/MySQL
```

You need reliable, ordered communication.

### File transfer

```text
file.pdf
```

You don't want:

```text
file.pdf
```

arriving with random chunks missing.

---

# 18. Where UDP makes sense

UDP is useful when the application values low overhead, latency, or datagram semantics and can tolerate loss—or implements its own reliability.

Examples include:

```text
DNS
Real-time gaming
Voice communication
Video communication
Some streaming protocols
Network discovery
```

One important modern example:

**HTTP/3 uses QUIC, and QUIC runs over UDP.**

QUIC then implements many transport features itself, including reliable streams, encryption integration, and congestion control.

So don't make the mistake:

> "UDP means unreliable application."

Not necessarily.

It means **UDP itself doesn't provide TCP's reliability guarantees**.

An application/protocol built on UDP can add its own mechanisms.

---

# 19. The most important system-design mental model

When designing a system, ask:

```text
Do I need guaranteed delivery?
        │
        ├── YES ──→ TCP is a natural choice
        │
        └── NO
             │
             ↓
       Is very low latency /
       datagram behavior important?
             │
             ├── YES ──→ UDP may make sense
             │
             └── NO ──→ Evaluate based on protocol requirements
```

But don't choose based purely on:

```text
TCP = slow
UDP = fast
```

That's too simplistic.

The real trade-off is:

```text
TCP
────────────────────────
More transport guarantees
More protocol state
More overhead
Reliable ordered stream


UDP
────────────────────────
Minimal transport guarantees
Less protocol state
Lower overhead
Independent datagrams
```

# 20. TCP vs UDP in your Spring Boot world

This is particularly useful for you as a Java/Spring developer.

When you write:

```java
@RestController
public class UserController {

    @GetMapping("/users")
    public List<User> users() {
        ...
    }
}
```

and a browser calls:

```text
https://example.com/users
```

the conceptual stack is:

```text
Browser
   ↓
HTTP
   ↓
TLS
   ↓
TCP
   ↓
IP
   ↓
Network
```

Your Spring application generally doesn't need to worry about:

```text
packet #17 was lost
packet #18 arrived before #17
retransmit packet #17
```

TCP handles those transport concerns underneath.

That's the beauty of layering.

---

# 21. One subtle but important point: TCP is a byte stream

This is a common interview trap.

Suppose you send:

```text
send("Hello")
send("World")
```

TCP does **not** preserve those application-level message boundaries.

The receiver might see:

```text
"HelloWorld"
```

or:

```text
"Hel"
"loWor"
"ld"
```

TCP gives you:

> **An ordered stream of bytes.**

It does NOT give you:

> **A stream of messages.**

Your application protocol has to define message boundaries.

UDP is different because each UDP datagram maintains its own boundary:

```text
Datagram 1 = "Hello"
Datagram 2 = "World"
```

# 22. The interview answer

If an interviewer asks:

> **"What's the difference between TCP and UDP?"**

A strong answer would be:

> TCP is a connection-oriented transport protocol that provides reliable, ordered delivery using acknowledgements, retransmission, flow control, and congestion control. UDP is connectionless and provides datagram-based communication without built-in guarantees for delivery, ordering, or retransmission. TCP is commonly used when correctness and reliable delivery are important, such as HTTP and database communication, while UDP can be useful for latency-sensitive applications such as real-time communication and gaming.

Then if they ask:

> **"What's the difference between flow control and congestion control?"**

Answer:

```text
Flow control
→ protects the receiver

Congestion control
→ protects the network
```

That's an important distinction to have completely clear.
