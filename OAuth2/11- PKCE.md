# Phase 3 — OAuth 2.0

## 12. OAuth Flow

### PKCE (Proof Key for Code Exchange)

PKCE is an extension to the **OAuth 2.0 Authorization Code Flow** that protects the authorization code from being stolen and exchanged by an attacker.

It is especially important for:

* Mobile applications
* Single-page applications (SPAs)
* Public clients that cannot safely store a client secret

The key idea is:

> The client creates a secret before starting the OAuth flow and proves possession of that secret when exchanging the authorization code for tokens.

---

## 12.1 The Problem PKCE Solves

First understand the normal Authorization Code Flow.

Without PKCE:

```text
User
  ↓
Client Application
  ↓
Authorization Server
  ↓
Authorization Code
  ↓
Client
  ↓
Authorization Server
  ↓
Access Token
```

The important part is the authorization code.

For example:

```text
Authorization Code:

abc123
```

The client receives:

```text
https://myapp.com/callback?code=abc123
```

The client then sends:

```http
POST /token

grant_type=authorization_code
code=abc123
client_id=my-client
redirect_uri=https://myapp.com/callback
```

The Authorization Server responds:

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer"
}
```

### The problem

Imagine an attacker manages to steal:

```text
authorization_code = abc123
```

The attacker could potentially send:

```text
POST /token

code=abc123
```

and obtain the tokens.

This is called an **authorization code interception attack**.

PKCE adds an additional secret that the attacker does not have.

---

# 12.2 The Core PKCE Idea

PKCE introduces two values:

```text
code_verifier
code_challenge
```

The client generates a random secret:

```text
code_verifier
```

Then it derives:

```text
code_challenge
```

from the verifier.

Conceptually:

```text
Random Secret
     │
     │
     ▼
code_verifier
     │
     │ SHA-256
     ▼
code_challenge
```

The client sends the `code_challenge` during the authorization request.

Later, when exchanging the authorization code for tokens, the client sends the original `code_verifier`.

The Authorization Server checks:

```text
Does SHA256(code_verifier)
        equal
code_challenge?
```

If yes:

```text
Authorization Code
        +
Correct Verifier
        ↓
Access Token
```

If no:

```text
Authorization Code
        +
Wrong Verifier
        ↓
Request rejected
```

---

# 12.3 Important Terminology

There are three important pieces:

### Code Verifier

A cryptographically random string generated by the client.

Example:

```text
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

Think:

```text
code_verifier = secret
```

The client keeps it temporarily.

---

### Code Challenge

A transformed version of the verifier.

With the recommended method:

```text
code_challenge =
Base64URL(
    SHA256(code_verifier)
)
```

Think:

```text
code_challenge = proof derived from secret
```

The challenge is sent to the Authorization Server.

---

### Code Challenge Method

This tells the Authorization Server how the challenge was generated.

The recommended method is:

```text
S256
```

Meaning:

```text
SHA-256
```

The authorization request therefore contains:

```text
code_challenge=...
code_challenge_method=S256
```

Avoid relying on:

```text
plain
```

for modern implementations.

---

# 12.4 Complete PKCE Flow

Now let's walk through the complete flow.

```text
                 ┌──────────────────────┐
                 │   Authorization      │
                 │       Server         │
                 └──────────┬───────────┘
                            │
                            │
                    OAuth Authorization
                            │
                            │
┌──────────────┐            │
│    Client    │────────────┤
│              │            │
└──────────────┘            │
       │                    │
       │ 1. Generate        │
       │ code_verifier      │
       │                    │
       │ 2. Calculate       │
       │ code_challenge     │
       │                    │
       │ 3. Authorization   │
       │    Request         │
       ├───────────────────►│
       │                    │
       │                    │
       │              User authenticates
       │                    │
       │                    │
       │ 4. Authorization   │
       │    Code             │
       │◄───────────────────┤
       │                    │
       │ 5. Token Request    │
       │    + verifier      │
       ├───────────────────►│
       │                    │
       │              Verify verifier
       │                    │
       │                    │
       │ 6. Access Token    │
       │◄───────────────────┤
       │                    │
```

Now let's examine each step.

---

# 12.5 Step 1 — Generate the Code Verifier

The client generates a random value.

Example:

```text
code_verifier =
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

This value must be:

* Random
* Unpredictable
* Generated for each authorization request
* Kept secret by the client

Do not use something predictable such as:

```text
user123
```

or:

```text
my-secret
```

The verifier is effectively a temporary secret.

---

# 12.6 Step 2 — Generate the Code Challenge

The client derives the challenge from the verifier.

The recommended algorithm is:

```text
S256
```

The conceptual operation is:

```text
code_challenge =
BASE64URL(
    SHA256(code_verifier)
)
```

For example:

```text
code_verifier
      │
      ▼
   SHA-256
      │
      ▼
   Base64URL
      │
      ▼
code_challenge
```

The important property is:

```text
code_verifier → code_challenge
```

but an attacker who only knows:

```text
code_challenge
```

should not be able to recover:

```text
code_verifier
```

---

# 12.7 Step 3 — Authorization Request

The client redirects the user to the Authorization Server.

Conceptually:

```http
GET /authorize?
    response_type=code
    &client_id=my-client
    &redirect_uri=https://myapp.com/callback
    &scope=openid profile
    &state=xyz
    &code_challenge=ABC123
    &code_challenge_method=S256
```

Important parameters:

```text
response_type=code
```

Means:

```text
I want an authorization code.
```

---

```text
client_id
```

Identifies the application.

---

```text
redirect_uri
```

Tells the Authorization Server where to send the authorization response.

---

```text
scope
```

Defines what access is being requested.

For example:

```text
scope=openid profile email
```

---

```text
state
```

Helps protect against CSRF and authorization response injection.

PKCE does **not** replace `state`.

You should generally understand these as two separate protections:

```text
state
  ↓
Protects the authorization request/response relationship

PKCE
  ↓
Protects the authorization code exchange
```

---

```text
code_challenge
```

Contains the transformed verifier.

---

```text
code_challenge_method=S256
```

Tells the Authorization Server:

```text
The challenge was generated using SHA-256.
```

---

# 12.8 Step 4 — User Authenticates

The Authorization Server now interacts with the user.

For example:

```text
Client
  ↓
Authorization Server
  ↓
Login page
  ↓
Username + Password
  ↓
MFA
  ↓
Consent
```

The user may see:

```text
"My Application wants permission to:

✓ Read your profile
✓ Read your email
"
```

The Authorization Server handles authentication.

The client application does **not** receive the user's password.

---

# 12.9 Step 5 — Authorization Server Creates Authorization Code

After successful authentication and authorization, the Authorization Server generates an authorization code.

Example:

```text
code = XYZ789
```

The server redirects the browser to:

```text
https://myapp.com/callback?code=XYZ789&state=xyz
```

The client receives:

```text
XYZ789
```

At this point:

```text
Client has:

authorization_code
code_verifier
```

The Authorization Server has:

```text
authorization_code
code_challenge
```

The important relationship is:

```text
Authorization Code
        │
        └── associated with ──► code_challenge
```

---

# 12.10 Step 6 — Client Exchanges the Code

The client now calls the token endpoint.

For example:

```http
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=my-client
&code=XYZ789
&redirect_uri=https://myapp.com/callback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

Notice something important.

The client sends:

```text
code_verifier
```

It does **not** send:

```text
code_challenge
```

The challenge was sent earlier.

Now the Authorization Server can verify the proof.

---

# 12.11 Step 7 — Authorization Server Verifies PKCE

The Authorization Server receives:

```text
code_verifier
```

It calculates:

```text
SHA256(code_verifier)
```

Then:

```text
Base64URL(SHA256(code_verifier))
```

This produces:

```text
calculated_challenge
```

The server compares:

```text
calculated_challenge
        │
        ▼
   matches?
        │
        ▼
original code_challenge
```

If:

```text
calculated_challenge
        =
stored code_challenge
```

the proof is valid.

Then:

```text
Authorization Code
        +
Valid PKCE Proof
        ↓
Issue Tokens
```

---

# 12.12 What Happens If an Attacker Steals the Code?

This is the most important part of understanding PKCE.

Suppose an attacker intercepts:

```text
authorization_code = XYZ789
```

The attacker tries:

```http
POST /token

code=XYZ789
```

But the Authorization Server expects:

```text
code_verifier
```

The attacker does not know the verifier.

Remember:

```text
Client generated:

code_verifier
     │
     ▼
code_challenge
```

The attacker may know:

```text
code_challenge
```

but cannot practically derive:

```text
code_verifier
```

from the challenge.

Therefore:

```text
Attacker
   │
   │ stolen authorization code
   ▼
Authorization Server
   │
   │ missing/wrong verifier
   ▼
REJECT
```

The stolen authorization code is therefore useless by itself.

---

# 12.13 The Security Property

Without PKCE:

```text
Authorization Code
        ↓
Token Exchange
```

With PKCE:

```text
Authorization Code
        +
Code Verifier
        ↓
Token Exchange
```

The authorization code is effectively bound to the client instance that generated the verifier.

The attacker needs both:

```text
authorization_code
+
code_verifier
```

instead of only:

```text
authorization_code
```

---

# 12.14 Why Is the Challenge Sent First?

This is a common point of confusion.

You might ask:

> Why not just send the verifier during the authorization request?

Because the authorization request travels through the browser/user-agent.

The client wants to establish a commitment without exposing the secret.

Therefore:

### Authorization request

Send:

```text
code_challenge
```

### Token request

Send:

```text
code_verifier
```

The Authorization Server can then verify:

```text
SHA256(code_verifier)
        =
code_challenge
```

This creates the proof.

---

# 12.15 PKCE Timeline

Think of the entire process as a timeline.

```text
CLIENT

Generate random verifier

code_verifier
     │
     ▼
Calculate SHA-256
     │
     ▼
code_challenge
     │
     │
     │ Authorization Request
     ▼
AUTHORIZATION SERVER
     │
     │ Store challenge
     │
     │ Authenticate user
     │
     │ Ask for consent
     │
     ▼
Authorization Code
     │
     │
     │ Redirect
     ▼
CLIENT
     │
     │
     │ Token Request
     │
     │ code
     │ code_verifier
     ▼
AUTHORIZATION SERVER
     │
     │ SHA256(verifier)
     │
     │ Compare with challenge
     │
     ▼
   MATCH?
    /   \
  YES    NO
   │      │
   ▼      ▼
Tokens   Reject
```

# 12.16 PKCE vs Client Secret

This distinction is extremely important.

Traditional confidential clients can have:

```text
client_id
client_secret
```

The secret is stored securely on the server.

For example:

```text
Backend Server
      │
      ├── client_id
      └── client_secret
```

A browser SPA cannot safely keep a permanent client secret.

Why?

Because JavaScript running in the browser is delivered to the user.

Therefore:

```text
SPA

client_id       → public
client_secret   → cannot be safely kept secret
```

PKCE solves a different problem.

It creates a **per-request secret**:

```text
code_verifier
```

The verifier exists for the authorization transaction rather than being a permanent application credential.

---

# 12.17 Public vs Confidential Clients

This distinction helps explain why PKCE became so important.

### Confidential Client

Example:

```text
Backend Server
```

The server can protect:

```text
client_secret
```

Architecture:

```text
Browser
   ↓
Backend
   ↓
Authorization Server
```

The backend can securely store credentials.

---

### Public Client

Examples:

```text
SPA
Mobile App
Desktop App
```

These applications cannot reliably keep a permanent client secret.

Architecture:

```text
Browser
   ↓
SPA
   ↓
Authorization Server
```

or:

```text
Mobile App
   ↓
Authorization Server
```

PKCE gives these clients a secure mechanism for binding the authorization request to the later token exchange.

---

# 12.18 PKCE Does Not Encrypt the Authorization Code

Another common misunderstanding:

> Does PKCE encrypt the authorization code?

No.

PKCE does not encrypt the code.

Instead:

```text
PKCE = proof of possession
```

The authorization code can still be intercepted.

The important difference is:

```text
Before PKCE:

Stolen Code
    ↓
Potentially exchangeable


With PKCE:

Stolen Code
    +
No Verifier
    ↓
Not exchangeable
```

---

# 12.19 PKCE Does Not Replace HTTPS

PKCE is not a replacement for TLS.

You still need:

```text
HTTPS
```

because HTTPS protects communication between:

```text
Client
   ↕
Authorization Server
```

PKCE protects the authorization code exchange against interception scenarios.

Think of the protections as complementary:

```text
HTTPS
  ↓
Protect communication

PKCE
  ↓
Protect authorization code exchange

state
  ↓
Protect request/response correlation
```

---

# 12.20 PKCE Does Not Replace `state`

This is another important concept.

You should not think:

```text
PKCE = state
```

They solve different problems.

### `state`

Used to correlate:

```text
Authorization Request
        ↓
Authorization Response
```

It helps protect against CSRF and response injection.

---

### PKCE

Used to prove:

```text
The party exchanging the authorization code
        ↓
possesses the original verifier
```

So:

```text
state
   +
PKCE
   +
HTTPS
```

provide complementary security protections.

---

# 12.21 Authorization Code + PKCE

The full conceptual flow is:

```text
                Authorization Server
                       │
                       │
                       │
                User authenticates
                       │
                       │
                       ▼
Client ──────── Authorization Request
  │                    │
  │                    │
  │              code_challenge
  │                    │
  │                    ▼
  │              Authorization Code
  │                    │
  ◄────────────────────┘
  │
  │ code
  │ code_verifier
  │
  ├──────────────────────────────►
  │
  │       Verify:
  │
  │ SHA256(code_verifier)
  │          =
  │ stored code_challenge
  │
  │
  ◄──────────────────────────────
  │
  │ Access Token
  │
  ▼
Resource Server
```

# 12.22 PKCE Parameters to Memorize

For practical OAuth development, remember these parameters.

### Authorization Request

```text
response_type=code
client_id=...
redirect_uri=...
scope=...
state=...
code_challenge=...
code_challenge_method=S256
```

### Token Request

```text
grant_type=authorization_code
client_id=...
code=...
redirect_uri=...
code_verifier=...
```

The most important relationship:

```text
code_verifier
      │
      │ SHA-256 + Base64URL
      ▼
code_challenge
```

# 12.23 Minimal Example

Imagine your application is:

```text
My Mobile App
```

The app generates:

```text
code_verifier = RANDOM_SECRET
```

Then:

```text
code_challenge = BASE64URL(SHA256(RANDOM_SECRET))
```

The app sends the user to:

```text
/authorize?
response_type=code
&client_id=my-app
&redirect_uri=myapp://callback
&code_challenge=ABC123
&code_challenge_method=S256
```

The user logs in.

The Authorization Server returns:

```text
myapp://callback?code=XYZ789
```

The application receives:

```text
XYZ789
```

The application then sends:

```text
POST /token

grant_type=authorization_code
code=XYZ789
client_id=my-app
redirect_uri=myapp://callback
code_verifier=RANDOM_SECRET
```

The Authorization Server calculates:

```text
BASE64URL(
    SHA256(RANDOM_SECRET)
)
```

If the result is:

```text
ABC123
```

which matches the original challenge:

```text
ABC123
```

then:

```text
Authorization Code
        +
Valid Verifier
        ↓
Access Token
```

# 12.25 PKCE in One Sentence

> **PKCE prevents a stolen OAuth authorization code from being exchanged for tokens unless the attacker also possesses the original code verifier.**

# 12.26 After Learning PKCE

You should be able to answer these questions before moving on:

1. Why does the Authorization Code Flow need protection?
2. What attack does PKCE mitigate?
3. What is a `code_verifier`?
4. What is a `code_challenge`?
5. Why is `S256` preferred?
6. Why is the verifier sent only during the token exchange?
7. Why can't an attacker derive the verifier from the challenge?
8. Why are SPAs and mobile apps considered public clients?
9. Why doesn't PKCE replace HTTPS?
10. Why doesn't PKCE replace `state`?
11. What happens when the verifier doesn't match the challenge?
12. Why is the authorization code useless to an attacker who doesn't have the verifier?

If you can explain this sequence from memory:

```text
Generate verifier
       ↓
Create challenge
       ↓
Authorization request
       ↓
User authentication + consent
       ↓
Authorization code
       ↓
Send code + verifier
       ↓
Server hashes verifier
       ↓
Compare with challenge
       ↓
Match
       ↓
Access token
```

then you have a solid understanding of **PKCE**.

## Practical Exercise

Implement a small OAuth client using Authorization Code + PKCE.

Your application should:

```text
1. Generate code_verifier

2. Generate code_challenge

3. Redirect user to /authorize

4. Receive authorization code

5. Validate state

6. Send authorization code + code_verifier to /token

7. Receive access token

8. Call a protected API
```

Then deliberately test:

```text
Correct code
+
Correct verifier
        ↓
SUCCESS
```

and:

```text
Correct code
+
Wrong verifier
        ↓
REJECTED
```

This experiment makes the purpose of PKCE much easier to understand.
