# 25. PostgreSQL + pgvector

## 1. What is pgvector?

**pgvector** is a PostgreSQL extension that adds **vector data types and vector similarity search** to PostgreSQL.

Normally PostgreSQL stores things like:

```text
String
Integer
Date
JSON
Boolean
```

With pgvector, PostgreSQL can also store:

```text
Vector
```

For example:

```text
[0.12, -0.83, 0.42, 0.91]
```

And, more importantly, it can perform similarity searches over those vectors.

So instead of introducing a completely separate vector database, you can have:

```text
PostgreSQL
├── normal relational data
├── application data
└── embeddings
```

# 2. Why is this useful?

Imagine your application already uses PostgreSQL.

You have:

```text
customers
orders
products
documents
```

Now you want to add RAG.

Without pgvector, you might introduce another database:

```text
Spring Boot
   │
   ├── PostgreSQL
   │      └── Application data
   │
   └── Vector Database
          └── Embeddings
```

Now you have two databases to operate.

With pgvector:

```text
Spring Boot
      │
      ▼
 PostgreSQL
      │
      ├── Application tables
      └── Vector data
```

That's one of the reasons PostgreSQL + pgvector is such a nice starting point for learning RAG.

---

# 3. What does pgvector actually add?

At a high level, pgvector gives PostgreSQL:

### Vector data type

You can store something like:

```text
[0.12, -0.83, 0.42, ...]
```

### Similarity calculations

You can calculate distances between vectors.

For example:

```text
Query Vector
     ↓
Compare against stored vectors
     ↓
Calculate distance
     ↓
Rank results
```

### Vector indexes

For larger datasets, pgvector supports indexes designed for approximate nearest-neighbor search.

So PostgreSQL can efficiently answer:

> "Which documents have embeddings most similar to this query embedding?"

# 5. What is the vector dimension?

This connects directly to what you learned in Topic 21.

Suppose your embedding model produces:

```text
[0.12, -0.83, 0.42, ...]
```

with **1536 dimensions**.

Then every vector stored in that particular vector column must have 1536 dimensions.

Conceptually:

```text
embedding vector
       ↓
[ x1, x2, x3, ... x1536 ]
```

So your database knows:

```text
vector(1536)
```

This is important because you **cannot randomly mix vectors generated by incompatible embedding models/dimensions** in the same vector column.

# 8. What happens during a search?

Now the user asks:

> "How do I change my password?"

Spring AI receives:

```text
"How do I change my password?"
```

First:

```text
Question
   ↓
EmbeddingModel
   ↓
Query Vector
```

For example:

```text
[0.15, -0.79, 0.46, ...]
```

Then:

```text
Query Vector
     ↓
PgVectorStore
     ↓
PostgreSQL + pgvector
     ↓
Similarity Search
     ↓
Top-K Documents
```

For example:

```text
Password reset guide       0.95
Account recovery guide     0.91
Login troubleshooting      0.86
```

And those `Document`s are returned to your Spring application.

# 9. How does pgvector determine similarity?

This connects directly to Topic 21.

You learned:

* Cosine similarity
* Distance
* Vector dimensions
* Semantic similarity

pgvector supports different distance/similarity approaches.

Conceptually:

```text
Query Vector
     │
     ├──── Document A → distance 0.08
     ├──── Document B → distance 0.15
     ├──── Document C → distance 0.31
     └──── Document D → distance 0.72
```

The smaller the distance, the closer the vectors are **for a distance metric**.

This is an important distinction:

> **Similarity scores and distances don't necessarily have the same direction.**

For example:

```text
Similarity:
higher = more similar

Distance:
lower = more similar
```

Don't mix those two concepts.

# 10. Why do we need an index?

This is where things get interesting from a database/architecture perspective.

Imagine you have:

```text
1,000 documents
```

You could potentially compare the query vector against every stored vector.

That's manageable.

But imagine:

```text
10 million vectors
```

Doing a brute-force comparison against every vector for every query becomes expensive.

You therefore need specialized vector indexes.

pgvector supports approximate nearest-neighbor indexing approaches such as:

```text
HNSW
IVFFlat
```

You don't need to master their internals yet.

For now, understand:

```text
Without vector index

Query
 ↓
Compare against everything
 ↓
Potentially expensive
```

versus:

```text
With vector index

Query
 ↓
Vector Index
 ↓
Efficient nearest-neighbor search
 ↓
Top-K results
```

Later, when you study production RAG, these choices become architecture/performance decisions.

# 11. HNSW vs IVFFlat — basic understanding

You don't need to go deep here yet, but you should know the names.

### HNSW

**Hierarchical Navigable Small World**

Think:

```text
Graph-based index
```

It generally provides very good search performance/recall characteristics, at the cost of more memory and index-building/storage overhead.

### IVFFlat

**Inverted File with Flat vectors**

Think:

```text
Cluster vectors
      ↓
Search relevant clusters
      ↓
Search vectors within them
```

It can be more lightweight in some scenarios, but has different tuning and recall/performance tradeoffs.

For your current stage:

> **Know what HNSW and IVFFlat are. Don't spend hours learning their algorithms yet.**

Your roadmap gives only 3–4 hours to PostgreSQL + pgvector before moving on.

# 12. PostgreSQL doesn't become an LLM database

This is an important misconception to avoid.

pgvector doesn't understand language.

It doesn't know:

```text
"password" means account security
```

The **EmbeddingModel** creates the semantic representation.

pgvector simply stores and compares those representations.

So:

```text
             Semantic understanding
                     │
                     ▼
               EmbeddingModel
                     │
                     ▼
                   Vector
                     │
                     ▼
               pgvector
                     │
                     ▼
             Similarity search
```

Think of pgvector as the **search/storage engine for vectors**, not the thing that understands language.

# 15. Spring AI's role

Here's the abstraction stack:

```text
Your Java Code
      ↓
Spring AI VectorStore
      ↓
PgVectorStore
      ↓
PostgreSQL
      ↓
pgvector
```

Your application ideally shouldn't be littered with PostgreSQL-specific vector queries.

Instead:

```java
vectorStore.add(documents);
```

and:

```java
List<Document> results =
        vectorStore.similaritySearch(request);
```

Spring AI handles the integration with the underlying vector store.

This is the same abstraction philosophy you saw earlier with:

```text
ChatClient
EmbeddingModel
VectorStore
```
