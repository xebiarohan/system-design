# Phase 14 — Agents

## Topic 47: Planning and Topic 48: Tool Selection

## 1. Introduction

In previous phases of Spring AI, we learned about tool calling and MCP. We understood how an LLM can invoke Java methods or external tools to retrieve information and perform operations.

Now, in the Agents phase, we learn how an AI system can decide what steps to perform, which tools to use, and how to achieve a goal.

Consider this user request:

> Find my latest order, check whether the product is in stock, and tell me when it will arrive.

The application might expose the following tools:

- `getLatestOrder()`
- `checkInventory(productId)`
- `trackShipment(orderId)`

An agent needs to determine which tools are required and how to use their results to answer the request.

### Difference between planning and tool selection

| Concept        | Meaning                                                               | Example                                                  |
| -------------- | --------------------------------------------------------------------- | -------------------------------------------------------- |
| Planning       | Determines the steps needed to achieve a goal and their dependencies. | Retrieve the order before tracking its shipment.         |
| Tool selection | Determines which tool is appropriate for a particular step.           | Choose `trackShipment()` to obtain delivery information. |

Planning answers: "What should I do?"

Tool selection answers: "Which tool should I use?"

These concepts work together when building an AI agent.

# Topic 47 — Planning

## 2. What is planning in an AI agent?

Planning is the process of breaking a high-level user goal into smaller, actionable steps.

Consider this request:

> I ordered a laptop. Tell me its delivery status and whether I can get a refund if it is delayed.

This request may require several operations:

1. Retrieve the user's latest order.
2. Retrieve the order's shipment information.
3. Determine whether the delivery is delayed.
4. If necessary, check the applicable refund policy.
5. Explain the verified delivery status and refund options to the user.

The agent needs to understand the goal, identify the necessary steps, and determine the dependencies between those steps.

### Step-by-step example

Step 1: Retrieve the order

Input: Authenticated customer ID.

Output: Order ID and expected delivery date.

Step 2: Track the shipment

Input: Order ID obtained in Step 1.

Output: Current shipment status and estimated delivery date.

Step 3: Evaluate the delivery status

Compare the expected delivery date with the actual shipment information, using the application's business rules.

Step 4: Check the refund policy

If the order is delayed and the user's question requires it, retrieve the applicable refund policy.

Step 5: Generate the response

Combine the verified information and explain the delivery status and available options.

Notice that Step 2 depends on Step 1 because the agent needs an order ID before tracking the shipment.

This is called a dependency between steps.

## 3. Types of planning

An agent can use different planning strategies depending on the task.

### A. Sequential planning

Steps execute in a specific order.

Example:

```
Retrieve Order
     |
     v
Obtain Order ID
     |
     v
Track Shipment
     |
     v
Return Delivery Status
```

Use sequential planning when later steps depend on the results of earlier steps.

### B. Conditional planning

The next step depends on the result of a previous operation.

Example:

```
Retrieve Order
     |
     v
Check Delivery Status
     |
     v
Is the order delayed?
     |
   /   \
  Yes   No
   |     |
   v     v
Check   Explain
Refund  Expected
Policy  Delivery
```

Use conditional planning when the workflow changes based on the information returned by a tool.

### C. Parallel planning

Independent operations can execute simultaneously.

For example, a product-support agent may need to retrieve product specifications and customer reviews. If these operations do not depend on one another, the application can execute both concurrently.

```
         User Request
              |
       +------+------+
       |             |
       v             v
Get Product      Get Customer
Specifications   Reviews
       |             |
       +------+------+
              |
              v
       Combine Results
              |
              v
        Final Answer
```

Use parallel execution when there are no dependencies between operations.

Parallel execution is an orchestration decision; an LLM's plan alone does not make Java operations execute concurrently.

### D. Dynamic planning

The agent changes its next steps based on the results it receives.

Example:

1. Retrieve the order.
2. Track the shipment.
3. Discover that the package was returned to the warehouse.
4. Decide to investigate replacement options rather than continue with the original delivery plan.
5. Explain the available options.

The agent does not need to know every step in advance. It can determine the next action using the latest tool result.

Use dynamic planning when the complete workflow cannot be determined before execution.

## 4. Who creates the plan?

There are two common approaches.

### Approach A: The LLM generates a plan first

The application asks the LLM to break the user's goal into steps.

For example, the LLM might return the following structured plan:

```
{
  "goal": "Explain the order's delivery status and refund options",
  "steps": [
    {
      "id": 1,
      "action": "get_latest_order",
      "dependsOn": []
    },
    {
      "id": 2,
      "action": "track_shipment",
      "dependsOn": [1]
    },
    {
      "id": 3,
      "action": "check_refund_policy",
      "dependsOn": [2]
    }
  ]
}
```

The application then validates and executes the plan.

The JSON above is an illustrative format, not an automatic Spring AI feature. The application must define the plan schema, validate the requested actions, resolve dependencies, and implement execution.

Advantages:

- The complete plan can be inspected before execution.
- The application can validate the proposed steps.
- The plan can be logged for debugging and auditing.
- Human approval can be requested before executing sensitive operations.

Disadvantages:

- The plan may need to be revised when tool results differ from expectations.
- Generating and validating the complete plan adds complexity.
- The LLM may propose invalid or unnecessary steps.

### Approach B: The LLM plans while executing

Instead of generating a complete plan first, the LLM decides the next action based on the current context and previous tool results.

Example:

```
User Request
     |
     v
LLM Decides Next Action
     |
     v
Execute Tool
     |
     v
Return Tool Result
     |
     v
LLM Evaluates Result
     |
     +------> Execute Another Tool
     |                 |
     |                 v
     |          Return Tool Result
     |                 |
     +<----------------+
     |
     v
Generate Final Answer
```

For example:

1. The LLM calls `getLatestOrder()`.
2. The tool returns the order details.
3. The LLM calls `trackShipment()` using the order ID.
4. The shipment result indicates that the package was returned to the warehouse.
5. The LLM decides to check replacement options.
6. The LLM explains the available options.

This is commonly described as iterative or dynamic planning.

### Which approach should you use?

| Situation                                    | Recommended approach                     |
| -------------------------------------------- | ---------------------------------------- |
| Steps are fixed and predictable              | Application-defined workflow             |
| Next steps depend on tool results            | Iterative agent                          |
| The plan requires approval before execution  | Generate, validate, and approve the plan |
| Several independent operations are needed    | Orchestrate parallel operations          |
| The operation involves strict business rules | Enforce those rules in application code  |

Important architectural principle: Do not use an LLM to plan something that ordinary Java code can reliably determine. For predictable workflows, application code is often cheaper, faster, and easier to test.

## 5. How does planning relate to Spring AI?

Spring AI provides abstractions for interacting with chat models and invoking tools. However, building a multi-step agent may require additional orchestration logic.

A simplified architecture looks like this:

```
AgentService
     |
     v
Planning / Orchestration
     |
     v
ChatClient
     |
     v
LLM
     |
     | Tool Call Request
     v
Spring AI Tool Execution
     |
     v
Java @Tool Method
     |
     v
Tool Result
     |
     v
LLM
```

For a basic tool-calling application, Spring AI can manage the model/tool-call interaction.

For a multi-step agent, your application may also need to manage:

- Workflow state.
- Dependencies between steps.
- Iteration limits.
- Retry policies.
- Error handling.
- Human approval.
- Completion conditions.

Remember: Tool calling is a capability; planning is a strategy for using capabilities to achieve a goal.

# Topic 48 — Tool Selection

## 6. What is tool selection?

Tool selection is the process of determining which available tool is appropriate for the current task.

Imagine that your Spring AI application exposes these tools:

```
getCustomer(customerId)
getLatestOrder(customerId)
trackShipment(orderId)
checkInventory(productId)
calculateRefund(orderId)
cancelOrder(orderId)
```

Now consider different user requests.

Request 1:

> Where is my latest order?

Relevant tools:

```
getLatestOrder()
       |
       v
trackShipment()
```

Request 2:

> Is the laptop I ordered in stock?

Relevant tools:

```
getLatestOrder()
       |
       v
checkInventory()
```

Request 3:

> Can I cancel my order?

The agent may need to retrieve the order, validate its current status, and determine whether cancellation is allowed before any cancellation operation is performed.

The available tools remain the same, but the user's intent changes which tools are relevant.

## 7. How does the LLM select a tool?

In a typical Spring AI tool-calling flow, the model receives descriptions of the tools available to it, including their names, purposes, and parameter schemas.

The model uses this information, together with the user request and conversation context, to decide whether to request a tool call and which tool to request.

The execution flow is:

```
1. Spring AI exposes available tool definitions
                    |
                    v
2. LLM evaluates the user request
                    |
                    v
3. LLM selects an appropriate tool
                    |
                    v
4. LLM requests a tool call with arguments
                    |
                    v
5. Spring AI / application executes the tool
                    |
                    v
6. Tool result is returned to the LLM
                    |
                    v
7. LLM selects another tool or returns an answer
```

For example, the model may request:

```
{
  "name": "trackShipment",
  "arguments": {
    "orderId": "ORD-123"
  }
}
```

This represents a tool-call request, not the execution of the Java method itself.

Spring AI and the application handle the actual tool invocation.

## 8. Why are tool descriptions important?

Suppose you expose two tools:

```
@Tool(description = "Gets order details")
Order getOrder(String id);

@Tool(description = "Gets order details")
Order getOrderHistory(String id);
```

These descriptions are ambiguous. The model has little guidance for distinguishing the two tools.

Better descriptions would be:

```
@Tool(description = """
    Retrieves the details of one specific order using its order ID.
    Use this when you need information about a particular order.
    """)
Order getOrder(String orderId);

@Tool(description = """
    Retrieves a customer's previous orders, ordered by purchase date.
    Use this when the customer asks about their order history.
    """)
List<Order> getOrderHistory(String customerId);
```

The improved descriptions clearly explain the purpose of each tool and when it should be used.

Good tool definitions should have the following characteristics:

1. Clear purpose: Explain what the operation does.
2. Distinct responsibilities: Avoid tools with overlapping or ambiguous responsibilities.
3. Meaningful parameters: Use clear names such as `orderId` and `customerId`.
4. Explicit constraints: Describe whether the operation reads data or changes application state.
5. Predictable outputs: Return structured information that the model can use in subsequent steps.

Think of tool descriptions as an API contract written partly for the model, not just for a human developer.

## 9. Practical Spring AI example

Let's implement a small order-support agent.

### Step 1: Define the tools

```
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.stereotype.Component;

@Component
public class OrderTools {

    @Tool(description = """
        Retrieves the latest order for the authenticated customer.
        Use this when the customer asks about their most recent order.
        """)
    public Order getLatestOrder() {
        return orderService.getLatestOrderForCurrentCustomer();
    }

    @Tool(description = """
        Retrieves the current shipment status and estimated delivery
        date for a specific order ID.
        Use this when the customer asks where their order is.
        """)
    public ShipmentStatus trackShipment(String orderId) {
        return shipmentService.track(orderId);
    }

    @Tool(description = """
        Retrieves the refund policy applicable to an order.
        Use this when the customer asks about refund eligibility.
        This operation only reads policy information.
        """)
    public RefundPolicy getRefundPolicy(String orderId) {
        return refundService.getPolicy(orderId);
    }
}
```

`Order`, `ShipmentStatus`, and `RefundPolicy` are illustrative domain types. The service fields represent dependencies that would be injected into the component.

### Step 2: Configure ChatClient

A typical Spring AI configuration can look like this:

```
@Bean
ChatClient orderChatClient(
        ChatClient.Builder builder,
        OrderTools orderTools) {

    return builder
            .defaultSystem("""
                You are an order support assistant.

                Use available tools to retrieve accurate information.
                Retrieve the order before tracking its shipment.
                Check the refund policy when relevant to the request.
                Never invent order or shipment information.
                """)
            .defaultTools(orderTools)
            .build();
}
```

The exact registration APIs depend on your Spring AI version and tool configuration. This example illustrates the annotated-tool approach.

### Step 3: Invoke the agent

```
String answer = orderChatClient.prompt()
        .user("Where is my latest order?")
        .call()
        .content();
```

### Step 4: Understand the runtime flow

For the request `"Where is my latest order?"`, the intended flow is:

```
User Request
     |
     v
LLM selects getLatestOrder()
     |
     v
Spring AI invokes the Java method
     |
     v
Order details returned
     |
     v
LLM selects trackShipment(orderId)
     |
     v
Shipment status returned
     |
     v
LLM generates final response
```

This demonstrates both concepts:

- Planning: Retrieve the order before tracking its shipment.
- Tool selection: Choose `getLatestOrder()` and `trackShipment()` for the request.

The model is not guaranteed to follow this sequence every time. If the sequence is a strict business requirement, enforce it in Java instead of relying only on the system prompt.

## 10. Advanced tool selection: Who decides which tools are available?

There are three different mechanisms to understand.

### A. LLM-driven selection

Expose tools such as:

```
getLatestOrder()
trackShipment()
getRefundPolicy()
```

The model chooses which available tool best matches the user's request.

This approach provides flexibility because the model can handle different requests without requiring a separate hardcoded workflow for each one.

### B. Application-driven tool filtering

Your Java application exposes only a permitted subset of tools for a particular user, task, or controller.

For example:

```
Order Status Controller
    |
    +-- getLatestOrder()
    +-- trackShipment()
    +-- getRefundPolicy()
```

A cancellation controller might have a different set of tools.

This limits the capabilities presented to the model and can simplify tool selection.

Application-driven filtering is especially useful when you have multiple `ChatClient` beans or different agents serving different business functions.

However, tool filtering is not a substitute for authorization. Every sensitive tool must still validate the authenticated user's permissions and the requested operation.

### C. Deterministic application routing

Java code determines which workflow or tool to invoke using explicit business rules.

For example, a refund endpoint might always execute a validated refund workflow instead of asking the model whether a refund should be initiated.

This approach is predictable and easier to test for fixed business processes.

### Combining the approaches

These mechanisms can work together:

```
User Request
     |
     v
Application determines permitted tools
     |
     v
LLM selects from available tools
     |
     v
Application validates the requested operation
     |
     v
Tool executes
     |
     v
Result returned to LLM
```

This is a useful architecture for Spring Boot applications with multiple controllers, agents, or security boundaries.

Security rule: Hiding a tool from the model does not establish authorization. Sensitive operations must enforce authorization and business rules in application code.

## 11. What happens when the model selects the wrong tool?

Imagine the user asks:

> Can you cancel my order?

The model might first call `getLatestOrder()` to obtain the order ID. That is reasonable.

But what if it immediately selects `cancelOrder()` with an incorrect order ID?

Your application needs safeguards beyond good tool descriptions.

| Risk                               | Engineering control                                    |
| ---------------------------------- | ------------------------------------------------------ |
| Wrong tool selected                | Clear descriptions, narrower tool sets, and tests      |
| Invalid parameters                 | Bean Validation and domain validation                  |
| Access to another user's order     | Authorization in the service layer                     |
| Accidental destructive operation   | Explicit confirmation before execution                 |
| Agent loops indefinitely           | Maximum tool calls and iteration limits                |
| Tool or API unavailable            | Timeouts, bounded retries, and error handling          |
| Model invents a successful outcome | Verify the actual tool result before reporting success |

For a production agent, treat the LLM as an untrusted decision-maker.

The LLM can propose an action, but your application owns the final authority to execute it.

# 13. Summary

## Topic 47 — Planning

Planning involves:

- Breaking a user goal into actionable steps.
- Identifying dependencies between steps.
- Determining sequential, conditional, or parallel execution.
- Revising the next action based on tool results.
- Managing workflow execution and completion.

## Topic 48 — Tool selection

Tool selection involves:

- Choosing the right tool for the current task.
- Understanding tool names, descriptions, and parameter schemas.
- Using tool results to determine subsequent actions.
- Restricting tools according to application requirements.
- Validating tool calls and enforcing security.

## Key takeaway

```
User Goal
    |
    v
Planning
    |
    v
Determine Next Step
    |
    v
Tool Selection
    |
    v
Execute Tool
    |
    v
Observe Result
    |
    v
Re-plan if Necessary
    |
    +------> Another Tool
    |
    v
Final Answer
```

Planning and tool selection form part of the reasoning and orchestration process of an AI agent. Spring AI provides the tool-calling infrastructure, while your application is responsible for implementing the necessary workflow, security, and execution controls.
