# Agent Fundamentals

### 1. First: What is an AI Agent?

The simplest definition:

> **An AI Agent is an LLM-based system that can decide what actions to take in order to achieve a goal.**

A normal LLM interaction looks like:

```text
User
  ↓
Prompt
  ↓
LLM
  ↓
Answer
```

The LLM receives a request and produces an answer.

An **agent** adds a decision/action loop:

```text
User
  ↓
Goal
  ↓
LLM
  ↓
Decide what to do
  ↓
Take action
  ↓
Observe result
  ↓
LLM
  ↓
Decide next action
  ↓
...
  ↓
Final Answer
```

That's the fundamental difference.

---

# 2. LLM vs Tool Calling vs Agent

This distinction is **very important**.

You've already studied tool calling, so let's build on that.

### Normal LLM

Suppose the user asks:

> "What is the weather in Dubai?"

```text
User
  ↓
LLM
  ↓
"I don't have access to current weather."
```

The LLM itself doesn't know the current weather.

---

### LLM + Tool

Now give the LLM a weather tool:

```text
User
  ↓
LLM
  ↓
Call getWeather("Dubai")
  ↓
Weather API
  ↓
35°C
  ↓
LLM
  ↓
"It's 35°C in Dubai."
```

The LLM has now been given **an ability**.

But this doesn't necessarily make the whole system an agent.

---

### Agent

Now imagine:

> "I'm travelling to Dubai tomorrow. Check the weather, find a suitable hotel near downtown, and tell me what I should pack."

There isn't necessarily one tool call.

The system may need to figure out:

```text
Goal:
Prepare me for my Dubai trip
        ↓
       LLM
        ↓
Need weather
        ↓
Weather Tool
        ↓
Weather result
        ↓
Need hotel
        ↓
Hotel Search Tool
        ↓
Hotel results
        ↓
Need packing recommendation
        ↓
LLM reasoning
        ↓
Final recommendation
```

The important thing is:

**The LLM is deciding the sequence of actions.**

That's the beginning of agentic behavior.

---

# 3. Think of an Agent as a "Decision Maker"

A useful mental model for you as a Java/backend developer is:

```text
Agent = LLM + Tools + State + Loop
```

Not a strict mathematical definition, but an excellent engineering mental model.

For example:

```text
                 ┌──────────────┐
                 │     User     │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │    Agent     │
                 │              │
                 │     LLM      │
                 └──────┬───────┘
                        │
             ┌──────────┼──────────┐
             │          │          │
             ▼          ▼          ▼
          Tool A      Tool B      Tool C
             │          │          │
             └──────────┼──────────┘
                        │
                        ▼
                    Results
                        │
                        ▼
                      LLM
                        │
                   More actions?
                    /       \
                  Yes        No
                  │           │
                  ▼           ▼
                Tools      Final Answer
```

The **loop** is the key concept.

# 4. What does the Agent actually do?

Imagine this request:

> "Find my customer's latest order and tell me whether it has been delivered."

Suppose we have:

```java
getCustomer()
getOrders()
getOrderStatus()
```

The agent could do:

### Step 1

Understand the goal:

```text
Find customer's latest order
and determine delivery status
```

### Step 2

Decide:

```text
I need customer information.
```

Call:

```text
getCustomer()
```

Result:

```json
{
  "id": 123,
  "name": "John"
}
```

### Step 3

Agent decides:

```text
Now I need John's orders.
```

Call:

```text
getOrders(123)
```

Result:

```text
Order 501
Order 502
Order 503
```

### Step 4

Agent decides:

```text
Order 503 is the latest.
I need its delivery status.
```

Call:

```text
getOrderStatus(503)
```

Result:

```text
DELIVERED
```

### Step 5

Agent decides:

```text
I have enough information.
```

Final answer:

```text
John's latest order (#503) has been delivered.
```

Notice something important:

**The application didn't hard-code this exact sequence.**

The agent determined the sequence dynamically.

# 5. Agent vs traditional workflow

This is one of the most important architectural distinctions.

Consider a traditional application:

```java
Customer customer = getCustomer();

List<Order> orders = getOrders(customer.getId());

Order latest = findLatestOrder(orders);

Status status = getOrderStatus(latest.getId());

return buildResponse(status);
```

The developer determines the workflow.

It's deterministic:

```text
A → B → C → D
```

---

An agent is closer to:

```text
Goal
 ↓
LLM
 ↓
"What should I do next?"
 ↓
Tool
 ↓
Result
 ↓
LLM
 ↓
"What should I do next?"
 ↓
Tool
 ↓
Result
 ↓
LLM
 ↓
"Am I done?"
```

The workflow can change based on the situation.

For example:

```text
Request A
   ↓
Tool 1
   ↓
Tool 2
   ↓
Done
```

while another request might be:

```text
Request B
   ↓
Tool 3
   ↓
Tool 1
   ↓
Tool 4
   ↓
Tool 2
   ↓
Done
```

This **dynamic workflow** is what makes agents powerful.

# 6. Agent ≠ just "LLM with tools"

This is a common misconception.

You might say:

> "If I give an LLM 10 tools, isn't it an agent?"

Not necessarily.

Consider:

```text
User
 ↓
LLM
 ↓
Tool
 ↓
Result
 ↓
Answer
```

That's simply **tool calling**.

An agent usually involves some combination of:

```text
Goal
 ↓
Decision
 ↓
Action
 ↓
Observation
 ↓
Decision
 ↓
Action
 ↓
...
 ↓
Final result
```

So the important concept is not the number of tools.

It's the **autonomous decision/action loop**.

# 7. The Agent Loop

Your roadmap shows this concept as:

```text
Goal
 ↓
LLM
 ↓
Plan
 ↓
Tool
 ↓
Result
 ↓
LLM
 ↓
Tool
 ↓
Result
 ↓
Final Answer
```



Let's expand that.

## Step 1 — Goal

The user gives the agent something to accomplish.

```text
"Find why order #123 hasn't been delivered."
```

---

## Step 2 — LLM understands the goal

The LLM interprets:

```text
I need to investigate order #123.
```

---

## Step 3 — Decide an action

It might choose:

```text
getOrder(123)
```

---

## Step 4 — Tool executes

Your Java code executes the tool:

```java
getOrder(123)
```

Maybe the result is:

```json
{
  "status": "SHIPPED",
  "carrier": "DHL",
  "trackingId": "ABC123"
}
```

---

## Step 5 — Agent observes the result

Now the LLM sees:

```text
Order is shipped.
Tracking ID = ABC123.
```

It decides:

> I need tracking information.

---

## Step 6 — Another tool

```text
getTrackingStatus("ABC123")
```

Result:

```text
DELAYED
```

---

## Step 7 — LLM decides it's finished

Now it has enough information.

```text
Final Answer:
Order #123 is delayed in transit.
```

That's the agent loop.

# 8. Why does the loop matter?

Because the result of one action can determine the next action.

For example:

```text
getCustomer()
      ↓
Customer found?
   /       \
 No         Yes
 |           |
Stop     getOrders()
             ↓
        Orders found?
         /       \
       No         Yes
       |           |
      Stop    getLatestOrder()
                    ↓
              getOrderStatus()
```

The next step depends on **what happened previously**.

A fixed workflow can't easily handle every possible path without lots of conditional code.

An agent can dynamically decide.

# 9. Agent + RAG

You've already studied RAG.

An agent can use RAG as one of its capabilities.

Suppose the user asks:

> "Why was this customer's payment rejected?"

The agent might have:

```text
Tools:
    getCustomer()
    getPayment()
    getPaymentStatus()

Knowledge:
    RAG over payment documentation
```

The agent could do:

```text
Goal
 ↓
Agent
 ↓
getPayment()
 ↓
Payment declined
 ↓
RAG search
 ↓
Find relevant payment documentation
 ↓
LLM
 ↓
Explain reason
```

So:

```text
RAG = information retrieval capability

Tools = action capability

Agent = decision-making/orchestration capability
```

That's a very useful distinction.

# 10. Agent + Memory

Memory adds another dimension.

Suppose a user says:

> "Book me a hotel in Dubai."

Agent:

```text
User
 ↓
Agent
 ↓
Hotel search
```

Later:

> "Make it cheaper."

If the agent has conversation memory:

```text
Previous conversation
       ↓
Memory
       ↓
Agent
       ↓
Understands "it" = Dubai hotel
       ↓
Search cheaper hotels
```

So:

```text
Memory → remembers context

Tools → performs actions

RAG → retrieves knowledge

Agent → decides what to do
```

# 11. Agent + MCP

This is especially relevant because you just finished Phase 13.

MCP gives an agent standardized access to external capabilities.

For example:

```text
                    Agent
                      │
                 Spring AI
                      │
                MCP Client
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      Fetch MCP    Database MCP   Filesystem MCP
       Server         Server         Server
```

The agent can potentially decide:

```text
"I need information from this website."
       ↓
Fetch tool
       ↓
"I also need information from a file."
       ↓
Filesystem tool
       ↓
"I now have enough information."
       ↓
Final answer
```

So MCP doesn't replace agents.

Instead:

```text
MCP
 ↓
provides standardized tools/resources

Agent
 ↓
decides when/how to use them
```

That's an important distinction.

# 13. Agent vs workflow — architect-level thinking

Since you're targeting the Architect/Principal Engineer path, there's an important architectural question:

> **Should I use an agent at all?**

Don't automatically use an agent.

Suppose your process is:

```text
Validate payment
 ↓
Charge payment
 ↓
Create order
 ↓
Send email
```

That's a predictable business workflow.

You probably want:

```text
Java service
 ↓
State machine / workflow
 ↓
Deterministic execution
```

Not:

```text
LLM
 ↓
"Maybe I'll charge payment..."
```

😄 You definitely don't want your payment system improvising.

Agents are useful when:

* the exact steps aren't known beforehand
* the task requires decisions
* multiple tools may be needed
* the path depends on intermediate results
* natural-language goals need to be translated into actions
* the problem is somewhat open-ended

Traditional workflows are better when:

* steps are known
* correctness is critical
* deterministic behavior is required
* transactions are involved
* compliance requires predictable execution

This distinction becomes **very important in production AI architecture**.
