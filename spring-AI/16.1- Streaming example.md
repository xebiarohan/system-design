For this, I recommend using Spring AI + Spring WebFlux + Project Reactor + Server-Sent Events (SSE).

We'll build a streaming API that handles all four scenarios:

1. Completion – AI finishes generating the response.
2. Error – AI provider or streaming request fails.
3. Cancellation – Client explicitly cancels the request.
4. Disconnect – Client closes the browser, loses connection, or navigates away.

Spring AI returns a `Flux<String>`, so we can use Reactor operators to handle the lifecycle.

## 3\. Define your streaming event

Instead of returning plain strings, I recommend returning structured events.

java

```java
public record StreamEvent(
    String type,
    String content,
    String message
) {}
```

Our API will send events like these:

| Event | Meaning |
| --- | --- |
| `token` | A piece of AI-generated content |
| `complete` | AI finished successfully |
| `error` | Something went wrong |

Cancellation and disconnect are server-side lifecycle events. They generally cannot be delivered to a client that has already disconnected.

## 4\. Create the streaming service

java

```java
@Service
@Slf4j
public class ChatService {

    private final ChatClient chatClient;

    public ChatService(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    public Flux<String> stream(String message) {

        return chatClient
                .prompt()
                .user(message)
                .stream()
                .content();
    }
}
```

Notice that we are not subscribing manually. We return the original `Flux` so that WebFlux controls the subscription, cancellation, and backpressure.

## 5\. Create the streaming controller

This is where we handle completion, errors, cancellation, and disconnects.

java

```java
@RestController
@RequestMapping("/api/chat")
@Slf4j
public class ChatController {

    private final ChatService chatService;

    public ChatController(ChatService chatService) {
        this.chatService = chatService;
    }

    @PostMapping(
        value = "/stream",
        produces = MediaType.TEXT_EVENT_STREAM_VALUE
    )
    public Flux<ServerSentEvent<StreamEvent>> stream(
            @RequestBody ChatRequest request) {

        return chatService.stream(request.message())

            // 1. Every generated token
            .map(token ->
                ServerSentEvent.<StreamEvent>builder()
                    .event("token")
                    .data(new StreamEvent(
                        "token",
                        token,
                        null
                    ))
                    .build()
            )

            // 2. Successful completion
            .concatWithValues(
                ServerSentEvent.<StreamEvent>builder()
                    .event("complete")
                    .data(new StreamEvent(
                        "complete",
                        null,
                        "Generation completed"
                    ))
                    .build()
            )

            // 3. Handle errors
            .doOnError(error ->
                log.error("AI streaming failed", error)
            )

            .onErrorResume(error ->
                Flux.just(
                    ServerSentEvent.<StreamEvent>builder()
                        .event("error")
                        .data(new StreamEvent(
                            "error",
                            null,
                            "Unable to generate response"
                        ))
                        .build()
                )
            )

            // 4. Handle cancellation
            .doOnCancel(() ->
                log.info("Client cancelled AI stream")
            )

            // 5. Observe all terminal signals
            .doFinally(signalType ->
                log.info("Stream terminated: {}", signalType)
            );
    }
}
```

### What happens in each scenario?

| Scenario | Reactor behavior | Your handler |
| --- | --- | --- |
| AI completes | `onComplete` | `concatWithValues()` sends `complete` |
| AI throws error | `onError` | `onErrorResume()` sends `error` |
| User cancels | `cancel` | `doOnCancel()` |
| Browser disconnects | Usually `cancel` or a transport write error | `doOnCancel()` / `doFinally()` |

Important: `doFinally()` can receive three particularly useful signals:

- `SignalType.ON_COMPLETE`
- `SignalType.ON_ERROR`
- `SignalType.CANCEL`

This makes it useful for logging, metrics, and cleanup.

## 6\. Understanding client cancellation and disconnect

This is probably the most important part.

Suppose the user starts generating an AI response, but then clicks a Cancel button.

The frontend should cancel its HTTP request.

For example, using JavaScript:

javascript

```javascript
const controller = new AbortController();

async function startChat(message) {

    const response = await fetch("/api/chat/stream", {
        method: "POST",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify({ message }),
        signal: controller.signal
    });

    const reader = response.body.getReader();

    while (true) {
        const { value, done } = await reader.read();

        if (done) break;

        const chunk = new TextDecoder().decode(value);

        console.log(chunk);
    }
}

function cancelChat() {
    controller.abort();
}
```

When `controller.abort()` is called:

1. The browser terminates the HTTP request.
2. WebFlux detects the cancellation.
3. Reactor propagates cancellation upstream.
4. Your `doOnCancel()` callback executes.
5. The AI streaming subscription is cancelled.

The same general cancellation path applies when a browser disconnects, although the server might only discover it when the next write fails.

One important detail: cancellation is not the same as an error.

When a client disconnects, the server generally cannot send an `error` or `cancelled` event back to that client because the connection is already gone.

Also, cancellation propagates through Reactor, but whether the actual upstream HTTP request to the AI provider is stopped depends on the provider integration.

If something goes wrong:

text

```text
event: error

```

The error event can only be delivered if the connection is still usable.

## 8\. My recommended production improvements

I'd add these things before deploying:

- Request ID: Associate each streaming request with a unique ID for logging and tracing.
- Timeout: Use Reactor's `timeout()` operator to prevent indefinitely running streams.
- Cleanup: Use `doFinally()` for releasing resources associated with the request.
- Safe errors: Never expose raw provider exceptions or API credentials to clients.
- Heartbeat: For long-running streams, consider periodic SSE heartbeat events to help detect dead connections. WebFlux documents this consideration.

## 9\. Final lifecycle summary

| Operator | Purpose |
| --- | --- |
| `map()` | Transform AI tokens into SSE events |
| `concatWithValues()` | Send completion event |
| `doOnError()` | Log errors |
| `onErrorResume()` | Return an error event |
| `doOnCancel()` | Detect cancellation |
| `doFinally()` | Observe all termination signals |
| `timeout()` | Enforce maximum stream duration |

My recommendation: Use the implementation in sections 4 and 5 as your starting point. It keeps the streaming pipeline reactive and lets WebFlux manage the HTTP lifecycle naturally.
