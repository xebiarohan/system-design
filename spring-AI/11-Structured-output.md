# Phase 4 — Structured Output

Structured Output is one of the **most important topics in Spring AI**, because it is where you move from:

> "LLM gives me some text"

to:

> "LLM gives my Java application data in a predictable structure."

Since you're learning Spring AI with a Java/Spring background, this is where things start feeling much more like normal backend development.

---

# 1. What is Structured Output?

Normally, an LLM returns **unstructured text**.

For example, you ask:

```text
Extract the product information from this text:

"iPhone 17 Pro, 256GB, priced at $1199"
```

The model might respond:

```text
The product is an iPhone 17 Pro with 256GB of storage,
and it costs $1199.
```

That's useful for a human.

But your Java application has a problem:

```java
String response = ...;
```

How do you reliably get:

```java
product.name
product.storage
product.price
```

You would have to parse the text yourself.

That's fragile.

---

# 2. Structured Output solves this

Instead, you tell the LLM:

> Return the result in a specific structure.

For example:

```json
{
  "name": "iPhone 17 Pro",
  "storage": "256GB",
  "price": 1199
}
```

Now your application can work with actual structured data.

Conceptually:

```text
User
 ↓
Spring AI
 ↓
LLM
 ↓
Structured JSON
 ↓
Java Object
 ↓
Business Logic
```

For example:

```java
public record Product(
    String name,
    String storage,
    double price
) {}
```

Your application can then work with:

```java
Product product;
```

instead of parsing arbitrary text.

---

# 3. Why is this important?

Imagine you're building an e-commerce application.

The user enters:

```text
I bought an iPhone 17 Pro 256GB for $1199
```

You want the LLM to extract:

```json
{
  "product": "iPhone 17 Pro",
  "storage": "256GB",
  "price": 1199
}
```

Your Java application might then do:

```java
if (product.price() > 1000) {
    // Apply some business rule
}
```

This is much easier than trying to interpret:

```text
"The customer appears to have purchased an iPhone..."
```

---

# 4. Structured Output vs normal LLM response

Think about it this way:

### Normal output

```text
The customer is John and he is 32 years old.
He lives in Dubai.
```

Good for humans.

### Structured output

```json
{
  "name": "John",
  "age": 32,
  "city": "Dubai"
}
```

Good for programs.

That's the fundamental idea.

---

# 5. How Spring AI handles Structured Output

Spring AI provides mechanisms for converting model output into structured Java objects.

One important concept you'll encounter is the:

**`StructuredOutputConverter`**

The basic idea is:

```text
Java Class
     ↓
Spring AI
     ↓
Instructions/schema
     ↓
LLM
     ↓
Structured response
     ↓
Java Object
```

Spring AI has several structured-output converter implementations.

The important ones to know are:

* `BeanOutputConverter`
* `MapOutputConverter`
* `ListOutputConverter`

You'll also encounter newer **native structured output / JSON-schema-based approaches**, depending on the model/provider.

---

# 6. BeanOutputConverter

Suppose you have:

```java
public record Movie(
    String title,
    String genre,
    int year
) {}
```

You want the LLM to return a `Movie`.

You can use a `BeanOutputConverter`.

Conceptually:

```java
BeanOutputConverter<Movie> converter =
        new BeanOutputConverter<>(Movie.class);
```

Spring AI can use the Java class to determine the expected structure.

The prompt can then include formatting instructions.

Conceptually:

```text
Return the movie information.

{format}
```

where `{format}` represents instructions generated by the converter.

The LLM might return:

```json
{
  "title": "Inception",
  "genre": "Science Fiction",
  "year": 2010
}
```

Spring AI then converts that into:

```java
Movie movie;
```

---

# 7. Why the Java class matters

This is particularly nice for Java developers.

Suppose you define:

```java
public record Customer(
    String name,
    int age,
    String country
) {}
```

Your desired output structure is effectively:

```text
Customer
├── name
├── age
└── country
```

You're telling the AI application:

> "I don't just want text. I want something that represents this Java object."

That's the bridge between the **AI world** and the **normal Java application world**.

---

# 8. ListOutputConverter

Sometimes you don't want one object.

You want a list.

For example:

```text
Give me 5 Java interview questions.
```

Desired result:

```json
[
  "What is JVM?",
  "What is garbage collection?",
  "What is a Java record?",
  "What is virtual thread?",
  "What is type erasure?"
]
```

Spring AI provides `ListOutputConverter` for this type of scenario.

Conceptually:

```java
List<String> questions;
```

instead of:

```java
String response;
```

---

# 9. MapOutputConverter

You can also ask for key-value data.

For example:

```json
{
  "language": "Java",
  "difficulty": "Advanced",
  "category": "Concurrency"
}
```

This maps naturally to:

```java
Map<String, Object>
```

Spring AI provides `MapOutputConverter` for this kind of output.

---

# 10. Structured Output is NOT the same as JSON

This distinction is important.

You might think:

> "Structured output means asking the LLM to return JSON."

Not necessarily.

JSON is **one format**.

Structured output is the broader concept:

> **The output follows a predefined structure that your application can reliably consume.**

For example:

```json
{
  "name": "John",
  "age": 30
}
```

is structured.

But conceptually you could have other structured representations too.

The important part is **predictability and machine-readability**, not JSON itself.

---

# 11. Prompt-based structured output

One approach is to instruct the model:

```text
Return the result as JSON.

The JSON must contain:

name
age
city
```

The model might return:

```json
{
  "name": "John",
  "age": 30,
  "city": "Dubai"
}
```

This is sometimes called **prompt-based structured output**.

The model is essentially being told:

> "Please behave."

😂

And usually it does.

But there is a problem.

---

# 12. The problem with prompt-only JSON

LLMs are probabilistic.

Even if you say:

```text
Return ONLY JSON.
```

the model could potentially produce:

```text
Sure! Here is the JSON:

{
  "name": "John",
  "age": 30
}
```

Now your JSON parser may complain because the response contains additional text.

Or it could produce:

```json
{
  "name": "John",
  "age": "thirty"
}
```

when your application expects:

```java
int age;
```

Or:

```json
{
  "name": "John"
}
```

with `age` missing.

This is why structured output becomes more interesting than simply saying "return JSON."

---

# 13. Native Structured Output

Modern LLM providers increasingly support **native structured output**.

Instead of relying entirely on:

```text
Please return JSON...
```

the application can provide a schema describing the desired output.

For example:

```text
Expected structure:

Customer
├── name: string
├── age: integer
└── city: string
```

The model/provider can then constrain the response according to that structure.

Conceptually:

```text
Prompt
   +
Schema
   ↓
LLM
   ↓
Structured response
```

This is generally more reliable than prompt-only formatting.

---

# 14. Schema is a very important concept

You'll hear the word **schema** a lot when learning structured output.

Suppose your Java object is:

```java
public record Customer(
    String name,
    Integer age,
    String city
) {}
```

The conceptual schema is:

```json
{
  "type": "object",
  "properties": {
    "name": {
      "type": "string"
    },
    "age": {
      "type": "integer"
    },
    "city": {
      "type": "string"
    }
  }
}
```

This tells the system:

> The response should be an object with these fields and these types.

# 15. Structured Output in a Spring AI application

Imagine you're building:

```text
POST /customers/extract
```

The user sends:

```text
"My name is Rohan, I'm 35 and I live in Dubai."
```

You want:

```java
public record Customer(
    String name,
    int age,
    String city
) {}
```

Your architecture becomes:

```text
             User
               │
               ▼
       Spring Boot API
               │
               ▼
          ChatClient
               │
               ▼
             LLM
               │
               ▼
      Structured Output
               │
               ▼
          Customer
               │
               ▼
       Business Logic
               │
               ▼
           Database
```

This is a **very realistic Spring AI use case**.

---

# 16. Example with ChatClient

Modern Spring AI code commonly looks like:

```java
Customer customer = chatClient
        .prompt()
        .user("""
            Extract customer information from:

            My name is Rohan, I'm 35 and I live in Dubai.
        """)
        // structured output configuration
        .call()
        .entity(Customer.class);
```

The important part to understand here is:

```java
.entity(Customer.class)
```

You're essentially telling Spring AI:

> "I expect the model's response to represent a `Customer`."

So instead of:

```java
String response
```

you get:

```java
Customer customer
```

That's the key idea you should remember.

---

# 17. Structured Output vs Function Calling

These two concepts are often confused.

### Structured Output

You ask the LLM:

> "Give me data in this structure."

Example:

```text
LLM → Customer
```

The LLM produces data.

---

### Function/Tool Calling

You give the LLM a tool:

```text
getWeather(city)
```

The LLM decides:

```text
I need to call getWeather("Dubai")
```

Then your application executes the function.

So:

```text
Structured Output:

LLM
 ↓
Structured data
```

while:

```text
Tool Calling:

LLM
 ↓
Tool selection
 ↓
Your Java function
 ↓
Result
 ↓
LLM
```

You'll eventually want to learn both, but they're different concepts.

---

# 18. Structured Output vs RAG

Also don't mix these up.

**RAG** answers:

> Where does the information come from?

For example:

```text
Documents
 ↓
Embeddings
 ↓
Vector DB
 ↓
Relevant context
 ↓
LLM
```

**Structured Output** answers:

> In what format should the answer come back?

You can actually combine them:

```text
Documents
   ↓
RAG
   ↓
Relevant information
   ↓
LLM
   ↓
Structured Output
   ↓
Java Object
```

For example, a RAG application could return:

```java
public record Answer(
    String answer,
    List<String> sources,
    double confidence
) {}
```

That's a very common architecture.

# 19. The biggest real-world problem: validation

Here's where your backend-development experience becomes useful.

Suppose you receive:

```java
Customer customer
```

Does that automatically mean the data is valid?

**No.**

The LLM could produce:

```json
{
  "name": "",
  "age": -500,
  "city": "Mars"
}
```

It may technically match the structure:

```text
name → String
age → Integer
city → String
```

but it's still bad business data.

Therefore:

```text
Structured Output
        ↓
Deserialization
        ↓
Validation
        ↓
Business Rules
        ↓
Database
```

You still need normal application validation.

For example:

```java
public record Customer(
    @NotBlank String name,

    @Min(0)
    @Max(150)
    int age,

    @NotBlank String city
) {}
```

The LLM does **not replace your application's validation layer**.

That's an important production lesson.

---

# 20. What can go wrong?

When working with structured output, understand these failure cases:

### Missing fields

```json
{
  "name": "Rohan"
}
```

but your application expects:

```text
name
age
city
```

---

### Wrong data types

```json
{
  "age": "thirty"
}
```

instead of:

```json
{
  "age": 30
}
```

---

### Invalid values

```json
{
  "age": -500
}
```

---

### Extra fields

```json
{
  "name": "Rohan",
  "age": 35,
  "city": "Dubai",
  "favoriteColor": "Blue"
}
```

Depending on the mechanism/schema/configuration, extra fields may or may not be accepted.

---

### Invalid JSON

```text
{
  name: Rohan,
  age: 35
}
```

Not valid JSON because the property names aren't quoted.

# 21. Structured Output and Prompt Engineering

This connects directly to the previous topics you studied.

You learned:

```text
Prompt Engineering
       ↓
Prompt Testing
```

Now:

```text
Prompt Engineering
       ↓
Structured Output
```

For example, you might write:

```text
Extract the following information.

Rules:
1. Return exactly one Customer object.
2. age must be an integer.
3. Do not invent missing information.
4. If age isn't available, return null.
```

Then your structured output mechanism ensures the **shape**, while your prompt defines **behavior/instructions**.

Think:

```text
Prompt
  = What should the model do?

Schema / Structured Output
  = What should the result look like?
```

That's a very useful mental model.

# 22. A real-world example

Suppose you're building an AI-powered support system.

User says:

```text
"My application has been crashing since yesterday
and I'm getting a NullPointerException."
```

You want:

```java
public record SupportTicket(
    String category,
    String priority,
    String summary,
    String technicalError
) {}
```

The LLM could produce:

```json
{
  "category": "TECHNICAL",
  "priority": "HIGH",
  "summary": "Application crashes",
  "technicalError": "NullPointerException"
}
```

Now your normal Spring application can do:

```text
SupportTicket
      ↓
Validate
      ↓
Save to DB
      ↓
Route to technical team
      ↓
Send notification
```

This is where Structured Output becomes **really useful**.

# 24. The most important mental model

If you remember only one thing from this topic, remember this:

```text
                LLM
                 │
                 │ normally produces
                 ▼
            String/Text
                 │
                 │ difficult for code
                 ▼
          Structured Output
                 │
                 ▼
            JSON/Object
                 │
                 ▼
          Java Object
                 │
                 ▼
       Business Application
```

And the distinction:

```text
Prompt
   ↓
Tells the LLM WHAT to do

Structured Output
   ↓
Defines WHAT SHAPE the result should have

Validation
   ↓
Checks WHETHER the result is acceptable

Business Logic
   ↓
Decides WHAT your application should do with it
```

That separation is **the key to understanding Structured Output in Spring AI**.

